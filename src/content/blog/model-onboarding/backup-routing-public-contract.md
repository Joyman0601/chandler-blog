> 一句话总结：备份渠道能接收同形请求，仍可能改变请求含义。兼容清单要从已经承诺给调用方的能力出发，覆盖字段、取值、文本语法、输入格式和默认处理，并区分本地实测与上游实测。

## 0. 起因：基础路由已经通过，还能漏掉什么

我让编程助手给一组生成模型增加备份上游。原渠道不可用时，任务可以切过去；原有标识和对外行为尽量保持一致。

第一轮已经做了参数兼容检查，把备份明确不支持的字段排除掉。本地链路、请求转换和部分边界测试通过了，代码审查也结束了。

后来我继续要求对照能力。按每个公开接口页的参数说明逐项核，仍然找到了遗漏：有的能力写在提示词里，有的藏在字段取值或旧路径的类型归一中，还有一条规则把本来可以尝试的请求排除了。

更需要纠正的是证据口径。助手一度把「旧代码会发出什么」写成「上游一定会生成什么」。当时相关真实生成尚未验证，后一个结论没有足够依据。本文保留这次更正，也区分后续真实探测得到的新结果。

## 1. 清单的起点是调用方能要求什么

只看备份上游的字段表，会得到一张「它支持哪些参数」的表。要判断能否接替原渠道，还需要另一张表：我们的接口已经允许调用方要求什么。

来源至少有三处：公开接口文档、页面上实际提供的选项，以及原渠道适配器的现有行为。三者不一致时，先记录差异，不能挑最方便的一份当答案。

我会按能力逐行整理，而不是只按字段名逐行整理：

| 能力来源 | 要核对的内容 | 容易漏掉的地方 |
|---|---|---|
| 字段定义 | 类型、必填、缺省值 | 未传与显式关闭是否不同 |
| 参数说明 | 取值范围、格式、组合限制 | 同名字段可能含义不同 |
| 提示词说明 | 是否约定结构化语法 | 文本原样传递却丢掉能力 |
| 页面控件 | 调用方可选择的模式 | 后端黑名单没有对应字段 |
| 原路径行为 | 归一、补默认值、隐式转换 | 两个适配器处理宽松输入不同 |

文档外的历史宽松行为需要单独标注。例如，文档只承诺布尔值，旧接口却也接受某种字符串。是否继续兼容它是一个明确选择，不能把它伪装成原本的公开规范，也不能在切换渠道时悄悄改变。

## 2. 字段名没变，语义仍可能变化

**提示词语法**是最典型的一类。某个接口允许在提示词正文里描述有结构的多段场景；备份只提供普通文本提示。两边都有 `prompt`，所以字段黑名单看不见差异。

本地可以证明旧代码会放行，并把文本原样发过去。至于备份会把它当普通描述、报错，还是理解成预期的结构，需要文档或真实探测支持。直接写「一定输出单段结果」就越过了证据边界。

**取值语义**也一样。一个接口区分自动规划和手动编排，另一个接口只有是否开启的布尔值。把前者转成真，证明了开关打开，却没有证明自动规划能力等价。

**输入格式**则藏在字段描述里。两个接口都收图片地址，允许的实际编码未必相同。文件后缀、内容类型和真实内容还可能不一致，单看 URL（统一资源定位符）只能得到有限线索。

如果本地规则按后缀过滤，至少应解析路径，排除查询参数对后缀判断的干扰。没有后缀也不等于格式受支持；放行这类地址是一项策略选择，需要明确它尚未验证的部分。

这些问题说明，适配器转换的是能力含义，而不只是把一组键名换成另一组键名。

## 3. 归一与兼容判断要使用同一份有效参数

这次还有一类本地就能确定的问题：原渠道会把字符串形式的开关归一成布尔值，备份路径却只比较是否为布尔真。相同输入在两条路径下得到了不同请求体。

如果兼容检查读原始输入，构造请求时又读另一份合并后的参数，也会出现判断与执行不一致。嵌套参数、顶层覆盖和默认值，都可能改变最终语义。

我会把处理顺序写清：先按既有契约得到有效参数，再基于有效参数判兼容，最后构造上游请求。下面是自编的小例子，仅接受布尔值和两种约定字符串，展示怎样避免各分支分别猜测：

```python
def parse_switch(value):
    if isinstance(value, bool):
        return value
    if isinstance(value, str):
        if value.lower() == "true":
            return True
        if value.lower() == "false":
            return False
    raise ValueError("unsupported switch value")

print(parse_switch(True))
print(parse_switch("true"))
print(parse_switch("false"))
```

这不是建议所有接口都接受字符串。允许哪些类型，要从该接口的既有行为或新契约取得。原路径若还接受别的写法，就需要决定是否保留，并给出对应用例。

修复测试也不能只断言兼容函数返回允许。还要捕获实际发出的请求，检查开关、结构化内容和默认值确实被带上。判定正确而构造时丢字段，仍然会产生同样的问题。

## 4. 排除规则也会误伤正常请求

兼容检查的另一面是可用性。规则越保守，不代表质量一定越高；排除了没有触发限制的请求，主渠道故障时它们就少了一条可用路径。

这次的一条规则涉及保留参考视频的原声。限制只在输入包含参考视频时有意义，旧判定却没有检查视频是否存在。只上传参考图片的请求，也因为开关的默认值被排除。

因此，每条不兼容规则至少要配一条邻近的正向对照：

| 拒绝条件 | 应保留的对照 |
|---|---|
| 带视频且要求保留原声 | 只有参考图片 |
| 使用不支持的规划模式 | 普通提示词模式 |
| 明确识别到不兼容格式 | 已支持的格式 |
| 带结构化文本语法 | 相近但普通的自然语言 |

对照不是为了凑覆盖率。它约束规则的边界，防止用「全拒绝」轻易满足负向用例。正向放行本身仍然不等于真实生成已经成功，需要与下一层验证分开。

## 5. 把差异分成能决定动作的三类

我现在会给每条差异写明风险和处置，而不是统一标一个「不支持」。

第一类是可能静默改变含义的组合。调用成功，但预期能力丢失、输出时长改变或结果性质变化。这类在没有等价依据前，应该阻止自动切到备份。

第二类是明确失败的组合。上游拒收、任务进入失败状态，且平台的终态和退款链路已经验证。可以根据产品要求决定暂缓适配，但要说明主渠道失效时的影响。一个错误码并不能自动证明退款发生。

第三类是未知。文档没写清、账号暂时无法执行、两边行为无法直接比较，都放进探测清单。未知不能写成已支持，也不能直接写成确定缺陷。

后续修复提交记载，拿到可执行条件后又做了真实生成探测。其中一个编辑路径的输出时长与原契约不一致，于是进一步收窄备份范围。但几条成功生成的请求，不能自动为早先所有语法和格式差异背书。

我会把一条结论拆成下面几列，避免随着任务推进又混在一起：

| 公开要求 | 本地发出什么 | 上游实际返回什么 | 证据层级 | 当前处置 |
|---|---|---|---|---|
| 保留指定模式 | 模式被转成普通开关 | 尚未验证等价性 | 本地实测、外部未知 | 暂不自动切换 |
| 某种输入组合可用 | 判定错误地提前拒绝 | 请求尚未发出 | 本地实测 | 修正判断，补生成验证 |

表中是抽象示例。实际记录还应带素材属性、版本和用例定位，留在私有证据里即可。

## 6. 首次选路和失败重派都要经过同一规则

兼容函数的单元测试通过，只能证明函数收到完整参数时能判断。真实入口可能没有把提示词、图片列表或嵌套参数传进去，规则就无从生效。

异步任务还多了一条重派路径。首次请求使用原始参数，失败后重派往往从持久化任务里恢复参数；两条路径的数据形状可能不同。

这次验证用了两层对照。先把新用例放到旧兼容逻辑上，确认能发现原错误；再在网关入口测试里把依赖的判定实现换回旧版，确认首次选路和任务重派都能被这些用例识别。

这样才能证明入口真的传了关键数据，并调用了目标规则。旧版失败时还要看失败原因：参数没接上导致断言失败，是有效线索；依赖缺失导致测试根本没编译，则不能冒充行为回归结果。

## 7. 接入前可以直接使用的核对顺序

1. 从公开接口和页面选项建立能力清单，保留组合条件。
2. 对照备份指南与原适配器，分别核字段、取值、格式、文本语法和归一。
3. 把差异分成静默变化、明确失败和未知，写清处置依据。
4. 为每条排除规则补邻近的允许用例，检查是否过度排除。
5. 捕获有效参数与上游请求体，验证判断和实际发送一致。
6. 覆盖首次选路与失败重派，确认旧逻辑会被目标用例识别。
7. 对仍未知的外部行为做真实探测，逐项更新结论，不扩大样本的证明范围。

## 收尾

1. **从承诺出发** —— 调用方能要求的能力，比字段列表更完整。
2. **保持转换一致** —— 归一、兼容判断和请求构造使用同一份有效参数。
3. **同时查漏放与误拦** —— 每条拒绝规则都需要合理的正向对照。
4. **分清两段证据** —— 本地请求体实测与真实上游结果分别记录。
