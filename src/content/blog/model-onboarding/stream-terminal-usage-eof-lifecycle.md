> 一句话总结：业务终态不等于传输结束，传输有字节也不等于业务有进展。收尾要区分 EOF、有效用量、业务尾帧和保活，再用真正悬挂的上游证明连接会按契约结束。

## 0. 起因：两种方向相反的收尾问题

我处理过一轮流式回归。终端已经显示完整内容，连接仍在等；但如果收到终态就立即返回，慢一点到达的用量又可能被截断。

前者像「结束太晚」，后者像「结束太早」。只改一个统一超时，很容易把两者来回切换。后来复盘发现，业务完成、用量完整、读取完成和保活退出，本来就不是同一个信号。

这里讨论一种特定应用契约：正常 EOF 及时收尾；传输未结束时，确认业务终态且取得有效用量后，才允许按空闲宽限结束。不是所有流式协议都要求有用量字段，也不能把这条应用规则当成 SSE 标准。

## 1. 四个信号，各回答一个问题

| 信号 | 表示什么 | 不能据此推出什么 |
|---|---|---|
| 业务终态 | 按应用协议，生成阶段结束 | TCP 已关闭、用量一定完整 |
| 有效用量 | 已取得契约认可的计量数据 | 后面没有其他有效尾帧 |
| EOF | 响应体已经读完 | 一定是正常业务成功 |
| 保活 | 连接仍可传输或避免空闲断开 | 业务有进展、用量已经到齐 |

SSE（Server-Sent Events，服务端发送事件）用空行划分事件，冒号开头的行是注释；注释本身不是业务数据。[HTML 标准的事件流解释规则](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation)

应用还要继续解析事件里的内容，识别自己的终态和用量。标准规定的事件边界，与应用定义的「可以结算了」，也不是同一层。

## 2. 完成通知不能被某一个协程吃掉

一个典型实现有读取协程、主控制循环和保活协程。读取结束后发一个 stop 值，主循环和保活都在收。看起来都订阅了结束，实际上普通 channel 上的一次发送只会被一个接收方消费。

如果保活先拿到通知，主循环可能继续等待；如果主循环拿到通知，保活又可能迟迟不退出。共享一个名字叫 stop 的通道，不代表具备广播语义。

我现在会区分事件通知和生命周期关闭。读取完成用专属信号，所有观察者只读；实际停止工作由明确的取消路径负责。关闭通道可以广播，但关闭权应唯一，不能让多个协程各自尝试关闭。

还要看等待依赖：如果「读取完成」要等一个仍在等待的保活协程退出，读取明明已经 EOF，也会被后者拖住。通知应该在真正的读取结束点发出，资源汇合另行完成。

这些是并发设计判断，不是看到某个 channel 就机械替换。已有实现可能使用 context、WaitGroup 或其他协调方式，关键仍是信号不会被竞争消费，也不会产生循环等待。

## 3. 宽限从完整有效的业务事件开始

网络可以把一条用量记录拆成很多小段。读到了前几个字节，不代表一整行已到；整行到了，也未必能解析出有效用量。

如果终态先到就开始很短的宽限，后面的用量半行还在路上，网关可能提前结束。最终文本完整，用量却成零，账务与缓存明细都会受影响。

我把计时条件写成：先完整解析到有效用量，且已经观察到契约要求的终态，再允许进入宽限。有效尾帧可以更新业务进展时间；注释、空行和本地保活不能无限刷新它。

正常 EOF 又是独立的结束入口。上游已经关掉响应体，没有必要为了凑满宽限继续空等。读错误、取消、回调停止和 panic 也需要各自正确释放响应体与协程。

无用量时怎么办必须有契约。有些协议允许无用量结束，有些要继续等 EOF 或原超时。不能因为没收到收费依据，就把整个请求改成永远等待。

## 4. 普通字符串桩会掩盖提前结束

测试写一个字符串响应，内容末尾放终态，然后返回。读取器很快就看到 EOF。哪怕应用完全没有终态宽限逻辑，也会正常退出。

这只能证明有限文本能读完，不能证明「上游迟迟不关连接时，网关会主动按契约收尾」。要验后者，夹具必须维持传输未结束。

可使用本地 HTTP 假上游：发完终态和用量后 Flush，随后保持 handler 存活，直到请求 context 被网关取消。还可以周期性发送注释，让网络持续有字节，但没有新的业务数据。

```text
假上游发业务终态与完整用量
    ↓
持续发送注释，保持响应体不 EOF
    ↓
网关应在应用宽限结束后返回
    ↓
假上游观察到取消，退出 handler
```

测试同时观察下游何时返回、上游是否被取消、响应体是否关闭、用量是否保留。只给整个测试设一个超时，跑完没挂，不足以证明是目标结束条件生效。

## 5. 慢传用量要故意晚于短宽限

为了抓提前截断，我会把用量行分多段写出，每段之间等待。总传输时间超过夹具设置的短宽限，让错误实现有机会在半行时结束。

固定预期包括输入、输出、缓存命中和缓存创建明细。仅断言「总 token 大于零」，可能放过丢失某个明细字段的实现。

还要给每个宽限配置留独立预期。默认值按需求字面值验证，禁用配置按原有语义验证；不能让测试同时从被测配置读取实际值和 expected，改坏常量仍一起变绿。

历史回归曾用去掉用量前置条件的最小变异，触发慢传数据归零；恢复竞争消费的完成通知，又触发 EOF 延迟。它们证明对应断言能抓目标缺陷，不证明所有真实供应商的尾部行为已覆盖。

## 6. 用矩阵覆盖生命周期交点

| 夹具 | 重点预期 |
|---|---|
| 正常 EOF，保活开与关 | 都及时返回，内容不丢 |
| 终态、完整用量、不 EOF | 按应用宽限结束，上游取消 |
| 终态、没有用量 | 按已约定的无用量规则处理 |
| 终态后迟到用量 | 完整解析后再进入宽限 |
| 用量半行慢传 | 不截断输入、输出和缓存明细 |
| 宽限期间只有注释 | 不无限延长业务空闲时间 |
| 有效尾帧或慢业务回调 | 按实际业务处理完成时刻计时 |
| 禁用、负值或热更新 | 符合配置契约，在途请求语义明确 |
| 取消、读错、panic | 响应体和自有协程收尾 |

重复运行用于发现竞争，但重复次数不等于独立覆盖数。一个场景跑很多轮，应报告为「这个场景的重复检查」，不能混进新场景数量背书。

时间断言也需要合理余量。负载较高时出现一次超限，要保留失败，判断是应用行为还是调度噪声；单独重跑通过不能直接删除第一次证据。更好的证明是目标变异稳定失败，候选在同样条件下满足宽容区间。

## 7. 收尾之后，还有账务边界

读取器保留了 usage，只证明数据到达了该层。后续 handler 是否传入正确结算入口、缓存明细是否选对价格角色、失败费用怎样处理，都需要另外核账。

同样，本地悬挂上游通过，只能说明夹具覆盖的状态机成立。生产是否运行对应版本、配置是否同步、真实供应商是否发送另一种尾帧，不由本地测试总数证明。

## 收尾

1. **四个信号分开** —— 终态、用量、EOF 和保活各自表达事实。
2. **完成通知要可观察** —— 避免竞争消费与相互等待。
3. **按完整事件计时** —— 用量半行不是有效计量，注释不是业务进展。
4. **夹具故意不结束** —— 验主动收尾，就不能让 EOF 帮它收尾。
5. **结束与结算分别验** —— 保留用量之后，还要核真正到账的结果。
