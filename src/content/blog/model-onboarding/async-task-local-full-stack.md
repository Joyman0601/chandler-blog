> 一句话总结：任务型接口的端到端要跑到结算，「创建成功、预扣对了」只走完了前两跳。本地起一套和生产同款派发路径的全栈，用 mock 验网关侧、用假上游验 SDK 侧，每一单核到实扣和冻结额归零；卡住时先找到是哪一跳、哪一次调用出的问题。

## 0. 起因：一个任务要走八跳

视频、图像、音频这类生成接口通常是异步的。一单请求在系统里大致要走这么几跳：

1. 网关校验参数、按估算预扣（冻结）用户额度、建任务；
2. 网关把任务投递到消息流，按任务类型和供应商分不同的流；
3. 任务 worker 消费消息，用供应商 SDK 调上游建任务；
4. worker 定时轮询上游，直到成功或失败；
5. 上游出结果后，把结果文件转存到自家的文件服务，不把上游直链给用户；
6. worker 把过程事件和终态回调给网关；
7. 网关按实际产出结算：实扣、退差额、冻结额归零；失败则全额退回；
8. 用户查询、回调、历史记录里看到的是过滤过内部字段的结果。

单测通常只覆盖某一跳的逻辑，「创建 + 预扣」级的冒烟只覆盖第 1、2 跳。这一个多月里我接了好几个任务型模型，后面几跳的问题基本都是在本地全栈里才暴露的。这篇讲全栈的搭法和踩过的坑，上游一律用「某视频生成模型」「供应商渠道 A / B」代替。

## 1. 端到端要跑到结算

**第一次的教训**：本地起网关加 mock 上游，验证一个复用现有客户端的新视频模型。创建请求 200，上游收到的请求体正确，用户额度里冻结的金额也和预期分毫不差，差点就写成了「端到端通过」。可任务一直停在处理中，mock 上游一次查询请求都没收到，网关日志反复报「查询时拿不到 API key」。

原因是派发路径不同。这个客户端的查询接口只认它自己定的一种凭证串格式，创建时也会返回这种格式；但网关本地派发路径的轮询不用创建时的返回值，而是按统一规则重新拼一个凭证串。客户端解析不出来，查询永远失败。生产走的是 worker 派发，查询由另一套逻辑完成，所以线上一直正常，这个缺口只在本地派发时暴露。后来同一上游的另一个客户端也栽在这里，它把统一拼法按三段切开，把用户令牌当成了查询地址。

这引出两条规则：

- **跑到终态和实扣**：轮询拿到结果、实扣和预期一致、冻结额归零，才算端到端通过；
- **写清走的是哪条派发路径**：网关有不止一条派发路径时（本地直调、消息流、独立 worker），每条路径拼查询凭证的方式可能不同。先确认测的是生产会走的那条，其余路径的结论单独写明。判断是不是自己引入的，用主干版本重新编一个网关跑同一用例，同样失败就是存量。

**退差额要单独设计素材**：有一单输入 5.4 秒、输出 5.07 秒，四舍五入后预扣和实扣相等，这个用例证明不了「实扣小于预扣时会退差额」。要选输出取整后小于输入取整的素材。另一个更省事的办法是请求 `n=2`、让 mock 只回 1 条结果，正好验「按实际返回数结算、退一半」。

## 2. 本地全栈的搭法

上游主机名往往写死在供应商 SDK 里，换不成本地地址。我最后用的是两种模式：

| 模式 | 怎么起 | 能验什么 | 验不了什么 |
|---|---|---|---|
| mock 模式 | worker 打开「全部供应商换成 mock 客户端」的开关，配一个 mock 服务 | 网关侧整条链路：校验、预扣、派发、换渠道、结算、退差额、结果过滤 | SDK 的请求构造、鉴权头、发往上游的请求体 |
| 假上游模式 | worker 用真实客户端，上游换成本地多端口假服务 | SDK 的请求路径、鉴权头、请求体、解析回包 | 上游的真实口径：假上游的错误体是照 SDK 编的 |

两种模式下，派发方式都要和生产一致：网关走消息流派发，worker 订阅这个任务类型的流。发往真上游的请求体和上游的真实行为都不在这条路上，留给带真实 key 的探测。

**端口即渠道**：每种失败场景开一个端口（正常、401、429、受理后失败、先 5xx 再成功），每条渠道的上游地址指向各自的端口。一开始在地址上加 `?scenario=` 查询参数来区分场景，结果 mock 客户端拼路径时把它拼坏，回 404。改成每个端口前面挂一个只给创建请求加场景头的小代理，代理日志顺便就是「哪条渠道收到几次创建」的证据。

**mock 的落点要先核**：worker 调上游用的地址可能不取自渠道本身的基础地址，只改基础地址，任务会带着真 key 打到真上游。这件事和付费前怎么核对，写在[按次付费接口的测试设计](/blog/billing-regression/paid-test-design/)的案例一。

**核账按交易号**：消息流派发下，网关建任务时会重新生成任务号，预扣记录里的任务号和任务表的 id 不是同一个值，按任务号一条都查不到。要按预扣交易号把两张表关联起来。每单核「额度扣减 = 实扣」，整轮按用户核「总扣减 = 实扣合计」，冻结额归零。

**脚本化**：前四次全栈都是手搭的，每次踩同样的坑。第五次拆成了四个脚本：起栈（临时容器、编译、迁移并补表、起桩、网关、worker）、灌数（安装脚本原样灌入再本地化、重启网关、签登录 token）、跑用例（按用例文件跑到结算并核账）、拆栈（按端口和工作目录停进程、删容器）。下面那些坑的处理都写进了脚本，改脚本时别删掉。

## 3. 只在全栈里出现的坑

按症状列。它们的共同点是：单测不会碰到，日志里也很少有一行直接告诉你原因。

| 症状 | 原因 | 处理 |
|---|---|---|
| 任务一直 pending，两边都不报错 | worker 默认只订阅通用的流，没订阅这个任务类型的流 | 订阅清单里显式加上；上线清单也要列这一项 |
| 补上订阅仍不消费 | 消费组从「最新」位置建，建组之前入队的消息不投 | worker 在任何任务入队前先起；测试环境把消费组位置重置到开头 |
| pending，每约 2 分钟重投，5 分钟后超时退款 | worker 每次都消费了，但它发的「换渠道」「重试」回调被网关回 500：本地库缺表，自动迁移关着 | 看 worker 日志里回调的 HTTP 状态；按模型定义补表 |
| worker 侧请求发不出去 | 渠道 key 里塞了带换行的假 JSON，被原样放进 Authorization 头 | 渠道 key 一律用短字符串 |
| 改了渠道状态或优先级不生效 | 渠道在网关启动时加载进内存 | 改完重启网关，核新旧进程号不同 |
| 「重启」后还是旧行为 | 旧进程没停，新进程绑端口失败只写一行日志 | 按端口取进程号，核对工作目录是自己的再停；别用 `pkill -f` |
| 轮询报 EOF，任务卡在处理中 | mock 服务或代理中途静默退出 | 每条检查前确认后台进程都在，重起了谁写进证据 |
| 下一单的请求数、冻结额对不上 | 上一单还在续派，它迟到的请求落进了下一单的观测窗口 | 每条用例开跑前、整轮核账前，先等全部任务终态 |
| 「前两次失败再成功」第一次就成功了 | 桩里的计数按进程累计，上一轮已经用掉 | 计数按用例清零 |
| 桩的日志里出现测试令牌 | mock 客户端把任务参数原样转发 | 写盘前替换，不靠事后正则 |

关于回调 500 还有一个细节：「重试」「换渠道」这类过程回调写的是任务状态流水，缺表只会让它们失败；终态回调不写那张表，照常成功。看到额外的 500，先分清是过程回调还是终态回调，前者只会少记一段流水，后者才会让任务卡住。

**观测窗口和业务错误要分开**：有一轮 47 个用例首轮过了 45 个，没过的两个在采样截止时还是 pending，冻结额没归零，差点按缺陷报。再查一遍终态账目，两单最后都正确退款了，只是 mock 环境下的重领和超时等待比采样窗口长。处理是只在 mock 环境里调短这几个等待，保留首轮的失败记录，再复测原来那两例。判「退款没退」之前，先查调度方式、重领和超时的配置和终态账目。

**预期本身也可能是错的**：另一个用例期望「渠道 A 回 401 后换到渠道 B，只扣一次」。跑完任务还在处理中，三次创建都落在 A。查下来，消息流派发下，共享的渠道选择器只在同一个供应商内换渠道，A 和 B 是两家，不互为备份；A 的渠道级 401 在原渠道重试 3 次，约 10 分钟后失败、全额退款。这不是缺陷，是用例写错了。实际行为写进了兼容问题，交给 leader 决定要不要做跨供应商互备。

**mock 结果要能打开**：mock 服务返回的结果地址是写死的占位域名，我在浏览器里点下载，提示「This site can't be reached」。助手在本机起了一个假 CDN，对任何结果路径都返回同一段 ffmpeg 生成的测试视频。我接着问：所有结果都指向同一段视频，怎么知道真的生成了？答案是 mock 回答不了这个问题。最后关掉 mock、用真实凭证跑了一条最便宜的档位，确认出片、结果已转存、用户响应里没有上游地址也没有内部计费字段。

## 4. 文件服务这一跳：先找到失败的是哪次调用

本地全栈里最容易误判的是文件服务。它往往仍然指向线上，而线上的文件服务拿你的凭证去线上网关校验，本地网关签的 key 一律被拒。网关的统一文案又看不出失败在哪一段。

我碰到过三种：

1. **前端上传返回 401，网关日志里没有请求**：前端的上传接口转发到线上文件服务，带的是本地网关建的 key。前端配置里有一行注释写着「本地没有这个服务，沿用线上」，写注释时后端是共享环境，换成本地网关后前提就不成立了。
2. **语音合成任务 3 秒内失败，用户看到「服务鉴权失败」**：同一套环境里，只返回一个 ID、不产出文件的任务完全正常。上游 key 是好的，失败在结果转存：转存用的是发起请求那个用户的 key，本地用户在线上不存在。第一反应去查渠道 key，方向就错了。
3. **结果是上游直链，被助手归成「本地没配转存服务」**：前两次的经验让助手看到直链就套用了同一个解释。我追问了一句「有没有把上游地址给用户」，助手才去读代码：这个供应商的客户端里根本没有转存这一步，日志里也没有任何转存尝试。同一客户端服务的已上线模型在生产上同样返回直链。

第 3 种是真缺陷，被当成了环境限制。区别在日志里一眼可见：转存失败会留下一次失败的请求和降级告警，这里一条都没有。我现在把现象归因到环境之前，固定做两步：

```bash
grep -i -E 'transfer|upload|转存' worker.log gateway.log   # 有没有尝试过？失败了吗？
grep -rn -i -E 'transfer|upload' <这个供应商的客户端目录>     # 代码里有这条路径吗？
```

日志里有失败的尝试，是环境问题，写明哪次调用失败；日志里没有尝试、代码里也没有，就是实现缺口，和环境无关。更一般的说法是：写「本地环境的限制」之前，要回答一句「如果环境是齐的，代码里哪一行会让结果不一样？」指不出那一行，就不是环境问题。

**怎么补验这一跳**：不改仓库，起一个本地文件服务桩（按 URL 上传、按 base64 上传两个接口，存本地目录、用一个 GET 吐回来，每次上传记一行日志），再用一个 compose 覆盖文件只改文件服务地址这一个环境变量。桩返回的文件地址写成浏览器能打开的 `localhost`，不写容器里才认识的主机名。

手里有一把线上账号的 key 时，还能零成本补验真实文件服务：在 SDK 这一层写一个仓库外的用例，上游用本地假服务（直接返回成功和一个公网可取的小文件），转存走真实的上传客户端。断言出结论前任务是处理中、不带地址；之后结果地址换成自家域名，转存后的文件字节数和源文件一致。再用一把无效 key 跑一次对照，确认 401 来自文件服务、并且会降级。实测同一个 7 MB 视频，本地桩 4 秒、真实服务约 49 秒，这段时间任务一直停在处理中。

## 5. 本地登录：不用第三方身份服务的服务账号

前端控制台要登录才能走页面流程，而登录用了第三方身份服务。读代码发现，前端只在登录那一刻拿第三方的 ID token 去网关换一枚**网关自签的会话 token**，之后所有请求都只带这枚 token。网关的签名密钥是本地自己设的，所以给一个本地用户签一枚同格式的 token、写进浏览器存储，就登录了，不改代码，也没有跳过任何校验。

要读三处：网关鉴权中间件的算法、密钥来源、claims 字段和签发者校验；前端存 token 的存储键名和页面加载时的恢复路径；前端登录状态机里的显式登出标志和上一个环境留下的 key 缓存，注入前一起清掉。

```python
# 本地网关专用：用自己设的会话签名密钥签一枚 access token
import base64, hashlib, hmac, json, os, secrets, time

def b64(b: bytes) -> str:
    return base64.urlsafe_b64encode(b).rstrip(b"=").decode()

signing = os.environ["LOCAL_SESSION_SIGNING_KEY"].encode()
now = int(time.time())
claims = {  # 字段按网关中间件的 claims 结构体写
    "sub": "1", "user_id": 1, "role": "admin", "type": "access",
    "iss": "<网关校验的 issuer>", "iat": now, "nbf": now, "exp": now + 7 * 86400,
    "jti": b64(secrets.token_bytes(16)),
}
head = b64(json.dumps({"alg": "HS256", "typ": "JWT"}).encode())
body = b64(json.dumps(claims, separators=(",", ":")).encode())
sig = b64(hmac.new(signing, f"{head}.{body}".encode(), hashlib.sha256).digest())
print(f"{head}.{body}.{sig}")
```

先用 curl 打网关的 token 校验接口，确认被接受，再在浏览器 Console 里写进存储、刷新页面。跳过了自动迁移的空库不会自动建管理员用户，token 里的用户 id 要自己插一行。这个办法只用于本地、密钥自己生成的网关；对共享环境或生产网关做同样的事等于伪造会话。

## 6. 续轮路径：转发代理只丢一类回调

「上游已经成功建了任务，但这条回调没送到网关」是一条很重要的路径：处理不好，任务会在上游被重复创建、重复花钱。单测能 mock，端到端却很难自然触发。

办法是把 worker 的网关地址指向一个本地转发代理：其余请求原样转发，只把指定任务的某一类回调回 503。worker 放弃这一轮，之后由重投机制带它走续轮，就能在真实网关上看到终态、扣费和渠道统计。下面是一个标准库写的最小骨架，回调路径和事件字段按项目实际改：

```python
import json
from http.client import HTTPConnection
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

GATEWAY = ("localhost", 3000)
DROP = {"on": True, "event": "upstream_created", "task": None}  # 运行中改它来开关

class Proxy(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def forward(self):
        n = int(self.headers.get("Content-Length") or 0)
        body = self.rfile.read(n) if n else None
        if DROP["on"] and body and self.path.startswith("/callback"):
            evt = json.loads(body)
            if evt.get("event") == DROP["event"] and DROP["task"] in (None, evt.get("task_id")):
                self.send_response(503)
                self.end_headers()
                return
        conn = HTTPConnection(*GATEWAY, timeout=120)
        skip = {"host", "content-length", "connection"}
        conn.request(self.command, self.path, body=body,
                     headers={k: v for k, v in self.headers.items() if k.lower() not in skip})
        resp = conn.getresponse()
        data = resp.read()
        self.send_response(resp.status)
        for k, v in resp.getheaders():
            if k.lower() not in {"transfer-encoding", "connection", "content-length"}:
                self.send_header(k, v)
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    do_GET = do_POST = do_PUT = do_PATCH = do_DELETE = forward

if __name__ == "__main__":
    ThreadingHTTPServer(("localhost", 3900), Proxy).serve_forever()
```

几个要点：

- **只拦一类、只拦一单**，其余回调和查询都放行，链路其余部分保持真实。worker 对回调失败一般会带退避重试几次（实测 4 次、约 15 秒），以日志里「回调失败」那一行为信号关掉拦截，不按固定秒数，否则续轮回来时也会被拦。
- **重投有两个入口，先到的那个赢**：worker 自己的待确认消息回收（Redis Streams 的 `XAUTOCLAIM`，实测是 5 分钟一次的定时器，启动时不扫），和网关的失联续派（任务约 2 分钟没有新事件就重新排进流，worker 收到的是一条新消息）。端到端多半走到的是网关续派。两个入口最后进同一段「已有上游任务号就跳过创建、转去轮询」的代码，报告里要写明实际走到的是哪个，没走到的那个靠单测覆盖。
- **断言四件事**：上游只被创建一次（日志里有「跳过创建」那一行，创建日志只有一条）；任务终态和失败文案；预扣全额退回；这次失败没被记成渠道错误。只看终态会漏掉重复扣上游的钱和误熔断渠道这两类事故。
- 测完切回原配置时网关容器会重建，日志就没了。断言放在切回之前做，或者看挂载出来的落盘日志。代理自己出错时，worker 看到的是连接被断开，失败发生在更早的步骤，第一次跑先看代理有没有异常堆栈。

## 7. 轮询循环：顺延守卫跳过了查询

接一个走异步转存的新模型时，助手读过 worker 轮询循环里的一段守卫：过了 deadline 时，如果转存还在进行、或者结论已就绪但还没被消费，就先不判超时，注释说「紧接着的轮询会正常收口」。助手当时判断没问题。外部审查用最小用例复现出相反的结果：转存几毫秒就完成了，deadline 之后每个 tick 只打一行「顺延」，状态查询次数停在 1，任务既不成功也不失败，直到结论缓存过期才按超时失败。

```go
for t := range ticker.C {
	if t.After(deadline) {
		if transferPending(taskID) { // 进行中，或结论已就绪但还没被消费
			continue // 跳过了下面的 poll
		}
		reportTimeout()
		return
	}
	if done := poll(); done { // 只有这里会消费转存结论
		return
	}
}
```

结论只在 `poll()` 里被取走，而过了 deadline 之后每一轮都进守卫、`continue`，再也到不了 `poll()`。守卫和它要等的事互相锁住。修法是让顺延分支落到查询上，并给顺延设一个硬上限。复现这类问题不需要真实上游：一个「首轮启动转存、之后返回结论」的假客户端，配 1 秒超时和略短于超时的轮询间隔，几秒就能看到查询次数不再增长。这段是共用的轮询代码，不是这次接入改的，所以上报给负责人，同时写进新模型的已知限制。

同一类「本地永远能过」的还有进程内状态：结果只存在创建它的那个 worker 进程的内存里，查询落到别的实例就查不到。本地单实例测不出来。接入评审时我会问三句：结果存在哪？有几个实例？查询请求怎么选实例？这一条是读代码推出来的，没在生产验证过。

## 8. 两个单测层面的小工具

**换域名：TLS 假上游加只放行目标主机的拨号器**。给客户端加新地域（换域名）时，要证明的是「渠道里写的那个域名被用上了，没有哪一步退回写死的默认域名」。直接把地址换成假上游的本地地址，只能证明客户端用了传进来的地址；某一步退回默认域名时，测试会真的连出去或者超时，不会清楚地变红。

```go
srv := httptest.NewTLSServer(handler) // handler 记录 r.Host、路径、鉴权头、请求体
target := srv.Listener.Addr().String()
client.HTTP = &http.Client{Transport: &http.Transport{
	DialContext: func(ctx context.Context, network, addr string) (net.Conn, error) {
		if addr != "api-region.example.com:443" {
			return nil, fmt.Errorf("blocked dial to %s", addr)
		}
		return (&net.Dialer{}).DialContext(ctx, network, target)
	},
	TLSClientConfig: &tls.Config{InsecureSkipVerify: true}, // 仅测试：假上游是自签证书
}}
```

渠道地址就传生产里真实会写的域名。任何一步落回默认域名，都会得到一行 `blocked dial to <默认主机>:443`。再做一次反证：临时让客户端忽略配置、固定用默认地址，确认测试红在「拨号被拦」上。

**时长上限：容器时长和视频流时长**。上游文档写参考视频不能超过 10 秒，官方自己的示例视频量出来是 10.054 秒，直接提交给上游却成功了。浏览器的 `video.duration` 和 ffprobe 的容器时长取的是最长的那条流；这个文件的视频流正好 10.000 秒，多出来的是音轨。前端按容器时长「大于 10 就拦」，会把官方示例拦下。

```bash
ffprobe -v error -show_entries stream=codec_type,duration,nb_frames:format=duration \
  -of compact=p=0 sample.mp4
```

同一次还发现，真正超限的 12 秒视频，上游也不在创建时拒绝，而是创建成功、几秒后任务失败，失败信息不带错误码，也不扣费。只看创建接口的状态码，会得出「上游不校验时长」的错误结论。边界用例要两种素材都备：容器超限但视频流不超限的，和视频流本身超限的。自己这一侧的校验不要比上游严。

## 收尾

1. **跑到结算才算通** —— 终态、实扣、冻结额归零三样都核；退差额单独设计素材。
2. **写清派发路径** —— 本地直调和消息流派发可能有不同的存量问题，结论只对测过的那条路径成立。
3. **两种模式各验一半** —— mock 验网关侧，假上游验 SDK 侧，上游真实口径留给真 key 探测。
4. **卡住先找那一次调用** —— 回调状态、订阅清单、转存尝试，日志里找到返回错误的那一跳再下结论。
5. **环境限制也要证据** —— 指不出「环境齐了哪一行会不一样」，就不是环境问题。
6. **续轮用代理制造** —— 只丢一类回调，断言上游只建一次、退款、不误记渠道错误。
7. **观测窗口不是缺陷** —— 采样截止时没收口，先查终态账目和等待配置，再判业务代码。

回头看，全栈里的每个坑单独都不难，难的是第一次碰到时日志里没有一行直接告诉你原因。把它们写进起栈脚本，比记在脑子里可靠。错误分类和换渠道那部分见[错误分类、重试和渠道禁用](/blog/model-onboarding/error-classifier-channel-disable/)，接入的整体顺序见[接一个新模型的五段流程](/blog/model-onboarding/onboarding-five-stages/)。
