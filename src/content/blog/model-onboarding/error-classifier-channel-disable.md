> 一句话总结：错误分类器只认写规则时见过的措辞，读分类结果的消费方又各自只看一部分规则。接新上游时，用假 key 打一遍真实上游，把它错误码表里每一条真实原文直接喂给分类器入口，再挨个核每个消费方看到的是什么。

## 0. 起因：一条上游错误要回答五个问题

模型网关收到上游的一条错误，至少要同时回答五个问题：

1. 给用户看什么文案、什么错误码、什么 HTTP 状态；
2. 要不要在同一个渠道上重发，要不要换一个渠道；
3. 记不记进渠道错误，累计到一定程度要不要自动禁用或熔断这个渠道；
4. 记不记进模型的健康度，也就是模型页上的成功率；
5. 记不记进兜底统计，比如数据库里按天汇总的失败数。

这五个问题通常由同一个分类器给出类别（鉴权、配额、参数、内容审核、服务端、未知），再由不同的消费方各自解读。分类器靠关键词和正则匹配上游原文，规则只对写它时见过的措辞有效。消费方匹配规则的范围也不一样：有的先看渠道专属规则再看全局规则，有的只看全局规则。

所以「接一个新上游、错误处理照旧」其实不成立。这一个月里我在这五个问题上各栽过跟头，下面按顺序讲。上游都用「某厂商」「供应商渠道 A / B」代替。

## 1. 没命中任何规则：上游原文透给用户

**现象**：给一个新上游配渠道时，故意把渠道 key 填错。用户收到 HTTP 401，消息是上游原文，大意是「credential check not passed，请在请求头的 Authorization 里带上 API key（40017）」。

这不只是不好看。终端用户读到这句话，会以为是**自己**的 API key 有问题，开始检查自己的配置；实际坏掉的是平台这一侧填给上游的 key。用户无从修起，还会去提工单。

**根因**：分类器里的鉴权规则是按常见写法写的，`unauthorized`、`invalid api key`、`authentication failed`、`HTTP 401`，外加一条「`code` 后面跟错误码」的正则。这家上游把认证失败写成 `credential check not passed`，错误码放在文案末尾的括号里，前面没有 `code` 字样，每条规则都差一点。没归类的错误只做了敏感词脱敏，其余原文照发。

mock 上游返回的是自己编的错误体，永远测不出这个问题。

**修复**：按真实文案补一条规则，文本请求和任务两套分类器都补，各配一条用真实原文写的单测。再经网关用假 key 打一遍，确认用户看到的是统一文案。

接新上游时我会做一次零成本的「假 key 巡检」：每个主机乘每个端点打一次，状态码、错误体、响应头全部落盘。

```bash
# 每个主机 × 每个端点用一个明显无效的 key 打一次，不会产生费用
# PROBE_KEY 事先设成一个随手编的、明显无效的串
for host in "$UPSTREAM_HOST_A" "$UPSTREAM_HOST_B"; do
  for ep in /v1/chat/completions /v1/images/generations /v1/tasks; do
    out="probe/$(echo "$host$ep" | tr '/:' '__').txt"
    curl -sS -D - -o - -X POST "https://$host$ep" \
      -H "Authorization: Bearer ${PROBE_KEY:?}" \
      -H "Content-Type: application/json" -d '{}' > "$out"
    printf '%s %s -> %s\n' "$host" "$ep" "$(head -1 "$out")"
  done
done
```

这一步的产物是后面所有核对的原料：每条真实原文都要拿去喂分类器。

## 2. 命中了也不算完：数字业务码会跨厂商归错类

**现象**：给一个视频上游加海外渠道，验证「海外 key 填错时用户看到什么」。上游回 HTTP 401，错误体是 `{"code":2061,"message":"api key not found"}`。网关没有透传原文，这一点是对的；但给用户的是「资源暂时耗尽，系统会自动切换线路」，错误码是配额耗尽类，HTTP 429。这其实是鉴权失败。同一上游的 2063（token 无效）倒是正确地落进了鉴权类。

**根因**：分类器里有一条给另一家上游写的配额规则，形如 `code.*(2061|2068|…)`，只看 `code` 后面跟的数字，不管是谁家的报错。业务码是各家自己编的号，A 家的 2061 是限流，B 家的 2061 是鉴权失败。SDK 把上游错误包成 `<上游名> API error (code=2061): …` 再交给网关，这串正好命中。

这个误判不影响换渠道，因为换不换由 SDK 按自己的业务码表判断，是另一套逻辑。所以端到端看一切正常，偏的只是用户文案、错误码和健康度的口径：鉴权失败被算成配额问题，排障时方向会被带偏。

**修复**：数字类规则带上厂商前缀或限定上下文，例如 `(?i)^<厂商前缀> API error \(code=20[6-9][0-9]\)` 归鉴权。不确定改通用规则会影响谁时，先只报告，再按渠道或厂商加一条更具体的规则，不改那条通用规则。

**验证方法**：不靠人读规则表推断，直接调分类器的入口函数，把每条原文的「类别、命中的规则、HTTP 状态、用户文案」打印出来存档。下面是一个通用的最小写法，`Classify` 换成你项目里分类器实际的匹配入口：

```go
func TestNewUpstreamErrors(t *testing.T) {
	cases := []struct {
		raw          string // 上游真实原文，按 SDK 实际产出的格式拼
		wantCategory string
		wantStatus   int
	}{
		{"Vendor API error (code=2061): api key not found", "auth", 401},
		{"Vendor API error (code=2063): token invalid", "auth", 401},
		{"Vendor API error (code=2101): concurrency limit", "rate_limit", 429},
		{"Vendor API error (code=2301): prompt rejected by moderation", "content_policy", 400},
	}
	for _, c := range cases {
		r := Classify(c.raw)
		// 存档用：每条打出命中的规则，核对它是不是为这家写的
		t.Logf("%-55s -> %s / rule=%q / %d / %q", c.raw, r.Category, r.Rule, r.Status, r.UserMessage)
		if r.Category != c.wantCategory || r.Status != c.wantStatus {
			t.Errorf("%s: got %s/%d, want %s/%d", c.raw, r.Category, r.Status, c.wantCategory, c.wantStatus)
		}
	}
}
```

错误码表里至少鉴权、配额、参数、内容审核、服务端各一条。日志里那列 `rule` 是关键：类别对了，但命中的是给别家写的规则，迟早会出事。

## 3. 一个分类结果，好几个消费方

这是这一个月里最绕的一条。

**现象**：接一个声音复刻类的模型时，按渠道类型加了 7 条专属规则：录音链接下载失败、不是音频、太短、静音、采样率不对、文件过大、审核不过，全部归参数类。用户看到的错误码和文案都对。上线回归时为了测失败退款，故意发了两单坏录音，结果当天那个时段的模型页健康条掉到了 87.5%。

**排查**：读健康度的计入逻辑，发现它只认不限渠道的全局规则；用户文案和跨渠道重试则按「渠道 id → 渠道类型 → 全局」的顺序匹配。把 7 条原文逐条喂给全局匹配，结果分成两类：

- 不是音频、太短、静音、审核不过这 4 条，全局规则不认识，落成未知错误（500），计入失败；
- 下载失败、采样率、文件过大这 3 条，碰巧被别处写的几条宽泛全局规则接住了（按关键词加长度窗口匹配，比如两个关键词之间隔着不超过十个字符），判成参数错误，不计入。

8 单里只有 1 单被计入，正好是 87.5%。这是推断：线上的分桶数据我看不到。

我把这几个消费方整理成一张表，之后每加一条渠道专属规则都对着它过一遍：

| 消费方 | 匹配范围 | 新规则没覆盖到时会怎样 |
|---|---|---|
| 用户文案和错误码 | 渠道 id → 渠道类型 → 全局 | 透出原文，或给出别类的文案 |
| 跨渠道重试 | 同上 | 该换的不换，或不该换的换了 |
| 渠道错误上报（禁用、熔断） | 视实现而定 | 用户的坏输入把正常渠道熔断 |
| 模型健康度 | 只看全局 | 用户的坏输入拉低成功率 |
| 兜底统计 | 只看全局 | 统计口径和健康度对不上 |

**看起来是 bug 的，先查是不是有意的**：助手的第一版改法是让健康度也按渠道匹配，和其它消费方一致。推送前审视时翻历史，发现「渠道规则只改展示、不动健康度口径」是当初有意的分层：提交注释里写着，测试里还有一条专门守这个口径的护栏，参考文档把改计入口径列为「需业务决定」。

再给每条渠道专属规则造一条样例原文，跑新旧两种口径对比：34 条里 21 条的计入结论会变。其中 20 条从计入变成不计入，包括渠道侧的真故障，比如余额不足、上游额度不足、并发已满、轮询超时。专属规则把它们归进了鉴权、配额、超时这些不计入的类，口径一改，健康条就看不出渠道出事了。另有 1 条反过来，从不计入变成计入。改口径就是推翻原设计，我选了窄修作为默认，全量版留给 leader 定。

**窄修**：只给这 7 条原文各加一条不限渠道的全局规则（只有正则，归参数类）。健康度直接认得；渠道上仍然先命中专属规则，用户文案不变。

**线上配置会整类覆盖代码默认**：窄修第一版只补了会被计入的 4 条。独立复核时查出：线上的错误规则配置一旦定义了某个类别，就整类替换代码里这个类别的默认规则。那 3 条碰巧被接住的原文，靠的是代码默认里的宽泛规则，线上那份配置里未必有。于是扩成 7 条全部显式写出，并加了一组测试：只加载交给运维的那份规则文件，结论也要成立；再加一条测试守住代码和运维文件两份规则逐字一致。

**测试先加正向对照**：单测的第一步不是断言「不计入」，而是先断言「全局规则不认识这条原文」，再断言补上规则后不计入。否则碰巧被宽泛规则接住的原文会让测试空转。这次 7 条里有 3 条就是这样，对照一加就报了出来。

验证时做了 19 个变异，16 个被新用例抓到；没抓到的 3 个是「只在代码默认里删掉某条规则」，代码默认下有宽泛规则兜着，属于预期，由逐字一致那条测试抓到。

## 4. 任务类失败绕过了渠道错误上报

上面说的「渠道错误上报」是请求中继层的机制。异步任务类的接口（出图、出视频、出音频）建任务时往往不走中继，失败只落在任务本身。

**现象**：把一个任务类渠道的 key 换成假的，连续 6 次上游 401，任务全部失败、全额退款，用户看到「鉴权失败」。可渠道状态一直是启用，日志里没有任何禁用、熔断的记录。坏 key 会一直吃请求。

**根因**：任务类的失败有四个出口，当时一个都没接进渠道错误上报：

1. 建任务时直接返回 error；
2. 同步型客户端的「软失败」：没有返回 error，而是返回一个状态为失败的结果，任务立刻落成失败；
3. 异步客户端的上游错误要轮询到终态才成为失败，包括 worker 回调里的终态出口；
4. 任务分发到 worker 执行时，worker 把失败判成渠道级、请求网关换渠道，任务随后在别的渠道上成功，根本不经过终态出口。

第 4 个最隐蔽。只接了前三个时，只要还有备用渠道，坏渠道永远不会被上报：每笔请求都先白打它一次再改投，用户只觉得慢了几秒，没有任何报错。这个出口是代码审视之后补跑分发模式才发现的。

**修复和其中的坑**：

- 四个出口都调渠道错误上报，交给它按错误规则、致命关键词、HTTP 状态和累计阈值处置。
- 软失败上报时登记任务号，紧随其后的终态出口看到登记就跳过，**同一次失败不能计两次**。
- 终态出口要带上回调里的 HTTP 状态。第一版只传了文案，于是上游限流（429）被当成普通错误累计，本该走熔断，却在走「累计 N 次就禁用」。
- 平台自己判定的超时、取消，以及 worker 自己的失败（关停时放弃在飞任务、结果回传失败、卡在内部阶段）不算上游错误。worker 重启一次就可能有一批任务以这些原因失败，计进去会把正常渠道熔断。
- 只剩文案、没有状态码的失败，先过错误分类：用户的录音链接 404、音频太短、审核不过这类不上报。复测时，一条真渠道上用户的录音 404 被计了一次。按「累计 5 次禁用」算，一个用户连发 5 条坏录音就能把正常渠道关掉。
- 累计计数「成功也不清零」：代码审视时有人指出，成功请求不清零的累计规则下，偶发错误迟早攒满阈值。这是存量行为，我写进了上线说明，没在接入时顺手改。
- 上游文案里的关键词可能和致命关键词表差一个连字符（`Invalid API-key` 和 `invalid api key`）。补进表里时又碰上和第 3 节一样的问题：线上配置里如果有这张表，会整体覆盖代码默认，只改代码不生效，要写进上线步骤。

**验证的渠道组合**：本地只有一条渠道时，「禁用后模型就没有可用渠道」的保护会拦住禁用，只留一行日志，看不到真禁用。要看到禁用和后续切换，得再加一条真渠道、把假渠道的优先级调高。分发模式下还必须是「假渠道优先、真渠道并存」：只留假渠道时任务终态失败，走的是终态出口，测不到换渠道那条路；两条并存时任务是成功的，要看的是假渠道有没有被禁用、第二笔请求有没有直接落到真渠道。

## 5. 渠道全禁用之后，用户看到的是 404 还是 400

设计文档和验收预期都写着「渠道全禁用时返回 400，可重试」。本地实测把某模型的渠道全部禁用，请求回的却是 404，文案是「模型不可用于这个 key，这是永久错误，不要用同一个 model 重试」。

**根因**：网关先选渠道，没选到时再判断：模型对这个分组「可见」就回可重试的 400，不可见就回永久的 404。「可见」和模型列表接口同一个口径，取的是能力表里该分组、启用的模型。改渠道状态的统一入口会同步能力表的启用位，所以手动全禁用之后，模型就从可见集合里消失了。

自动禁用有一道保护：禁掉以后模型没有渠道可用的，拒绝禁用。所以 404 只出现在手动全禁用的情形；平时「部分渠道被熔断」看到的一直是 400。

| 情形 | 渠道 | 能力表 | 返回 |
|---|---|---|---|
| 有启用渠道，但能力规则都不兼容 | 启用 | 启用 | 400，可重试 |
| 兼容渠道被熔断，模型还有别的渠道 | 熔断 | 置 0 | 400，可重试 |
| 模型的渠道全部手动禁用 | 禁用 | 置 0 | 404，永久 |

本地复现还有一个坑：库里如果只有这一个模型，可见列表为空时网关会放行（当成可见），也回 400。必须先在分组里放一个别的启用模型，才复现得出生产上的 404。

想让全禁用也回可重试的 400，要么下线时只关能力路由、保留模型可见，要么改「可见」的判定。这是产品决定，不在接入时顺手改。

禁用和恢复这一段，后来又在审查里查出三个边界：

- **跨供应商改投时源渠道没上报**：A 失败后改投到另一家供应商的 B，这条路径提前返回，A 的失败一次都不计，A 欠费或鉴权失败永远不会被禁用。只在模型配了跨供应商重试策略时触发。
- **按状态码写的排除误伤别家**：为了不让内容审核类的 403 计入渠道错误，加了一条 403 排除。它按状态码判断，把另一家上游「model not found」类的 403 也排除了，而那类错误原来是直接上报的。排除条件要带上错误类别或厂商，不能只看状态码。
- **手动启用后去重没清**：禁用时有一个 5 分钟的告警去重。渠道被自动禁用后，有人在 5 分钟内手动启用（比如充值完马上启用），而渠道其实还坏着：同一个网关实例再收到致命错误时，既不禁用也不告警，最长要等满 5 分钟。去重是进程内的，多实例下只清得掉本进程那份，这个限制写进了上线说明。

## 6. 重试：同渠道重发、换渠道、直接失败

**现象**：某图像生成模型的供应商渠道 A 欠费，上游回 `HTTP 403` 加一个表示账户欠费的业务码。SDK 把它当成可以原地重发的错误，对 A 连发 3 次；worker 的完成路径遇到失败一律直接报失败，从不请求换渠道；网关其实有现成的换渠道机制，但「没有候选渠道」时只记一行日志，任务不收口。

上游账户欠费不是用户余额不足，也不是用户参数错误。它是渠道级的致命错误：同渠道重发没有意义，应该换渠道；换不了就直接失败退款。

**修复**：

- 识别只认「403 加结构化的欠费业务码」，不把所有 403 当同一种错误（同一个 403 也可能是内容审核）；
- SDK 对渠道致命错误停止同渠道重发，并把 HTTP 状态和业务码结构化地带给上层，不只给一段拼好的文案；
- worker 在完成阶段识别欠费、请求换渠道；
- 网关加两条：同一任务因欠费最多换一次（A 换到 B 后，B 再失败不换 C、也不回 A），没有候选时直接终态失败并退款；
- 同一个上游在渠道配置里有两个类型名，两个都要认（见[改名、别名和重定向](/blog/model-onboarding/rename-alias-redirect-ripple/)第 3 节）。

验证用本地假上游按端口计数：A 欠费、B 成功时，A 收到 1 次、B 收到 1 次；B 也欠费时任务失败退款，C 不被调用；余额扣减和实扣合计一致，冻结额归零。限流类的 429 仍保留原来的 3 次重试。「只换一次」依赖任务级的失败渠道记录，缓存不可用时由 worker 的次数上限兜底，所以不能承诺所有故障下都严格只换一次。这些都是本地模拟，真实候选渠道没有验收。

另一个上游的重试策略做的是「同任务、同渠道自动重建」。开发中发现一个时序问题：旧的上游任务号的失败回调晚到，会再消耗一次新任务的重建次数，还重复记一次熔断。回调要按上游任务号核对它属于当前这一轮，旧轮次的回调直接丢弃。

我最后把每一类错误的处置整理成一张表，接新上游时照着填：

| 错误类别 | 同渠道重发 | 换渠道 | 计入渠道错误 | 计入健康度 |
|---|---|---|---|---|
| 网络抖动、5xx | 是，有上限 | 重发用完后 | 是 | 是 |
| 限流 429 | 是，退避 | 视策略 | 走熔断，不累计禁用 | 否 |
| 渠道鉴权失败、欠费 | 否 | 是，最多一次 | 是，致命 | 是 |
| 用户参数错误、坏素材 | 否 | 否 | 否 | 否 |
| 内容审核 | 否 | 否 | 否 | 否 |
| 平台超时、取消、worker 内部失败 | 否 | 否 | 否 | 视口径 |

表里每一格都应该能指到一条测试。

## 7. 熔断阈值：和实测数据同单位，写全复位条件

**现象**：给另一个上游的终态失败设计「同渠道重建一次加事故熔断」，第一版阈值写的是「渠道近 5 分钟失败不少于 20 条」，依据是「事故期每小时上百条」。审查时按渠道做 5 分钟滑窗实测：事故期三条渠道的 5 分钟峰值分别是 7、14、25 条，常态日为 0。这个阈值正常日不会误触，但事故期大半时间也不会响，整场事故只在一条渠道上响过约 40 分钟，等于没有熔断。

**根因**：阈值是按「感觉上的事故规模」写的，没有换算到阈值自己的时间窗和维度。按小时、按全平台看很大的事故，按渠道、按 5 分钟看就小。

**第二版**改成数事件：连续 5 次重建失败，停 30 分钟；再触发就翻倍，封顶 240 分钟。正常日连续失败次数为 0，天然不触发；事故期按每小时条数能算出多久触发。

审查又指出：没写复位条件。熔断是一个状态机，只写了「进入」，没写「退出」。两种读法在表里都说得通：

- 按「档位永不复位」读，事故过去几天后一次 5 连败，直接停 240 分钟；
- 按「熔断到期就回到 30 分钟」读，每渠道每天最多 48 个周期，而不是按翻倍算的 9 个。三条渠道一天最多 720 次重建，被日上限 500 截住；按翻倍读法是 135 次。前者是后者的 3.7 倍，而成本估算默认的是后一种读法，表里没写。

最后的默认写全了四件事：进入条件、停多久和翻倍上限、连续计数什么时候清零（该渠道一次重建成功即清零）、翻倍档位什么时候回落（该渠道连续 24 小时未再熔断才回到 30 分钟，熔断到期本身不回落）。两种读法的最坏敞口各算一次，连同日上限交给 leader 定。

写成代码，四个条件都要有明确的位置：

```go
type Breaker struct {
	Threshold int           // 进入：连续失败次数
	Base, Max time.Duration // 停多久：初始时长与翻倍上限
	Cooldown  time.Duration // 回落：多久没再熔断，档位回到 Base

	consecutive int
	level       time.Duration
	openUntil   time.Time
	lastTripped time.Time
}

func (b *Breaker) OnSuccess() { b.consecutive = 0 } // 清零：一次成功

func (b *Breaker) OnFailure(now time.Time) {
	b.consecutive++
	if b.consecutive < b.Threshold {
		return
	}
	switch {
	case b.level == 0 || now.Sub(b.lastTripped) >= b.Cooldown:
		b.level = b.Base // 首次熔断，或已经安静了一个冷却期
	case b.level*2 <= b.Max:
		b.level *= 2
	default:
		b.level = b.Max
	}
	b.openUntil, b.lastTripped, b.consecutive = now.Add(b.level), now, 0
}

func (b *Breaker) Allow(now time.Time) bool { return !now.Before(b.openUntil) }
```

注意 `Allow` 只管「现在放不放行」，到期放行不等于档位回落；档位回落只看 `Cooldown`。把这两件事分开写，读代码的人就不用猜。

这条后来的结局是：按 leader 的决定（转述），这个上游改用已有的熔断机制，同任务同渠道最多重建两次，单渠道不加熔断。上面这些推演没有直接落地，但「阈值和数据同单位、复位条件写全」这条方法我之后一直在用。

## 收尾

1. **假 key 打真上游** —— mock 返回的是自己编的错误体，测不出原文透传和措辞没覆盖；每个主机乘每个端点打一次，原文全部落盘。
2. **直接调分类器入口** —— 每条原文打印类别、命中的规则、状态和文案，核对命中的是不是为这家写的规则。
3. **数字业务码带上厂商** —— 各家的业务码是自己编的号，只看数字的通用规则迟早跨厂商归错类。
4. **逐个核消费方** —— 文案、重试、渠道上报、健康度、兜底统计各自的匹配范围不同；改口径之前先查是不是有意设计，并把两个方向的变化都列出来。
5. **线上配置会整类覆盖** —— 修复不能依赖代码默认里碰巧存在的宽泛规则；测试只加载交给运维的那份规则再跑一遍。
6. **失败出口列全** —— 建任务、软失败、终态、换渠道四个出口都要上报，同一次失败只计一次，用户错误和平台自己的失败不计。
7. **熔断写全四件事** —— 阈值和实测数据同单位，进入、时长、清零、回落都写明，两种复位读法的敞口都算出来交决策人。

回头看，这些问题的共同点是「默认一切照旧」：新上游的措辞照旧、消费方的口径照旧、出口照旧、阈值凭感觉。每一条都要拿真实原文和真实数据去对。上游原文从哪来，见[上游接口实测](/blog/model-onboarding/upstream-probe-evidence/)；任务类接口怎么在本地起全栈测换渠道，见[异步任务链路](/blog/model-onboarding/async-task-local-full-stack/)。
