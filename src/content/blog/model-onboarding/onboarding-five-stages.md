> 一句话总结：接一个新模型，代码只占一半；另一半是开工前的三次搜索（旧分支、同族契约、团队规范）和上线前的一张配置清单。顺序搞反，返工就落在最贵的那一段。

## 0. 起因：第一次接模型，坑都在「顺序」上

我所在的平台是一个多供应商的模型 API 网关：用户用统一的接口调文本、音频、图像、视频模型，后面挂着不同厂商的上游。接一个新模型，要改的东西分散在五个仓库：供应商 SDK（负责和上游协议互转）、主后端网关（路由、校验、计费）、任务 worker（执行异步任务）、前端控制台、文档站。这篇只讲后端这条线。

第一次接的是某厂商的声音复刻模型。代码写完、本地也跑通了，回头一看问题一串：契约是代码写完才补的；数据脚本里的一个开关照着最近一份同类脚本抄，和团队规范相反；跑通真实调用的那处 SDK 修复，落在了下游仓库被 git 忽略的 `vendor/` 目录里；模型名改了一半，超时和预扣费配置悄悄回落到默认值。

每个问题单拎出来都不难修。麻烦在于它们都是顺序问题：该在开工前做的事放到了最后，返工就落在代码已经写完、测试已经跑过的阶段。之后一个多月又接了文本、视频、图像、TTS 几类模型，我把流程固定成「开工前三次搜索 + 五段推进 + 上线前配置清单」。下面按顺序讲。

## 1. 开工前：三次搜索比写代码更早

### 搜全部远端分支：前人可能做过没合入的尝试

后来接某视频生成模型的轻量档时，任务说明只写了「参考同系列已上架的版本」。我按模型名搜了所有相关仓库的全部远端分支，发现这个模型半年里被接过两次，两次都停在特性分支上，没有合并记录，提交信息也没写为什么停：

- 第一次接了两条上游，选的计费项 ID 后来被别的模型占了；
- 第二次只接一条上游，换了 ID，有完整的契约文件和两百多行校验测试。

能直接拿来用的是决策：对外名、上游 id、计费口径、参数边界、哪些参数组合上游其实接受。代码基本用不上。第二条分支的基线已经很旧，主干在那之后做过一次大的结构调整：上游客户端迁进了独立的 SDK 仓库，分支里改的那个文件在主干上已经不存在；前端那条分支按旧的页面骨架写，现在会撞上四道新加的机器闸。

最后的做法是在当前主干上重做，旧分支只当参考。旧分支选过的 ID 在全部分支上再核一次，确认仍然空闲后沿用。要是没搜，调研得重做一遍，还可能重新选一个 ID，正好撞上那条旧分支。

命令是固定的几条，每个相关仓库各跑一次：

```bash
git fetch --all --prune
# 提交信息里提到这个模型的，跨全部分支
git log --all --format='%h %ad %an %s %d' --date=short -i --grep='<模型名>'
# 分支名里带关键词的
git branch -a | grep -i -E '<关键词1>|<关键词2>'

# 对每条命中的分支：合没合、基线多旧、改了多大
git merge-base --is-ancestor <tip> origin/<主干> && echo merged || echo not-merged
base=$(git merge-base <tip> origin/<主干>)
git log -1 --format='%ad' --date=short "$base"
git rev-list --count "$base"..origin/<主干>     # 落后主干多少个提交
git diff --stat "$base" <tip>
```

后来做一个和模型无关的业务功能，也用这几条搜到过一条半年前的完整实现，约一万行，同样没合。那次的关键词要用业务词的几种英文变体，只搜功能名搜不到。所以这一步不限于接模型。

提炼旧分支时，我会派一个只读的子任务，让它把决策整理成表（对外名、上游 id、计费口径、参数边界、拒绝项、为什么没合），明确不要它提炼代码。子任务交回的表也要自己核一遍，见[子代理的审查发现是线索](/blog/ai-workflow/subagent-findings-are-leads/)。

### 按同族名 grep 主干：已有的能力别写成「要新建」

第二次搜索针对主干里已经有的东西。旧分支是没合入的工作，同族模型的契约是已经合入、还在用的工作。

有一次助手的一个窗口交来一份接入调研，结论里列了几项「现有结算逻辑要补齐」。调研做过代码只读核验，引用的结算函数行号全部对得上。我让另一个窗口评审，它拿同系列模型的名字在主干 grep 了一下，发现主干早就有对应的契约和结算逻辑。整节「与现有代码衔接」的方向因此是反的：要做的不是新建，而是新增一条渠道、复用已有的部分。

问题出在核验方式。调研是按功能找代码（找结算、找预扣），只能证明通用能力存在。某一批模型有没有专属配置，要按模型名找，因为专属配置恰好写在契约文件和按名字判断的函数里。

评审的窗口自己也差点犯了反方向的错：看到名单里有 `x-6`，就把 `x-6.1` 当成已接入。回头逐字核，名单里没有 `x-6.1`，契约目录里也没有。同族不等于同一个型号。

现在我把搜索结果整理成四列，方案里的「要新建」只从后两列来：

| 能力 | 已有（文件和行号） | 可复用 | 要新增 | 待生产核实 |
|---|---|---|---|---|
| 分角色定价 | 同族契约的定价一节 | 是 | 新渠道的定价行 | 生产库里定价行装了没有 |
| 长上下文档位 | 同族契约的元数据 | 是 | 无 | 阈值和上游一致 |
| 用量拆分 | 结算函数里的按名判断 | 是 | 新上游的用量来源 | 名单里有没有这个精确型号 |

最后一列要单列出来：代码里存在，不等于生产数据已经装上。

### 读团队规范：最近的先例可能正好是例外

第三次「搜索」是读团队的权威接入规范。第一次接文本模型时，助手照最近一次同类接入写数据初始化脚本，把新模型的对外可见开关写成了关，打算上线时再打开。做完按规范复核，规范写的是新模型默认可见，软上线靠「渠道禁用 + 路由关闭」，不靠把模型藏起来。抄的那份先例恰好是个例外。同一次复核还查出另外三处缺口，其中一条是规范要求写代码前先把前后端契约落成文件，而这次是写完代码才补的。

也碰到过反过来的情况。规范明文要求加的一句 SQL，被外部审查指出有副作用。回头看规范引用的出处脚本，发现出处自己一个多月前已经删掉这句并写了理由，之后的新脚本也都不这么写了，只是规范的文字没跟上。那次按仓库现状改，并把不一致单独报给规范的维护者。

所以规则是三条：开工第一步读规范；抄先例之前，把先例里的每个默认值、开关和步骤和规范对一遍；规范和仓库现状冲突时，用 `git log` 看规范引用的那个文件现在怎么写，按现状做并报出不一致，不要悄悄二选一。

## 2. 第一段：契约

契约是一份 Markdown 文件，写在代码之前，放进后端仓库，前端、文档、验收都引用它。我的契约固定有这几节：

```markdown
# <对外模型名> 接入契约

## 1. 对外参数
| 参数 | 类型 | 必填 | 默认 | 范围 / 枚举 | 发给上游的字段 | 备注 |
|---|---|---|---|---|---|---|

未知参数：严格 400（不透传、不静默丢）
互斥规则：带 A 走模式一，带 B 走模式二，同时带返回 400

## 2. 和上游文档的差异（实测）
| 项 | 官方文档 | 实测 | 我们怎么处理 |

## 3. 计费口径
计费单位；预扣怎么估；实扣取哪个字段；失败退不退

## 4. 错误映射
| 上游错误（原文） | 归类 | 对用户的文案 | 可否重试 |

## 5. 待真实 key 验证的清单
```

「未知参数怎么处理」要在这里定死。上游常对不认识的参数一律返回 200（见[上游接口实测](/blog/model-onboarding/upstream-probe-evidence/)），网关这一层不定规则，用户写错的参数名就会静默失效。第 2 节只填实测结论：参数名、范围、默认值逐个跑过，不从官方文档抄。

先写契约的价值不在文件本身。它逼你在动代码之前把参数、计费、错误三件事想清楚。事后补只能补出文件，补不回它本来要避免的返工。

## 3. 第二段：供应商 SDK

SDK 里的新客户端只做协议转换：把网关的统一请求翻成上游的格式，再把上游响应翻回来。参数校验、计费这类业务规则不放在这里。交付前写单测，并至少直调一次真实上游。

这一段最容易出的事是改错地方。第一次接模型时，助手在下游仓库的 `vendor/` 目录里把 SDK 客户端改对了（模型名、动作名、请求体字段、endpoint 四处都和官方文档对不上），真实调用跑通。可 `vendor/` 被 git 忽略，SDK 仓库里的同一个文件还是旧实现。这时推 SDK，别人构建出来是坏的；本地任何人跑一次 `go mod vendor`，修复就被旧版覆盖。当时汇报里写的「SDK 直调通过」属实，但测的是 vendor 里的修改版，这句话得连着条件一起写。

多仓库的合并顺序也在这一段定：

1. SDK 先合；
2. 下游仓库把 SDK 版本固定到合并后的那个提交；
3. 需要 vendor 的仓库重新 vendor。

反过来做，下游会依赖一个 SDK 主干上不存在的版本。开发期间我用 `go.mod` 的 `replace` 指向本地的 SDK 检出，两边可以一起改。代价是 replace 会让跨仓接口不同步时照样编译通过，审查时两个仓都要看（见[多任务并行的 git 用法](/blog/git-collab/worktree-multi-task/)）。

## 4. 第三段：主后端网关

网关这一段的活最多：路由、参数校验与映射、模式互斥、错误码映射、超时和预扣费配置。这里只讲两条「按名字」的坑。网关改写请求时的其他漏洞，单独写在[网关改写请求的几个漏洞](/blog/model-onboarding/gateway-outbound-body-pitfalls/)。

**名字改一半**：按名字查表的配置查不到就静默回落默认值，改名只改一部分时编译和单测都会过。改名前要全局搜齐。

**子串规则误归类**：按名字子串判断家族的规则，会把碰巧含那段子串的新名字归错类。选对外名之前，把全库的子串规则逐条代入新名字走一遍。

这两类问题的案例和检查方法写在[改名、别名和重定向](/blog/model-onboarding/rename-alias-redirect-ripple/)第 1、3 节。

还有一条容易漏：本地判定的错误（参数不支持、超出范围）要返回 4xx，不能被压成 5xx。5xx 会触发重试和熔断，调用方的问题就变成了渠道故障（见[错误分类、重试和渠道禁用](/blog/model-onboarding/error-classifier-channel-disable/)）。

## 5. 第四段：任务 worker

同步的文本模型不经过 worker。视频、图像、长音频这类异步任务由网关建任务，worker 按派发配置取出来执行。这一段的代码量通常最小：注册新的 provider，复用 SDK 客户端。

要盯的是配置：任务分发配置里有没有这个新 provider。缺了的话，任务建得出来、预扣也扣了，却没有 worker 认领，一直挂到超时退款。本地测试往往走网关单体轮询那条路径，发现不了这个问题；生产如果走 stream 派发，就要单独核。异步链路的完整测法见[异步任务链路：在本地起全栈怎么测](/blog/model-onboarding/async-task-local-full-stack/)。

## 6. 第五段：数据初始化

计费项、渠道、能力表这些初始数据，用一份 SQL 装进生产库。我对这份脚本的要求：

- 单文件、可重复执行：重跑不多建行，不覆盖运维已经改过的值，不碰已启用的渠道；
- 目标 ID 已被占用时整份零写入并报出来，不覆盖；
- 渠道以禁用态、占位 key 装入，软上线靠渠道禁用和路由关闭；
- 用户组、渠道这类只有生产库知道的清单，开工时用只读查询定下来写死，只在一处定义；
- 带回滚段和自检，自检里有分组一致性这类断言。

这份脚本在开发库上全绿说明不了什么。我们有三次都是验收全绿、提交后才被审出问题（列宽不同、生产表没有自增 id、排序规则不同），原因都是验证用的表结构来自开发库。后来固定成提交前在「按线上建表语句整理的表结构 + 几套排序规则」上整份真跑，细节写在[要进生产库的 SQL](/blog/billing-regression/sql-on-prod-shaped-db/)。

## 7. 端到端和上线前配置清单

五段都做完，还要通过网关的公开接口跑一遍完整链路，只直调 SDK 不算。异步任务要跑到终态和实扣：创建和预扣都对，轮询仍可能因为各条路径拼查询凭证的格式不同而永远不通。

上线前我逐项过下面这张表。大多数项本地验不了，要找有权限的人在生产核：

| 项 | 要确认什么 | 为什么单列 |
|---|---|---|
| 地域 | 接口在哪个地域提供，渠道配的是哪个 | 有的接口只在某个地域提供；第一次探测就因为地域配错，请求全部 401 |
| 账号 | 上游账号是否已开通这个模型 | 没开通时上游回的错误，很容易被当成 key 有问题 |
| 上游限速 | 配额够不够上线初期的量 | 本地和验收环境的量测不出来 |
| 计费链路 | 单价很小的按次计费项，计费精度表示得了 | 本地用的是测试价 |
| 初始化用的 ID | 在生产是否空闲 | 脚本设计成被占用就整份不写，要提前知道 |
| 任务分发配置 | 是否包含新 provider | 缺了任务会一直挂到超时退款 |

部署顺序写进交付说明：程序 → 数据 → 刷缓存 → 粘贴 key → 测试 → 启用。需要真实 key 才能验的项单独列出来，交给有 key 的人。

## 收尾

1. **先搜旧分支** —— 没合入的工作只在全部远端分支里看得到；拿它的决策，不拿它的代码。
2. **按名字搜主干** —— 按功能找只能证明通用能力存在，专属配置要拿精确型号名搜；同族不等于同一个型号。
3. **规范先于先例** —— 开工第一步读规范，先例里的每个默认值都对一遍。
4. **修复落在源仓库** —— 在 vendor 里改对了只是本地能跑，改动不属于任何仓库。
5. **端到端要到结算** —— 经网关公开接口跑到终态和实扣，只直调 SDK 不算。

下次接新模型，我第一个小时只做三件事：在每个相关仓库搜全部分支，拿同族名 grep 主干的契约和判断函数，打开团队规范对一遍开工清单。三件做完再写契约，契约定了再动代码。上游的真实行为怎么探测，见[上游接口实测](/blog/model-onboarding/upstream-probe-evidence/)。
