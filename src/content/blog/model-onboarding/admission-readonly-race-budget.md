> 一句话总结：只读探测提供选路依据，真正占位仍由执行端裁决。设计时要分别处理快照过期、并发扎堆、恢复时间和调用预算，不能把「刚才有空位」当作已经拿到了名额。

## 0. 起因：让网关先看一眼剩余容量

异步任务的派发通常先选渠道，再由执行器领取名额。如果选中的渠道正在退避，或者令牌已经用完，这次派发会白跑一趟。

我参与的一次改动把检查提前了：网关用只读脚本查看候选渠道的状态，再挑一个看起来能执行的目标。执行器仍负责最终准入，网关不预扣令牌，也不替执行器建立占用。

思路简单，边界却很多。后续修复涉及选择策略、等待时间、错误处理和回调时限。我按提交差异和当时的复盘整理了这些判断；文中的演算是通用例子，不代表生产参数，也不声称某种权重适合所有系统。

## 1. 一次原子读取，无法保住下一次占位

先看一个时序：

```text
时刻 A：网关甲读到渠道还有一个名额
时刻 B：网关乙读到同一个名额
时刻 C：甲、乙分别把任务送入队列
时刻 D：执行器开始领取，只有一个任务成功
```

把读取放进 Redis 的 Lua 脚本，可以保证这次脚本执行期间的原子性。Redis 官方对这个保证有明确说明，见[Lua 脚本执行语义](https://redis.io/docs/latest/develop/programmability/eval-intro/)。但脚本结束后，另一条请求仍能改变状态。

所以，即使读写两侧使用相同的限额算法，检查与占用分成两次执行，仍然存在竞争窗口。消息排队、网络延迟和执行器负载会把这个窗口拉长。

只读探测的契约应写得很窄：它报告当前可见状态下的可用性估计，不刷新状态的过期时间，不扣令牌，也不占并发槽位。最终领取失败需要有明确的重投或等待路径。

验收时可以先后比较目标键的值和过期时间，确认探测没有偷偷写状态。不过，过期时间会自然流逝，断言应区分时间经过与主动续期，不能要求两个时刻的剩余时间逐字相等。

## 2. 剩余比例用于分散选择，不能代替限额

最初很容易想到「挑在跑最少的」。但一个只有少量名额的小渠道，与容量更大的渠道，不能只按在跑数量比较。

这次后续实现选择同一优先级里的候选，再按剩余比例加权随机。比例取已配置约束中更紧的一项：并发空位比例和令牌余额比例。

用自编数字说明：

| 候选 | 并发剩余比例 | 令牌剩余比例 | 用于选择的余量比例 |
|---|---|---|---|
| A | 四分之三 | 四分之一 | 四分之一 |
| B | 二分之一 | 二分之一 | 二分之一 |
| C | 未配置 | 三分之一 | 三分之一 |

在这个策略下，B 更容易被选中，但不会每次都成为第一名。确定地挑同一个最优目标，会让同时看到相近快照的多个决策一起涌向它。

**加权随机只能缓解集中选择。** 两个请求仍然可能抽到同一个目标，最后的限额还得由执行器的原子占位保证。权重还需要结合系统目标评估，不能仅凭这个案例推导出普遍最优的负载均衡算法。

未配置某项约束时，也要明确语义。本次策略把它当作该维度不设限；允许作为受控降档目标的渠道，至少需要有一项可判断容量的约束。如果要求并发和速率都配置，只有速率限制的有效目标就会被整个排除。

## 3. 短期放行记录覆盖派发前后的空档

往容量较小的备选渠道集中转移任务时，只随机选择还不够。多个网关读到同一批剩余名额，仍可能同时把过多任务送过去。

后续修复增加了短期放行记录：决定转移前，先对目标申请一个共享的放行名额。达到本次观测到的可放行数量，就尝试其他候选。记录有过期时间，覆盖「决定派发到执行器真正占位」的时间差。

这与执行器的最终占位有不同职责。放行记录控制一小段时间内送过去多少任务，执行器控制实际能开始多少任务。两层都要说明失败后怎么处理，不能把放行成功写成执行必定成功。

窗口从什么时候开始也有影响。这个案例使用首个放行开始计时、到期整体清零的窗口。若每来一单就刷新过期时间，持续请求可能一直延长窗口，空出的资源迟迟不能重新参与选择。

窗口长度需要结合实际派发延迟设定。太短，执行器尚未占位记录就消失；太长，任务早已结束仍被旧记录挡住。文章不保留当时的业务秒数，因为可以复用的是量延迟和验证边界的方法。

此外，短窗口记录仍然依赖状态位置和作用域正确。网关实例们必须对同一组目标看到同一份记录；跨进程连接问题可对照[两台 Redis 的复现](/blog/testing/redis-topology-local-prod/)。

## 4. 同一候选取最晚，候选之间再找最早

一个渠道可能同时被多个条件挡住：还在退避、令牌不足、并发已满。要估计它何时可能再试，需要考虑这些条件同时解除。

假设退避还剩 2 秒，补足令牌还需要 8 秒，当前占用预计 5 秒后释放。只返回第一个遇到的 2 秒，会安排一次仍然没有令牌的重试。

下面用 Python 表达这个通用演算，数字只用于说明：

```python
waits = {
    "A": {"backoff": 2, "token": 8, "slot": 5},
    "B": {"backoff": 3, "token": 4, "slot": 0},
}
per_candidate = {
    name: max(reasons.values())
    for name, reasons in waits.items()
}
print(per_candidate)
print(min(per_candidate.values()))
```

对 A 要等最晚的条件，对 B 同样处理。任务可以去任意一个合格候选时，再从各候选的等待估计中取最早者。这里有两层集合，取最大与取最小分别回答不同的问题。

并发槽位什么时候释放，往往无法精确预测。此时返回的是重查时机的估计，不能当作预约承诺。估计、已知下界和未知状态最好明确区分，以免调用方把同一个时长字段理解得过强。

## 5. 一个候选坏了，只降级这个候选

批量探测可以减少往返，但某个渠道的状态可能损坏：非数字、负计数，或者计算时出现异常。若直接让整段脚本失败，其余健康候选也会被拖累。

这次修复把单个候选的执行包在保护调用里。读不出的候选标为未知，其他候选照常返回。调用方不选择未知目标，也不拿它计算可靠的恢复时间。

未知与已满还要分开。如果一个优先级里的渠道都确定已满，可以考虑降档；如果其中一个状态根本读不出来，就没有足够证据说「这一档全部已满」。把未知折成零余量，会把观测失败变成错误的调度依据。

整个 Redis 请求失败则属于另一层问题。没有有效快照时，系统应回到事先约定的保守路径，不能用默认零值拼出一批「看起来空闲」的渠道。

对应的夹具应同时包含正常、已满、损坏和整批不可达几种情形。单个状态异常后，既要断言该目标不被选，也要断言健康目标仍能参与选择。

## 6. 回调总预算，比单次超时更重要

网关的部分选路运行在同步回调里，执行器会等待回执。如果每尝试一个目标，都重新申请一份完整超时，最坏时长会随着候选数增长。

例如，单次操作只等一小会儿，看起来很保守；连续尝试很多次，累计时长却可能超过调用方等待回调的上限。调用方超时后，网关仍在继续决策，又会引出重复投递或状态竞态。

本次修复让一轮放行尝试共用同一个截止时间，同时限制最多尝试的候选数。名额用完可以换目标；Redis 操作出错则停止这一轮降档，返回原有等待路径。

这两个条件需要分别测试。快速返回「没有名额」时，次数上限限制工作量；操作变慢时，共用截止时间限制等待。两者相乘的估算可以帮助审查，但最终还要测真实调用链是否响应取消。

## 7. 验收围绕会改变决策的条件

| 场景 | 需要观察的结果 |
|---|---|
| 多个决策读取同一空位 | 最终占位不越限，失败任务有确定后续 |
| 只配置一种限额 | 按该限额判断，不被额外条件误排除 |
| 退避短、补令牌慢 | 同一候选按较晚条件安排重查 |
| 单个候选状态损坏 | 只标该候选未知，其他结果保留 |
| 未知与已满混在一起 | 不把整档写成确定已满 |
| 多次放行均被拒绝 | 尝试次数和总耗时都受约束 |
| 共享存储不可达 | 回到约定路径，不伪造可用状态 |

重试节奏也要单独核。把间隔缩短，在重试次数固定时，会缩短任务愿意等待的总时间。固定渠道、最后一次投递和兜底分支，可能无法从快速换路获益，不能一并套上相同的提速规则。

## 收尾

1. **明确快照边界** —— 只读探测看到容量，执行端才真正取得容量。
2. **分散并发选择** —— 权重和短期放行减少扎堆，原子占位继续兜底。
3. **区分等待集合** —— 同一候选看最晚阻塞，多个可替代候选再找最早恢复。
4. **给整轮设预算** —— 单个候选隔离错误，整轮尝试共用截止时间。

我现在审这类逻辑，会先画「读快照、做决定、真正占位」的时序，再沿着时间差找竞争和超时。只要这几步分属不同进程，就值得把中间可能变化的条件逐个写出来。
