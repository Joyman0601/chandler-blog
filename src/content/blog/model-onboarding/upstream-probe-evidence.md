> 一句话总结：上游返回 200 只说明请求没被当场拒掉；参数生效了、回答的是你要的模型、能力真起了作用，每一条都要指到一个证明它的字段。判拒也一样，先问请求为什么失败。

## 0. 起因：文档会错，状态码也会骗人

接一个第三方模型之前，我会先写一份实测报告：参数名、取值范围、默认值、限制、错误格式，逐条用真实请求跑出来，每条结论链接到原始响应。原因很简单，上游文档靠不住。我碰到过新旧两套参数名混在同一篇文档里，碰到过写着「不支持图片输入」的接口其实收首帧图，也碰到过发布公告里的型号名在接口里根本调不通。

文档靠不住，就得靠响应。可响应也会骗人，而且骗法很固定。这一个多月我做了十几轮探测，栽过的跟头大致分成五类：

1. 请求根本没到上游，失败被记成「按预期被拒」；
2. 上游对参数静默处理，200 被记成「参数生效」；
3. 兼容端点换了模型、能力没有真的执行，结果「看起来对」；
4. 自己拼的请求通了，SDK 发出去的那个不通；
5. 按家族、按命名规律推出来的模型事实，逐个核对时不成立。

下面按探测的先后顺序讲，最后给一个执行器骨架。

## 1. 先做不花钱的预检

**现象**：第一次跑一套一百多个用例的探测，结果几乎全是「符合预期」。实际上是地域配错了，所有请求都返回 401；而脚本对负向用例的判定是「非 2xx 就算按预期被拒」，把 401 也算了进去。

**根因**：负向用例只判断了「失败了没有」，没判断「为什么失败」。这些请求根本没走到参数校验那一层。

**修复**：正式用例之前加一段免费的预检，不通过就整批中止。预检分三种情况：

| 手里有什么 | 预检怎么做 | 能拿到什么 |
|---|---|---|
| 还没有真 key | 用一个明显无效的 key，对每个主机 × 每个端点各打一次 | 主机可达；路径存在（回 401 而不是 404）；认证失败的错误体长什么样；上游把请求 id 放在哪个响应头 |
| 有真 key | 先调模型列表接口 | 目标模型在不在这把 key 的列表里，不在就停下换 key |
| 有 key，不确定上游有没有这个型号 | 发一个故意缺必填字段的请求体 | 见下面的判据 |

缺必填字段的请求在上游参数层就被拒，不建任务、不花钱，最适合用来区分「key 的问题」和「型号的问题」。有一次接代理渠道的新型号，leader 说渠道 key「可能有问题」（转述）。助手用同一把 key 各打一次：老型号回 400，报错里带着缺的字段名，说明 key 和线路都通；新型号回 404，正文是「模型未在元数据中注册或已被删除」，换两种拼法也一样。结论不是 key 坏了，而是代理侧还没登记这个型号，这条渠道上线就会全部失败。判据整理成一张表：

| 预检响应 | 说明 |
|---|---|
| 401 / 403 | key 或权限的问题，请求没到参数层 |
| 404，正文带「未注册」「不存在」 | 上游（或代理）没有这个型号 |
| 400，正文带你故意缺的那个字段名 | key、线路、型号都通，请求到了参数层 |
| 429 / 5xx | 上游当时不可用，什么结论都不能下 |

无效 key 那一步还顺带查出过一个网关缺陷：上游的认证失败文案没命中网关的任何认证规则，上游原文直接透给了用户；网关也不采集上游放请求 id 的那个响应头，出了事没法拿 id 去找上游联调。这类问题的处理见[错误分类、重试和渠道禁用](/blog/model-onboarding/error-classifier-channel-disable/)。

## 2. 判拒：先问请求为什么失败

预检通过以后，负向用例仍然可能「假拒」。我碰到过两次请求没到上游、却被记成限制生效的情况。

**渠道地址重复拼前缀**：经网关测一组边界值，结果全是「任务失败」，看起来每条限制都生效了。其中混着一条本应成功的合法请求，它也失败了。原因是本地渠道地址已经带了接口前缀，客户端又拼了一次，请求根本没到上游的正确地址。修好配置重测，原来「被拒」的用例里有 6 条其实会成功。

**素材上游拉不到**：核对一个文本模型能不能读视频，助手用公网上一个示例站点的 mp4 当素材，上游回 400，报错是「输入格式或解析错误」，于是记成「不支持视频输入」，还据此提了删文档的补丁。一周后复核才发现，那个外站地址上游根本下载不到。改用平台自己文件服务托管、先 `curl -I` 确认可以公开下载的小视频重测，模型读得出来，能力其实是支持的。

两次的共同点是：负向用例只看了「有没有失败」。修法有三条：

- 负向矩阵里放一条合法请求做对照，对照失败就整批作废；
- 负向用例断言具体的拒绝原因，例如「400 + 字段名」，401、403、429、5xx 一律记为出错；
- 「不支持」的结论配一条能成功的对照：同一素材换一个已知支持的型号，对照也失败，就是素材的问题。

## 3. 参数：200 照收、受理后失败、生效带副作用

「返回 200 → 参数被接受 → 参数按文档语义生效」这条推理，每一步都断过。

### 未知参数一律 200

早期的一份探测报告说有十几个参数「被接受」，后来发现上游对任何未知参数都返回 200。以某厂商的 TTS 模型为例，指令参数正确的写法是单数 `instruction`；写成复数 `instructions`，或者加上文档里另一套旧写法的参数，请求都照常成功，只是不起作用。上游收到不认识的字段就直接丢掉。

判断方法：先故意发一个明显不存在的参数（比如 `foo: 1`），上游不报错，就说明这个上游的 200 不能当作参数生效的证据。之后每个参数都要「带和不带」或「取两个差异明显的值」各调几次，比较输出。

### 非法参数先受理，几秒后才在任务里报错

给某视频生成模型发两个不在它档位表里的分辨率和时长，提交接口返回 200 和任务 id，和成功请求一模一样。第一次轮询，任务就已经结束，没有结果，只有一个 `error`：「不支持的输出分辨率」。同一轮里，非法的画面比例和超量的参考图却是同步 400。上游把校验拆成了两层：请求形状在接入层同步校验，模型能力（分辨率档、时长档）在模型侧异步校验。文档只写「不支持」，不写在哪一层拒。

只记提交时的状态码，会把「受理后失败」误记成「接受」。所以异步上游的每条用例都要提交、轮询到终态、再看 `error` 字段，按三类记录：

| 类别 | 提交时 | 终态 |
|---|---|---|
| 同步拒绝 | 4xx，报错带字段名 | 没有任务 |
| 受理后失败 | 200，给了任务 id | `error` 有值，没有结果 |
| 静默接受 | 200 | 正常出结果，参数没起作用 |

网关这边，对「受理后失败」的参数要在本地前置 400。否则每笔请求都要走「预扣 → 创建成功 → 轮询失败 → 退款」的绕路，用户还会看到上游的英文原文。

### 参数生效，却带文档没写的副作用

调研阶段对某个语音合成音调参数的结论是「生效」，依据是输出文件的 md5 变了，文档据此写成「大于 1 声音更高，小于 1 声音更低」。验收时顺手量了音频时长：同一句话基线约 2.8 秒，音调取 2.0 时被压到不足 1 秒，取 0.5 时拉长到约 11 秒，时长大致和音调值的平方成反比。同时传了不等于 1 的语速时，音调参数干脆不起作用。

「md5 变了」只能证明参数被读到了，对任何有副作用的实现都会通过。修法是按语义先写下观测量，再测：

| 参数 | 应该变 | 不应该变 |
|---|---|---|
| 音调 | 基频 | 时长、用量 |
| 语速 | 时长 | 基频、用量 |
| 音量 | 响度 | 时长、基频 |
| 采样率 / 格式 | 文件头里的编码和采样率 | 时长 |

时长和编码用 `ffprobe` 读，基频可以低通后数过零点粗估，只看相对变化。数值参数测两端加至少两个中间值，再和相关参数两两组合测一次。发现副作用以后有三种处理：文档写明、网关收窄范围、网关不开放这个参数，交给能拍板的人选。那一次定的是保留范围、文档写明副作用和实测时长。

## 4. 判通：model 字段、搜索痕迹和暗号

成功响应也要指到证明字段。三种我实际碰到的「看起来对」：

**兼容端点把模型静默换掉**：拿到一把真实 key 实测，OpenAI 兼容的两个端点对目标模型回 400「未知模型」；Anthropic Messages 兼容端点对同一个模型名回 200，响应里的 `model` 却是另一个老模型，没有思考块。再用一个明显编造的模型名去打 Messages 端点，也是 200，也由那个老模型回答。模型列表里根本没有目标模型：这把 key 是按量计费的，目标模型只对订阅套餐开放。放到网关里，后果是用户按新模型付钱、拿到老模型的回答，而且全程不报错。所以每个成功响应都要断言 `响应.model == 请求.model`（或等于映射后的上游名）；已知会静默回落的上游，网关在那个端点校验响应 model，流式在第一个事件里就查。

**联网搜索看痕迹，不看回答像不像新闻**：一份旧记录写着某个搜索参数「通，返回了时事」。复测同样的请求，响应里没有任何搜索字段，输入只有十几个 token，回答的标题和上次不一样，两次都可能是模型编的。联网的效果是看不见的，上游没搜时多数不报错。判通只认响应里的痕迹：搜索工具调用条目、来源链接或 grounding 字段，或者输入 token 明显跳变。一个都没有，就记为「未见搜索」。

**文件和媒体输入用暗号**：PDF、图片、视频这类输入，返回 200 不代表模型读了。我碰到过同一份 PDF，一个端点回 200、回答却和文件内容无关。现在的做法是在素材里放一个只有真看到内容才答得出的暗号，比如画面上写一串字、PDF 里埋一个编号，提问里不出现答案，用回答对不对来判「读到了」。生成这种素材很便宜：

```bash
# 2 秒、画面中央写着暗号的小视频；暗号从文件读，避开 shell 引号
echo 'K7-PLUM' > code.txt
ffmpeg -f lavfi -i color=c=white:s=320x240:d=2 \
  -vf "drawtext=textfile=code.txt:fontsize=48:fontcolor=black:x=(w-tw)/2:y=(h-th)/2" \
  -pix_fmt yuv420p probe.mp4
```

素材放在上游一定拉得到的地方，发请求前先确认能公开下载。

## 5. 裸请求通过，不等于 SDK 路径通过

**现象**：给供应商渠道 A 接一个新的图像型号。上午用脚本照文档拼请求直打上游，默认档、4K、极端比例各一单，全部 200、出图尺寸正确，结论写了「渠道通」。本地全栈用 mock 上游也全绿。晚上顺手经网关走 SDK 真打一单：上游 400，报「不支持的安全类别」，客户端还把这个 400 当瞬时错误重试了 3 次。

**根因**：SDK 客户端对所有型号固定下发五类安全设置，外加系统指令、响应模态这些探测脚本没带的字段，新型号不认其中一类。探测脚本拼的「同形请求」从来没拿客户端真正发出去的 body 对过。对照裸请求也印证了：带五类的 400，带四类的 200。

**修复**：每条渠道交付前，至少一单「经网关 → SDK → 真上游 → 终态 → 核实扣」。在那之前，先用假上游抓一次 SDK 实际出站的 body，和探测请求逐字段比，多出来的字段每个都在真上游验一遍。探测报告里把「裸请求」和「经网关 / SDK」分成两列，裸请求通过只填前一列。抓出站 body 的假上游写起来很短：

```python
# fake_upstream.py：把收到的请求原样落盘，回一个固定的成功响应
import json, http.server

class H(http.server.BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        with open("captured.jsonl", "a") as f:
            f.write(json.dumps({"path": self.path, "headers": dict(self.headers),
                                "body": json.loads(body or b"{}")}) + "\n")
        out = json.dumps({"id": "fake-1", "status": "succeeded"}).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(out)

http.server.HTTPServer(("localhost", 18080), H).serve_forever()
```

本地渠道地址指到这个端口，经网关发一单，`captured.jsonl` 里就是 SDK 真正发出去的东西。

同一类问题还有凭证格式：上游换了凭证格式，旧客户端只认旧格式。某视频上游的控制台现在发的是新格式的 key，直连上游鉴权正常。配进网关渠道，任务几秒就失败，上游没收到任何请求：网关里那个老客户端按旧格式解析渠道 key，在发请求之前就报格式错误了。mock 上游和用旧格式假 key 做的测试都发现不了。验收要用运营现在实际能从控制台申请到的那种 key，直连和经网关各打一次，两边的结论分开写。

## 6. 模型事实按接口、按枚举逐个核

最后一类错不在响应，在推理：按家族、按相似型号、按命名规律推出来的结论。

**名字相近的是两个模型**：排查某厂商的声音复刻接口时，助手把官方枚举里两个只差一个前缀的模型名当成了同一个模型的两种写法，还把代码里的名字改了，多花了约 2 小时。实际上它们属于两个不同的体系：一个收音频链接，一个收音频数据，请求结构完全不同。看到相近的名字，第一步是查官方枚举，各自核一遍请求结构。

**能力藏在次要接口里**：一份能力表写着某视频模型「文档没写是否带声音」。复核时在它的视频编辑接口里找到一个「不保留原声、由模型生成新声音」的开关。家族的能力分散在生成、编辑、延长、参考几个接口文件里，只看主接口会漏。全文 grep `audio` 也不行，每个文件都会命中任务响应里共用的输出类型枚举。要只在请求 schema 的属性里搜，每格结论对应「文件 + 字段名 + 原文」。

**能力按端点给**：生产回归时助手只在 Responses 端测了某文本模型的内置搜索，两单都没搜，报告里写成「这个型号不搜了」，被 leader 反问「哪个端点」。补测 Messages 端，同一个问题真搜了一次，按次的搜索费也扣得分毫不差。实测结论要写明端点，只测了一个端点就写「只测了 X 端」。

**判「平台文档写错」前先读网关映射**：平台文档写某图生视频接口收 1 到 7 张图，上游文档说这一代只收一张首帧，助手据此报「平台文档写错了」。读网关和 SDK 代码才发现，一张图发首帧字段，多张图发参考图字段，上限是网关对上游实测出来的。平台中间有一层映射，上游文档说的只是上游。

**组合关系要端到端测**：一个方案依赖「A 模型建的音色给 B 模型合成」，照两份文档推是通的。实测发现新一代的合成模型用不了这个复刻模型建的音色，换另一个复刻接口建的就可以，前端文案和后端路由都返工了一轮。方案依赖两个模型配合时，定方案之前先用最小链路「建资源 → 目标模型使用 → 删资源」把组合表填满。

## 7. 落盘、分类和一个执行器骨架

每次请求保存两份证据：响应体，和元数据（请求参数、状态码、耗时、请求 id）。报告里每条结论链接到对应文件，结论分三类：与文档一致、与文档不符、文档未说明，后两类单独列。机器判不了的（听感、画质）列成「样本 + 要判断的问题」，约时间让人过。测试中创建的资源（音色、文件）记进台账，结束时按台账删除，并核对没有误删不属于自己的。

我现在把要花钱的探测写成执行器，而不是一串 curl。骨架如下，按自己的上游填 `submit`、`poll` 和用例：

```python
import json, os, pathlib, time

OUT = pathlib.Path("probe-out")
OUT.mkdir(exist_ok=True)
ERROR_STATUS = {401, 403, 429}

def save(name, **rec):
    (OUT / f"{name}.json").write_text(json.dumps(rec, ensure_ascii=False, indent=2))

def run_case(case, submit, poll):
    t0 = time.time()
    status, headers, body = submit(case["request"])
    final = None
    if status == 200 and case.get("async"):
        final = poll(body["task_id"], deadline=time.time() + 600)   # 一律轮询到终态
    save(case["name"], request=case["request"], status=status, headers=headers,
         body=body, final=final, seconds=round(time.time() - t0, 2))
    return classify(case, status, body, final)

def classify(case, status, body, final):
    if status in ERROR_STATUS or status >= 500:
        return "出错"                               # 没走到参数层，不下任何结论
    if status == 400:
        hit = case.get("field", "") in json.dumps(body, ensure_ascii=False)
        return "同步拒绝" if hit else "拒绝原因不符"
    if final and final.get("error"):
        return "受理后失败"
    proof = case.get("proof")                       # 证明字段，例如 lambda r: r["model"] == "x"
    if proof and not proof(final or body):
        return "静默接受（证明字段不成立）"
    return "通过"

def main(cases, submit, poll, precheck):
    if not precheck():                              # 鉴权 / 模型列表，不花钱
        raise SystemExit("预检失败，整批中止")
    control = run_case(cases[0], submit, poll)      # 第一条固定放合法对照
    if control != "通过":
        raise SystemExit(f"对照用例结果是「{control}」，整批作废")
    for c in cases[1:]:
        print(c["name"], run_case(c, submit, poll))

if __name__ == "__main__":
    key = os.environ["PROVIDER_API_KEY"]
    # 在这里按上游实现 submit / poll / precheck，并写好 cases
```

要真花钱的话，在 `main` 前面再加两道闸：按最坏情况（预期被拒的请求也可能被静默受理）估付费次数，超过预算整批拒绝；超时的任务只轮询、不重提。付费用例怎么合并设计，见[按次付费接口的测试设计](/blog/billing-regression/paid-test-design/)。

## 收尾

1. **预检先行** —— 鉴权、模型列表、缺必填字段的探针都不花钱，不通过就整批中止。
2. **判拒问原因** —— 401、429、5xx 和请求没到上游都是出错；负向矩阵放一条合法对照。
3. **参数看终态和观测量** —— 未知参数 200 照收、非法参数受理后才失败；「生效」要写清该变和不该变的量。
4. **判通看证明字段** —— 响应 model、搜索痕迹、素材里的暗号，不看回答像不像。
5. **SDK 路径单独验** —— 先抓 SDK 的出站 body 和探测请求比，每条渠道至少经网关真打一单到终态。
6. **事实逐个核** —— 相近的名字查枚举，能力按接口文件和端点给，组合关系端到端测。

一次探测跑下来全部「符合预期」时，我现在的第一反应是怀疑它：先看对照用例过没过、拒绝原因对不对、成功响应里的证明字段是不是真的成立。探测得到的结论最后要落进契约，接入的整体流程见[接一个新模型的五段流程](/blog/model-onboarding/onboarding-five-stages/)。
