> 一句话总结：任务型接口的「边界」有两条。一条在建单那一刻：没拿到任务号，只说明响应没回来，不说明上游没接单，重发前要先分清「确认没送达」「明确被拒」「结果不明」。另一条在兼容旧调用时：旧名字映射到新版本是平台政策，要连同返回的元数据、文档里的下载入口和各语种正文一起改完，才算收口。

## 0. 起因：两次修复，碰到同一类问题

第一件事是一个视频生成模型的建单重试。任务型接口的链路是：主后端网关建任务、预扣，任务 worker 从队列取出任务，调供应商 SDK 向上游发建单请求，拿到上游任务号后轮询结果。问题出在 SDK 这一层：建单请求发出去后等响应超时，SDK 把这种情况当成普通失败，内部又发了一次。上游可能两单都接了，平台只记住第二单的任务号，第一单成了没人管、却可能计费的孤儿任务。

第二件事来自一条用户反馈：调用某音乐生成模型的旧版本名，拿到的却是新版本的结果。表面看是「名字映射错了」，查下去是另一个问题：旧名字到新版本的映射本来就是平台的兼容决定，但这个决定没有公开说明。返回结果里也看不出每首歌实际用了哪个引擎。文档里还留着旧版本的能力承诺。

两件事看着不相关，复盘时我发现它们犯的是同一类错：**把「看起来像」当成「已经是」**。超时看起来像失败，就当失败重发；返回里回显了旧名字，看起来像跑的旧版本；代码合并了，看起来像线上修好了。下面按顺序拆开讲。修复过程里助手犯了几处错，我照实写出来，它们正好说明这些边界在哪。

## 1. 建单超时：没拿到任务号不等于上游没接单

**现象**：我用本地假上游复现。假上游收到第一次建单请求后正常创建任务，但故意拖住响应不回。旧版 SDK 等到超时，又发了第二次建单请求，最后只留下第二单的任务号。假上游那边实际收到两次 POST，建了两个任务。

**根因**：建单是改变上游状态、可能计费的调用。请求一旦发出，「等不到响应」有好几种可能：请求没到上游，请求到了但上游还在处理，上游处理完了但响应在路上丢了。后两种情况上游都已经接单。SDK 把它们统统归成「失败、可重试」，等于默认了最乐观的那种。

更隐蔽的一处在错误分类。传输层的错误是一段文字，代理层报错时，文字里可能带着「504」这样的数字。助手修复的初稿里，用了一个现成的辅助函数：从错误文本里解析出 HTTP 状态码，再查通用的状态码表决定能不能重试。问题是，错误文字里出现 504，不等于真的收到了一个 504 响应。前者没有任何上游响应可依据，后者至少是网关明确回了话。把前者送进通用码表，「结果不明」就被覆盖成「暂时失败」，又触发一次重发。反过来也一样：一个真实的 401 响应，正文里恰好有「连接被拒」之类的字样，也不能因此改判成网络错误。

我写了独立测试后，助手改掉了这个用法：错误的来源（传输错误、真实 HTTP 响应、我方后处理失败）在调用点就记成结构化类型，上层只读类型，不再从文字里重建事实。

**验证**：光测「返回了错误」不够，关键断言是两个：假上游实际收到几次建单 POST，上层拿到的错误是什么类型。我把同一组测试放到旧版上跑，「超时只发一次」的断言变红。再做一次最小变异：只把那一行文本解析的分类构造恢复回去，目标用例实收 3 次 POST，在次数断言上失败。这样才能说明守卫挡住的就是重复建单，而不是碰巧被别的报错或提前返回挡住。

下面是一个通用的最小写法，思路是让「结果不明」成为一个独立的、不会被自动重试的类型：

```go
type CreateOutcome int

const (
	NotSent    CreateOutcome = iota // 确认没发出去：连接没建立、请求体没写完
	Rejected                         // 收到真实响应，上游明确拒绝
	Accepted                         // 收到真实响应，拿到了任务号
	Ambiguous                        // 可能已送达，但拿不到可用结果
)

type CreateResult struct {
	Outcome    CreateOutcome
	HTTPStatus int    // 只有真的收到响应才填，0 表示没有响应
	TaskID     string
	Cause      error  // 原始错误，只做日志，不参与分类
}

func canAutoRetry(r CreateResult) bool {
	switch r.Outcome {
	case NotSent:
		return true // 有上限地重试
	case Rejected:
		return retryableStatus(r.HTTPStatus) // 按真实状态码和产品策略决定
	default:
		return false // Accepted 不用重试；Ambiguous 停下，交给上层收口
	}
}
```

`Cause` 只进日志。分类全部在发请求的地方完成，上层任何一处都不该再对 `Cause.Error()` 做字符串匹配。

## 2. 判断表：送达状态、HTTP 状态和 body 要交叉看

修复推上去之后，leader 在此基础上又改了一轮，我回归时把他改了什么、为什么改都过了一遍。

第一处是策略取舍。我的原修复对 5xx 一律保守，不重试。leader 改成：504 仍按「结果不明」停发，其余 5xx 在同一个建单时间预算内有限重试。这是用一定的重复成本风险，换回一部分本来能成功的请求，属于产品取舍。它不说明 5xx 天然代表上游没接单，换一个上游、换一种计费方式，结论可能不同。他还把单次请求的时限和整条建单链的总预算拆成了两个独立守卫。原版本身就有总时限，这次是拆分，不是从无到有。

第二处是我原修复里的漏洞。真实收到了一个非 2xx 响应，随后读响应正文时连接断开，或者正文超过大小上限。我的实现先看到「body 读坏了」，就整体判成结果不明，把已经拿到的 401、429、503 裁决全抹掉了。修前两个建单入口各 3 个状态、共 6 条用例精准失败；504 那组对照一直是结果不明，修前修后都对。

HTTP 状态和 body 是否完好是两个维度，不能互相覆盖。我现在审建单重试，先把下面这张表填满，每一格对应一条测试，同时断言实际 POST 次数和上层错误类型：

| 送达情况 | 真实 HTTP 状态 | body | 判定 | 自动重发 |
|---|---|---|---|---|
| 连接没建立、请求没写完 | 无 | 无 | 确认未送达 | 可以，有上限 |
| 请求已写出，等响应超时 | 无 | 无 | 结果不明 | 不重发 |
| 传输错误，文字里含「504」 | 无 | 无 | 结果不明 | 不重发 |
| 收到响应 | 2xx | 完好，有任务号 | 已接单 | 不需要 |
| 收到响应 | 2xx | 读坏或没有任务号 | 结果不明 | 不重发 |
| 收到响应 | 504 | 任意 | 结果不明 | 不重发 |
| 收到响应 | 401 / 403 | 完好或读坏 | 明确拒绝 | 不重发 |
| 收到响应 | 429 | 完好或读坏 | 明确拒绝，可退避 | 按限流策略 |
| 收到响应 | 其他 5xx | 完好或读坏 | 按产品策略 | 按策略，计入总预算 |
| 收到响应 | 4xx 参数类 | 正文含「连接被拒」字样 | 仍按状态码判 | 不重发 |

body 读坏的那个错误只进日志，不往下游传。否则下游拿到一段含「超时」「断开」的文字，可能再一次把已有裁决改判成未知。

还有一个阴性结果骗过了我们一次。原测试里，超长 body 的夹具是一串纯字符，本身不是合法 JSON，测试只断言「结果不明」。可即便把大小守卫删掉，解析失败照样会让它判成结果不明，测试照样绿，证明不了大小保护有效。独立复核改用一段合法 JSON，在尾部补空格：恰好等于上限时返回同一个任务号，多 1 字节时准确返回大小错误，两代接口都只发 1 次 POST。

**边界测试要只改变一个因素**：合法的那一侧和超限的那一侧，除了长度什么都不变。否则一个绿灯背后，可能是另一条规则在起作用。

## 3. SDK 只发一次，不等于整条链不重发

SDK 把结果不明的建单限制成只发一次，是必要的一层，但只是一层。重复付费还可能从别处来：

- worker 拿到结果不明后，怎么向网关报终态；
- 网关收到「结果不明」，会不会把任务改投给别的渠道再建一次；
- 任务租约在长等待里有没有正常续上，过期后会不会被别人接手重跑；
- 下游消费者有没有真的用上新版 SDK。

所以 SDK 的测试全绿、分支推上去，都推不出「线上重复付费已经清零」。我在本地按生产同款的派发路径起了全栈（搭法见[异步任务链路：从建任务到结算](/blog/model-onboarding/async-task-local-full-stack/)），用真实 SDK 加假上游跑了三条：EOF 和 504 各只发一次建单，没有切到备用渠道，失败后全额退款；正常那条只扣一次，冻结额归零，队列里没有残留。这仍是本地模拟，不替代生产账单。

全栈首轮还出过一次夹具错误。助手看着 SDK 里的字段写请求，把上游的分辨率字段当成了平台对外的画质参数。平台不认这个字段，按默认画质计价，和独立算出的价格预期对不上。正确的做法是改输入，走真实的公开参数，而不是改预期去迁就结果。这次修正输入后重跑通过。

验收任务型接口时，输入要从用户真正会用的公开入口进，而不是照着内部字段猜。

## 4. 让 SDK 响应取消之后：回收入口也要跟上

leader 的改动里还有一处是在 worker。新版 SDK 开始认真响应 context 取消，这本来是好事，却让 worker 一个早就存在的问题露了出来。

**现象**：worker 有两个入口会调建单。一个是正常消费，另一个是回收入口：进程重启后，把上一轮没确认完的消息捞回来继续处理。回收入口把「接收消息」的 context 直接传给了建单，而且没有登记进等待组。滚动重启时，接收 context 一取消，正在进行的建单立刻被打断；进程退出时也不会等它。旧 SDK 不怎么理会取消，问题被盖住了，新 SDK 一认真，问题就显露出来。

**修复**：建单用一个独立的工作 context，和接收消息的 context 分开；每个在途任务都登记进等待组。关停时先停止接收，给在途任务一段宽限期自然收尾；宽限耗尽才取消，并且把任务报成终态、确认消息，而不是留在半路。

```go
func (w *Worker) handle(msg Message) {
	w.wg.Add(1) // ← 回收入口原来漏了这一步
	go func() {
		defer w.wg.Done()
		// 工作 context 独立于接收 context：停止接收不打断在途建单
		res := w.sdk.Create(w.workCtx, msg.Task)
		w.reportAndAck(msg, res)
	}()
}

func (w *Worker) Shutdown(grace time.Duration) {
	w.stopIntake() // 先停接收，不再领新消息
	done := make(chan struct{})
	go func() { w.wg.Wait(); close(done) }()
	select {
	case <-done:
	case <-time.After(grace):
		w.cancelWork() // 宽限耗尽才取消，被取消的任务报终态并确认
		<-done
	}
}
```

注意 `wg.Add` 和关停之间要有锁序保证，否则关停开始后仍可能有新任务登记进来。另一个容易混的点：关停的宽限期通常只有几十秒，SDK 的建单预算可能长达几分钟。宽限期不等于 SDK 预算，宽限耗尽时被取消的建单，按上面的判断表多半落进「结果不明」，要有终态出口。

回归时旧版上两个目标用例变红，修后带竞态检测的用例全绿，覆盖了宽限耗尽时的终态和消息确认。**给 SDK 加取消响应时，要把正常消费和回收两个入口的生命周期一起追一遍**。

## 5. 线上生效：源码、依赖、制品、实例是四层证据

回归做完，我自然想知道：线上修好了没有？这一步助手的表达出了问题。

它看到下游服务的依赖记录里，SDK 版本号还是旧的，就把这件事叫成了「发版缺口」。我第一反应是担心 leader 的合并顺序弄错了。实际情况是：依赖记录里写着旧版本号，但同时有一条本地替换指令，实际打进 vendor 的代码可能已经是新的。旧版本号最多说明依赖记录没同步，既推不出线上没修好，也推不出合并顺序有错。

我后来固定按四层问，每层只接受它能证明的结论：

| 层 | 问什么 | 能证明 | 证明不了 |
|---|---|---|---|
| 源码 | 修复提交合进主干了吗 | 代码存在 | 有没有被构建 |
| 依赖与 vendor | 消费方实际装的是哪份 SDK 代码 | 构建输入 | 构建有没有发生 |
| 制品与实例 | 运行中的镜像由哪次构建产出，所有目标实例都切换了吗 | 线上跑的是什么 | 目标行为有没有触发 |
| 行为 | 目标场景实际发生过、表现符合预期吗 | 修复生效 | — |

还有一个容易犯的错：拿线上一笔正常成功的单子当「修好了」的证据。这次的修复只在建单超时、关停回收时才起作用，正常单子走不到那条分支，修前修后表现一样，区分不出来。为了取证再额外花钱下单，也换不来这层证据。

我这边看不到部署信息。最后的交接是请 leader 或负责发布的同事，确认所有目标 worker 实例的镜像，以及镜像里 worker 和 SDK 的构建来源。复盘时我发现，其实开工时助手提过本地和线上是两层，缺的是早点说清：线上这一层还没开始、缺哪份证明、谁能提供。**缺运行证据时，要在开工就转成具体的交接动作**，而不是收尾时才说「线上未知」。

这条只针对「某个特定修复是否已生效」的专项判断。普通的功能、计费回归，用普通账号从用户侧核就够了，不需要因此要后台权限。

## 6. 兼容旧调用：先分清 model 字段的四种身份

回到第二件事。一条用户反馈说，请求音乐生成模型的旧版本名，得到的是新版本的结果。反馈附了同事整理的排查结论。我把它当定位线索，方案自己重新核。

一次调用里，「模型」其实有四种身份：

1. **请求名**：用户在请求里写的 `model` 值；
2. **兼容目标**：平台决定把这个名字映射到哪个版本；
3. **供应商枚举**：真正发给上游的版本参数；
4. **实际引擎**：上游为每一首歌实际使用的版本，可能和请求的不一样。

响应顶层回显用户的请求名，这只证明第 1 层，不能说明还在跑旧引擎。旧名映射到新版本，这是第 2 层的平台政策。旧版本不再可用时，这是合理的兼容做法，但它应该作为政策写进文档，让用户知道发生了什么。实际引擎未知时如实标未知，不能从请求名去猜。

我起初给 leader 的方案只盯着映射本身。leader 回复（我转述）：还要定重定向本身怎么做，可以看看供应商文档对旧版本是怎么说的。这一步让我注意到一个细节：供应商的旧文档链接跳到了新页面，但这只说明文档搬了家，不说明 HTTP 接口的协议也迁移了。两件事要分别取证。

全局别名的影响也比看起来大：它会同时改变渠道选择、定价、权限、模型级限流和在途任务的归属。默认同价时，映射到错的计费项也看不出来。这部分我在[改名、别名和重定向](/blog/model-onboarding/rename-alias-redirect-ripple/)里展开过，这里只提一句：生产里的全量相关配置当时还缺，只阻塞对应的上线判断，不妨碍先完成本地实现和给用户的说明。

## 7. 元数据投影：数据早就存了，只是没露出来

用户要区分第 3、4 层，就得在结果里看到每首歌的实际引擎和歌词。查下去发现，供应商 SDK 早就把这些元数据存下来了，只是主后端网关组装对外响应时没有投影出来。

所以修复只在网关一层：把已有字段加进公开响应。不必先假设 SDK、worker 要一起升级，那会把一次投影修改扩成三处联动发布。上游本身没返回歌词的，就保持空值，不用空串或占位文字去填。

**先查数据在哪一层断的**，再决定改哪一层。很多「上游没给」的问题，其实是「我们存了没露」。

## 8. 完整性：从旧契约列清单，而不是从生成器的输出列

收口兼容还要改文档。这里助手连出了三处覆盖遗漏，都是我和独立复核找出来的。

**第一处，多语种正文**。助手一开始只查了文档里型号枚举的那几行，改掉了旧版本名。可模型介绍页的「为什么选它」「功能特点」「常见问题」几段正文里，多个语种都还写着旧版本的能力，有的承诺并无依据。用户读的是正文，不是枚举表。旧方案上，有十几条目标检查失败。

**第二处，下载入口**。对外 API 文档是脚本从规范生成的。助手改完生成器后，用「剩下的建单 POST 接口定义和原来逐字段相等」来证明没改坏。直到独立复核才发现，旧文档里查询任务、下载结果的 GET 接口整段没了。剩下的部分全等，恰恰掩盖了少掉的那部分。修复恢复了两个完整的接口定义，和固定版本的文档源逐值比对，并实际下载一次，核对拿到的文件字节。

**第三处，坏输入**。生成器遇到缺失的描述字段，会默默兜底成空串。某个语种的错误要到很晚才抛出，那时前面几个语种的文件已经写到磁盘上了。修复改成所有语种先全部校验，再统一写出。测试对坏输入同时断言两件事：进程非零退出，以及已有产物的哈希没有变化。最后跑了几十条负例，复核另覆盖 10 类坏输入，旧版、新版隔离对照各有原始输出。它证明的是「目标坏输入不会覆盖已有成品」，不扩大成磁盘故障时也有事务保证。

**独立复核本身也要核方法**。第一轮复核的代理先读了主审写好的报告，再写自己的预期，预期已经被主审结论带偏，这一轮按方法不合格处理。重开一个全新上下文，先把预期落盘，再看主审产物。这里也有限度：这个复核代理按协作规则读过任务登记表，知道大致主题，所以不算完全盲审，交付时写明了。

把这三处合起来，完整性检查的顺序应该是：

1. 从旧契约列出必须保留的集合：接口、方法、章节、语种、对外承诺；
2. 对集合里每一项比值，正确性和完整性分开检查；
3. 用户入口实测一遍：真实页面的读取处、真实下载拿到的字节；
4. 坏输入断言副作用：退出码之外，已有产物有没有被改动。

不能从生成器当前愿意输出的那个集合，反过来定义什么叫「完整」。

## 收尾

1. **建单超时** —— 没拿到任务号只说明响应没回来；可能已接单的调用不自动重发，「结果不明」要有自己的类型和终态出口。
2. **状态与 body** —— 真实 HTTP 状态、body 是否完好、是否送达是三个维度，按判断表逐格测，同时断言 POST 次数。
3. **一层的守卫** —— SDK 只发一次不代表 worker、网关、租约不重发；也不代表线上已经用上。
4. **取消与回收** —— SDK 开始响应取消时，正常消费和回收入口都要用独立工作 context，并登记进等待组。
5. **证据分层** —— 源码、依赖、制品与实例、行为各证一层；正常成功单区分不了只在异常路径生效的修复。
6. **兼容政策** —— 请求名、兼容目标、供应商枚举、实际引擎是四种身份；映射是政策，要写出来。
7. **完整性** —— 从旧契约列清单再逐项比，别拿局部相等证明整体完整。

这次两个案子里，最早的错都不是写错一行代码，而是对「已经发生了什么」下结论太快。超时就当失败，回显就当旧引擎，合并就当上线，剩下的部分相等就当完整。下次碰到任务型接口的改动，我会先问每个结论背后是哪一层的证据，再动手写测试。同一条链路上，结果确认这一跳的问题，可以接着看[结果已经存好：为何回报失败仍会丢掉任务](/blog/model-onboarding/result-retention-until-ack/)；错误分类和换渠道的处置，见[错误分类、重试和渠道禁用](/blog/model-onboarding/error-classifier-channel-disable/)。
