> 一句话总结：按名字查表、按子串归类、按解析后的名字存配置，这三类逻辑名字对不上时都不报错，只是行为悄悄变了。改名、加同族名字、改别名指向、换默认档之前，先把所有「拿名字当键」的地方列出来，把新名字逐条代进去。

## 0. 起因：名字是网关里最常用的键

在模型网关里，模型名几乎是所有逻辑的键：白名单、参数校验、超时、预扣费、结算策略、路由规则、令牌白名单、准入和限流规则、模型列表、前端路由、任务回放的登记表、用量和账单的展示。改一个名字，就是改所有这些地方的查表结果。

这些查表有一个共同的性质：查不到不报错。按名字查配置的，查不到用默认值；按子串归类的，先命中哪条算哪条；先解析别名再当键的，别名表一变，同一份存量数据的含义就变了。所以名字没对齐的后果不是崩溃，而是超时变短、预扣变少、规则管错了对象，往往要到对账或者用户投诉才看得出来。

这一个多月我碰到的情形可以归成七类：改名改一半、新增同族名字、子串误归类、市场名撞名、别名改指向、默认档变化、展示层换名。前四类是「名字本身」的问题，后三类是「名字指向的东西变了」。下面逐个讲。所有型号名都是我编的示例。

## 1. 改名改一半：查不到就回落默认值

**现象**：排查一个模型的问题时，助手一度认为它的名字写错了，在超时和预扣费两处配置里改成了新名字，白名单和参数校验里还是旧名字。编译通过，单测通过，请求也正常返回。

**根因**：这两处配置的逻辑是「按名字查表，查不到就用默认值」。请求进来按新名字查不到配置，超时和预扣费悄悄用上了默认值。后来查明原来的名字才是对的（官方枚举里两个相近的名字是两个模型），改名全部回滚。

**修复**：改名前先列出所有出现的位置，逐个判断要不要改；改完再搜一次旧名，结果要么为零，要么每一处保留都写得出理由。

```bash
rg -n --hidden -g '!vendor' '<旧名>'          # 改之前
rg -n --hidden -g '!vendor' '<旧名>' | wc -l  # 改之后，应为 0 或每处有理由
```

有条件的话，让关键配置在查不到时打一条日志，别静默用默认值。

## 2. 新增同族名字：旧名散落各处，新名一处都命不中

改名的反方向是新增：给一个已上架的模型加一个兄弟版本，上游是同一个端点、只换一个版本参数，客户端可以原样复用。听起来只是「复用旧链路」，可旧名字散落在网关各处，新名字一处都命不中。

**现象一**：读代码时数出网关里约 15 处用 `model == "<旧名>"` 或 `strings.Contains(model, "<旧名前缀>-")` 做判断，覆盖白名单、默认清晰度、参数校验、预扣费、结算策略、超时。新名字一处都命不中：请求先被判为不支持；就算放行，结算策略也查不到，落到默认的 1 倍，按秒计费的视频任务每个只收 1 秒。这一条是读代码推出来的，补回归测试时才证实。

**现象二**：另一个家族的判断写法不统一：预扣和参数校验用子串匹配，结算用精确匹配。新名字在预扣时命中了旧型号的规则，结算时却掉进通用的计价逻辑，两边算的不是同一套东西。

**修复**：不要再往每一处加 `|| model == "<新名>"`。把散落的字面量判断收口成一个家族判断函数，版本之间不同的参数放进一张按型号查的表，预扣和结算共用同一个计价函数；收口之前先用回归测试钉住旧型号现在的行为。这个案例的代码和验证过程写在[计费规则的几个暗坑](/blog/billing-regression/billing-rule-pitfalls/)第 1 节。

## 3. 子串规则：新名字碰巧含一段子串，就被归到别的类

`strings.Contains(name, "xxx")` 式的分类规则，是给写它那一刻已有的模型用的。新名字只要碰巧含这段子串，就被静默归到别的类别。

**现象**：一个新接入的语音合成模型，任务响应里的类型字段返回的是「音乐」。功能完全正常，没有任何报错，只是这个字段和文档示例对不上。

**根因**：分类函数里有一条按系列名子串判类别的规则，是给某个音乐模型系列写的。新名字里的一个普通单词碰巧包含了这段子串，而这条规则排在「含 tts 就算语音合成」之前，先命中了。顺着查下去，另一个已经上线的音频模型也被判成了音乐，一直没人发现。

**修复**：助手最初的建议是把那条子串规则改严。复查后改了主意：它同时决定着已上线模型的返回值，改了就是对外行为变更，要单独评估。最后只在函数开头给新模型加一条精确匹配，并用单测把存量模型的当前返回值一起锁住：

```go
func audioType(model string) string {
	switch model { // 新模型一律精确匹配，放在所有子串规则之前
	case "zephyr-speech":
		return "tts"
	}
	// ……下面是原有的子串规则，不动
}

func TestAudioTypePinsExisting(t *testing.T) {
	for model, want := range map[string]string{
		"zephyr-speech":    "tts",   // 新加
		"brightline-2":     "music", // 存量：锁住当前返回值
		"quartzfx-1":       "music", // 存量：已知不准，但这次不改
		"plainvoice-tts":   "tts",
	} {
		if got := audioType(model); got != want {
			t.Errorf("%s: got %s, want %s", model, got, want)
		}
	}
}
```

同一个函数如果另一条并行分支也在改，新分支加在不相邻的位置（比如函数开头），合并时不容易冲突。

子串问题在接模型时最容易撞上。有一次给一个新型号选对外名，按其中一种拼法会命中另一个家族的前缀判断，被按那个家族计费。我的做法是把全库按模型名做子串、前缀判断的地方都 grep 出来，把新名字逐条代进去，每一处写下「该不该命中、实际命中哪条」：

```bash
rg -n 'strings\.(Contains|HasPrefix|HasSuffix)\(\s*(model|name|upstream)' --type go \
  | grep -v _test.go > substring-rules.txt
wc -l substring-rules.txt   # 那次是 25 处，代入后命中 11 处，逐条核过
```

还有一种变体是类型名的别名。助手给某个上游加了一条「欠费时换一次渠道」的判断，条件写的是「provider 类型等于 A」。单测和本地全栈都过，因为夹具里的渠道全建成了类型 A。审查的窗口指出，同一个上游在渠道配置里还能用另一个类型名，走的是同一个客户端。用那个类型名建渠道复跑，判断没认出来，任务多换了一次渠道并扣了费。动手前要先查客户端注册表里这个上游登记了几个类型名，判断函数列全，夹具对每个别名各建一套渠道。

## 4. 市场名撞名：同一个词在代码里早就指别的东西

接一个新版本之前，我会把它的市场名后缀在全部仓库里 grep 一遍。

**现象**：上游新发布的一个版本，市场名带一个档位后缀，这里叫它「X 档」。grep 代码库，这个后缀已经满处都是：网关里的注释、测试文件名、计费策略的注释，前端的变体 id 和常量，博客文案。这些全部指的是另一个内部条目。

**根因**：市场名在代码里先被另一个内部条目占用了。那个后缀是内部给它起的口头昵称，没有登记在任何命名约定里，写进代码后就成了事实上的占用。上游后来正式用了同一个词，两个来源撞了名。前人没合入的尝试里，函数名也直接用了裸的后缀，和存量测试文件只差一个词。

**修复**：

1. 对市场名后缀的每种写法（全小写、首字母大写、带连字符、全大写带下划线）在每个仓库各 grep 一次，命中分成「指本模型」「指别的模型」两列；
2. 有「指别的模型」的命中，新标识符一律带来源限定，函数、测试文件、SQL 文件、前端常量都带上渠道或来源的后缀；
3. 对外模型名跟同一来源已上架版本的命名风格走，不借用昵称；
4. 把撞名写进契约的第一节，让前端、文档、验收都知道。

## 5. 别名改指向：旧名 A → 新目标 B，存量配置跟着换了含义

前四类是名字本身没对齐。这一类是名字都对齐了，但它指向的东西变了。

场景是这样：旧名 A 原来是模型 X 的别名。X 要下线，决定让 A 改为指向新模型 B，老用户的代码不用改就能继续调。代码上只改了别名表的一行，单测和本地端到端全绿。问题出在线上已经存好的配置上。

**机制**：网关里有一批配置在加载时先把名字做别名解析，再拿解析后的标准名当键，并且为了防止歧义拒绝重名。最小化写出来是这样：

```go
func loadRules(saved map[string]Rule, resolve func(string) string) (map[string]Rule, error) {
	out := make(map[string]Rule, len(saved))
	for name, r := range saved {
		canon := resolve(name) // 先解析别名，再当键
		if prev, dup := out[canon]; dup {
			return nil, fmt.Errorf("duplicate rule for %s: %v vs %v", canon, prev, r)
		}
		out[canon] = r
	}
	return out, nil
}
```

改指向之前，`{A: 给 X 的规则, B: 给 B 的规则}` 是两个不同模型的规则，合法。改指向之后，A 和 B 解析成同一个名字，变成同一个模型的重复定义，整份配置被拒。配置是热加载的，非法时保留上一份有效快照，所以失败是静默的；而刚启动的节点上一份就是代码默认值，于是**别的模型的自定义限制也一起失效**，只在日志里留一行错误。

只写了 A 的那份规则更隐蔽：它当初是写给 X 的（比如「只允许原生协议的接口」），改指向后按名字归一落到了 B 头上。本地实测，它把 B 自己唯一能用的生图接口拦掉了。

我现在把每份这样的配置按三种情形写一句结论，写进上线说明：

| 存量配置里有 | 改指向后会怎样 | 要做什么 |
|---|---|---|
| 只有旧名 A | 规则改为作用在 B 上 | 判断对 B 是否成立，不成立就和代码一起改配置 |
| 只有新目标 B | A 的流量也会被它管到 | 判断老用户该不该受这条规则约束 |
| A 和 B 都有 | 重名，整份配置被拒，所有模型回落默认 | 上线前合并成一条 |

同一类「跟着换目标」还有：只写了 A 的令牌白名单改为放行 B、不再放行 X；准入规则按解析后的名字精确取值，写给 X 的规则不再管 A 的流量；模型列表里 A 改挂到 B 下面。

**清单要从代码 grep，不凭记忆列**：第一版存量配置清单列了端点规则、令牌白名单、分组准入、自动路由档位，新上下文复核时才发现漏了「按用户存的准入覆盖」。它排在分组和全局之前，按解析后的名字精确查，挂在 A 上的个人限额上线后就不再生效。所有拿模型名做键的读取处都要 grep 出来，全局、分组、个人每一个覆盖层级都是一份要查的存量：

```bash
# 找出所有「先解析别名再当键」的地方，函数名按项目实际换
rg -n -i 'resolve.?(model)?.?alias|canonical(ize)?.?model' --type go | grep -v _test.go
```

其中读已保存配置的，写成一组只读查询交给有生产库权限的人跑。那次助手写了九段只读 SQL，先在种子数据上跑：种子里故意放了三行应该被查出的、三行不该被查出的，两边逐行一致，才把查询交出去。

**旧计价条目保留时，出口会把旧名单列**：那次的决定是旧名 A 的计价条目保留（不删历史）。复核时实测发现，按计价目录取数的「可用模型列表」和公开的模型目录，把 A 单列一行、标着旧价，而请求实际按 B 的价格计费。公开价格页本来就跳过别名行，这两处没有。处理只有两条路：让旧条目的状态落到列表的取值范围之外，或者在出口跳过别名行；后者会改变所有已有别名的展示，所以交给 leader 定。

**参数语义也可能跟着变**：如果 X 和 B 的某个参数形式不同（比如一个收数值预算、一个收档位），换算只对旧名生效，并用一条守卫测试钉住「换算只和别名一起存在」，免得以后有人删了别名、换算还挂在那里。

## 6. 默认档变化：没写目标的入口全跟着走

前端也有同一类问题，表现为「默认值决定落点」。

**现象**：一个合了五个变体的模型页，按评审意见把默认变体从最贵的一档改成最便宜的一档。测试和截图只验了两件事：裸路由落到新默认档，带 `?model=` 参数的旧链接仍落原档，全绿。审视时才发现三类入口都去了新默认档：旧地址的 301 直接指向裸路由；定价总表上两行本该指向具体变体的链接取的是裸路由，点进去是另一个变体、另一个价；一条介绍某个高规格能力的旧公告链接，也落到了不支持这个能力的那一档。

**根因**：这些入口从来没写变体参数，「落到哪一档」是默认值顺带决定的，没有任何一处显式记录「这个链接想去哪一档」。默认值一变，含义全变，不报错。

**修复**：

1. 改默认前，grep 全仓这条路由的裸写法：重定向配置、定价和目录数据源的链接字段、更新日志、博客、站内其它页面；
2. 逐个判原意：泛指整个模型的（目录卡片、导航）保持裸路由，指具体某一档的补上 `?model=<那一档>`；
3. 页面数据里的路由字段如果同时被当作分组键，不能直接在字段里加查询串，那会把同一页拆成两组；深链加在生成链接的地方；
4. 补一条测试：从链接里解析出 `?model=`，断言落到预期的变体，并把参数故意改错跑一次，确认会红。

整页下线、旧路由 301 到另一页的某个变体，是同一个问题的放大版。重定向之外，页脚、集合页卡片和从同一个数组生成的结构化数据、带链接的选型表、按路由白名单开功能的表（例如任务日志的「再次运行」），都要逐个处理。白名单里留着下线的路由，按钮照样出现，跳过去的新页不认旧模型 id，表单是空的。

## 7. 展示层换名和隐藏内部字段：出口要实测枚举

最后一类是名字在内部和对外不一样。

**现象**：一个对外模型在内部按两个名字记账：用户调的是对外名，网关按参数分流到另一种模式时，内部换成一个路由名去选渠道、计费，消费日志记的就是这个内部名。用户会在账单里看到一个自己没调过、文档里也查不到的模型。

**取舍**：改写入口径会牵动对账和历史数据，所以选了「落库不动，在用户侧的读取出口换名」。换名不只是替换字符串，有三件连带的事：

- **聚合要合并**：按模型分组的统计里，对外名和内部名本来是两行，只替换字符串会得到两行同名数据，前端按名字当 key 会互相覆盖。换名后按「分组维度 + 新名字」把数值相加；
- **筛选要反向展开**：用户在下拉里选对外名，记录里存的是内部名。在解析筛选参数的那一个点，把对应的内部名补进去，否则换名后的记录「看得见、筛不出」；
- **排名要重排**：「每个 key 花费最高的模型」这类取第一行的逻辑依赖原排序，合并后按原规则重排。

没有任何一行是内部名时原样返回，保证其它模型的响应逐字不变。

**出口有几个，靠实测数**：助手第一次估计是两个读接口。实际用一枚用户会话把用户侧接口全调一遍、递归遍历 JSON，数出来是 5 个接口、8 个字段。修完以后同一个脚本应该全部为 0：

```python
# find_name.py：列出 JSON 响应里值或键含某个名字的字段路径
import json, os, sys, urllib.request

NAME = sys.argv[1]
session = os.environ["SESSION_TOKEN"]

def walk(node, path="$"):
    if isinstance(node, dict):
        for k, v in node.items():
            if NAME in k:
                yield f"{path}.{k}（键）"
            yield from walk(v, f"{path}.{k}")
    elif isinstance(node, list):
        for i, v in enumerate(node):
            yield from walk(v, f"{path}[{i}]")
    elif isinstance(node, str) and NAME in node:
        yield path

for url in open("user-endpoints.txt").read().split():
    req = urllib.request.Request(url, headers={"Authorization": f"Bearer {session}"})
    data = json.load(urllib.request.urlopen(req))
    hits = list(walk(data))
    print(f"{len(hits):3d}  {url}")
    for h in hits:
        print("     ", h)
```

验收看守恒：换名合并前后，总请求数、总花费不变；合并后的那一行等于原来两行之和；按对外名筛选的条数等于原来两个名字各自条数之和。有意保留内部名的出口（例如前端靠它取实时价的接口、内部管理端）写进映射表的注释，别让下一个人以为「全换了」。

隐藏内部字段是同一个道理，要列全两个维度：**入口**和**键**。碰到过一次：任务结果里新增了一个只供内部对账的字段（转存前的上游原始地址），助手新写了一个「对外专用」的过滤函数，接到任务详情和回调上，两处都验过了。外部审查发现，用户的历史列表、账本和导出走的是另一条读取路径，调的还是旧函数，字段原样返回。修法是 grep 旧过滤函数的每一个调用点，逐行归类：

| 调用点 | 给谁 | 处理 |
|---|---|---|
| 单查、批量、回调 | 用户 | 已用新函数 |
| 历史、账本、导出 | 用户 | 换成新函数 |
| 管理后台列表与详情 | 内部 | 保留旧函数，加一条测试锁定「这里仍然有」 |
| 只处理别的数据形态的 | 无关 | 写明为什么不用动 |

再反向查一遍有没有入口压根不调任何过滤函数。回归测试从每个入口的真实读取函数走，断言序列化后的响应里没有内部字段，不直接测过滤函数。键的维度也一样：剥离表是按某个接口版本的键名写的，上游出新版接口、成本字段换了名字和结构，旧清单一个都命不中。接新接口版本时，把查询响应的每个顶层键都过一遍剥离表。

## 收尾

1. **查表不报错** —— 按名字查配置、按子串归类、按解析后的名字存规则，名字对不上时只会悄悄改行为。
2. **新名字逐条代入** —— 把全库按名字判断的地方 grep 出来，新名字代进每一处，写下该不该命中、实际命中哪条。
3. **新模型精确匹配** —— 不改共享的子串规则，在前面加精确分支，并锁住存量模型的返回值。
4. **收口成家族表** —— 散落的字面量判断收成一个函数和一张按型号查的参数表，预扣和实扣共用。
5. **别名改指向按三种情形核** —— 只含旧名、只含新目标、两个都有，每份存量配置写一句结论，清单从代码 grep。
6. **入口和键都要列全** —— 默认档变化补深链；换名和隐藏字段的出口用脚本实测枚举，不凭印象。

下次碰到任何「把一个名字改成另一个」的需求，我会先跑一遍 grep 和代入，把结果写成表，再改代码。新模型的接入顺序见[接一个新模型的五段流程](/blog/model-onboarding/onboarding-five-stages/)；守卫测试为什么要先在改动前跑红，见[守卫测试的三个要求](/blog/testing/guard-tests-three-rules/)。
