> 一句话总结：同意状态要作用于实际的数据读写和发送路径；先画清用途、工具与存储的关系，再把首次拒绝、分类接受和后续撤回分别验，才能看出只给一个组件加开关会漏掉什么。

## 0. 起因：几个名词混在一起，修复范围就容易看小

看一项网站数据采集问题时，我先追问了几个基础概念：GA、GTM 是什么，自己的来源归因为什么有业务价值，为什么同在一个容器中的标签还要分开控制。

助手最初的解释也省略了触发前提。例如「拒绝后会重建归因」很容易被理解成：原来的来源数据被删除以后，又完整恢复了。实际核对的路径，只会在存储为空时重新生成一个访客编号，旧来源仍是空的。

另一个疑问是：既然首次拒绝就不应该加载，为什么还要处理已经运行的脚本？这里又把「从未接受」与「接受以后撤回」混到了一起。

这些并非术语润色。理解错了对象，就可能只修改弹窗或一个延迟加载组件，把登录、排队回调和后端发送留在原处。下面用通用例子说明数据流，不介绍任何具体站点的配置，也不展开地区法律判断。

## 1. 先分四层：目的、工具、数据、控制

我现在先把概念放进下面这张表。不同层的东西可以互相联系，但不能互相替代：

| 层次 | 例子 | 应回答的问题 |
|---|---|---|
| 业务目的 | 改善页面、衡量渠道效果、计算邀请关系 | 为什么需要这些数据 |
| 工具与代码 | 分析平台、广告标签、自写记录函数 | 谁采集、谁处理、发往哪里 |
| 数据与存储 | 来源参数、事件、访客编号、Cookie、本地存储 | 记了什么、怎样连接、保存多久 |
| 控制与说明 | 用户选择、触发条件、清理策略、政策文字 | 哪些用途何时允许、怎样停止与解释 |

Google Analytics，简称 GA，是流量与事件分析产品；Google Tag Manager，简称 GTM，是管理标签及其触发规则的工具。GTM 不是一份政策，也不是它所装载的每个服务。它更像一处配置入口，里面可以管理多种用途的代码。[GTM 官方介绍](https://support.google.com/tagmanager/answer/6102821?hl=en)、[Analytics 设置说明](https://support.google.com/analytics/answer/9304153?hl=en)。

Clarity 提供行为分析、热力图与会话回放；Google Ads 的网站转化衡量，则关心广告之后是否发生了指定动作。一个页面同时出现这些产品名，仍需继续核对实际功能和配置。[Clarity 官方概览](https://learn.microsoft.com/en-us/clarity/setup-and-installation/about-clarity)、[Ads 转化衡量](https://support.google.com/google-ads/answer/1722054?hl=en)。

工具名也不能直接决定分类。同一工具可能服务不同目的；某个容器被加载，更不能推导出它包含的全部标签都获得了许可。

## 2. 自家归因：把一次来访与后续动作连接起来

假设一个虚构网站在社区文章里放了带来源参数的链接。访客打开页面，网站希望知道这批来访后来有没有注册，而不是只知道页面被打开了几次。

```text
链接带 utm_source=community
→ 浏览器获得访客编号 V1
→ 记录首次来源与最近一次明确来源
→ 注册成为账号 U1
→ 按约定把 V1、来源与 U1 的事件关联
```

这里有三个不同对象。UTM 参数是入口信息；访客编号用于识别某次浏览器环境；账号编号属于注册后的业务身份。把它们连接起来，才形成跨阶段的归因。它们不会因为名字相近就自动属于同一个平台。

`first-touch` 可以表示最早记录的来源，`last-touch` 可以表示转化前最近的明确来源。直接访问是否覆盖旧来源、跨设备如何处理，都要由具体规则决定，不能只凭字段名推断。

这类数据可以有业务价值。判断它是否影响核心功能，还要看调用链：少了来源信息，登录是否仍能成功？分析发送失败时，是否会拖住主请求？某些显式邀请输入是否还承担独立的权益确认用途？

因此要把用途拆开核，不因同在一份存储里就一起删除，也不因业务希望保留就把所有用途归成一种。本文只讨论怎样查清工程事实，具体许可与告知要求仍需按实际场景确定。

## 3. 拒绝后再写入：漏的是另一条入口

**反例**：一个名字像读取函数的辅助方法，实际会「读取存储、补一个缺失编号、写回存储」。如果进站组件尊重选择，登录路径仍调用这个方法，本地记录就可能再次出现。

需要把触发条件写完整：

```text
假设产品采用拒绝后清理对应归因记录的方案
→ 进站采集停止
→ 后来发生登录
→ 登录路径读取空存储
→ 辅助函数生成新编号 V2 并写回
```

这里重新创建的是一个空来源记录和新编号，不是把旧 UTM 历史恢复出来。一次保存的离线局部验证支持的也只是这个范围：固定函数在空存储下执行后，新增编号，来源字段仍为空。它没有模拟完整拒绝界面，更没有证明线上用户已经经历了这条链路。

这个区别会改变修法。如果目标是不再生成对应标识，单纯清空旧值不够；应核所有可能补值和写回的调用方。辅助方法是否应该只读取，或者是否明确接收当前许可状态，也需要一并讨论。

查找时不要只搜 `setItem`。写入可能藏在名为 `get`、`ensure`、`sync` 的封装里，浏览器和后端也可能各有一套入口。函数名字是线索，实际副作用才是依据。

## 4. 分类接受：共同入口不等于共同用途

假设产品已经明确支持「允许统计、拒绝广告」。那么页面加载了某个共享容器以后，还需要保证其中广告用途的标签不会沿原来的全站规则触发。

可以用一张用途矩阵先写下预期：

| 状态 | 已确定的统计用途 | 广告用途 | 核对重点 |
|---|---|---|---|
| 尚未选择 | 按既定默认策略 | 按既定默认策略 | 初始状态是否在调度之前建立 |
| 仅允许统计 | 允许相应处理 | 阻止相应处理 | 容器内标签是否分别控制 |
| 全部允许 | 按实际配置处理 | 按实际配置处理 | 数据和接收方是否与说明一致 |
| 后来撤回 | 停止对应后续处理 | 停止对应后续处理 | 已运行代码、队列和存储怎样处理 |

这张表不是普遍的默认政策；真正的项目要先确定承诺，再填写预期。它的作用是阻止实现者用一个总开关，默默代替所有用途的决定。

Google 官方也区分支持内置同意检查的标签，以及需要额外配置的标签。设置一组 Google 状态，并不意味着自定义脚本或第三方标签会自动跟随。[Consent mode 官方说明](https://developers.google.com/tag-platform/security/concepts/consent-mode)。

## 5. 撤回：同时处理正在运行和等待运行的代码

首次始终拒绝，与先接受再撤回，需要不同的测试路径。对于选择加载阻挡的方案，前者应核相应脚本是否从未启动；后者应核已经运行的代码如何停止后续处理。

删除一个 `<script>` 元素，不会自动撤销它先前注册的事件监听，也不会收回已经发出的请求。相同地，弹窗保存了新选择，之前排队的定时器或空闲回调也不会凭空消失。

一个稳妥的设计判断是：调度任务时检查一次，真正执行时再检查最新状态；可以取消的队列及时取消，并对可停止的订阅、监听或供应商接口执行相应操作。哪些旧记录要清理，要按已确定的策略处理，不能拿任意删存储代替设计。

还要区分「不写 Cookie」与「不发送数据」。Google 的 basic 模式会在许可之前阻挡标签；advanced 模式可以在拒绝存储时发送无 Cookie 的测量请求。因此验收目标如果是「此前零统计外发」，仅看到 Cookie 为空不够。[两种模式的区别](https://developers.google.com/tag-platform/security/concepts/consent-mode#basic-versus-advanced-consent-mode)。

后端独立发送也是同样的问题。浏览器停止某个脚本，不会自动关闭服务器的分析路径。需要核对实际调用方、运行开关，以及用户选择怎样传到那里；源码里默认关闭，也不能直接写成生产正在关闭。

## 6. 保存多久：归属窗口与删除时间分开核

另一处容易读错的是「窗口」。例如代码只把最近一段时间内的来源用于归因，说明的是计算规则；它不一定让浏览器记录在同一天自动过期。

我会分别确认：记录何时写入、是否带过期信息、每次读取是否判断、是否有主动清理，以及服务器副本有没有独立保存期。只找到一个天数，无法回答整条链路保存多久。

用途、保留时间与实际运行配置之间，需要有明确对应。代码提交可以解释当初为什么加入功能；当前源码可以说明存在什么路径；后台配置和实际请求，才支持它现在是否启用。三种证据不要合成一句「已确认」。

## 7. 一份沿数据流执行的检查清单

我会把检查对象写成下表，每行都有输入条件和能观察的结果：

| 路径 | 操作 | 观察 |
|---|---|---|
| 首次进入 | 清除测试偏好，尚未选择 | 脚本、网络、标识和本地写入分别是什么 |
| 分类接受 | 只允许一种用途 | 共享容器中的其他标签是否仍触发 |
| 登录与注册 | 在对应拒绝状态下继续核心动作 | 核心动作可用，归因辅助方法是否补写 |
| 排队任务 | 调度后、执行前改变选择 | 任务取消或按最新状态停止 |
| 接受后撤回 | 先触发一次，再撤回并继续操作 | 新请求停止，旧存储按策略处理 |
| 后端发送 | 核运行配置与实际调用方 | 是否独立外发，选择是否传到发送边界 |
| 保存期限 | 推进测试时间或读取过期记录 | 归属计算与真实清理各自成立 |

最后再核说明文字能否准确描述这些行为。按钮标签、Cookie 数量和一张截图都只能证明局部；链路正确需要看到写入与发送边界。

## 收尾

1. **名词分层** —— 工具、用途、存储与政策不是同一个对象。
2. **入口找全** —— 进站受控，不代表登录和后端也受控；读取封装可能带写入副作用。
3. **状态分别验** —— 首次拒绝、分类接受、排队后改变选择与撤回，需要各自观察。
4. **证据限定范围** —— 新编号不等于旧历史恢复，存储为空不等于没有外发。
