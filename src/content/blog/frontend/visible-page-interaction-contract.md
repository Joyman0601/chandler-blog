> 一句话总结：可见 HTML 不等于交互逻辑已接入，列表项在 DOM 中也不等于点击能到达；验收要沿用户动作检查最终状态，并覆盖脚本未就绪和真实遮挡这两类窗口。

## 0. 起因：常规测试通过，页面上还有两处异常

一次前端回归中，多语言优先级的单测通过，页面也已经显示语言链接，但在脚本尚未就绪时选择英文，仍会被送回原来的语言。链接成功导航了，手动选择却没有被记住。

另一页的日期计算、选项排序都正常。手机上打开一个长下拉列表，顶部选项也确实存在，但固定导航盖在它上面，手指点不到。

两件事的根因不同：前者涉及加载时序和跨页意图，后者涉及层叠与实际命中。它们共同暴露了一种验收缺口：观察到了页面元素，却没有证明用户动作穿过了完整链路。

本文沿这两个案例，记录怎样建立能区分正常和异常的检查。文中的地址与选择值都使用通用示例，不代表某个站点当前的运行状态。

## 1. 语言链接：导航与保存选择是两个动作

假设网站在 `/fr/` 显示法语，在 `/en/` 显示英语。没有手动选择时，入口会参考浏览器语言；用户明确选择以后，应当保留该意图。

服务端输出的链接可以立即具有原生导航能力：

```html
<a href="/en/">English</a>
```

但如果「记住选择」只写在 React 的点击处理里，交互代码未接入以前，点击仍然可能完成导航，却不执行那次保存。目标页最早运行的自动识别逻辑看不到记录，就再次参考浏览器语言。

```text
原语言页已显示链接
→ 用户点击 English
→ 原生 href 导航成功
→ 保存手动选择的处理尚未接入
→ 目标页读不到选择
→ 按默认规则回到原语言
```

这不是浏览器语言被改回去了。浏览器语言一直没变，丢的是「这一次访问来自用户主动选择」的信息。

React 官方说明，水合会把组件逻辑接到已经存在的服务端 HTML 上。因此 HTML 呈现与完整交互之间存在需要考虑的阶段。[`hydrateRoot` 官方说明](https://react.dev/reference/react-dom/client/hydrateRoot)。

同时也不能把所有水合期间点击一概描述成必丢。框架版本、加载阶段和事件处理方式都会影响结果。这次缺陷的依据，是特定实现与原生链接路径的受控对照。

## 2. 把手动意图带过这次导航

修复要解决的契约是：当用户已经能够发出明确选择时，接收这次导航的一方也能够识别它。并非只要求某个回调在页面完全加载以后能写入。

可选择的实现取决于项目：让一个很小的早期处理在链接出现前准备好；通过专门的选择入口由服务器保存；或让目标地址携带经过校验的选择意图。这里没有唯一写法，但需要保留普通导航与可接受的无脚本行为。

当时采用的是早期捕获监听。它仅识别明确标注的语言链接、校验支持的语言值，同步保存已有偏好，然后保留浏览器默认导航。框架接管后，原有处理仍可共存。

这种做法需要约束范围。不要把页面上的所有链接都当成语言选择，也不要为了等待大脚本而长时间拦住正常导航。对于内联脚本，还应沿用项目已有的内容安全策略和输出约定。

存储属性也属于行为契约。路径、有效期和安全属性如果被另写一份，很容易出现早期与正常处理互相覆盖。能共享的规则应共享；无法直接共享运行代码时，至少用同一契约验证两条写入路径。

## 3. 用慢脚本夹具覆盖真实时间窗口

普通用例等待交互就绪，是为了稳定检查正常路径；专项用例则刻意保留 HTML 与导航，延迟外部交互脚本，让这段窗口可以稳定出现。

我会按下面顺序执行：

1. 使用非目标语言的浏览器上下文，不预置手动偏好。
2. 访问真实生产构建的语言页，延迟或阻断选定的外部脚本。
3. 确认链接可见，框架点击处理尚未接入。
4. 发出真实点击，记录导航链、最终语言与保存的选择。
5. 释放资源，再验证交互就绪后的正常路径。

最有区分度的负对照，是仅移除新增的早期处理，其他 HTML、链接和目标页逻辑不动。历史验证里，这样会重新出现往返跳转与选择缺失；保留处理时，刷新和新标签页能维持选择。

这组对照说明用例能识别原来的时序问题。它不提供真实用户发生率，也不能用人为延迟的持续时间估算线上有多少访问会受影响。

还有一个夹具边界：若同时把目标页的自动识别脚本也移除了，矛盾就被测试自己绕开了。正例看似不再跳回，却没有证明选择已经传递。

## 4. 手机浮层：选项存在，不代表点击命中它

另一次回归的问题发生在空间上。下拉通过 portal 渲染在页面其他位置，长列表向上展开后进入固定导航区域；导航层级更高，挡住了顶部选项。

Portal 可以改变元素所在的 DOM 位置，不能自动保证浮层高于页面所有内容。排查时仍要看实际层叠上下文、相邻固定元素，以及最终参与命中的对象。MDN 对[层叠上下文](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Positioned_layout/Stacking_context)的说明也强调，子元素的层级比较受所属上下文约束。

这次修复很小：在既有层级体系内，让下拉高于会遮挡它的固定导航。关键在后续验收，不能只断言 CSS 数值变大，也不能用脚本直接调用点击处理来代替真实指针操作。

检查点应放在实际会被手指点到的位置。下面是独立编写的诊断片段，可在选项元素存在时判断中心点最上层对象是否属于它：

```js
function ownsCenterHit(option) {
  const rect = option.getBoundingClientRect();
  const x = rect.left + rect.width / 2;
  const y = rect.top + rect.height / 2;
  const hit = document.elementFromPoint(x, y);
  return hit !== null && option.contains(hit);
}
```

[`elementFromPoint()`](https://developer.mozilla.org/en-US/docs/Web/API/Document/elementFromPoint) 返回指定视口坐标上的最上层元素。这个片段只检查一个点，不能证明整个选项都无遮挡，更不能替代真实点击与选择结果断言。它适合回答「中心点现在被谁占着」。 <!-- check:ok -->

## 5. 把打开、滚动、选择与关闭作为一条路径

历史验证在手机竖屏、横屏和桌面视口检查了列表首、中、末位置，也测试了 Escape、外部点击关闭、焦点返回与偏好保存。恢复旧组件后，原来被遮挡的手机场景再次失败，说明新增断言没有只跟着修复结果走。

这些检查承担不同职责：

| 观察 | 能说明什么 | 不能替代什么 |
|---|---|---|
| 选项数量与顺序 | 数据完整、排序符合规则 | 指针能否点击 |
| 选项矩形在视口内 | 几何位置可见 | 上面是否盖着别的元素 |
| 中心点命中 | 该点最上层对象正确 | 整个控件的操作与保存 |
| 真实选择后值改变 | 动作到达业务逻辑 | 刷新后是否仍保持 |
| Escape 关闭、焦点返回 | 键盘关闭路径成立 | 外部点击与触摸路径 |

复测还遇到过测试拦截误伤生产静态资源的情况。页面加载失败来自夹具，不能马上计成产品回归。修正拦截范围后，应继续保留需要模拟的账号接口，再跑真实发布资源上的操作。

同样地，本地构建与模拟账号的通过，只支持对应交互范围。真实登录数据、线上缓存和最终部署，要有各自证据，不能因为页面上的点击成功就一并宣布完成。

## 6. 从用户动作反推验收点

这两个案例让我更愿意先写一句完整的业务动作，再决定断言。比如「选择英文，并在下一页继续保持」，而不是「点击处理调用了一次」；「滚到第一项、选中并保存」，而不是「列表中找到该文字」。

时间与空间还可以组合出现：慢加载时打开菜单、旋转手机后选择、折叠布局变化后恢复焦点。没有必要把所有组合穷举，但应找出改变动作归属和命中的条件。

我会在验收记录里保留四项：动作发出时的环境、独立预期、最终可观察状态、改前或最小撤销修复的对照。这样通过结果才有明确含义，也更容易判断是业务问题还是测试工具的问题。

修复范围可以很小，解释和断言仍应覆盖这条完整动作。

## 收尾

1. **拆开导航与意图** —— 链接打开了，不代表手动选择已保存并被下一页识别。
2. **区分显示与命中** —— 选项存在、位置可见，都不能代替实际点击到达。
3. **保留能失败的对照** —— 延迟脚本与旧组件应重新暴露目标问题。
4. **检查最终动作** —— 用最终语言、选中值、保存结果和焦点，解释测试究竟证明了什么。

以后看到页面已经显示，我会继续问：现在发出的这个动作，由谁接收，影响哪份状态，下一步还能不能看到它生效。这个问题能把许多「看起来正常」变成具体可验的行为。
