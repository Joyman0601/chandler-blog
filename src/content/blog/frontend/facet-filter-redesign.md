> 一句话总结：多选从交集改成并集，不只是把 `every` 换成 `some`，计数口径、组间规则、命中提示和行宽都要跟着改；标签设不设、拆不拆按定义判断，「A 的对象恰好都有 B」不等于 A 属于 B；每个标签都要能指到实测或文档。

## 0. 起因：给模型列表页加多选能力标签

前端控制台有一个模型列表页，几十个模型按模态（文本、图像、视频、音频）分类展示。原来只能按模态和厂商筛，这次要加一层能力标签：文本模型按「图片输入」「文件输入」「联网搜索」「长上下文」这类能力筛，视频模型按「文生视频」「首帧」「参考生视频」这类输入方式筛，并且可以多选。

这件事我是和 Claude Code（下文叫助手）一起做的。助手先做了样稿（一个独立的 HTML 页面，带假数据和自检脚本），出了三种布局方案，经过两轮评审，再落到真实页面上。比较方案时用了一个量：「1440×900 下第一张模型卡离页顶多远」。

| 方案 | 第一张卡的位置 |
|---|---|
| 线上现状 | 657px |
| 方案 A | 353px |
| 方案 B | 291px |
| 方案 C | 786px |

方案 C 评审时被认为「难看、占地方、用户看不到模型」，这张表给了这个判断一个数字：它比线上还低了一百多像素（实测）。C 就此删掉。

第二轮评审意见里有一句改变了整个筛选逻辑：「多选的逻辑是有问题的，应该取并而不是交集，二级全部取消换成同级，图生视频这一类不太好，改成首帧、尾帧、首尾帧三类。」这一句里有三件事：交集改并集，父子标签改同级，一个标签拆成三个。下面按这三件事展开，再讲打标签的证据和落到真实页面后的几个坑。

## 1. 交集改并集：四件事要跟着改

把 `every` 换成 `some` 只要改一行。改完页面上的数字和文案会和结果对不上，因为下面四件事还停在交集的口径上。

**计数口径**。交集时，标签上的数字一般是「再选它还剩几个」，会随其他选择变小。并集时这个数字要换成「它自己有几个」：受其他维度（模态、厂商、搜索词、别的组）影响，不受同组其他已选项影响。如果不改，选了 A 之后 B 上的数字变成 A∩B，用户点 B 结果反而变多，数字和行为矛盾。

**跨组规则**。并集只在同一组内成立。不同组之间仍然取交集：「图片输入或文件输入，并且是某个厂商的」。评审只说了「改并集」，组间仍取交集是助手自己补上的口径，它在交付说明里把这条单独标成了待确认。需求没说、实现时又必须定下来的规则，就该这样摆到明面上，最后写进文档：组内满足任一，组间同时满足。

**命中提示和文案**。并集的结果里混着「命中一个」和「命中多个」的模型，卡片上要能看出来。样稿里同时选两个能力时，结果里大约三分之一的卡两个都满足，单看卡片分不出来，列为待确认项。行标题从「同时满足」改成「满足任一」。空结果的提示也不能再写「去掉一个条件试试」：并集下去掉条件只会更少。

**选中态的宽度**。标签从父子改成同级以后数量变多，视频那一行在 1440 宽下刚好放满。选中时标签里多出一个 ✓ 图标，选到第二个就换行，吸顶栏的高度跟着跳。助手先把标签的内外间距各收紧了 2px，1440 宽下选 5 个以内能保持一行，但 1366 宽下选两个仍会换行。后来的版本去掉了选中态的 ✓，选中只换成深色底，宽度不再随选中变化，1366 宽下选几个都保持一行（实测）。收紧间距只是挪了临界点，根子在选中态改变了元素的尺寸。

逻辑本身写成两个函数，组内 `some`、组间 `every`，计数时跳过标签自己所在的组：

```ts
// filter.ts：组内任一、组间同时；计数忽略标签自己所在的组
export type Item = { id: string; tags: string[] }
export type GroupOf = (tag: string) => string

export function matches(item: Item, selected: string[], groupOf: GroupOf, skipGroup?: string) {
  const byGroup = new Map<string, string[]>()
  for (const t of selected) {
    const g = groupOf(t)
    byGroup.set(g, [...(byGroup.get(g) ?? []), t])
  }
  for (const [g, tags] of byGroup) {
    if (g === skipGroup) continue
    if (!tags.some((t) => item.tags.includes(t))) return false // 组内满足任一
  }
  return true // 每个有选择的组都满足
}

export const countFor = (items: Item[], selected: string[], groupOf: GroupOf, tag: string) =>
  items.filter((it) => it.tags.includes(tag) && matches(it, selected, groupOf, groupOf(tag))).length
```

验收脚本固定断言四个数：同组两个标签的并集大小、跨组的交集大小、多选以后各标签上的数字不变、选中 1 到 N 个时标签行的行数。

```ts
// filter.test.ts：假数据，四个断言各管一件事
import { countFor, matches, type Item } from './filter'

const items: Item[] = [
  { id: 'a', tags: ['图片输入', '厂商甲'] },
  { id: 'b', tags: ['文件输入', '厂商甲'] },
  { id: 'c', tags: ['图片输入', '文件输入', '厂商乙'] },
  { id: 'd', tags: ['长上下文', '厂商乙'] },
]
const groupOf = (t: string) => (t.startsWith('厂商') ? 'vendor' : 'capability')
const pick = (sel: string[]) => items.filter((it) => matches(it, sel, groupOf)).map((it) => it.id)

test('同组取并集', () => expect(pick(['图片输入', '文件输入'])).toEqual(['a', 'b', 'c']))
test('跨组取交集', () => expect(pick(['图片输入', '文件输入', '厂商乙'])).toEqual(['c']))
test('同组已选不影响计数', () => {
  expect(countFor(items, [], groupOf, '文件输入')).toBe(2)
  expect(countFor(items, ['图片输入'], groupOf, '文件输入')).toBe(2) // 交集口径会变成 1
})
```

第四个数（行数）要在浏览器里量，放在第 5 节。

## 2. 标签按准确度取舍，不按覆盖率

初版标签是助手做的。它参考了竞品调研里「长尾标签太多」的批评，做了三件按数量决定的事：

1. 把只有一两个模型支持的能力合并成一个「专项工具」兜底类；
2. 把几个图像后处理能力合并成一个「图像工具」；
3. 规定某个模态少于 6 个模型就不显示标签行。

看方案时我定了一条原则：取舍和覆盖率无关，和分类准确度有关。助手据此把三件事全部撤回：兜底类按真实任务拆开，显示阈值取消。

这条原则站得住，理由有三个：

- **兜底类描述不了任何对象**。用户想找某个具体能力，看到「专项工具」也不知道里面有没有。
- **覆盖率会变，分类错了一直错**。一个能力现在只有一个模型，说明的是目前上架得少。拿会变的量去决定不变的结构，方向就反了。
- **竞品被批评的真正问题是层级乱、同义重复**，比如「局部重绘」和「图像编辑」平级，而不是「标签多」本身。解法是理清层级，不是合并。

落成做法就是一条规则：**每个标签先写一句定义，写不出清晰定义的就不设**。只有一个模型才有的能力照样单列。

## 3. 语义包含和数据包含

评审时 leader 问（转述）：「图生视频」和「首尾帧」两个标签上的数字应该差不多，为什么差了这么多？

助手第一轮的猜测是：差出来的那些模型，上游其实支持尾帧，是我们的网关没暴露。第二轮它派了一个后台调研逐个去查上游的官方文档，再拿几个旗舰型号做对照，结论是猜错了：差出来的模型里，除了一个以外，上游本来就只收首帧，基本都是快速版或上一代（文档）。只有一个是真漏项：上游有尾帧参数，网关没暴露。

标签之间的「包含」因此要分成两种。

- **语义包含**：按定义一定成立。首尾帧一定是图生视频的一种；局部重绘、扩图、去背景一定是图像编辑的一种。
- **数据包含**：只是当前数据碰巧如此。比如目前所有支持「参考生视频」的模型也都支持「图生视频」，但参考生视频（素材作主体或风格参考）不是图生视频（图片作第一帧）的一种。明天上架一个只做参考生视频的模型，这条包含就不成立了。

判断方法分两步。先用脚本从映射表里算出所有候选包含，再对每个候选按定义判：

```python
# containment.py：从「模型 → 标签」映射里找出候选包含（假数据）
import itertools

cards = {
    "m1": {"文生视频", "首帧", "参考生视频"},
    "m2": {"文生视频", "首帧", "首尾帧"},
    "m3": {"文生视频", "首帧"},
}
tags = sorted(set().union(*cards.values()))
has = {t: {c for c, ts in cards.items() if t in ts} for t in tags}

for x, y in itertools.permutations(tags, 2):
    if has[x] and has[x] <= has[y]:
        print(f"候选包含：{x}（{len(has[x])}）⊆ {y}（{len(has[y])}）")
```

脚本只负责把候选找全，「是语义还是巧合」它判断不了。上面的假数据会打出「参考生视频 ⊆ 首帧」，按定义这是巧合，保持平级。

**并集让界面可以不做父子**。在交集逻辑下，父子标签需要一层联动：选了子标签，父标签显示「已包含」，取消父标签时连子标签一起清掉。改成并集以后，每个标签各筛各的，选大类出大类、选小类出小类，平级不会产生「能不能叠加」的歧义，这层联动可以整个去掉。所以评审说「二级全部取消换成同级」，在并集下是成立的。

包含关系不在界面上了，但要留在数据里。并集下这条更重要：如果一个模型只打了「局部重绘」没打「图像编辑」，用户选「图像编辑」时它就漏了。可以用一条数据约束测试守住：

```ts
// tags.test.ts：有小类标签就必须有大类标签
const IMPLIES: Record<string, string> = {
  局部重绘: '图像编辑',
  扩图: '图像编辑',
  去背景: '图像编辑',
}

test.each(models)('$id 的小类标签都带着大类', (m) => {
  for (const t of m.tags) {
    const parent = IMPLIES[t]
    if (parent) expect(m.tags).toContain(parent)
  }
})
```

「图生视频」最后拆成了「首帧」「尾帧」「首尾帧」三个同级标签，首帧就是原来的图生视频改名，口径不变。拆开以后标签名就是定义，不再需要一句「严格口径」的说明。拆完还要核一件容易想当然的事：「只给尾帧」和「首尾帧」互不包含。大多数型号要求有尾帧就必须有首帧，只有一个型号可以只传尾帧（文档）。这不能从「有尾帧参数」推出来。

## 4. 打标签要有证据：暗号素材和逐个端点

标签上线就是对用户的承诺。打标的规则是：只依据专门的接口、专门的参数、文档明确写出的能力打标；靠提示词能勉强做到的不算；文档没写明的默认不打，列进待确认清单，写明怎么确认。

实际核对时踩到了几个容易判错的地方。

**照定价打标会打错**。有一个系列的文本模型，定价里每个型号都列了「联网搜索」的按次价，标签也是照定价打的。实测一遍，整个系列只有两个型号真的返回了搜索结果，其余都回 400 不支持（实测）。问题出在渠道配置，不在模型能力。最后整个系列都不打这个标签。

**用答案已知的素材测能力**。「能不能看图」不能看模型回了一段像样的描述就算数。做法是给答案已知的素材：

- 看图：传一张纯红的 PNG，问「这是什么颜色」。有一个型号答成了蓝色，说明它根本没看到图。
- 读文件：传一个藏了暗号的 PDF，问暗号是什么。
- 看视频：本地做一段 2 秒的视频，画面上写着暗号。

**失败要先查原因，再判不支持**。有一次判了某个型号「不支持视频输入」，后来发现测试视频放在外部站点，上游下载不到，报的是解析错误。换成上传到平台文件服务的视频，两个型号都把暗号原样读了出来（实测）。

**每个端点各测一次**。同一个模型通过不同的接口格式调用，能力可能不一样。第一次只在一个端点上测联网搜索，判定几个型号都不会搜，拿掉了标签；后来在另一个端点实测，它们都真的执行了搜索，又补了回来（实测）。

真实页面实现后，又给文档站的全部 OpenAPI 文件建了一个索引，逐张卡核对标签，有疑问的点摘出文档原文，文档没写清的再查上游官方文档。绝大多数卡一致，改了 2 张，每条改动附原文。

## 5. 改完并排量：和参照组件比尺寸

排版上的偏差单看一个组件往往完全正常，并排量才看得出来。同期在详情页上碰到过两个例子，在列表页改版里也照这个办法量。

**槽位里再套全局容器类，内边距算了两次**。同一页上，价格区的卡片比上下两个区块每侧多缩进一截：桌面多 32px，手机多 16px。手机上按钮文字被挤成两行。根因是页面框架已经给每个槽位包了带内边距的容器，这个槽位组件的根节点又加了一次全局容器类（`max-w-* mx-auto px-*` 这种）。去掉以后，用脚本量每个区块的左右边界：

```js
// 在控制台或 Playwright 的 evaluate 里跑：同一页各区块的左右边界应该相等
const box = (el) => { const r = el.getBoundingClientRect(); return [Math.round(r.left), Math.round(r.right)] }
console.table([...document.querySelectorAll('section[id]')].map((s) => ({
  id: s.id, section: box(s).join(' – '), firstCard: s.firstElementChild ? box(s.firstElementChild).join(' – ') : '',
})))
```

**副行改成 `block truncate`，组件矮了 8px**。一个下拉触发器里，第一行是 13px 的主标题，第二行是 11px 的灰色副行，原来是行内的 `<span>`。副行太长会换行，所以加了 `block truncate` 做单行截断。改完所有语种和档位都不换行了，但按钮从 66px 变成了 58px，比参照组件矮一截。

根因是行框的高度。行内元素所在的行，高度至少是父元素的「字号 × 行高」，16px × 1.5 = 24px。改成块级以后，副行按自己的字号算：11px × 1.5 = 16.5px，少了 7.5px。截断又必须是块级，两件事绑在一起。修法是改块级时显式补回行高：

```html
<!-- 改前：行内，靠父级撑出 24px 的行 -->
<span class="text-[11px] text-gray-400">{subline}</span>
<!-- 改后：块级单行截断，leading-6 = 24px，高度和改前一致 -->
<span class="block truncate text-[11px] leading-6 text-gray-400">{subline}</span>
```

改的是公用组件，还要 grep 全部调用方：原来靠换行显示全文的长副行，现在会变成省略号。

列表页改版本身还栽在另一处：侧栏原有的勾选框、计数徽标、分组折叠被助手按样稿重画了。那次的经过和计算样式对照脚本写在[页面迁移那篇](/blog/frontend/page-framework-migration/)的第 5 节。

## 6. 换掉一份设计，旧读取方不会报错

标签方案前后改了好几版：交集改并集、一个标签拆三个、删掉一个方案、按十个同类站点的对照扩充标签。每次改的是同一份设计，而读这份设计的东西有很多：样稿、给实现窗口的执行提示词、十站对照表、后端清单、设计说明、汇报讲稿、幻灯片、截图。

问题出在「不在眼前的那个读取方」。有一次标签扩充以后，样稿、设计说明和讲稿都同步了，幻灯片还停在旧状态：旧的标签数，旧的待确认项。这是助手写交接说明时才查出来的。这类读取方不会报错，只会在被人打开时讲出一套过期的方案。

数字是最容易漏的。交集时写进文档、讲稿、截图里的「选 A + B 得到 N 个」，改成并集后一个都不能沿用。并集的结果比交集大好几倍，旧数字放在新页面旁边，读者会以为逻辑没改。

样稿上验过的规则，放到真实页面上也要重跑。有两条在样稿里成立、在真实页面上失效了：浏览器的滚动锚定会在结果变少时把页面滚回页头；真实页面有页脚，「内容列最小高度」兜不住。这两条的细节在 [sticky 的五种失败](/blog/frontend/sticky-layout-failures/)里。另外，真实页面的主干在样稿之后又上了新模型，卡片数和样稿不一样，新卡要按同样的规则补标签。

后来固定做三件事：

1. 改设计前，先列出它的全部读取方，`grep -rn` 旧的标签名、旧的数字、旧的文件名，把命中的文件写成清单；
2. 改完以后，每个读取方各跑一次冒烟（重新生成、打开截图、跑自检脚本），旧的「自检通过」不作数；
3. 所有演示数字从数据重新算，不手改。

## 收尾

1. **并集不只是换一个函数** —— 计数忽略同组已选、组间仍取交集、卡片要看得出命中几个、选中态不改变标签的尺寸。
2. **组间关系要主动确认** —— 需求只说「改并集」时，组内任一、组间同时是设计判断，写进文档。
3. **标签按定义取舍** —— 写不出定义的兜底类不设；覆盖率会变，分类错了一直错。
4. **数据包含不是语义包含** —— 脚本找候选，人按定义判；并集下界面可以平铺，包含约束留在测试里。
5. **打标要有证据** —— 用答案已知的素材测，失败先查原因，每个端点各测一次。
6. **并排量尺寸** —— 区块左右边界、组件高度都和参照比，截图目检看不出几像素的差。
7. **换数据源先列读取方** —— 讲稿、截图、演示数字不会报错，只会过期。

这次改版最大的收获是那条「准确度优先」的原则。初版按「这个类有几个对象」决定合不合并，少了就想合并，这是很自然的直觉。现在的顺序是先写定义，再看数据；数据只用来找候选和发现漏标，不用来决定结构。
