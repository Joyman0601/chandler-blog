> 一句话总结：迁移页面时，机器能判的交给契约测试和差分脚本，人只验浏览器里看得见的那部分；改版只改需求点名的地方，原有控件默认保留，动手前和主干逐个对照，交付前并排量计算样式。

## 0. 起因：一批模型详情页要搬到页面框架上

刚接手前端控制台时，碰上的第一件事是一次页面迁移。站上每个模型都有一张详情页，老写法是每页自己拼骨架。新的页面框架把骨架、路由、SEO 和包体都收走了，每一页只需要把自己的区块挂进框架留出的插槽。

第一期迁三页：一个文本模型页、一个图像模型页、一个视频模型页，正好覆盖三种模态。手边的东西有三样：

- 一份近九百行的页面规范，规定每种页型有哪些区块、放在哪、文案怎么写；
- 一个统计迁移进度的状态脚本；
- 几十个按页参数化的契约测试。

活主要是我和 Claude Code（下文叫助手）一起干：助手按规范改代码、跑测试、报进度，我验收。开头连着出了两次「检查全绿、需求没做完」，那两次的经过和后来补的闸另写在[两次「假完成」之后](/blog/testing/fake-done-and-gates/)。这篇讲的是迁移本身的做法：怎么并行，契约测试挡下了什么，交给验收的人什么东西。最后补一次两周后的改版教训，它和迁移是同一类问题的另一面。

## 1. 三页并行：一页一个 worktree，共享清单只追加

三页同时迁，最直接的办法是开三个 git worktree，每个 worktree 跑自己的 dev server，端口错开。这样三条线互不干扰，浏览器里可以同时开着三页对照。

**第一个坑是起点**。建 worktree 时，当前分支不在主干上，而在第一页的迁移分支上。另外两条线一开始就背着第一页的代码。查下来，第一页的提交里混着两类东西：页面代码和迁移工具脚本，两者文件零重叠。于是把它拆成两条：工具单独一条，页面单独一条，另外两页从工具那条切出来。教训是建 worktree 时显式写起点，不靠当前 HEAD：

```bash
git fetch origin
git worktree add -b <新分支> ../wt/<任务>/<仓库> origin/<主干>   # 起点写死
git -C ../wt/<任务>/<仓库> log --oneline -1                      # 确认起点是主干
```

**第二个坑是共享文件**。三条线都要改几个全局文件：页面登记清单、一份页面配置注册表，以及三份手工维护的契约测试清单。三条线各往同一个数组里加一项，合并时一定冲突。于是定了两条规则：

1. 手工清单的新增项一律追加到数组末尾。冲突时两边都保留，不挑一边。
2. 注册表是脚本生成的，冲突时不手工合。合并后重跑生成脚本，再看 diff。

后来一次 rebase 正好验证了第一条：别人的页面先合进了主干，三处冲突全是「两边各往同一个列表末尾加了一行」，两行都留就解决了。这类「各加一行」的合并还有更细的坑（两边改同一个计数会被静默接受、少加一次），git 那组文章里单独讲了[并行任务的 worktree 用法](/blog/git-collab/worktree-multi-task/)。

**第三个坑是 `.next` 目录**。包体检查报过几次「构建产物缺少某条路由」，查了半天代码没有问题。最后发现是同一个 worktree 里的 dev server 和 `next build` 共用 `.next` 目录，互相覆盖。停掉 dev server 再构建，问题就没了。并行 worktree 时更容易碰上：哪个终端里还挂着 dev server，很容易忘。

## 2. 契约测试红了，是它在干活

第一页迁完跑契约测试，两轮一共 9 个失败。乍看像是「配置没对齐」，逐个看下来，**9 个全是真缺陷，没有一个是配置问题**。归成三类。

**多语言文案缺失**。规范要求页头有 4–6 个标签，页面介绍区要有站点支持的每种语言的文案。老页面的文案结构和新框架要的不一样，迁过来时用 `as any` 从旧字段里凑，只凑出 1 个页头标签。介绍区在每种语言下都渲染成硬编码的英文。把各语言的三组文案补齐后，`as any` 清零（项目规范本来就禁用 `any`）。

第二页又碰到一次同类问题：中文页的整张参数卡在走英文兜底。除英文外，每种语言的文案文件里都完全没有参数卡那两组键（按钮名、字段名、历史表头、状态词），各缺 40 多个键。组件缺键时静默回落到英文，测试不报错，页面也不报错，只有切到中文去看才发现。

这类问题靠肉眼一页页切语言太慢。下面这段很短的脚本可以比对每种语言相对英文缺了哪些键：

```ts
// scripts/missing-keys.ts：以 en.json 为准，列出其他语言缺的键
import { readFileSync, readdirSync } from 'node:fs'

type Tree = { [k: string]: string | Tree }
const flat = (t: Tree, p = ''): string[] =>
  Object.entries(t).flatMap(([k, v]) =>
    typeof v === 'string' ? [`${p}${k}`] : flat(v, `${p}${k}.`))

const dir = 'messages'
const load = (f: string) => JSON.parse(readFileSync(`${dir}/${f}`, 'utf8')) as Tree
const base = new Set(flat(load('en.json')))

for (const f of readdirSync(dir).filter((f) => f.endsWith('.json') && f !== 'en.json')) {
  const have = new Set(flat(load(f)))
  const missing = [...base].filter((k) => !have.has(k))
  if (missing.length) console.log(`${f}: 缺 ${missing.length} 个`, missing.slice(0, 5))
}
```

它只回答「键齐不齐」，回答不了「译文有没有丢细节、术语和同类页面是否一致」。后者还得逐条对要点。

**一张 404 的封面图**。页面引用的一篇对比文章，配置里写的封面地址实测返回 404，页面上只是一片空白。同一篇文章各语言版本的 front matter 都声明了另一张图，实测 200。按 front matter 修正。图片、封面、OG 图（社交分享预览图）的地址要实测可达，不能看配置写了就当有。

**三份手工清单没同步**。新页面登记了，契约测试清单漏了一份。这正是契约测试该拦的。

还有一类失败不是这次改动引入的。全量测试里有 5 个支付相关的套件是红的，SEO 冒烟测试里有 7 条失败。这里没有凭感觉说「不是这次引入的」，而是复现了一遍：

```bash
git stash push -u -m before-check   # 把本分支改动连同未跟踪文件收起来
<只跑那几个失败的测试>              # 在主干状态下还是红的，就是存量失败
git stash pop
```

SEO 那 7 条是在一个纯主干的检出上单独构建复现的。两次都确认是主干上本来就红的（实测）。这个做法在那段时间里起了两次作用：一次省掉了排查别人的问题，一次避免把别人的失败写进自己的交付说明。

## 3. 计算器里的「典型值」：精确但虚构

图像页有一个价格计算器。上一版的计算器里有一张表：每个思考档位配一个「典型」token 用量，计算器按它估出思考部分的费用。

问题是这几个数是凭空编的，没有后端实测数据支撑。渲染出来以后，它和真实单价长得一模一样，用户没法分辨哪个数字有结算规则撑着、哪个是猜的。**精确但虚构的数字，比模糊但诚实的说明更危险。**

最后的处理是删掉：计算器只算有结算依据的两项（出图费乘张数、参考图费乘张数），和试用区同一口径；思考档位选择器也一并移除，因为它已经不影响任何数字，留着只会误导；免责说明改写成一句大意：计算器只覆盖能事先算清的部分，其余 token 费用以实际结算为准。

另一次情况正好相反。有个预估数字不随用户的选择变化，验收时被当成了 bug。实测它本来就应该是固定的，修法是在数字旁边加一句「为什么不变」的说明。两件事合起来是一条规则：

- 展示给用户的每个数字，都要能指到来源（结算代码、接口返回、官方文档）；
- 没有来源的字段留空，并加一条测试守着「留空」；
- 不随操作变化的数字，在页面上解释它为什么不变。

## 4. 交付物：一张只列肉眼可判项的卡

验收是我做的。交给我的东西，形态中途改过一次。一开始的思路是「把规范讲清楚」，后来发现让我读完那九百行规范不现实，也没必要：我要的是会验，不是会做。

最后交付的是一个证据包，三样东西：

1. **验收清单卡**（110 行）：只列浏览器里看得见的项，按页面从上到下排，每条后面附规范的节号。机器能判的不重复列。
2. **三栏对照**：老页、新页、范本页的同一区块截图并排放，下面逐条写差异。
3. **机器检查的原始输出**：契约测试和结构差分脚本的结果原样贴上，不转述成「全部通过」。

做三栏对照时有两个细节。

- **范本页要按页型选**。图像页的范本要找一个已验收的图像页，不能照抄清单里写的视频页。不同页型的区块本来就不一样，选错范本，差分全是噪音。
- **「按名字找不到」的老区块要顺着文案键追**。老页面有个区块在新页面里按组件名搜不到，可能是改名了，也可能是内容被删了。在名字对比里这两种情况看起来一样。做法是拿老区块用到的文案键和数据去新代码里搜，找到新落点才算迁过去了；配图、视频、按钮、表格行被去掉的，写进任务卡。

还有一条是当时定下的规矩：**偏离规范的决定，只写在代码注释里等于没写**。偏离要进决策日志，写清楚为什么、等谁拍板。代码注释验收的人看不到，也就没有拍板的机会。

## 5. 两周后的改版：原有控件被按样稿重画了

迁移做完两周，我接了模型列表页的筛选改版：多选标签、热门搜索，筛选逻辑也改了（细节在[模型列表页筛选改版](/blog/frontend/facet-filter-redesign/)）。助手先出样稿，再照样稿写完实现，都「按方案做完了」，机器检查全绿。

leader 看过之后指出了五处问题，我把它转给了助手（转述）：字体和按钮风格和线上略有区别，热门词位置不对，左边分组的展开功能没了，多了几个灰字。助手用脚本把线上和新版并排打开对照，问题比这几句话多（实测）：

- 原来的方形勾选框变成了圆形单选，灰底的计数徽标变成了纯数字，每行还多了彩色图标；
- 分组标题上的展开 / 收起箭头，三个分组里两个没了；
- 新增了几处说明性灰字，标题里还多了当前选择的摘要；
- 新文案用了 12.5px、13px、13.5px 这类页面上原本没有的字号，接口名用了等宽字体；
- 结果栏文案和卡片列数也变了，而这次需求根本没提它们。

**根因**：实现照的是助手自己画的样稿，样稿是脱离站点从零画的。里面的控件是助手「觉得好看」的版本，不是线上的版本。重写组件时没有拿主干上的原组件逐项对照，原有的交互（分组折叠）和视觉（勾选框、徽标）就被一起换掉了。机器检查量的是功能和数据，量不到「和线上长得一样」。

这和迁移时的问题是同一类：检查只覆盖了想到要检查的东西。迁移时漏的是「规范要求但没挂测试的区块」，改版时漏的是「需求没提、但本来就在的控件」。

**修复**分两头。开工前，对每个要动的组件读一遍主干版本，列出原有的交互和样式，写进改动清单，每项默认「保留」：

```bash
git diff origin/<主干>...HEAD -- components/FilterSidebar.tsx   # 已经改了的，看改掉了什么
git show origin/<主干>:components/FilterSidebar.tsx | less        # 还没改的，先读原样
```

交付前，用浏览器脚本打开线上和新版，对同一个控件取计算样式，并排打印：

```ts
// compare-styles.ts：同一选择器在两个地址上的计算样式对照
import { chromium } from 'playwright'

const PROPS = ['font-family', 'font-size', 'font-weight', 'line-height', 'color',
  'background-color', 'border-radius', 'border', 'padding', 'width', 'height']

async function read(url: string, selector: string) {
  const browser = await chromium.launch()
  const page = await browser.newPage({ viewport: { width: 1440, height: 900 } })
  await page.goto(url, { waitUntil: 'networkidle' })
  const out = await page.$eval(selector, (el, props) => {
    const cs = getComputedStyle(el)
    return Object.fromEntries(props.map((p) => [p, cs.getPropertyValue(p)]))
  }, PROPS)
  await browser.close()
  return out
}

const [live, next] = await Promise.all([
  read(process.argv[2], process.argv[4]),
  read(process.argv[3], process.argv[4]),
])
for (const p of PROPS) {
  const mark = live[p] === next[p] ? '  ' : '≠ '
  console.log(`${mark}${p.padEnd(18)} ${live[p].padEnd(28)} ${next[p]}`)
}
```

每一行「≠」都要标上「需求要求」或「改回」。截图比对看得出「不一样」，说不清差在哪个属性；计算样式能直接告诉你是 13.5px 还是 14px。

另外两条小规矩：新增的东西复用页面已有的字号和颜色，不自造档位；新增的说明文字先问一句「没有它用户会不会用错」，答不上来就不加。

## 6. 后续回归：机器读到的日期也属于页面契约

后来一次页面回归补出了另一层：浏览器画面正常，不代表结构化数据符合外部读取方的要求。视频内容的 `uploadDate` 只写日期，与包含完整时间和时区的时间值不是同一份信息。具体字段应按对应规范核，不能用一条「所有日期都补时间」的替换规则处理。

Google 的 [VideoObject 指南](https://developers.google.com/search/docs/appearance/structured-data/video)为该字段提供了带时间与时区的示例，并说明结构化数据的发布、测试和重新抓取步骤。我在这次回归中核的是最终 HTML 的 JSON-LD，逐项比较日期值，而不是只看源码常量或截图。多语言页面也分别检查，避免只改默认语言。

生成物还要单独核：sitemap 的修改日期、页面 JSON-LD 与正文日期可能来自不同来源。一处文案更新，不会让其他生成文件自动跟上；有既定生成器的，应重新生成并看实际差异，保留生成输入与输出的对应关系。

这次目标页取样证明当时的 HTML 已正确，不证明所有边缘缓存都更新；本地生产构建通过，也不证明搜索后台已经清除告警。外部抓取与索引还有自己的进度，最终状态需在相应工具里确认。

同一轮全站检查还暴露了存量脚本只识别一种 API 示例格式的问题。目标日期检查通过，与全站 SEO 检查尚有失败可以同时成立。逐条确认失败读取了什么、前后源码是否变化，再分别报告，不用一个总计数替代归属判断。

## 收尾

1. **worktree 显式写起点** —— 不靠当前 HEAD，建完先看一眼 `log -1`。
2. **共享清单只追加，生成物重跑** —— 冲突时两边都留；生成的注册表合并后重新生成，不手工合。
3. **契约测试红了先当真缺陷看** —— 第一页的 9 个失败全是真缺口；存量失败用 `git stash` 或纯主干构建复现过再下结论。
4. **多语言缺键会静默回落英文** —— 用脚本比对键，再逐语切过去看一遍。
5. **数字要有来源** —— 精确但虚构的数字比模糊的说明危险；不变的数字要解释为什么不变。
6. **交付证据包，不交文档** —— 只列肉眼可判项的卡、三栏对照、机器检查原始输出。
7. **改版默认保留原有控件** —— 动手前读主干版本列清单，交付前并排量计算样式。
8. **成品机器数据逐项核** —— JSON-LD、sitemap 与外部抓取分别取证，不靠画面正常推断。

回头看，这次迁移和两周后的改版，出问题的地方都不在「做了的部分」，而在「没人想到要看的部分」。下次接一个页面任务，我会要求动手前先列两张表：规范要求的区块清单，和页面上本来就有的控件清单。前一张防漏，后一张防改多。
