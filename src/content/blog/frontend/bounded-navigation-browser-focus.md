> 一句话总结：长报告导航要同时控制耗时、可见位移与返回状态；外链是否抢走前台则由浏览器能力和用户设置共同决定，页面应保留原生链接与明确的操作提示。

## 0. 起因：一次从开头滚到末尾的跳转

给长报告加目录以后，内容确实更容易找了。点击章节，页面会平滑滚到目标；再点返回，又滚回刚才的位置。功能上都能到达，看起来也有过渡。

但实际连续使用时，从页面最上方一路穿过大量文字到末尾，过程很机械。我要求助手缩短跳转时间，并强调要考虑人眼看到的运动。随后又发现，正向跳转改了，返回仍用原来的长距离滚动，体验并没有真正统一。

外链也暴露了另一种边界：我希望把资料打开在新标签里，自己继续留在报告。这里的「弹出」并不是页内预览，助手最初理解成了弹窗。澄清以后，问题从页面设计变成了浏览器焦点控制。

这两件事共同说明，导航验收不能只断言「目标存在」或「新页打开」。还要观察读者从哪里出发、看到了什么、最后留在哪里。

## 1. 远跳：缩短时间之外，还要减少掠过的内容

假设从页面开头到某章节相隔很多屏。把整个滚动过程压缩到很短时间，意味着每秒掠过的文字更多。时间变短，并不自动代表视觉运动更轻。

我采用的处理是区分近跳与远跳。近处保留短距离移动，帮助读者理解章节位置；远处先做短暂淡化，在不可见阶段完成主要定位，再在目标附近做少量移动。

这里需要分清三种量：

| 观察量 | 回答的问题 |
|---|---|
| 总耗时 | 用户发出动作后，多久稳定到达目标 |
| 可见位移 | 过渡期间实际看到多少内容移动 |
| 最终位置 | 目标是否清楚、是否被固定导航盖住 |

历史浏览器记录中，桌面与手机的远跳约三分之一秒完成，可见移动限制在目标附近。这个结果只证明当时页面在指定视口下满足了本次目标。它不能证明所有人都不会不适，也不能把某个时长直接当作所有网站的标准。

选择动画参数以前，先决定是否需要动画。对查阅频繁的工具页，直接定位可能已经足够；对需要解释空间关系的近距离切换，适量运动才有清楚的用途。

## 2. 返回：恢复的是阅读状态，不只是一个坐标

正向跳转和返回应该共享同一套定位原则。否则刚才用轻量过渡到达末尾，返回时又滚过全文，读者仍会遇到原来的问题。

长报告还常有折叠章节。如果仅保存 `scrollY`，返回前布局已经变化，同一个数值可能落在另一段。比较可靠的做法，是把需要恢复的展开状态与阅读位置一起考虑，再选择按锚点、相对偏移或坐标定位。

顺序也重要。假如先公开展开全部内容，再重新折叠，最后恢复位置，读者会看到多次跳动。我在这次改动中把状态恢复放到远跳的淡化阶段，布局稳定后再显示目标附近内容。

可以把一次返回想成以下步骤，而不是直接复制成所有项目的实现：

```text
接收返回动作
→ 结束尚未完成的导航
→ 恢复这一条历史对应的折叠状态
→ 等待需要的布局变化完成
→ 定位到原阅读位置
→ 使用与正向一致的显示策略
```

浏览器前进、后退与页面自己的返回按钮，都应进入相同的状态恢复约定。快速连续点击时，还要防止旧动画结束回调覆盖新一条历史。这里检查的是最终稳定状态，不能只看一次慢速操作成功。

## 3. 中断与减少动态效果：操作优先于动画

动画开始以后，用户可能滚动、触摸或点另一个章节。这些是新的意图，原过渡应当让位。如果旧动画继续抢滚动位置，界面会像在和人争夺控制。

历史验收覆盖了滚轮中断、快速再次导航，以及减少动态效果偏好。对于偏好减少动态效果的环境，采用直接定位，避免只是把同一段长距离运动加快。

[`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion) 用来读取设备上的相关偏好。CSS 和 JavaScript 各自实现的运动，都需要纳入处理。只覆盖一个过渡类，脚本仍可能继续执行滚动动画。

下面是独立编写的样式示意，用于说明默认无平滑滚动、仅在没有减少动态效果偏好时启用的思路：

```css
html {
  scroll-behavior: auto;
}

@media (prefers-reduced-motion: no-preference) {
  html {
    scroll-behavior: smooth;
  }
}
```

它没有实现本文的远跳策略；如果脚本自己计算每一帧的位置，仍需在那里读取偏好并取消运动。不要把这几行 CSS 当成完整的无障碍验收。

## 4. 后台新标签：先确认能力归哪一层

我说希望外链打开以后继续留在原页，助手最初准备做页内预览。这是两个完全不同的产品行为：一个仍在当前文档内显示内容，一个需要浏览器创建新的浏览上下文。

进一步验证发现，普通 HTML 调用 `window.open()` 后再请求原窗口 `focus()`，不能可靠保证原页留在前台。`target="_blank"` 也只表达打开新上下文，不承诺它一定处于后台。MDN 的 [`window.open()`](https://developer.mozilla.org/en-US/docs/Web/API/Window/open) 说明了用户设置、原生打开方式及脚本打开的限制。 <!-- check:ok -->

因此先拆成三层：

| 层次 | 可以考虑的控制 |
|---|---|
| 页面 | 提供真实链接、说明是否打开新页，保存本页阅读状态 |
| 浏览器原生操作 | 按平台习惯用修饰键或鼠标操作选择打开方式 |
| 浏览器扩展 | 在获得权限后使用标签管理能力，另行安装与维护 |

当时准备过最小扩展，并在隔离浏览器中验证了后台创建标签。最后我选择不启用，继续使用原生操作。隔离验证成功与日常浏览器已经安装是不同状态，记录时必须分开。

正文可以提供真实 `<a href>`，保留复制链接、右键和修饰键打开能力。若特定场景决定在新页打开，可用明确说明，不必把链接改成只有脚本认识的空地址。

## 5. 焦点测试：先排除工具改变了现象

这轮验证里还有一处值得保留的反例：早期探测得到父页和子页都报告聚焦，不能据此判断哪个标签真的在前台。焦点仿真会使自动化观察失真。

后续检查在有界面的独立 Chrome 中关闭焦点仿真，使用普通单击作对照，再执行真实 Meta 修饰键单击。前者切走前台，后者保留原页的焦点和滚动位置，才有区分行为的证据。

这里的有效范围是当时的 macOS Chrome。其他平台的 Ctrl、鼠标中键或浏览器偏好，需要各自验证。通过脚本构造一个带修饰键字段的事件，也不能直接当成真实输入的等价证据。

这种检查方法比记住某个快捷键更通用：只要被测目标与浏览器窗口、焦点、剪贴板或权限有关，都应先确认测试工具有没有接管或模拟同一件事。

## 6. 导航验收清单：沿完整路径观察

我会用下面的矩阵核长报告导航。数字目标由具体页面确定，保留相同条件下的改前、改后对照：

| 场景 | 至少观察什么 |
|---|---|
| 近距离跳转 | 到达位置、固定顶栏遮挡、是否有多余运动 |
| 跨多屏远跳 | 总耗时、可见位移、淡化后是否清楚定位 |
| 页面返回按钮 | 原阅读位置、折叠状态、返回控件的生命周期 |
| 浏览器前进后退 | 历史位置正确，快速连续操作不被旧回调覆盖 |
| 用户中断 | 滚轮、触摸、新导航能停止旧过渡，无残留遮罩 |
| 减少动态效果 | 直接定位或合适替代，页面与脚本都生效 |
| 外链 | 当前页位置、子页创建、实际前台状态分别记录 |
| 无脚本或加载失败 | 原生链接仍有合理行为，关键内容可访问 |

自动化适合量位置和耗时，目视适合判断过渡是否突兀；二者要针对同一最终页面。不能用脚本配置里的时长，冒充浏览器实际完成时间。

我还会把视觉到达与键盘阅读分开记录：只看到章节出现在视口里，尚未说明接下来的键盘操作会从哪里继续。是否移动焦点、返回后怎样承接，应该按导航方式确定，并用相应输入验证。这次保存的时长与位移结果，不能替代对所有辅助技术的兼容检查。

## 收尾

1. **把位移也列为目标** —— 总时间短，不代表整篇文字快速掠过会更舒服。
2. **返回共享恢复规则** —— 坐标、折叠状态和历史顺序一起决定读者回到哪里。
3. **新的意图优先** —— 用户操作可以中断过渡，减少动态效果偏好需要覆盖脚本。
4. **先判能力归属** —— 页面保留原生导航；后台标签行为按浏览器与平台取证。

以后我会从完整路径评价导航：动作开始、画面变化、最终焦点与阅读状态。能到达目标只是第一步，体验要在这些状态之间一起成立。
