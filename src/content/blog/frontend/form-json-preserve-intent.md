> 一句话总结：表单、JSON 和异步回调每转换一次数据，都可能丢掉一部分用户意图。校验要保留原始输入的证据，控件只改自己负责的内容，异步结果只合并到仍然有效的归属；最后从真实提交入口验证这些约束。

## 0. 起因：一次提示词问题，牵出几种数据丢失

我处理过一个图片生成试用页的问题。页面既有提示词和参数控件，也允许直接编辑 JSON。同一份请求可以从两种入口进入，还能上传参考图、切换操作模式和恢复草稿。

最初的现象很具体：包含空格的负向短语，被控件拆成了几个词。继续排查，又发现调整比例会丢正文，上传完成会回滚新输入，JSON 切回表单会丢蒙版区域。页面有时仍能提交成功，只是实际请求已经偏离了填写内容。

原有测试全部通过。其中两条甚至把错误拆词当成正确预期。这提醒我，已有测试只能证明实现符合那套断言，还需要从页面说明和接口契约核对断言本身。

助手修复这些问题后，又在独立审视中暴露出一个遗漏：统一校验只看最终请求对象，而构造函数已经把非法蒙版省略了。可选字段缺失本来合法，于是错误输入变成了另一种合法操作。

这些问题的共同点是：**一次转换丢掉了下一步作判断所需的信息。** 下面的结论来自本地源码、真实组件回归和失败日志；没有用生产生成结果或账单证明线上效果。

## 1. 编辑文本：解析出的值不足以重建用户原文

解析器通常只关心参数值，编辑器还要保留用户正在输入的文本。两者要求不同。

例如，下面使用一个自拟的提示词格式：

```text
quiet garden
  at sunrise --ratio 4:3 --exclude bright signs, crowded streets
```

比例控件只负责修改 `--ratio`。如果实现先按空白拆词，再把整条提示词拼回来，换行和连续空格会消失；如果负向项同时按逗号和空格拆分，短语含义也会改变。遇到解析器不认识的参数，还可能整段丢弃。

修复时需要区分两件事：读取参数，供控件显示；修改参数，只替换原文里对应的片段。非目标正文、未知参数以及暂时没有值的片段，都应按明确规则保留。

这并不表示不完整文本可以直接提交。编辑阶段允许中间状态，提交阶段再提示用户修正。把两阶段合在一起，会出现另一个问题：用户刚输入的尾随空格或逗号，被解析和回填立即裁掉，下一次按键只能接在前一个词后面。

因此，负向输入框保留自己的编辑草稿，同时明确它与主提示词、重置操作的同步时机。测试也要真的逐字输入空格和逗号。一次性粘贴完整字符串，覆盖不到这个问题。

## 2. 请求校验：缺失和非法必须保留为两种状态

统一请求校验可以减少表单与 JSON 的规则分叉，但有一个前提：构造请求的过程没有提前抹掉错误。

这次蒙版问题的调用链是：

```text
表单中有一份非法蒙版
    → 解析失败
    → 构造函数省略 mask
    → 校验器看到「没有提供可选蒙版」
    → 请求获准提交
```

在这个操作中，未提供蒙版允许进行整图编辑；用户填写了非法蒙版，则应提示修正。两者最终变成同一个缺字段对象，后面的校验器已经无法还原用户意图。

| 原始状态 | 可保留的信息 | 提交时的处理 |
|---|---|---|
| 未填写可选字段 | 用户选择省略 | 按接口的缺省规则处理 |
| 填写了合法值 | 明确的有效参数 | 构造并校验请求 |
| 填写了非法值 | 用户想设置该字段，但内容无效 | 报错并阻止提交 |

原实现把「未提供」和「非法」都可能解析成空值，再由构造函数决定省略。修复后保留了原始蒙版检查，并与共享请求校验共同决定能否提交。

更通用的接口设计，是让解析结果明确区分「未提供」「有效」「非法」。如果函数只返回一个对象或空值，调用者需要另有办法区分缺省与错误，否则很容易把错误当成默认值。

边界也要保留：用户确实删除了可选蒙版，就应清除旧状态。不能为了防止非法值被丢弃，又从旧表单中把已经删除的值恢复回来。

## 3. 模式往返：先判断表单能否完整表达 JSON

JSON 编辑器能表达的结构，往往比表单丰富。例如接口支持多块区域和更多顶点，而当前表单只有一块固定顶点的区域。

如果切换时只取第一块区域，或者截取表单认识的部分，界面可能正常显示，下一次提交却已经丢数据。这里需要核对的是两种表示之间的表达能力。

这次采用的处理是：能完整表达的 JSON 可以切回表单；存在多区域、额外顶点或其他无法保留的结构时，保留原 JSON，并提示继续在 JSON 中编辑。表单暂时不支持某种结构，不应被解释成接口也不支持。

转换还要检查这些细节：

- JSON 中删除的可选字段，回表单后仍然保持缺失。
- 重复点击当前 JSON 标签，保留编辑器原文。
- 未识别但允许保留的字段，不因重新生成对象而消失。
- 判断兼容性时，以当前实际操作入口为准。
- 源图尺寸尚未就绪时，避免生成一份缺少必要结构的自动请求。

估价、冲突检查和提交也要读取同一套有效参数规则。这次发现，大小写和顶层、嵌套字段的优先级若各自处理，界面会按一种配置估价，实际请求却按另一种配置执行。

共用有效值的读取规则，可以减少分歧；字段类型错误仍需明确报出。只有契约允许的缺省值，才能进入回退逻辑。

## 4. 异步结果：保留归属，再合并本次增量

上传是另一种信息转换。开始时捕获了一份状态，完成时页面可能已经发生变化。直接把旧提示词加上新图片地址后整段写回，会覆盖等待期间的新输入。

改成读取最新状态，也还需要回答：这个最新状态属于哪个模式？如果上传开始于 A，用户已经切到 B，读取当前表单就会把结果写错地方。

这次需要同时保留三类信息：发起模式、该模式的重置代际、登录会话代际。完成时先判断旧结果是否仍有资格写入，再把本次新增素材合并到发起模式的最新内容。

```text
开始上传
    → 捕获发起模式和有效代际
    → 等待完成
    → 核对重置及会话是否仍有效
    → 读取发起模式的最新状态
    → 只合并本次上传增量
```

这里只保存模式名称还不够。A→B→A 后，A 已经可能有新编辑；退出后重新登录同一账号，账号标识虽然相同，也已进入新的会话。重置和会话代际用于区分这些情况。

JSON 暂时无效时，还要保留恢复路径。上传完成后不能覆盖原文，也不能只把结果藏在内存里。本次增加了可见的待合并地址和操作入口，让用户修正 JSON 后再显式合并，并保留其他手改字段。

异步归属的基本方法见[一个 await 就是一道缝](/blog/frontend/async-seam-url-variant/)。这里多了一层编辑器要求：结果有效，还要让用户能够找回并使用它。

## 5. 回归测试：从真实入口数提交次数

纯函数可以证明解析和构造规则，组件测试还要证明用户操作能经过这些规则。

非法蒙版的回归用例从真实表单控件进入：先加载合法编辑参数，再把蒙版基准宽度改成非法值，最后点击生成。失败日志显示，修复前调用了一次测试中的生成服务桩，而且请求体没有蒙版。这个结果把问题定位在构造与校验的组合上。

修复后的关键预期有两条：显示蒙版错误，生成调用次数为零。只检查错误文字还不够，因为界面报错和请求已经发出可能同时发生。

| 要守住的行为 | 操作顺序 | 主要断言 |
|---|---|---|
| 逐字编辑不吞分隔符 | 输入短语、空格、逗号 | 输入框保留实际文本 |
| 上传不覆盖新内容 | 开始上传、继续编辑、再完成上传 | 新文字与新增素材同时保留 |
| 返回原模式仍保留新编辑 | A 上传、切 B、回 A、增删素材、完成 | 新内容保留，已删素材不复活 |
| 重置使旧上传失效 | 上传、重置、输入新内容、完成 | 旧结果不再写入 |
| 非法可选值不能变成缺省 | 填入非法值、点击提交 | 提示正确，提交次数为零 |
| 不支持的转换保留原文 | 填入复杂 JSON、切表单 | 转换被提示阻止，原文仍在 |

延迟上传用可控制完成时机的 Promise，按操作顺序推进。关键回归再放回旧实现，或只恢复一处缺陷，确认目标断言会因预期原因失败。模块加载错误或无关断言提前退出，都不能充当检出证明。

这次并非初始覆盖就完整。助手统一校验时遗漏了原始蒙版防线，独立审视发现后才补齐；上传恢复入口的中间源码也未保存，因此只保留最终行为的验证结论，不补写不存在的历史红绿证据。

## 6. 合入前的追加修改：保真之后还要分清校验哪一层

这批修复合入前，leader 在我推送的版本上又追加了两次修改。后来做回归时，我把自己最后推送的版本和合入版本逐文件对比，再用 blame 区分哪些行是基线旧行、哪些是这次新写的。

leader 保留了原文区间编辑、模式归属与代际保护、表单和 JSON 共用校验，另外补了几处边界。它们都属于助手原实现和测试覆盖的遗漏。下面按三个问题整理。

### 原文和发送值：两种长度，两种口径

**现象**：第 1 节保住了换行和连续空格，校验正文长度时却仍直接数编辑器原文。新加的严格校验还会把「参数在前、正文在后」的写法判成缺少描述，例如用自拟格式写的 `--size 2 a cat`。

**根因**：同一个解析结果被拿去回答两种问题。保真回答「用户写了什么」，限长和「有没有描述」回答「最终发出去的正文是什么」。保留格式以后，原文里多出的空白和参数都被算进了正文。

**修复**：leader 先按发送端的规范化规则剥掉已知参数，压缩空白，再判断缺描述和正文限长。原文自身的长度上限仍按原文计算。

| 限制 | 约束对象 | 计算前的处理 |
|---|---|---|
| 输入框长度上限 | 编辑原文 | 不处理，按原文计数 |
| 是否缺少描述 | 发送正文 | 剥掉已知参数，压缩空白 |
| 正文长度上限 | 发送正文 | 同上 |

拒绝规则还要配一个形似合法的反例。输入法常把两个连字符自动改成破折号，原规则于是把所有「破折号加单词」都当成写错的参数。修改后只识别已知参数名，普通的 `—beautiful` 照常通过。

同一轮还补了几条漏拦：几个开关类参数、非数字的参数值，以及某类参数后面的描述。最后一项是基线旧问题：解析器把这类参数后面的正文也当成参数值，删除参数时会连描述一起删掉。助手的修复没有补齐它。

共享校验也会放大旧规则。某个操作对一种图片格式的界面限制原本只在旧入口生效，助手把它搬进了共享校验，所有入口都开始误拦。leader 依据当前成功调用的证据撤掉了这条限制。这只说明那一种格式可用，不能推断所有格式都已验证。

复盘时我在两个固定版本上跑了 9 个纯函数样本的前后对照，覆盖参数前置、空白计数、普通破折号、引用参数后的描述等情况。同一条测试命令下，合入版比我的版本多出 12 个用例。更早阶段的用例总数覆盖范围不同，不能拿来直接相减。

### 迟到上传：同一字段的每种合法写法

第 4 节保证了上传结果回到发起模式的最新内容。合并函数本身却只认一种写法：数组形式的源图列表。请求层其实还接受单数字段，以及字符串形式的复数字段。下面用自拟字段名表示：

```json
{ "source_urls": ["https://example.com/a.png"] }
{ "source_urls": "https://example.com/a.png" }
{ "source_url": "https://example.com/a.png" }
```

用户在上传期间手改 JSON，用了后两种写法中的一种。上传完成后，合并函数看不到这张源图，可能覆盖它，也可能留下两个并存的别名字段。

leader 的改法是复用请求层已有的读取函数，统一写回数组，再移除别名。已有的手写源图优先，迟到的上传结果不覆盖它。立即合并和第 4 节的待合并入口也改成共用同一条路径。

这条补充说明：结果写到了正确的归属，还要保留这个归属里最新输入的含义。已有读取函数时，不要在上传回调里另写一套简化解释。

### 切换模式：回写发起档，还是切换即丢弃

回归时拿到的验收清单是转述来的。其中一条可以读成「切换模式就丢弃上传」。原始需求和实际实现是另一种口径：

| 口径 | A 发起上传，切到 B 后完成 | 重置或退出登录 |
|---|---|---|
| 原始需求与实现 | 合并进 A 的最新草稿，B 不变 | 旧结果作废 |
| 转述清单的一种读法 | 结果丢弃 | 旧结果作废 |

在真实页面里延迟一次上传，观察到的是回写 A。助手把这一条作为口径差异写进验收结论，没有写成「转述清单全部通过」。

两种口径都可能合理，取决于产品想让用户怎样理解模式。验收前要先写下依据：哪条需求定了回写或作废。用例按依据写，而不是按记忆或转述写。这个案例也不说明所有产品都应该回写发起档。

把三处合起来，下次我会追问：

- 这条限制约束的是原文，还是发送值？
- 保留原文以后，计数的含义是否悄悄变了？
- 每条拒绝规则有没有一个形似合法的反例？
- 同一个字段在上传、模式切换、草稿恢复里，是否由同一段代码解释？
- 切走以后回写还是作废，依据是哪条需求？

## 7. 交付证据：让每个通过结论都有范围

本地组件回归可以控制上传顺序、登录变化和错误输入。浏览器走查可以观察逐字输入、桌面和手机布局，以及无效操作是否发出请求。两类证据互补，记录时要写清各自实际执行了什么。

本次浏览器使用了真实页面组件，但网络和身份是本地夹具。上传乱序主要由组件测试覆盖，不能写成真实浏览器上传已经验证；前端估价正确，也不能据此认定生产扣费已验证。

构建证据同样要绑定版本。完整预渲染构建完成之后，又补了一处蒙版守卫。最终候选执行了生产编译和相关回归，记录中分别保留两者范围，避免把较早版本的完整构建说成最终版本重新全跑。

下次我会在改动前先列出数据转换链，再为每一处写清：输入有哪些状态、转换会丢什么、谁负责报错、失败后允许哪些副作用。这样更容易在重构共享校验时保留旧入口的必要防线。

## 收尾

编辑器的可靠性，取决于每一步是否保住了后续判断所需的信息。原文要能保留，缺省与非法要能区分，模式转换要核表达能力，异步写回要核归属和资格。

我下次检查双模式页面，会先沿着「输入 → 转换 → 校验 → 提交」追一遍，再用延迟结果和非法可选值验证边界。测试通过之后，还要能指出：原缺陷恢复时，究竟哪一条内容或提交次数断言会失败。

合入前的追加修改又补了一条：保真和校验要分层。每条限制先标出约束原文还是发送值，同一字段的每种合法写法都走同一个读取函数；模式切换后回写还是作废，先找到需求依据，再写验收用例。
