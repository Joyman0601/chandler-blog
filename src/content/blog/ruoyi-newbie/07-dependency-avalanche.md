> 系列第七篇，时间上最近的一次经历。我同步了一次主分支后，**编译、启动、联调接连崩**，一连串看似无关的报错砸过来。这篇按它们出现的顺序逐个拆解——它们其实是同一个动作（一次全量重构）引出的连锁反应。

## 起因：同步主分支

主分支合并进来了一大批新代码（新增了好几个子模块、新增了若干依赖、还改了一些配置）。新代码逼着我**必须重新全量构建**。问题就是从「重新构建」这个动作开始爆发的——而且每个症状都长得不像「构建问题」。

下面五个坑，是我那天按顺序踩过来的。

## 坑 1：服务起不来，Nacos 连接超时（gRPC 9848）

**现象：** 启动服务，刷屏报错：

```
Server check fail, please check server 127.0.0.1, port 9848 is available
UNAVAILABLE: io exception
```

`9848` 是 Nacos 的 gRPC 端口（Nacos 2.x 在 HTTP 端口基础上 +1000 用作 gRPC）。

**排查：** 先看本地 Nacos 到底在哪个端口。一查发现——本地 Nacos 跑在**非标准端口**上（HTTP 是个加了前缀的端口，gRPC 相应也不是 9848）。也就是说：**服务去连的 9848，根本没有 Nacos 在听。**

**根因：** Maven **profile 不匹配**。这套工程有两个 profile：

| profile | Nacos 地址 | gRPC 端口 |
|---|---|---|
| `dev`（默认） | 指向本地实际在跑的那个非标准端口 | 匹配 ✅ |
| `prod` | 指向标准 `...:8848` | → 9848 ❌（本地没有） |

报错连的是 `9848`，说明这个服务是**用 `prod` profile 构建的**。本地只有 `dev` 的 Nacos 在跑，于是去连一个不存在的 9848。

**怎么确认：** 看构建产物里被替换后的实际配置。脚手架的 `application.yml` 里 Nacos 地址是个占位符（`@nacos.server@`），**构建时**才被 profile 的值替换。直接看编译出来的那份：

```bash
grep "server-addr" 某模块/target/classes/application.yml
# 输出 127.0.0.1:8848  →  实锤是 prod 构建出来的
```

**解决：** 用 `dev` profile **重新构建**。关键认知：

> 占位符是**构建时**替换的。**prod 打出来的包，没法在运行时指向 dev 的 Nacos**——必须重新构建，不是改个启动参数能解决的。

```bash
mvn clean package   # dev 是默认 profile，别带 -P prod
```

IDE 里则要检查 Maven 面板的 Profiles 有没有误勾 `prod`，勾回 `dev` 后刷新、重新编译。

> **经验：** 「连不上 Nacos / 配置不对」时，**先看构建产物里被替换后的实际值**，再倒推是哪个 profile 构建的。占位符类配置的问题，根源往往在构建阶段而非运行阶段。

## 坑 2：编译报「程序包不存在」

**现象：** 单独构建网关模块，报：

```
java: 程序包 org.dromara.common.mybatis.core.domain 不存在
```

**排查：** 先确认这个包是不是真没了——结果**包好好地在 `common-mybatis` 模块里**。所以不是代码缺失。

**根因：** 我之前为了让新代码生效跑了 `mvn clean`，把本地仓库/`target` 里 **公共模块的产物清掉了**。然后我**单独**构建网关、没带 `-am`，Maven 在本地仓库找不到 `common-mybatis` 的产物，编译到依赖它的代码时就报「包不存在」。

**解决（任选）：**

```bash
# 方案 A：单模块构建时带 -am，自动把上游依赖一起构建
mvn clean package -pl ruoyi-gateway -am -DskipTests

# 方案 B：先在根目录把所有模块装进本地仓库，之后单独构建任意模块都不缺
mvn clean install -DskipTests
```

> **经验：** 多模块工程里，**单独构建某个模块前，它依赖的上游模块必须已经在本地仓库里**。刚跑过 `mvn clean` 之后尤其要注意——要么用 `-am`，要么先 `install` 一遍。「程序包不存在」但包明明存在 = 上游没编译/没安装，不是代码问题。

## 坑 3：IDEA「命令行过长」

**现象：** 在 IDE 里运行启动类，报：

```
运行 XxxApplication 时出错。命令行过长。
```

之前一直能跑，偏偏现在不行。

**根因：** 这是 Windows 的命令行长度上限（约 32KB）。IDE 启动 Java 程序时拼的命令大致是：

```
java [JVM参数] -classpath "<几百个 jar 的绝对路径，用 ; 拼接>" 主类
```

依赖一多，`-classpath` 那一长串就超长。我刚 `mvn install` 完，加上主分支新增的依赖，classpath 字符串**正好越过了 32KB 这条线**——所以是「之前能跑、现在不行」。

**解决：** 改 IDEA 运行配置的 **Shorten command line** 选项，选 **`JAR manifest`**。

它的原理很巧妙：IDE 生成一个**临时的空 jar**，把那一长串依赖路径写进这个 jar 的 `META-INF/MANIFEST.MF` 的 `Class-Path` 属性里，启动命令只引用这**一个** jar：

```
java [JVM参数] -classpath "C:\...\Temp\classpath123.jar" 主类
```

JVM 加载这个 jar 时会自动读 manifest 里的 `Class-Path`。于是命令行长度从几万字符骤降到几百。

> **经验：** 「命令行过长」是依赖膨胀的信号，和代码无关。在运行配置（或配置模板）里把 **Shorten command line 设为 `JAR manifest`** 一劳永逸，所有启动配置都不再犯。

## 坑 4：端口被悄悄改了——前端联调全超时

服务终于起来了，但**前端联调全部超时**（`ETIMEDOUT`）。明明合并前还好好的。

**排查：** 看服务启动日志里它**实际注册/监听的端口**——发现网关监听的不是我印象里的端口，而是一个**加了前缀的新端口**！再查 git，合并进来的提交里赫然有一条提交信息就叫「**端口修改**」：

```diff
# 网关 application.yml
-  port: 8085
+  port: 58085      # 所有服务的端口都加了 "5" 前缀
```

**根因：** 主分支这次合并，**把全部服务的端口都改了**（统一加前缀，为了适配部署环境的端口规划）。我之前能联调，是因为那时还是旧端口；合并后端口变了，前端代理还指着旧端口，自然全超时。

> **经验：** 「合并后突然连不上」要**回去看合并带进来的 commit 改了什么**——尤其是 `application.yml` / 配置类的改动。一条「端口修改」的提交，足以让整条联调链路断掉。`git show <commit> -- '**/application.yml'` 几秒钟就能定位。

## 坑 5：前端代理目标，端口和地址都不对

承接坑 4，前端那边的报错是：

```
[vite] http proxy error: /xxx/getInfo
Error: connect ETIMEDOUT 192.168.x.x:8085
```

**两个问题叠加：**

1. **端口错**：前端代理指向旧端口 `8085`，但网关已经改到新端口了 → 那个端口上根本没服务。
2. **地址可疑**：前端代理的主机 IP 是本机一块**虚拟网卡（WSL/虚拟机网卡）的地址**，不是 `localhost`——多半是某次自动探测选错了网卡留下的。

> 一个有用的判断：那个 IP **能 ping 通**（主机可达），但端口连接**超时**而不是 refused。端口没服务通常该是「拒绝连接」，而这里是「超时」——因为防火墙对「没人监听的端口」往往直接丢包，表现为 timeout。**ping 通 ≠ 服务在**。

**怎么定位服务真实端口：**

```bash
netstat -ano | findstr ":58085"
# TCP  0.0.0.0:58085  ...  LISTENING   <PID>   ← 服务真在这个端口、且绑 0.0.0.0
```

绑 `0.0.0.0` 意味着所有网卡都能访问，所以其实「只把端口改对」就能先通；但规范做法是地址用 `localhost`、端口用新值。

**解决：** 前端代理目标改成 `http://localhost:58085`（新端口），重启前端。

> **额外认知（呼应第 01 篇）：** 前端**只需要改网关那一个端口**。后面各业务模块的端口也都变了，但前端**完全不用管**——因为前端只跟网关通信，网关靠**服务名**而不是写死端口去找后端模块。这就是网关架构省心的地方。

## 复盘：五个坑其实是一根藤上的

把这天的经历串起来看，**没有一个是「主分支代码引入了依赖冲突」**，它们全是「一次被迫的全量重构」连带暴露出来的：

```
同步主分支（新代码 + 新依赖 + 改了端口）
        │
        ├─ 逼我重新全量构建
        │     ├─ 构建时选了 prod profile   → 坑1：连 9848 失败
        │     ├─ clean 后单模块构建没带 -am → 坑2：包不存在
        │     └─ install 后依赖变多          → 坑3：命令行过长
        │
        └─ 改了端口
              ├─ 服务监听新端口             → 坑4：前端旧端口超时
              └─ 前端代理目标过时           → 坑5：端口+IP 都不对
```

这些坑平时「增量编译、配置不变」时根本不显现，是同步主分支这一下**把它们一次性全勾了出来**。

**最稳的收尾动作：** 在根目录用默认（dev）profile 跑一次完整构建，把所有模块装进本地仓库，再配合 IDE 的 `JAR manifest`：

```bash
mvn clean install -DskipTests   # 别带 -P prod
```

## 小结

- 「同步分支后一堆问题」往往不是分支代码有冲突，而是**它触发了一次完整重构，暴露了本就存在的环境/构建问题**；
- profile 污染、缺 `-am`、classpath 膨胀，这三个是多模块 + 配置中心工程的高频构建坑；
- 「连不上」类问题，**先确认对端真实在哪个端口/地址**（`netstat`、启动日志），再回头看是不是配置/合并改动导致的；
- 排查链路问题要有「分层」意识：构建层（profile/依赖）→ 启动层（端口/Nacos）→ 联调层（前端代理）。逐层定位，别在表象上打转。
