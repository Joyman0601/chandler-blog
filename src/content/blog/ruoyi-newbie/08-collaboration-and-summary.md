> 系列最后一篇。前面讲的都是「技术上怎么填坑」，这篇讲「人和人之间怎么不互相挖坑」——接口文档口径、权限命名、和带教协作的边界，最后做一次整体复盘。

## 一、接口文档：口径不统一，比没文档还糟

我一开始写接口文档，沿用了某个旧项目的风格，结果被带教指出和框架/团队口径不符。差异集中在这些点：

| 维度 | 我最初写的（旧风格） | 团队/框架的正确口径 |
|---|---|---|
| 成功响应码 | `code: 0` | `code: 200`（框架 `R.SUCCESS = 200`） |
| 分页参数 | `pageNo` | `pageNum` / `pageSize`（框架 `PageQuery`） |
| 时间范围 | 自定义的时间数组 | `params[beginTime]` / `params[endTime]`（基类 `BaseEntity` 的 `params` Map） |
| URL 格式 | 无版本号 | 带版本号，如 `/biz/<资源>/v0.1/<action>` |
| 写操作返回 | 自定义 | `data: null`（`toAjax` 返回 `R<Void>`） |

**关键认知：接口文档不是「我觉得怎么清晰」，而是要「和框架实际序列化出来的结构一致」。** 比如列表响应，框架实际吐出来的是 `R<TableDataInfo>` 的嵌套结构，文档就得照着它写，而不是凭感觉简化。

> **经验：** 进一个有框架的团队，**接口文档要以「框架默认行为 + 团队既有样板」为基准**，而不是带着上个项目的习惯。定文档口径时，最高优先级是「和能跑通的真实响应对齐」，而不是个人审美。这件事越早对齐越省事，否则前端按错文档对接，返工的是两边。

## 二、权限串命名：一个字都不能错

框架用 `@SaCheckPermission("xxx:yyy:zzz")` 做按钮级权限校验。这里有几个新人必踩的认知点：

**1. 权限串前缀要和团队约定一致。** 我这个模块统一用某个固定前缀（如 `biz:`），格式 `前缀:资源:动作`，对齐带教定的范例。不能自己另起一个前缀。

**2. 「功能权限」和「数据权限」是两套，别混。**
- `@SaCheckPermission` 校验的是**按钮/功能权限**（对应菜单表里 `menu_type=F` 的行）；
- 数据权限是**另一套**注解（`@DataPermission` / `@DataColumn`），控制「能看哪些行」。

**3. 菜单表是和别人共享的，改动要克制。**
- 菜单表里的 **C（菜单）级**记录是前端为页面显示建的，归前端/带教管，**我不要动**；
- 我只负责往对应菜单下挂 **F（按钮）级**权限，且 F 的权限串**必须和 Controller 注解一字不差**；
- 因为菜单表在共享库里，插记录要**只增不撞**，且等命名敲定后再插。

**4. 权限串前缀 ≠ URL 路径前缀。** 权限串（鉴权用）和 URL 前缀（前端调接口用）是两回事，改一个不影响另一个。新人很容易把它们当成一个东西。

> **经验：** 在共享数据库 + 多人协作下，**「哪些是我能改的、哪些是别人的地盘」要划清楚**。权限/菜单这种全局共享的东西，遵循「只增不撞、命名先对齐、改动最小化」。

## 三、和带教协作的边界

整个过程里，「我负责什么、带教负责什么」这条线，决定了很多技术决策：

- **部署边界**：我只负责打包部署自己的业务模块；其它模块（如系统模块）由带教在测试环境部署。**这条边界直接导致了第 03 篇那个 Dubbo 大坑**——我以为「部署我自己的就行」，但我改了公共契约，结果实现方没更新就崩了。
  > 引申出的原则：**部署边界 = 你能独立交付的范围。一旦改动越过了这条边界（动了公共契约/别人的模块），就不再是「我自己能搞定」的事，必须协调。**

- **自给自足优先**：能用现有的公共能力拼出需求，就别去改公共模块。**减少跨人协调，就是减少出错面。**

- **共享资源只增不删**：共享的业务库、菜单表、字典，DDL 一律只增不删，改之前先确认不会影响对方。

## 四、整个过程的复盘

回头看这段从零接手模块的经历，真正的难点几乎都**不在「写业务逻辑」**，而在周边：

| 难点类别 | 占用我的精力 | 典型代表 |
|---|---|---|
| 环境 / 配置 | ★★★★ | Nacos 命名空间、profile、启动顺序 |
| 构建 / 部署 | ★★★★ | `-am`、classpath、跨模块 Dubbo 部署 |
| 前后端边界 | ★★★ | 雪花 ID 精度、字典两套机制 |
| 协作 / 规范 | ★★★ | 接口文档口径、权限串、共享库边界 |
| 纯业务逻辑 | ★★ | CRUD、全量覆盖、聚合查询 |

如果让我给「即将接手类似项目的新人」提炼几条最有用的心法：

### 1. 报错的字面意思常常会骗你
- `403「没有访问权限」` 可能是加密开关、可能是网关转发、可能才是真没权限；
- `连不上 9848` 的根因在「构建用错了 profile」；
- `程序包不存在` 的根因是「上游模块没编译」。

**先定位「这个症状归哪一层管」，再动手**，别顺着字面去查。

### 2. 配置中心 + 多模块，意味着「真相分散在很多地方」
本地 `application.yml`、Nacos 配置、网关路由、profile、本地仓库的 jar……任何一处错位都会以「不像它的样子」的报错出现。养成习惯：**看构建产物的实际值、看启动日志的实际端口、看 Network 的实际请求**——以「实际是什么」为准，别凭印象。

### 3. 跨边界的东西，两边的理解必须一致
- ID 跨「后端 Long / 前端 JS Number」边界 → 约定「永远是字符串」；
- 方法跨「consumer / provider」边界 → 签名一字不差、两端一起部署；
- 字段跨「导出 / 导入」边界 → 对称处理，别只做一头。

**几乎所有最难缠的 bug，都发生在两个系统/语言/人的交界处。**

### 4. 顺着框架走，但要知道它的魔法边界
框架帮你做了多租户过滤、ID 序列化、字典翻译、分页……**用它、别重复造**；但也要知道**每个魔法在哪生效**（翻译只在序列化时、租户只在拦截器、占位符只在构建时），用错地方就会踩坑。

### 5. 留痕：给「为什么这样」留记录
占位 `0` 的设计、暂未实现的接口骨架、待回填的字段……这些「现在故意这样、将来要补」的决定，如果不写下来，后来人（包括三个月后的自己）会当成 bug 去查。**代码说明「是什么」，注释/文档/团队记忆说明「为什么」。**

## 结语

从「第一次启动就 `Unknown database`」到「能独立交付一个模块」，这条路上 80% 的时间花在了和业务无关的地方：环境、构建、配置、协作。这不是浪费——**这些「周边能力」才是微服务工程师和「会写 CRUD 的人」之间真正的区别。**

如果这个系列能让你在某个类似的坑前少卡几个小时，它就值了。
