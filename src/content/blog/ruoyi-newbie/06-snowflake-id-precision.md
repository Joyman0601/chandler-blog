> 系列第六篇。一个独立成篇的经典 bug：**列表查得到、详情查不到**。它让我先后误判了两次，最后发现根因根本不在后端。这类「前后端类型边界」的坑，值得每个全栈/后端新人记一辈子。

## 现象

- 列表接口正常，数据一行行都在；
- 点某条记录看详情 / 调 `getInfo`，**返回 null**，像是这条数据不存在；
- 但它明明在列表里。

## 两次误判

排查这个 bug，我走了两次弯路，把它们写出来，因为**误判的过程本身就是教训**：

1. **第一次**：以为是数据缺失或多租户过滤把它挡了。去查库、查租户条件——数据好好的，租户也对。
2. **第二次**：以为是后端没把 ID 序列化成字符串，前端拿到的是数字。去翻序列化配置——结果发现**后端该做的都做了**（详见下文）。

两次都扑空后才意识到：**问题发生在「前端发请求之前」，后端再怎么改都没用。**

## 根因：19 位雪花 ID > JS 的安全整数上限

主键用的是**雪花算法 ID**，19 位长整数，比如：

```
1234567890123456789
```

而 JavaScript 的 `Number` 是 IEEE 754 双精度浮点，能精确表示的最大整数是：

```
Number.MAX_SAFE_INTEGER = 9007199254740991   （2^53 - 1，只有 16 位）
```

**19 位的雪花 ID 远超这个上限。** 一旦前端把这个 ID 当成 `Number` 处理（哪怕只是 `JSON.parse` 后读了一下、或 `Number(id)`、`parseInt(id)`），**末几位就会被静默改写**，通常末位变成偶数：

```
真实： ...3456789
前端处理后： ...3456788   ← 末位被改了
```

于是前端拿着这个**被篡改过的 ID** 去请求详情，后端按它查库，自然查不到 → 返回 null。

## 怎么坐实是「精度丢失」而不是别的

这是这篇最有用的部分——**怎么快速确认就是这个原因**：

1. **看浏览器 Network**：详情请求里的 `id=...`，把它和列表里那条记录的**真实 id** 逐位对比。如果末位被改成了偶数、和库里对不上，基本就是它。
2. **连库二次确认**：
   ```sql
   SELECT count(*) FROM biz_asset WHERE id = <列表里的真实ID>;   -- 1 条
   SELECT count(*) FROM biz_asset WHERE id = <请求里的可疑ID>;   -- 0 条
   ```
   真实 ID 查得到、可疑 ID 查不到 → 实锤是前端把 ID 改了。

> **排查口诀：** 「列表有数据、详情 / getInfo 返回 null」→ **第一怀疑对象就是前端 ID 精度丢失**，而不是数据缺失或后端 bug。

## 后端其实已经尽力了

值得说清楚：**后端在这件事上能做的，框架早就做了：**

- 框架的 `BigNumberSerializer` 会把「超过 `MAX_SAFE_INTEGER` 的 `Long`」自动**序列化成字符串**返回；
- VO 上往往还加了 `@JsonSerialize(using = ToStringSerializer.class)` 做双保险。

也就是说，**后端返回给前端的 ID 本来就是字符串**。问题在于前端拿到字符串后，**自己又把它转成了 Number**（或者路由参数按数字解析），在「发请求前」就把 ID 弄坏了。后端无力回天。

> 顺带解释一个现象：为什么有的页面（比如另一个模块）不受影响？纯属那个页面**恰好全程把 ID 当字符串处理**，没碰过 `Number()`，所以躲过一劫。这进一步说明：**根因在前端怎么处理 ID。**

## 解决

后端无需再改（序列化已到位），修复在前端：

> **前端必须全程把 ID 当字符串处理：**
> - 不要 `Number(id)` / `parseInt(id)`；
> - 路由参数、查询参数里的 ID 按 `string` 取；
> - 如果用了会把大整数转 Number 的 JSON 解析方式，要换成保留字符串的处理（或后端始终以字符串下发，前端不再转换）。

## 引申：long ID 与前端的「天然不兼容」

这不是某个框架的 bug，而是 **JS 数字精度的固有限制 + 后端用了大整数主键** 撞在一起。任何「后端 long 主键 / 雪花 ID + JS 前端」的系统都会遇到。通用的根治方向有两类：

1. **传输层始终用字符串**：所有超过 2^53 的整数，后端一律序列化成字符串，前端约定「ID 永远是 string」。（本项目走的就是这条，只是前端没贯彻到底。）
2. **前端用 BigInt / 专门的大数库** 处理这类值（成本更高，一般没必要）。

> **经验：** 团队里只要用雪花 ID，就应该立一条铁律：**「ID 在前端永远是字符串，任何地方都不许把它当数字」**，并在联调初期就对齐。否则这个 bug 会在不同页面、不同人手上反复出现。

## 小结

- 现象「列表有、详情无」，**先怀疑前端 ID 精度**，别一头扎进后端；
- 根因：19 位雪花 ID 超过 JS `MAX_SAFE_INTEGER`，前端当数字处理就被静默改写；
- 后端该做的（字符串序列化）通常框架已做好，**真正的修复点在前端「不要把 ID 转数字」**；
- 这是「前后端类型边界」的典型问题——**一个值跨越语言/运行时边界时，两边对它的类型理解必须一致**。
