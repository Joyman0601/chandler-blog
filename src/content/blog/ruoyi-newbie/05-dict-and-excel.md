> 系列第五篇，也是「同一类问题反复炸我」最密集的一篇。枚举字段的展示、下拉、导入、导出，看着都是小功能，背后却有两套字典机制和一堆类型陷阱。每个坑我都付过学费。

## 一、字典翻译有两套机制，先分清你用的是哪套

「把编码 `1` 显示成中文『类型A』」这件事，RuoYi 里有**两种完全不同的实现**，行为差异巨大：

| 机制 | 怎么写 | 依赖数据库字典表? |
|---|---|---|
| **内联表达式** | `@ExcelDictFormat(readConverterExp = "1=类型A,2=类型B")` | ❌ 映射写死在注解里，自包含 |
| **DB 字典** | `@ExcelDictFormat(dictType="biz_asset_type")` / 前端 `<dict-tag>` / 后端 `@Translation(type=DICT)` | ✅ 库里必须有对应的 `sys_dict_data` |

这两套最大的区别是**对数据库的依赖**：

- **内联表达式**：映射就在代码里，**换任何环境都不用灌字典**。列表、导出照常工作。
- **DB 字典**：每个环境的数据库里都**必须有对应字典数据**，否则前端下拉是空的、翻译出来也是空的。

### 它怎么坑我的

资产主表的几个枚举（类型、状态等）走的是**内联表达式**。所以哪怕联调库、测试库都没灌对应字典，列表/导出/导入照样正常——我曾一度误判「字典缺了肯定要出问题」，跑去排查半天，其实根本不影响。

而附属设备的「数据来源」字段走的是 **DB 字典**，它的字典数据就**必须在每个库都存在**，否则前端下拉空白。

> **排查口诀：** 遇到「枚举显示成数字 / 下拉是空的」，先确认这个字段走哪套——
> - **内联** → 看注解里的映射表达式对不对；
> - **DB 字典** → 看库里那条字典数据在不在。
>
> **设计取舍：** 前端要**下拉选择**的字段，必须走 DB 字典（内联给不了下拉数据源）；纯列表/导出展示的，用内联更省事（免去每个环境灌字典的依赖）。

## 二、`char(1)` vs `tinyint`：枚举字段的类型约定

这套框架对「类型/状态/是否X」这类字典枚举，有个惯例：**用 `char(1)`，Java 侧用 `String`**（参考框架自带的 `sys_user.status`、`sex` 都是 `char(1)`）。

于是我把资产、设备的枚举字段统一成 `char(1)` / `String`。**但有个故意的例外**：「数据来源」字段保留 `tinyint unsigned` / `Integer`（因为它是本端新增、对齐的参照表里没有这个字段）。

这个类型选择会连锁影响到三个地方，新手很容易只改一处：

```
char(1) / String 的枚举字段：
  - 查询过滤用 StringUtils.isNotBlank(...)   （不是 ObjectUtil.isNotNull）
  - BO 校验注解用 @NotBlank                  （不是 @NotNull）
  - 前端收到的是字符串 "1"，不是数字 1        （对接时注意）
```

> **经验：** 字段类型不是孤立的决定。把 `tinyint` 改成 `char(1)` 后，**校验注解、查询条件、前端类型预期**都要跟着改，漏一个就会出现「过滤不生效」或「校验不触发」。改完字段还要重新构建模块刷新 MapStruct 生成类（见第 04 篇）。

## 三、Excel 导入：字典转换器会「反向解析」，`char(1)` 列极易爆

这是最隐蔽的一类坑。`ExcelDictConvert` 这个转换器在**导出（写）**时把编码→中文，在**导入（读）**时会做**反向解析**：把中文标签→编码。问题就出在这个「反向」上：

| 情况 | 结果 |
|---|---|
| 用户在 Excel 里填的是**编码**（如 `1`） | 转换器拿 `1` 去反查标签，查不到 → **静默存成空串**（无报错！） |
| 去掉转换器后，Excel 里是**中文** | 中文原样塞进 `char(1)` 列 → `Data too long` 报错 |

两个历史 bug（一个存了空、一个 `Data too long`）全是它造成的。根源在于：**导出文件是中文，用户拿导出文件改完回传，导入端却没做对称处理。**

### 稳健做法：别用自动转换器，在 Service 层手动规范化

```java
// 接受「中文标签」或「编码」两种输入，统一转成编码；识别不了的抛异常进 failList
private String normalizeEnum(String input, Map<String,String> label2code) {
    if (StringUtils.isBlank(input)) return null;
    if (label2code.containsValue(input)) return input;          // 本来就是编码
    String code = label2code.get(input);                         // 是中文标签
    if (code == null) throw new ServiceException("无法识别的枚举值：" + input);
    return code;
}
```

> **经验：** 导入枚举列**不要依赖 `ExcelDictConvert` 的自动反解析**——它会静默存空或撑爆字段。改为在 Service 层手动规范化：两种输入都接受、统一转编码、识别不了的**显式抛异常进失败列表**，而不是静默存空。映射表要和导出 VO 的内联表达式保持一致。

## 四、Excel 导入：VO 里的强类型字段会把整批导入炸成 500

更狠的一个。导入 VO 里如果有 `Long` / `Integer` / `Date` 这类**强类型字段**，FastExcel 按**表头名**匹配列，一旦匹配到的那列里有**任何一个**单元格转不动（空、中文、脏值），就抛 `Convert data ... error`，**整批导入直接 500 中断**——注意，是整批崩，不是这一行进失败列表。

### 它怎么坑我的

导入 VO 里有个 `gasUserId`（`Long` 类型）+ 表头「客户ID」。可这一版业务**根本不关联客户表，压根不该让用户填这列**，但字段留着了。于是 Excel 那列只要有人填了非数字，整批导入瞬间 500。

**解决：**
- 把这个不该让用户填的字段**从导入 VO 里直接删掉**；
- 在 Service 层给它**赋固定占位值**（如 `setGasUserId(0L)`），不从 Excel 行里读。

> **经验（两条）：**
> 1. 导入 VO **能不放强类型字段就不放**，尤其是「不该让用户填的 id / 占位字段」——直接从 VO 删、在 Service 层赋固定值。
> 2. 确实要导入的数字/日期列，用 `String` 接收，在 Service 层手动 `parse` + 校验，**失败的进失败列表**，别让 FastExcel 的自动转换卡死整批。
>
> 删字段后记得**同步更新导入模板**（去掉对应列）和接口/数据库文档。

## 五、一个相关的「占位 0」设计

承接上面：那个 `gasUserId` 字段，全表现在都是 `0`。**这不是 bug，是故意的占位设计**——这一版资产表不与客户表关联，采用冗余存储（客户编号/名称等直接按 Excel 值存进资产表自己的列，不反查客户表）。导入时没人填客户 ID，代码兜底存 0。

相应地，导出 VO 用 `@ExcelIgnoreUnannotated` 把这个全 0 的列从导出里剔除了（导出一列全是 0 没意义）。

等将来「资产关联客户」功能上线，再按户号反查客户表回填真实 ID 和冗余字段、把这列加回模板。

> **经验：** 「占位设计」一定要**留下记录**（注释 + 文档 + 团队记忆），否则后来人看到「整列都是 0 / 导出怎么没这列」会当成 bug 去查。把「现在为什么这样、将来怎么补」写清楚，比代码本身更重要。

## 小结

Excel 和字典这块的坑，本质都是**「类型 / 方向 / 环境依赖」的不对称**：

- 字典两套机制 → **环境依赖**不同（内联自包含 vs DB 字典要灌数据）；
- `ExcelDictConvert` → **方向**不对称（导出中文、导入要反解析）；
- 强类型导入字段 → **类型**太刚，一个脏值炸全批。

应对的总原则就一句：**导入这种「外部不可控输入」的边界，不要信任框架的自动转换，自己在 Service 层做规范化和容错**，让坏数据进失败列表而不是炸掉整批或静默存错。
