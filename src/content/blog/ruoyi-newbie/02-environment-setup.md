> 系列第二篇。微服务最劝退新人的不是写代码，而是**第一周连不上、起不来、调不通**。这篇把我首次搭建本地环境踩的坑按顺序排出来，每个都给「现象→根因→解决」。

## 坑 1：第一次启动就 `Unknown database`

**现象：** 满怀期待启动 `ruoyi-system`，直接报 `Unknown database 'ry-cloud'`。

**根因：** 我以为「拉下代码就能跑」，但**数据库和表结构都不存在**。框架的系统表（用户、菜单、字典、租户……）需要先用初始化脚本建出来。

**解决：**
```sql
-- 1. 先建库
CREATE DATABASE `ry-cloud` CHARACTER SET utf8mb4;
-- 2. 导入框架系统表
--    mysql -uroot -p ry-cloud < script/sql/ry-cloud.sql
-- 3. 业务库同理：先建库，再跑业务 DDL
CREATE DATABASE `biz-db` CHARACTER SET utf8mb4;
--    mysql -uroot -p biz-db < script/sql/biz-module.sql
```

**经验：** 每次有新模块要上，**先确认对应的库和表存在再启动服务**。脚手架的 `script/sql/*.sql` 是必跑项，不是可选项。

## 坑 2：Nacos —— 配置不在「本地文件」里

这是微服务对新人最大的认知颠覆。**业务服务的大部分配置不在 `application.yml`，而在 Nacos 配置中心。** 本地 `application.yml` 往往只有一句「Nacos 在哪」，剩下的（数据源、Redis、网关路由……）都从 Nacos 拉。

由此引出三个连环坑：

### 坑 2.1：配置导错了命名空间，服务死活拉不到

Nacos 用**命名空间**隔离环境。配置必须导进 `dev` 命名空间（对应 `spring.profiles.active=dev`）。我一开始导进了 `public`，服务启动时按 `dev` 去拉，自然一片空白。

> **经验：** 配置一定要进**和 profile 同名的命名空间**。启动拉不到配置，先确认命名空间对不对。

### 坑 2.2：中文注释把配置写进库时炸了

用 API 往 Nacos 推配置时，含 **4 字节 Unicode（某些中文/emoji）** 的注释会触发 MySQL `Incorrect string value` —— 因为底层 `ry-config` 库是 `utf8mb3` 字符集，存不下 4 字节字符。表现是：UI 里导入看着成功，**Nacos 一重启配置就丢了或回退到旧版**。

> **解决：** 推含特殊字符注释的配置前，先把注释去掉再推；或把库字符集升到 `utf8mb4`。
> **经验：** 「配置重启后丢失」别第一时间怀疑代码，先看推送时有没有静默的字符集错误。

### 坑 2.3：内嵌 Nacos 也要先初始化它自己的库

这套脚手架的 Nacos 是**内嵌源码启动**的（`ruoyi-visual/ruoyi-nacos`），它自己也要一个 `ry-config` 库存配置。这个库同样得先用 Nacos 官方对应版本的 `mysql-schema.sql` 初始化。

> **经验：** 「Nacos 起不来」可能是它自己的存储库没建。注意用**和 Nacos 版本号匹配**的 schema 脚本。

## 坑 3：启动顺序错了，全是连锁报错

微服务有依赖关系，乱序启动会看到一堆「连不上 XXX」的红字，但根因只是顺序不对：

```
Nacos  →  ruoyi-system  →  ruoyi-auth  →  ruoyi-gateway  →  业务模块
```

Nacos 必须第一个（大家都要从它拿配置/注册）；`ruoyi-system` 是地基（很多模块依赖它的 Dubbo 服务）；网关和业务模块最后。

> 还踩过一个端口冲突：业务模块和 `ruoyi-system` 默认端口撞了，同时跑必须改其中一个。**新模块定端口前先看现有服务占了哪些。**（这套环境后来把端口规则整体改过一轮，见第 07 篇。）

## 坑 4：新模块加了，请求却一律 404 —— 网关没配路由

**现象：** 业务模块明明起来了，前端/Postman 打过去全是 404 或被拦。

**根因：** 网关不认识这个新模块。**每新增一个模块，都要在网关配置里加一条路由**，告诉它「这个路径前缀转发给哪个服务名」：

```yaml
- id: biz-module
  uri: lb://biz-module          # lb = 走服务发现的负载均衡
  predicates:
    - Path=/biz/**              # 命中这个前缀的请求
  filters:
    - StripPrefix=1             # 转发前剥掉第一段路径
```

网关路由支持 Nacos 热更新，改完推上去**不用重启网关**。

> **经验：** 「模块起来了但 404」第一反应查网关路由，而不是查 Controller。

## 坑 5：鉴权——那些把人带偏的 403

调试业务接口时，403 是最容易让人误判的，因为**报错信息常常是「没有访问权限」，但真实原因五花八门**。我整理了三种：

| 现象 | 真实根因 | 处理 |
|---|---|---|
| 直接打业务服务端口就 403 | `sa-token.check-same-token=true` 要求请求**必须经网关转发**，直连内网服务被拒 | 开发环境把它设为 `false` |
| 登录接口发明文 JSON 返回 403 | 登录接口带请求体加密（RSA+AES），明文进不去，报错却显示「没有访问权限」 | 走完整登录拿 Token，或临时关加密开关 |
| 业务接口 403 说没权限 | `@SaCheckPermission` 要求当前账号有对应按钮权限，而我没配菜单按钮 | 用超管账号绕过校验来验业务逻辑 |

> **经验（最实用的一条）：** 开发期验业务逻辑，优先用**超管账号**（可绕过 `@SaCheckPermission`），或临时摘掉 Controller 上的权限注解直打服务端口，验完再加回来。别在权限配置上和框架死磕，那是上线前才需要补的事。
>
> 另外注意：加密开关 `api-decrypt.enabled`、`check-same-token` 这类是**全局开关，改了要重启**，不是热更新配置。

## 坑 6：最诡异的一个——所有命令突然 `command not found`

这个和框架无关，但太典型了，单独记一笔。

**现象：** 终端会话进行到一半，`mvn`、`mysql`、连 `ls`/`cat` 都突然 `command not found`，可前半段同一个终端明明好好的。

**根因：** 会话用的是 Unix 风格的 bash，但它拿到的 `PATH` 不知怎么变成了 **Windows 格式**——用 `;` 分隔、带 `C:\` 盘符、反斜杠。bash 期望的是 `:` 分隔的 `/c/` 路径，于是把整串 `PATH` 当成「一个不存在的目录」，所有程序都找不到了。程序本身没丢，只是「找路的规则」坏了。

**解决：** **重启终端会话**即可——`PATH` 在启动时重新初始化。代码改动早落盘了，重启不丢。

> **经验：** 一旦「所有命令包括手动敲的都 `command not found`」，先 `echo $PATH` 看是不是 `;`+`C:\` 的 Windows 格式；是就直接重启会话，别浪费时间找绝对路径或修 `.bashrc`。

## 小结

环境搭建的坑可以归成一句话：**微服务的「配置」和「依赖」是分散在多个地方的，任何一处没就位，都会以一个看似无关的报错砸到你脸上。**

- 库没建 → `Unknown database`
- 配置进错命名空间 → 拉不到配置
- 网关没加路由 → 404
- 鉴权开关/账号问题 → 一堆误导性 403

排查的通用心法：**别信报错的字面意思，先定位「这个能力归哪一层管」**——库、Nacos、网关、还是鉴权。
