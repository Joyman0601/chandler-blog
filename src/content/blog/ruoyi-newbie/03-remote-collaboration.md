> 系列第三篇。一个人玩脚手架和「和别人共用一套环境」完全是两回事。这篇讲：远程共享环境怎么接、配置和数据怎么分家、多套环境怎么对应，以及一个让我「本地全绿、测试环境全红」的 Dubbo 部署约束。

## 背景：我们共用一套远程数据

联合开发的核心约束是：**我和带教要共用同一套业务数据**。带教在一台远程服务器（记为 **库 A**）上搭好了完整环境：MySQL 业务库（带数据）、Nacos 配置库、Redis、消息队列。我要把本地服务接到这套数据上。

第一个反直觉的事实就来了：

> **远程的 Nacos 端口对外不开放，但 MySQL / Redis 是通的。**

意味着我**不能直连对方的 Nacos**，必须**本地自己跑一个 Nacos**。那本地 Nacos 的配置从哪来？这就引出了两种接入方案，我们前后用过两套。

## 方案一：本地 Nacos 读「远程配置库」

最初的做法，改动极小——只改一个文件，让本地 Nacos 的存储指向远程的配置库：

```properties
# ruoyi-visual/ruoyi-nacos/.../application.properties
db.url.0=jdbc:mysql://<远程>:3306/ry-config
db.password.0=<远程密码>
```

这样：本地 Nacos 启动后读的是**远程配置库**里的配置，而那些配置本来就指向远程的 MySQL / Redis。业务服务连本地 Nacos，自动拿到「全部指向远程」的配置。一键接入，省事。

**缺点很快暴露：** 本地 Nacos 读的是**和对方共享的配置库**。我在本地 Nacos 控制台改任何配置，**都会改到对方共用的那份**。联调阶段两个人互相覆盖配置，很危险。

## 方案二：配置全本地，只有业务库连远程（最终方案）

为了不互相干扰，我们调整成：

- **配置库走本地**：把远程配置库整库 dump 下来，导进本地 MySQL（导入前先备份本地旧库）。从此本地 Nacos 读**本地配置库**，我怎么改都不影响对方。
- **业务库仍连远程**：本地配置库里的「数据源配置」依然指向远程业务库——数据还是共享的那份。
- **Redis / 消息队列改本地**：各自起本地容器，互不干扰。

这套方案的精髓是**把「配置」和「数据」解耦**：

| 东西 | 放哪 | 为什么 |
|---|---|---|
| Nacos 配置 | 本地 | 避免改配置时互相覆盖 |
| 业务数据（MySQL） | 远程共享 | 必须用同一份数据联调 |
| Redis / MQ | 本地 | 各自独立，互不污染 |

> **经验：** 联合开发时，**「我能随便改的东西」和「大家共享、改了会影响别人的东西」一定要物理隔离**。配置属于前者（搬本地），核心数据属于后者（连远程、且 DDL 只增不删）。

### 一个改配置时的小坑

改本地配置里的 Redis 密码时遇到：配置内容里中文注释是乱码，用「中文锚点」做字符串替换匹配不中。最后用脚本读出内容、**按 `port: 6379` 后面第一个 `password:` 定位**来替换，绕开了乱码注释。

> **经验：** 改这种「带乱码注释的配置文本」，别用中文做定位锚点，用稳定的英文结构（字段名、缩进层级）定位。

## 多套环境：库 A 联调、库 B 测试

随着开发推进，环境变成了两套，新人很容易搞混：

| 环境 | 角色 | 谁维护 | 我怎么用 |
|---|---|---|---|
| **库 A** | 共享**联调**业务库 | 带教 + 我共用 | 本地服务连它做开发联调，DDL **只增不删** |
| **库 B** | **测试**服务器（部署目标） | 带教配环境 | 我把业务模块打成 jar → 镜像 → 推到库 B |

> 还踩过一个纯粹的「凭据」坑：被告知库 B 的账号是某个特殊用户名 + 一个空格密码，结果怎么连都 `Access denied`，折腾半天才发现实际就是最普通的 `root/root`。
>
> **经验：** `Access denied` 说明**网络是通的、只是凭据不对**（网络不通会是 timeout / connection refused，是另一回事）。别因为登录失败就去查网络。

## 重头戏：让我「本地全绿、测试环境全红」的 Dubbo 约束

这是整个联合开发里最深的一个坑，值得每个新人记住。

### 现象

我做了个功能：**按「负责人姓名」搜索区域**。姓名不在我的库里，得调 `ruoyi-system` 的能力把「姓名」换成「用户 ID」。于是我给那个 Dubbo 接口**加了一个新方法**：

- 接口（契约）定义在 `ruoyi-api`；
- 我在本地的 `ruoyi-system` 里把它**实现**了；
- 在我的业务模块里 `@DubboReference` 调它。

本地测试：完美。部署到测试环境（库 B）：**RPC 报错**，大意是「找不到这个方法 / 解码请求失败」。

### 根因

回到第 01 篇那句话：**`ruoyi-api` 只有接口，实现在 provider 模块（这里是 `ruoyi-system`）里。**

Dubbo 是 provider / consumer 架构：
- 我的业务模块是 **consumer**（调用方）；
- `ruoyi-system` 是 **provider**（真正实现方法的人）。

我只把**自己的模块（consumer）**部署到了测试环境，但测试环境上的 `ruoyi-system`（provider）还是**带教部署的旧版本，根本没有我新加的那个方法**。consumer 喊了一个 provider 不认识的方法名，运行时解码直接失败。

> 一句话：**给 `Remote*Service` 加方法，光部署调用方没用，必须同时部署实现方。**

### 解决与经验

```
改动落地前，先问自己一句：「我动了哪些模块？」

1. 只动了自己的业务模块        → 只部署自己的模块，OK
2. 动了 ruoyi-api（接口契约）   → 契约变了，provider 也得重新部署
   或动了 ruoyi-system 等别人的模块
   → 这些模块也必须一起部署，否则 consumer 单独上线必崩
```

落地时有两个选择：
- **(a)** 把对其它模块的改动交给负责部署那个模块的人，让他一起更新；
- **(b)** 干脆不动别人的模块，**改用测试环境上已经存在的 Dubbo 方法**自己拼出需求（最省事，自给自足）。

我后来更倾向 (b)：**能不改公共契约就不改**，避免「跨模块部署」这种需要多方协调的事。

还有一条魔鬼细节：consumer 和 provider 两端的方法**签名必须一字不差**（方法名、参数类型、返回类型）。即使 provider 部署了，签名对不上，照样 RPC 解码失败。

> **排查口诀：** 「本地好、测试环境 RPC 报错」→ 看报错里 Dubbo provider 暴露的方法列表，你调的方法不在列表里 = **provider 端版本旧 / 缺实现**。

## 小结

- 联合开发的第一原则：**把「能随便改的配置」搬到本地，把「必须共享的数据」留在远程**；
- 多套环境（联调 / 测试）要在脑子里贴好标签，别把「只增不删的共享库」当成自己的试验田；
- Dubbo 跨模块改动是新人最容易忽视的部署陷阱：**改了契约或别人的模块，就不是「只部署我自己」能解决的**；
- 通用心法：遇到「本地好、远程崩」，先想**两个环境到底哪里不一样**——版本、配置、还是数据。
