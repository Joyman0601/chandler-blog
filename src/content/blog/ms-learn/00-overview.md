> 这套系列记录我用「分步走 + 检查点 + 亲手跑」的方式，从零搭一套最小可运行的微服务 demo，逐个攻克微服务的核心问题。每一步都讲清楚一条主线：**拆开单体后冒出了什么问题 → 为什么需要这个方案 → 怎么落地 → 踩了哪些坑**。本篇是总览，给你一张系列地图。

## 为什么写这个系列

市面上讲微服务的资料，要么停在概念（CAP、最终一致性、服务治理……），要么直接堆 API（加这个 starter、配那个 yaml）。但真正卡住初学者的，往往是中间那一层：**单体跑得好好的，凭什么要拆？拆完之后，那些原本不存在的问题是从哪冒出来的？**

我的做法是反过来：先把单体拆成几个小服务，**让问题自己暴露出来**，再去理解每个组件到底在解决哪个具体的痛。比如——

- 服务拆开后，A 怎么找到 B？（注册发现）
- 配置散落在每个服务里，改一次要重启一圈？（配置中心）
- 外部请求直接打到每个服务，鉴权逻辑要写 N 遍？（网关）
- A 调 B，B 突然变慢甚至挂了，会不会把 A 也拖死？（限流熔断）
- 下单要扣库存，跨两个库的写操作怎么保证「要么全成、要么全滚」？（分布式事务）
- ……

每一个问题，都对应这个系列里的一篇。

## 技术栈与业务主线

- **技术栈**：Spring Boot 3.2.4 + Spring Cloud 2023.0.1 + Spring Cloud Alibaba 2023.0.1.0，JDK 17
- **业务主线**：极简电商，三个核心服务——用户（ms-user）、订单（ms-order）、库存（ms-stock），外加一个网关（ms-gateway）和一个公共契约模块（ms-api）
- **中间件**：全部用 Docker 起（Nacos / Redis / MySQL / Seata / RabbitMQ / Prometheus / Grafana / Zipkin）

业务故意做得极简：一次「下单」会扣库存、建订单、发积分事件。简单到一句话能说清，这样注意力才能全放在**微服务模式本身**，而不是业务复杂度上。

> 第一条要记住的经验：**三大版本必须按官方矩阵配套**。Spring Boot → Spring Cloud → Spring Cloud Alibaba 三者的版本是绑定的，错配一个，启动直接崩。这是入门第一个坑。

## 服务怎么互相寻址：靠「名字」，不靠 IP

整套 demo 有一条贯穿始终的设计：**服务靠名字存在**。

每个服务在 `application.yml` 里声明自己的身份：

```yaml
spring:
  application:
    name: ms-user   # 这就是服务的身份, 别人调我时用这个名字, 全程不写 IP
```

加上 Nacos discovery 的 starter，服务启动就**自动注册**到注册中心。之后无论是 RestTemplate、Feign 还是 Dubbo、网关路由，调用方都只写服务名（`http://ms-user/...` 或 `lb://ms-user`），由框架去 Nacos 解析成真实的 `ip:port`。

这是微服务和单体最根本的差别之一：单体里方法调用是进程内的内存跳转，微服务里「调用」变成了**跨进程、跨网络**，于是「怎么找到对方」本身就成了一个需要专门组件来解决的问题。

## 系列地图

| 篇 | 主题 | 解决的问题 | 关键组件 |
|----|------|-----------|---------|
| 1 | 注册发现与配置中心 | A 怎么找到 B；配置怎么集中管理、不重启就生效 | Nacos |
| 2 | 网关与统一鉴权 | 横切关注点（鉴权/路由）怎么提到统一入口 | Spring Cloud Gateway |
| 3 | 服务间通信 | 跨进程调用有哪几种姿势，怎么选 | Feign vs Dubbo |
| 4 | 分布式会话 | 登录态凭什么能跨进程共享 | Sa-Token + Redis |
| 5 | 限流与熔断 | 下游病了，怎么不被它拖死 | Sentinel |
| 6 | 分布式事务 | 跨服务写操作怎么「要么全成要么全滚」 | Seata AT |
| 7 | 事件驱动与可靠消息 | 同步调用换成异步后，重复/失败怎么办 | RabbitMQ + 幂等 + 死信队列 |
| 8 | 可观测性 | 出了问题怎么定位 | Prometheus / Grafana / Zipkin |

这八篇大致按「**先让服务跑起来、能互相调用 → 再加治理（鉴权、限流、事务）→ 最后解决看不见的问题（异步、可观测）**」的顺序递进。每一篇都能独立读，但连起来读，你会看到一条清晰的演进线：每加一个组件，都是在为前一步埋下的某个隐患兜底。

## 一个反复出现的主题：从「实时强一致」到「最终一致」

如果说整个系列有一条暗线，那就是：**分布式系统里，很多在单体中理所当然的「确定性」都不再成立，你得学会和「不确定」共处。**

- 注册发现是**最终一致**的：实例挂了，调用方的本地缓存还没刷新，仍会把请求发给死实例 → 这就是为什么需要熔断兜底。
- 配置推送有**传播延迟**：改完配置，要一两秒才生效。
- 消息是**至少投递一次**：同一条消息可能被消费多次 → 这就是为什么需要幂等。
- 异步解耦换来了响应速度，**代价是不再强一致**：积分会稍后才到账。

理解这一点，比记住任何一个 API 都重要。后面每一篇，我都会把这种「单体里没有、拆开后冒出来」的新问题，作为讲解的起点。
