> 一句话总结：内容型的个人博客用 Astro 生成纯静态页面、交给 Cloudflare 托管就够了。最大的一个坑是静态站被按 SSR 的方式部署，卡在 SESSION KV 上，用一份只声明静态资源的 `wrangler.jsonc` 解决。

## 0. 为什么要做个人网站

我希望有一个稳定的位置来沉淀技术笔记、项目复盘和长期学习记录。相比把内容分散在不同平台，个人网站更适合长期维护，也方便把 GitHub、B站和项目经历统一展示出来。

定位很明确：个人主页 + 技术文章 + 项目展示 + 关于页面。第一阶段不追求复杂功能，先保证它能访问、能更新、能持续写。功能是后来一点点加上去的，下面按先后讲。

## 1. 技术选择：Astro 生成纯静态页面

第一版用 Astro 搭建，原因是它适合内容型网站：

- 页面在构建时生成静态 HTML，访问速度快。
- 文章直接用 Markdown 管理。
- 项目结构简单，适合长期维护。
- sitemap、RSS 这类功能都有官方集成，按需加。

整站没有服务端渲染的需求：`astro build` 输出 `dist/` 目录，部署就是把这个目录当静态资源上传。代码推到 GitHub 的主分支后，Cloudflare 自动构建并发布。

第一版有四个页面：首页（个人方向、最近文章、精选项目）、文章、项目、关于。

## 2. 域名和基础 SEO

域名买下后，把 nameserver 切到 Cloudflare：

```text
alice.ns.cloudflare.com
maciej.ns.cloudflare.com
```

这样 Cloudflare 就成为这个域名的权威 DNS，DNS 解析、HTTPS 证书、自定义域名绑定和重定向规则都在一处管。`www` 子域名 301 跳转到根域名，避免搜索引擎把两者当作两套重复内容。

第一版就补上了基础 SEO：每个页面独立的 title 和 description、统一指向根域名的 canonical、Open Graph 和 Twitter Card、sitemap、robots.txt。后来 sitemap 又加了 `lastmod`：构建时读每篇文章 front matter 里的 `updatedDate`，没有就用 `pubDate`。

## 3. 部署卡在 SESSION KV：静态站被当成 SSR 部署

**现象**：Cloudflare 的部署日志走到「Provisioning SESSION (KV Namespace)」这一步，请求创建 KV 命名空间的接口报错。文件其实已经上传成功，但网站不更新。

**根因**：纯静态站被按 Workers / SSR 的方式部署了。Astro 6 默认开启 sessions，Cloudflare 部署时自动给它注入一个 `SESSION` KV 绑定，并尝试创建这个 KV。创建失败（当时判断多半是部署用的 token 缺 KV 的写权限），部署就卡住了。可静态博客根本用不到 KV。

**修复**：在仓库根目录加一份 `wrangler.jsonc`，显式声明「只上传静态资源」，不写 `main`、不写 `kv_namespaces`，wrangler 就不再自动创建 KV：

```jsonc
{
  // 纯静态博客：只把 astro build 产出的 dist 作为静态资源上传
  "name": "my-blog",
  "compatibility_date": "2026-06-04",
  "assets": {
    "directory": "./dist"
  }
}
```

如果改完还报错，去 Cloudflare 项目的 Settings → Bindings 里删掉残留的 `SESSION` 绑定。另一个相关的约定是：不装 `@astrojs/cloudflare` adapter。这个站没有 SSR 需求，装了反而会引入 SESSION KV 这类麻烦。

## 4. 内容集合与系列

文章放在 `src/content/blog/` 下，用 Astro 的内容集合（content collections）管理。front matter 的字段由 schema 约束，构建时校验：

```ts
schema: z.object({
  title: z.string(),
  description: z.string(),
  pubDate: z.date(),
  updatedDate: z.date().optional(),
  tags: z.array(z.string()).default([]),
  series: z.string().optional(),
  seriesLabel: z.string().optional(),
}),
```

文章多了以后，按主题成组更好读，于是加了 `series` 和 `seriesLabel` 两个字段：同一个 `series` 的文章在首页和归档里按 `seriesLabel` 分到一组，文章页提供系列内的上一篇、下一篇。系列放在同名子目录里，组内按文件名排序，所以系列文章的文件名带 `00-`、`01-` 这样的前缀。

字段写错、日期格式不对，`npm run build` 会直接报错，这比上线后才发现页面空白好得多。

## 5. 阅读体验：目录、搜索、评论

第一版只有正文。后来陆续加上了这些：

- 文章页：右侧吸顶目录、标题锚点、阅读进度条、代码块复制按钮、自定义 404 页。
- 标签页、RSS、深色模式。
- 站内搜索：构建完成后用 Pagefind 给 `dist/` 建索引，整个过程不需要后端。
- 评论：接入 giscus，评论存在 GitHub Discussions 里，同样不需要自己的服务端。

这些功能都没有改变「纯静态」这个前提，部署方式一直没变。

## 6. 从本地文章库导入，按复盘日期定发布日期

后来我在本地另外维护了一个文章库，按统一的写作规范写稿、过检查，博客只当发布端。仓库里有一个导入脚本，把文章库里标记为可发布的文章导入博客：

- 分类映射成博客的系列；文章之间的相对 `.md` 链接转成站内 `/blog/` 地址。
- 链接指向不存在的文章、元数据格式不认识、和已有文章冲突时，导入直接失败，不写文件。
- 重复导入同样的输入不改文件；在博客里手动改过的导入文章不会被直接覆盖。
- 有 `--check` 模式，只检查导入副本是否和原稿同步。

发布日期走过一段弯路。一开始为了让文章列表看起来分布均匀，给导入的文章随机排了日期。后来改成：每篇原稿都写明 `pubDate`，取这篇文章对应那次复盘的日期，不取整理、导入或推送当天，也不再随机。改稿时保留原发布日期，实质更新另记 `updatedDate`。日期反映「这件事是什么时候想清楚的」，比排得均匀更有用。

## 7. 改版：字体、动效、光标和配图

文章多起来之后，做过一轮整体改版，几个取舍：

- 字体：标题用细字重，正文优先用系统的苹方，缺失时用自托管的 Noto Sans SC，不依赖外部字体服务。
- 导航动效：目录跳转、返回顶部这类页内移动，用约 0.35 秒的轻微模糊加小幅滑动代替长距离滚动；用户开启「减少动态效果」时直接定位。
- 光标：桌面端用一个跟随的小圆环，靠近按钮、短链接时吸附到目标上；触屏、输入框、键盘操作时回退到原生光标。
- 正文栏：后来又按实测把正文栏加宽一档、字号降一号，让桌面一行的字数和常见的中文技术博客接近。

最近一次是配图。原来文章里的结构示意都是代码块里的字符画，宽的在手机上要横向滑动。现在改成 SVG 图，随文章一起导入：导入时先校验，不允许脚本、外链和内嵌图片；图里的文字保持为文本；夜间主题对图整体反色，所以图里不填白底。

## 收尾

1. **静态站就按静态部署** —— 用 `wrangler.jsonc` 把部署方式钉死，别让平台按 SSR 去猜。
2. **让构建替你校验** —— front matter 用 schema 约束，错了构建就失败。
3. **写作和发布分开** —— 文章在文章库里维护，博客只负责展示，导入脚本负责同步和拦错。
4. **日期要有含义** —— 发布日期取复盘日期，不为了好看随机排。

回头看，这个站的功能几乎都是在「需要了」的时候才加的。先能访问、能持续写，比一开始就设计周全更重要。
