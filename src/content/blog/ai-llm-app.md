## 学习定位

我的大模型应用学习方向不是模型算法或训练，而是站在 Java 后端开发的角度，学习如何把 LLM、RAG、Tool Calling 和 Agent 工作流落地到真实业务系统里。

这个方向更关注工程问题：

- 如何稳定调用模型接口。
- 如何把企业知识接入问答流程。
- 如何让模型安全调用业务工具。
- 如何控制成本、延迟和失败风险。
- 如何让系统可排查、可测试、可持续维护。

## LLM API 基础

第一阶段需要先把模型当作一个外部服务来处理，而不是把它看成万能逻辑层。

后端需要负责：

- API Key、Base URL、model 等配置管理。
- timeout、重试、错误分类和降级。
- 输入长度限制和输出 token 限制。
- 流式输出。
- JSON 或结构化输出解析。
- 日志、requestId 和用量统计。

一个重要原则是：Prompt 只能提高模型遵循规则的概率，不能替代后端校验。权限、参数、工具执行和最终业务边界必须由后端控制。

## RAG

RAG 解决的是模型如何基于外部知识回答问题。它的核心链路包括：

```text
文档上传
-> 文本解析
-> chunk 切分
-> embedding
-> 向量检索
-> 构造上下文
-> LLM 回答
-> 返回 sources
```

学习 RAG 时，我会重点关注这些问题：

- chunk size 和 overlap 如何影响召回质量。
- topK 和 score threshold 如何控制上下文质量。
- sources 如何由后端生成，避免模型编造引用。
- 文档更新后旧版本 chunk 如何处理。
- 用户权限如何在检索阶段过滤。
- 如何通过评估集持续改进召回和回答质量。

## Tool Calling

Tool Calling 的关键不是让模型“执行函数”，而是让模型提出工具调用意图，再由后端决定是否执行。

后端需要做：

- 工具白名单。
- 参数 schema 和必填校验。
- 权限码校验。
- 风险等级判断。
- 高风险操作二次确认。
- 审计日志。
- 工具调用次数和超时限制。

模型输出不能直接信任。尤其是业务系统里，用户可能通过 prompt injection 诱导模型调用不该调用的工具，或者伪造 userId、tenantId 等参数。最终执行权必须在后端。

## Agent

Agent 可以理解为“带工具和状态的多步任务编排”。但生产环境里，我更倾向于使用受控 Agent，而不是完全自由行动的 Agent。

受控 Agent 至少要有这些边界：

- 最大步骤数。
- 最大执行时间。
- 工具调用白名单。
- 重复调用检测。
- 高风险操作确认。
- 每一步的状态记录和停止原因。
- 成本和用量限制。

这样即使模型判断错误，系统也能在后端边界内停止、回滚或交给人工处理。

## 工程治理

大模型应用上线后的核心问题不是“能不能回答一次”，而是能否长期稳定运行。

我会持续关注：

- requestId 和链路日志。
- token usage 和成本统计。
- LLM 错误率、RAG 无答案率、工具失败率。
- 限流和额度控制。
- RAG 评估集。
- 灰度策略和 Shadow Mode。
- 安全回归测试。

这些内容会在后续项目文章里结合实际代码继续展开。
