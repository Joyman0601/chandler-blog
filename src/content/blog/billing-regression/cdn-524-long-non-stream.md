> 一句话总结：经 Cloudflare 的非流式请求，如果源站约 100 秒内回不来响应头，客户端就收到 524，拿不到结果和请求 ID；源站不知道连接断了，照常跑完、照常扣费。但这只对走那个地址的用户成立。第一天的报告写成「用户照文档用就会碰上」；第二天按文档默认的直连地址复跑，结论收窄成「只有走备用地址的用户会碰上」。

## 0. 起因：给一个长输出能力做生产回归

一个文本大模型刚上线了长输出能力，我在生产上做回归，要验证「一次写满单次输出上限」时的行为和扣费。其中一单是这样设计的：非流式对话请求，输入约 16K token，`max_tokens` 设 16000，让它尽量写满。

这一单走的是网关的主域名，主域名挂在 Cloudflare 后面。测试脚本里把这个地址写死了，当时没有记录为什么选它。这个细节第二天成了更正的起点。

同一轮里还有几笔流式长请求，跑在同一个域名上。

## 1. 现象：125.8 秒收到 524，看着像没扣钱

请求是 AI 助手照方案发的。到第 115 秒左右还没断，助手当时的判断是「这条连接撑过了 100 秒，还在等」。这个判断下早了。

第 125.8 秒，客户端收到了这样一个响应：

```text
HTTP/1.1 524
Server: cloudflare
Content-Type: text/plain

error code: 524
```

正文只有一行，没有网关的请求 ID，也没有 usage。

收到 524 后，助手等了 20 秒，读了一次已用额度，和发请求前一模一样。看起来这笔没扣钱。

又过了一会儿，用量明细里出现了这一行：状态「已完成」，源站耗时 163 秒，输入 13,719 token、输出 16,000 token，按 usage 正常扣费（实测）。也就是说，客户端收到 524 的时候，源站还在生成；读额度的时候，源站还没跑完。

同一个域名上的两笔流式长请求，分别跑了 828 秒和 890 秒，都正常收完（实测）。

## 2. 根因：CDN 等的是响应头，源站不知道连接断了

### 100 秒等的是什么

Cloudflare 默认等源站返回 HTTP 响应最多 100 秒，超时就给客户端回 524（文档：Cloudflare 对 524 错误的说明）。

非流式请求要等全部内容生成完，源站才发响应头。生成超过 100 秒，CDN 就先放弃了。流式请求一开始就发响应头，之后数据一直在流，所以跑十几分钟也不受影响。两种请求在同一个域名上一个断、一个不断，原因就在这里。

实测的切断点是 125.8 秒，比 100 秒晚一截。晚出来的这段我没查清从哪来，所以「第 115 秒还没断」什么也说明不了。判定只能看最终结果。

### 为什么扣了钱却看不出来

524 是 CDN 和客户端之间的事。CDN 到源站的那条连接还在，源站照常执行、照常结算。扣费发生在源站跑完的时刻，比客户端收到 524 晚。

这个网关的用量明细在请求完成时才写入，在途的请求没有行；已用额度也不含预扣（实测）。所以在途期间，客户端看不到这笔花了多少，只能等它结束。助手在 524 之后 20 秒读额度，正好落在「源站还在跑」的窗口里。

### 为什么用户拿不到请求 ID

请求 ID 是网关在响应里给的。客户端收到的 524 是 CDN 自己生成的错误页，源站的响应根本没送到。用户手里只有一个时间点，想找客服对账，连凭证都没有。

### 作者的内网实测为什么不够

功能作者在内网直连时测过一次写满上限，用了 221 秒，能正常返回（文档：作者的测试记录）。这条结论换到公网主域名就不成立了，因为路径上多了一层 CDN。

## 3. 第一版结论：写成了「用户照文档用就会碰上」

当天负责汇总的 AI 会话把这条写进回归报告，列为要 leader 定的事。结论是：非流式请求超过约 100 秒，用户收到 524、拿不到结果，但照常扣费；文档写的单次输出上限要跑两百多秒，用户照文档用就会碰上。要定三件事：要不要提示「长输出用流式」，超时的扣费怎么处理，由谁来做。

这条结论有一个问题，交出去之前助手没核出来，我转交时也没看出来：报告同一条的「依据」栏里，写着「模型页的示例代码用的地址不经 Cloudflare」。依据和结论放在一起，是互相矛盾的。

## 4. 第二天的更正：按文档默认地址复核

### leader 的一句话

leader 看报告后跟我说（转述）：按文档站，文本接口走的是另一个直连地址。

复核从核文档开始（文档）。文档把直连地址列为文本接口的默认地址，经 CDN 的地址只作备用；接口描述文件里列在第一位的也是直连地址。

第一天测的恰恰是备用地址。脚本写死了它，记录里没有理由。

### 零花费核路径

先不花钱，确认两个地址哪个经 CDN。不带 key，只看响应头：

```bash
for base in "$CDN_BASE" "$DIRECT_BASE"; do
  echo "== $base"
  curl -sI "$base/v1/models" | grep -iE '^(server|cf-ray):'
done
```

结果（实测）：直连地址回 `Server: nginx`，没有 `cf-ray`，域名解析到非 Cloudflare 的 IP；备用地址回 `server: cloudflare`，带 `cf-ray`。

### 判定先写下来

复跑会花钱，所以发之前先写判定，免得跑完再找理由：

| 结果 | 读法 |
|---|---|
| 200，且耗时超过 100 秒 | 直连地址不受这个问题影响 |
| 200，但耗时不到 100 秒 | 没碰到阈值，不能下结论 |
| 5xx 或断连 | 直连地址也有问题，影响面不收窄 |

发之前还做了两步免费预检：先 dry-run 打印请求体，和第一天那笔逐字段比；再带 key 查一次模型列表，确认这把 key 在直连地址上能用、目标模型在列表里。

### 一个小失误

预检这一步助手出了个错。它本来想先 dry-run，结果把 `dry` 写成了样本名，漏掉了 `--dry-run` 参数，请求直接发了出去。好在这一单和计划里要发的完全一样，没有多花。助手在汇报里自己说明了这次失误，并补记了台账。

教训是：会花钱的脚本，默认就应该是 dry-run，真发要显式加参数。反过来设计，一个笔误就是一笔真实扣费。

### 复跑结果

同一请求体、同一把 key，只把地址换成直连地址（实测）：

- 200，耗时 165.8 秒；
- 带请求 ID，usage 完整，输入 13,719、输出 16,000；
- 响应里的 model 和请求的一致，扣费和 524 那笔同额。

直连地址上既没有 100 秒那一档切断，也没有 nginx 默认 60 秒那一档。

顺带看到一个现象：这一单的正文是空的，16,000 个输出 token 全部记在推理 token 里。推理模型把输出额度全耗在思考上，没剩下写正文的额度。这和 524 无关，但提醒我测长输出时额度要给够。

### 改过的结论

只有用备用地址发长时间非流式请求的用户，才会碰上「524 但扣费」。按文档默认地址用的用户不受影响。助手建议把这条从「必须由 leader 定」降成「已按默认处理」，写清是备用地址上的现象，并附上复跑的证据。

## 5. 附带：同一层 CDN 拦下 Python urllib

同一轮回归里，我还被这层 CDN 拦过一次，表现完全不同。

回归脚本用 Python 标准库 urllib 下载生成结果的文件，也读一个挂在同一层 CDN 后面的公开页面，全部 403。浏览器打开同一个链接正常，curl 也正常。第一反应是「签名链接过期了」或者「文件只对登录用户开放」。

看了一眼响应：`Server: cloudflare`，带 `CF-RAY`，`Content-Type: text/plain`，正文只有一行 `error code: 1010`。1010 是 Cloudflare 的「按浏览器签名拒绝访问」（文档：Cloudflare 错误码说明）。

urllib 不设请求头时发的是 `User-Agent: Python-urllib/3.x`，命中的正是这个默认串。我做了一张对照表（实测）：

| 客户端 | 公开页面 | 结果文件 |
|---|---|---|
| urllib 默认 UA | 403 | 403 |
| urllib 自定义 UA | 200 | 200 |
| requests、httpx | 200 | 200 |
| curl、Node fetch、Go net/http | 200 | 200 |

同一台机器、同一时刻，只改 UA 就回 200，所以不是 IP，也不是频率。修法是统一给请求加头：

```python
import urllib.request

def fetch(url, timeout=30):
    req = urllib.request.Request(url, headers={"User-Agent": "my-regression/1.0"})  # ← 不用默认 UA
    with urllib.request.urlopen(req, timeout=timeout) as r:
        return r.status, r.read()
```

这条我写成「附带观察」，不当缺陷：要不要放宽规则归站点负责人定。另外，拿这类站点上的文件当负向用例素材也不合适，上游拉素材的客户端可能被同一条规则拦下（推断），会测成「下载失败」而不是「格式不对」。

同一天还有一个边缘层的 403：一个新加的账单下载入口在生产打不开。我不带签名，对比了几条同前缀的路径，发现边缘规则只放行了其中一部分，部署手册里少了「加白名单」这一步。运维第二天放行，在那之前我每 10 分钟用一个不存在的导出编号探一次入口，零花费地等它变成业务层的 404。

三件事有一个共同点：**先看响应是谁给的。**`Server` 头和正文格式能告诉你，这个错误来自 CDN、边缘规则，还是你的源站。

## 6. 怎么防：一张清单

长输出、长耗时的付费实测之前：

- [ ] 接口地址取文档站给这类接口写的默认地址；用别的地址，在记录里写理由。
- [ ] 用 `curl -sI` 看 `server` 和 `cf-ray`，零花费分清哪个地址经 CDN。
- [ ] 路径上有 CDN 时，先用便宜模型经同一地址发一笔预计超过 100 秒的非流式请求做探测；回 524 就改走流式，不拿贵模型去撞。
- [ ] 判定写在发之前：200 且超过 100 秒算能返回，524 或断连算失败，不到 100 秒算没测到。
- [ ] 会花钱的脚本默认 dry-run，真发要显式加参数。

收到 524 之后：

- [ ] 不用紧跟着读到的额度差下结论；等源站耗时过去，按时间和模型去用量明细里找那一行，取实扣。
- [ ] 台账写「客户端 524，没拿到请求 ID，以用量明细为准」。
- [ ] 影响范围按地址分开写；文档推荐的不是这个地址时，不写「用户照文档用就会碰上」。
- [ ] 交出去之前，拿每条结论对一遍同一条的依据栏，看两者有没有矛盾。

## 收尾

1. **CDN 等的是响应头** —— 非流式请求生成多久，响应头就晚多久，超过约 100 秒就被切；流式先发头，不受这个限制。
2. **524 不等于没执行** —— 源站照常跑完、照常扣费，扣费比 524 晚，要等源站跑完再从用量明细取。
3. **影响面按地址写** —— 先查文档写的默认地址，实测走那个地址，再下「用户会不会碰上」的结论。
4. **403 先看是谁给的** —— `Server: cloudflare` 加 `error code: 1010`，先换一个 User-Agent 对照。
5. **花钱的脚本默认空跑** —— 一个参数漏写，就是一笔真实扣费。

这次最该反省的不是 524 本身，而是第一版结论：依据栏写着「示例地址不经 CDN」，结论却写「用户照文档用就会碰上」。助手写的时候没对，我转交之前也没对。下次写影响面，我会先问一句「用户默认走的是哪条路」，再去测那条路。上线回归的完整流程见[上线前回归](/blog/billing-regression/pre-launch-regression-real-billing/)。
