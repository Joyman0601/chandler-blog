> 一句话总结：agent 一次任务会反复调用模型，每次都把系统提示、工具定义、历史和文件内容重新带上，这部分大多命中缓存。所以 agent 接口的 token 大头是缓存读，不是「每轮输入 + 输出」。估算表的第一行要写三类输入各占几成、依据是什么；测试时用实测回填。想按单个会话算出实际花费之前，先确认每个计价项都能单独量到。

## 0. 起因：估一个 agent 接口的测试花费

我要估一个 agent 类接口的 token 花费，并想按单个会话算出实际花了多少。这类接口的用法是：提交一个任务，比如「把这份 PDF 做成幻灯片」，服务端开一个会话，模型一边想、一边调工具执行命令，直到交付。

第一版测试方案按「每轮多少输入、多少输出」估花费，乘上单价，得出一个总数。leader 看完说（转述）：这个测算模型不太符合真实的业务场景。agent 对话场景里缓存最多，经验值是输入输出加起来的 10 倍左右；方案里「缓存读占六成」可以先这么定，但要写进计算的第一行；命中率要看测试时实测，有可能完全不命中。

这句话让我回头去补了三件事：agent 的 token 到底长什么样，「缓存是输入的几倍」到底在比什么，以及估算表该怎么写。

## 1. 为什么「每轮输入 + 输出」估不准

### agent 的调用是一个循环

一个 agent 任务不是一次请求。最外层的一次 API 调用背后，是很多次模型调用：模型读任务 → 决定调一个工具 → 工具执行完把结果塞回上下文 → 模型再读、再决定……每一次调用，都要把系统提示、工具定义、到目前为止的全部历史重新发给模型。上下文越来越长，而前面那一大段每次都一样。

一样的前缀会命中缓存。所以输入侧的 token 可以分成三类：

| 类型 | 是什么 | 相对普通输入的单价（文档） |
|---|---|---|
| 普通输入 | 没命中缓存、也不写缓存的输入 | 1 |
| 缓存写 | 第一次出现、被写进缓存的前缀 | 1.25 倍 |
| 缓存读 | 命中缓存、直接读出的前缀 | 0.1 倍 |

单价关系取自一家云厂商公开价格页上的一个模型，缓存写取较长的那一档留存。再加上输出，一共四类 token。

### 占比一变，总价变很多

缓存读只有普通输入的十分之一，缓存写却比普通输入还贵。同样 5 万输入 token，全按缓存读算和全按缓存写算，输入侧金额差了一个数量级。

所以「每轮多少输入」这个数本身意义不大。真正决定花费的，是这堆输入里三类各占多少。这个占比不写出来，估算的数字什么时候失效，读者无从判断。

## 2. 先看手边的量级：150 个会话的实测

要测的接口还没跑，我先拿手边现成的数据建立量级感：本机 Claude Code 的 150 个会话。Claude Code 本身就是一个编码 agent，会话记录里每次模型调用都带 usage 字段，按字段汇总就行。

结果（实测）：输入侧 97.6% 是缓存读，2.0% 是缓存写，普通输入接近 0。按会话里的模型调用次数分档：

| 调用次数 | 缓存读占输入侧 |
|---|---|
| 1–10 次 | 81% |
| 10–30 次 | 91% |
| 30–100 次 | 96% |
| 100 次以上 | 98% |

调用越多，缓存读占比越高。这符合直觉：会话越长，「已经出现过的前缀」越多。反过来，调用次数少的短会话，缓存写的占比明显更高，1–10 次时约 19%。测试用例大多是短任务，拿长会话的占比去估，会估低。

再看缓存读和「输入 + 输出」的比值：单会话中位数是 127 倍。1–10 次的会话约 53 倍，300 次以上的约 354 倍。

汇总脚本很简单，按自己工具的字段名改一改就能用：

```python
from collections import defaultdict

FIELDS = ("input_tokens", "cache_creation_input_tokens", "cache_read_input_tokens", "output_tokens")

def mix(usages):
    """usages：一个会话里每次模型调用的 usage 字典（Anthropic 风格字段）。"""
    t = defaultdict(int)
    for u in usages:
        for k in FIELDS:
            t[k] += u.get(k, 0) or 0
    side = t["input_tokens"] + t["cache_creation_input_tokens"] + t["cache_read_input_tokens"]
    return {
        "calls": len(usages),
        "普通输入%": round(100 * t["input_tokens"] / side, 1),
        "缓存写%": round(100 * t["cache_creation_input_tokens"] / side, 1),
        "缓存读%": round(100 * t["cache_read_input_tokens"] / side, 1),
        "缓存读÷(输入+输出)": round(t["cache_read_input_tokens"] / max(1, t["input_tokens"] + t["output_tokens"]), 1),
    }
```

这组数字只能当量级参考。编码 agent 的系统提示和工具定义很长，又显式打了缓存断点，所以命中率高。别的 agent 服务走隐式缓存、提示也不同，命中率可能低得多，甚至不命中。不能拿它直接当别家服务的前提。

## 3. 「缓存是输入的几倍」，先问 input 指什么

leader 说的是「10 倍左右」，我统计的是「127 倍」。差一个数量级，先别急着判谁对，先看两边说的 input 是不是同一个东西。

两种主流的 usage 口径不一样：

- **OpenAI 风格**：`cached_tokens` 是输入数的一个细分。输入数已经包含了缓存命中的部分。这种口径下，缓存读永远不会超过输入。
- **Anthropic 风格**：`input_tokens` 不含缓存，缓存读写另列成 `cache_read_input_tokens` 和 `cache_creation_input_tokens`。本机记录里三者分列，`input_tokens` 的合计只有缓存读的约六万分之一（实测）。

所以「缓存是输入加输出的 10 倍」在 OpenAI 口径下根本不可能成立，它只能是拿缓存和「没命中缓存的输入 + 输出」比。我的 127 倍也是这个口径。两个数是同一种比法，差距来自工作负载：一边是经验值，一边是一个系统提示极长的编码 agent。结论是：引用任何「缓存是几倍」的数字，都要先写清口径和它来自什么场景。

同一个道理也用在对账上。网关要按协议取字段：输入数含不含缓存，缓存读和缓存写是不是分开给。字段取错，账就对不上。

## 4. 估算表怎么写：前提在第一行，上限按最贵的算

重写后的估算，每条付费用例都按这个顺序写：

```text
前提：每轮累计输入约 N token，其中普通 a%、缓存写 b%、缓存读 c%（依据：经验值 / 文档示例 / 实测）
      输出约 M token
预估：输入侧 = N × (a% × 1 + b% × 1.25 + c% × 0.1) × 普通输入单价
      输出侧 = M × 输出单价
上限：输入全部按缓存写算（N × 1.25 × 普通输入单价），输出按上限算
闸门：当天台账 + 本条上限 ≤ 每日预算，否则不跑
回填：跑完记下 usage 里各类字段，算出实际占比，替换第一行的前提
```

几条原则：

- **前提写在数字前面**。读者先看到「缓存读按六成算、依据是经验值」，才知道这个数在命中率变了以后要重算。
- **上限按最贵的一类算**。缓存写比普通输入还贵，所以上限是「输入全算缓存写」，不是「全算普通输入」。预算闸门按上限设，不按预估设。
- **字段不全就写明**。有的接口只给缓存读、不给缓存写。那缓存写只能从账单反推，表里要写出来，不能默认是 0。只按缓存读算，会算少。

## 5. 实测回填：两天的账单

测试跑了两天，账单次日才出。拿到账单后，我把前提一行换成实测值。

**第一天**：输入由 36,221 缓存读、7,558 缓存写、28 普通输入组成，合计和监控里的输入总数一致。缓存读约 82.7%。一份验证记录里把它记成了「97%」，是笔误，按原数改了过来。

**第二天**：缓存读 128,166、缓存写 30,902、普通输入 116，输出 8,382。输入三项的合计和输出，都和监控里的两个总数相等。前一天我按「缓存不跨会话」推算过：缓存写约 3.1 万、缓存读约 12.8 万。账单出来，对上了。

两天的实际花费只有方案预估的十分之一左右。一是任务本身比较小，二是输入大量走了缓存。

这里助手犯过一个错。结果报告的初稿是它写的，里面有一条结论：只要让监控里的数和单个会话一一对上，就能拿到每个会话的实际花费。我转给它的复核意见指出，这条和报告前面「监控的输入不拆缓存读写」那句矛盾。核下来确实不成立：

- 会话接口不返回用量；
- 监控只按项目汇总输入 token 的总数，拆不出缓存读和缓存写；
- 账单按天合计，第二天才出。

缓存读和缓存写的单价差了一个数量级。总数对得上，不等于金额算得准。所以结论改成：单个会话的实际花费，现在从监控里拿不到，只能估算；监控和账单只用来对总账。

**能不能算出单个会话的实际花费，要看每个计价项能不能单独量到**，不是看总数对不对得上。

## 6. 长任务：调用频率、缓存过期和自动压缩

短用例跑完以后，我又加测了几条长任务，看三件事。

### 命令跑着时一直在花钱，会话闲着不花

一个把 PDF 做成幻灯片的任务，前 4 分钟都在装软件。这期间模型隔几十秒就被调一次，每次只带两三千 token。PDF 读进上下文后，每次调用的输入跳到约 1.7 万。之前另一条用例里，一个跑了 4 分钟的命令在等待期间也触发了周期性的模型调用。

同一个会话任务结束后，空闲了 36 分钟，这期间调模型 0 次（实测）。

所以长任务的花费取决于命令跑了多久，不取决于会话挂了多久。命令跑着时调用频率和上下文大小是什么关系，我还在用更长的命令测，还没有结论。

### 隔 36 分钟续做：缓存过期，整段重写

在同一个会话里，隔了 36 分钟追加一个小改动（改一页的标题）。54 秒做完，调了 2 次模型，每次约 2 万 token，和上一轮结束时的上下文一样大。整段历史都带上了（推断，监控只有总数）。

第二天的账单里，这一天的缓存写约 4 万，正好是 2 万的 2 倍。也就是说，36 分钟的间隔超过了缓存的留存时间，缓存已经过期，整段上下文又按缓存写的价格收了一次。按单价关系推算，如果在留存时间内接上，这一轮的花费会是现在的五分之一左右（推断）。

对估算的影响是：多轮任务的轮间间隔要写进前提。间隔超过留存时间，每一轮都要按「整段历史缓存写」算。

### 上下文推过阈值：自动压缩

最后一条用例，我把上下文一轮一轮推大，看服务端的自动压缩什么时候触发、对用量和结果有什么影响。每一轮塞进一大段材料，每段里藏一个校验码。

- 第 5 轮，上下文约 30 万 token，照常回答，没有报错。
- 第 6 轮推理了 2 次，输入合计约 48 万，比预期多了一次。之后上下文从约 36 万掉到约 18 万。我推断是先用整段上下文做了一次摘要，再带着压缩后的上下文回答。看起来保留了最近两段原文，前面的只剩一小段摘要。
- 第 7 轮，我问两个校验码。第 6 段的答对了；第 1 段的，模型回答「无法确定」，没有瞎编。说明压缩后前面的内容确实丢了。
- 会话的消息记录里能看到全部用户消息，却没有任何「压缩」类的条目。消息记录是对话历史，不是模型实际看到的上下文。压缩只能从用量突然掉下来看出来。

对估算的影响有两条：压缩那一轮会多一次整段上下文的调用，比平时贵；之后每次调用的输入减半，又便宜下来。对测试设计的影响更大：依赖早期上下文的用例，在压缩之后会失败，而且从消息记录里看不出原因。

## 7. 一张估算清单

估之前：

- [ ] 弄清一次任务背后有几次模型调用，不把最外层一次请求当成一次推理。
- [ ] 列出四类 token：普通输入、缓存写、缓存读、输出，缓存写不能漏、不能默认为 0。
- [ ] 查清 usage 口径：输入数含不含缓存，缓存读写是不是分开给。

写估算时：

- [ ] 第一行写三类输入的占比和依据（经验值、文档示例或实测）。
- [ ] 给预估，也给上限；上限按输入全算缓存写。
- [ ] 多轮任务写清轮间间隔，超过缓存留存时间的按整段重写算。
- [ ] 上下文可能超过压缩阈值的，单独估压缩那一轮。

测完以后：

- [ ] 用每条用例的 usage 算实际占比，回填第一行。
- [ ] 账单出来后逐项对：缓存读、缓存写、普通输入、输出。
- [ ] 说「能算出单个会话的实际花费」之前，确认每个计价项都能单独量到。

## 收尾

1. **大头是缓存读** —— agent 每次调用都重带越来越长的前缀，按「每轮输入 + 输出」估不贴实。
2. **前提写在第一行** —— 三类输入的占比和依据先写出来，读者才知道数字什么时候失效。
3. **倍数先问口径** —— 「缓存是输入的几倍」在不同 usage 口径下是不同的量。
4. **上限按最贵的算** —— 缓存写比普通输入还贵，预算闸门按「全算缓存写」设。
5. **总数对上不等于金额准** —— 拆不出单价差一个数量级的两类 token，就算不出单个会话的实际花费。

回头看，第一版估算错在把 agent 当成了「问一句、答一句」的接口。下次估任何 agent 类接口，我会先拿一个手边的 agent 汇总一下 usage，看清 token 的形状，再写第一行前提。付费用例怎么排、停止规则怎么写，见[按次付费接口的测试设计](/blog/billing-regression/paid-test-design/)；上下文花费在自己的工作流里怎么省，见[上下文花费的大头是重读前缀](/blog/ai-workflow/context-compaction-cost/)。
