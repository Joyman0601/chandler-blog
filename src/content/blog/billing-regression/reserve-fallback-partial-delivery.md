> 一句话总结：缺价时使用预扣额，需要同时回答两个问题：这个数已经乘过什么，实际交付还剩多少。封顶只能限制上界；对允许部分交付的任务，还要按同一计费口径计算应保留的份额，并把这条兜底限制在查价失败的分支里。

## 0. 起因：预扣修对以后，旧兜底反而算错

一次按秒计费的接口修复，表面问题是预扣只算了一个单位。实际请求可能执行更长时间，完成时才按完整时长结算，入口冻结额和最终消费对不上。

历史会话里，助手把按秒预扣移到正确的判断位置，并让入口和结算共用时长归一规则。随后审查又发现：缺少渠道定价时，结算会从预扣额反推一个单价，再乘实际倍率。

旧预扣恰好少乘了时长，错误的兜底偶然得到合理结果。预扣修成「单价乘时长」后，这条兜底却会把时长再乘一次。局部修复揭开了另一个长期被抵消的错误。

我在[计费规则的几个暗坑](/blog/billing-regression/billing-rule-pitfalls/)里记过重复放大。这次回查后续提交，又看到更完整的演变：先限制缺价时的实扣，再处理少交付；中间尝试过读取任务参数里的价格，随后因口径和来源问题撤回。下面按这些修订后的边界展开，提交中的测试也只视为历史代码证据。

## 1. 先给数标单位：总额不能再次充当单价

为了讨论清楚，用几个抽象量表示这条链路：`p` 是可信定价得到的基础单位价格，`r` 是按请求参数计算的倍率，`s` 是按实际交付计算的倍率，`R` 是已记录的预扣总额。

在口径一致、忽略取整的简化模型里，预扣是 `R = p × r`。正常查价成功时，可以按可信价格与实际倍率计算。查价失败，只剩 `R`，就不能直接把 `R` 填进原来放 `p` 的位置。

`r` 可能已经包含时长、画质、数量，甚至固定输入部分。变量都叫 amount 或 price 时，代码看起来很顺；写成「每秒单价」「请求总额」「实际条数倍率」，重复计算就容易被看出来。

这也是为什么保护条件不能只认型号前缀。同族名字可能走不同供应商、采用不同计费方式。需要确认真实的计费策略，以及预扣里究竟已经包含哪些维度，再决定哪种折算适用。

## 2. 封顶之后：少交付不能仍然收满预扣

假设请求了几份结果，最终只返回其中一部分。若缺价时一律收取全部预扣，虽然没有超过预扣额，却仍然收了没交付的部分。上界保护和少交付退款，是两个独立要求。

对于费用严格与数量成正比的策略，可以使用实际数量与请求数量之比。更一般的表达是：用同一策略分别算请求倍率和交付倍率，再用两者的比例折算预扣。缺价路径要求不超过预扣时，比例还要受上界约束。

关键是「同一策略」。如果请求倍率包含固定输入处理费，实际倍率也要保留这部分。假设固定部分为 `f`、每份输出为 `v`，那么请求三份、交付一份的比例应是 `(f + v) / (f + 3v)`，不能直接用三分之一。

下面是我另写的算术示例。数字都是虚构的记账单位；它只演示正数倍率如何折算，不代表任何真实价格、取整规则或产品政策。

```python
from fractions import Fraction

def fallback_share(reserved, requested_weight, delivered_weight):
    if reserved < 0 or requested_weight <= 0 or delivered_weight <= 0:
        raise ValueError("需要已确认的正数倍率；缺失和零交付另行处理")
    share = min(Fraction(delivered_weight, requested_weight), Fraction(1))
    return reserved * share

assert fallback_share(120, 3, 1) == 40
# 固定输入权重 2，每份输出权重 2：三份总权重 8，一份总权重 4。
assert fallback_share(120, 8, 4) == 60
assert fallback_share(120, 3, 4) == 120
```

「零交付」和「不知道交付数」没有放进同一个默认值。前者可能是失败或特殊终态，后者是证据缺失，应该分别进入契约规定的处理路径。把缺失强制转换为零，会意外退款；把所有零都当成满额，又可能隐藏实际失败。

真正落到整数记账单位时，还要明确取整发生在哪一步。先把比例截断，再乘总额，可能把很小但非零的交付份额直接算没；分别计算多项再取整，也未必等于合计后取整。这里的示例保留精确分数，故意不代替业务的取整约定。验收时应另选不能整除的样本，同时核实扣、退回差额与预扣记录能够闭合，不能只用恰好整除的数字证明公式正确。

如果倍率本身来自不同版本的策略，比例也可能失去意义。因此，复算请求侧倍率时还应检查原请求如何归一、默认值是否变化，不能直接拿今天的默认参数补齐昨天的任务。

这些差异最好连同复算依据写入测试名称或说明，让以后修改默认值的人知道，哪些历史口径仍然需要兼容。

## 3. 看似省事的价格快照：先查它从哪里来

后续提交中曾尝试在任务参数里保存一个价格字段，缺价时直接取它乘结算倍率。想法很直观：既然创建任务时查到过价格，之后用那时的值就行。

复查发现，这个字段并不总是当前规格的最终单价。一个模型有多档定价时，它可能只代表主规格。更麻烦的是，旧任务的同名字段可能从开放的扩展参数写入，来源没有经过同样的约束。

因此，该方案被撤回，后续修订改用已有预扣记录和已确认的交付份额。这里值得记住的不是某个字段名，而是信任边界：字段已经存在数据库里，并不能证明它来自服务端，也不能证明它包含完整的定价维度。

如果另一个系统确实需要不可变的价格快照，我会先检查四项：它由谁写入，客户端能否覆盖，包含哪些规格与版本，旧记录没有它时怎么处理。这是设计检查清单，不是上述历史修复已经完成的功能。

## 4. 正常结算和缺价兜底，要分别验证

缺价时封顶，是异常路径采用的处理策略，不能据此推出「任何请求的实扣都不应高于预扣」。正常结算可能按实际用量重算；是否允许超过预扣，需要按对应业务契约判断。

保护写得太宽时，会把正常查价也拦住。若测试里的渠道价格、正常结果和兜底值刚好相等，这种误拦仍然全绿。历史复核就补过一条对照：把正常价格对应的结果设成与预扣不同，才能看出代码是否误走兜底。

我现在会把下面几类场景放在同一组测试里。每一行先写独立预期，再看实际选择了哪条路径。

| 场景 | 要证明的行为 |
|---|---|
| 可信价格存在，正常实扣与预扣不同 | 使用正常结算规则，没有被兜底接管 |
| 缺价，完整交付 | 预扣中的时长和档位没有再次相乘 |
| 缺价，纯数量计费且少交付 | 只保留已交付部分对应的预扣 |
| 缺价，含固定费用且少交付 | 固定部分保留，按完整倍率比折算 |
| 任务参数带一个任意价格值 | 不把非可信参数当成结算依据 |
| 旧任务缺少新字段 | 使用明确的兼容处理，不静默猜测 |
| 交付数缺失、为零或超出请求 | 分别遵循约定，不靠同一个默认值吞掉差异 |

测试不能只写 `expected = productionCalculator(input)`。这样实现算错，预期也一起算错。简单样本用独立字面量钉结果，同时保留入口预扣与结算之间的交叉检查，才能既查绝对值，又查链路一致性。

## 5. 上线时，旧任务仍然带着旧预扣

还有一类边界发生在部署前后。任务创建于修复前，预扣记录仍然是旧口径；它可能在新代码运行后才完成。新程序再完善，也不能把已经写下的旧总额当作按新规则算过的值。

当时的记录把这个影响写进交付说明，没有宣称自动修正所有在途任务。复盘时也应保留这个限制。今天看见修复提交，不能倒推出过去的所有任务都已重新结算。

排查这类数据，我会沿一次任务读四个时刻：请求被接受、预扣被写入、执行结果产生、最终结算应用。再给每个时刻标上版本和计费口径。只看当前代码，很容易遗漏中间跨版本的那批任务。

兜底还应留下可区分的原因：确实没有定价、读取失败、参数不足，还是交付证据缺失。把这些全部合成一个正常金额，后续就无法判断系统是在按计划降级，还是长期掩盖配置错误。

## 收尾

预扣总额、单位价格和交付倍率各有自己的含义。缺价保护要避免重复放大，也要处理少交付；正常结算、来源可信度和旧任务兼容，则要用单独的对照守住。

下次再改预扣，我会沿着这个数追到结算的每个回退分支，检查旧代码是否曾经依赖那个错误值。局部修对以后，下游原本「碰巧正确」的地方，往往才开始暴露问题。
