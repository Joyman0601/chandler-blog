> 一句话总结：计费出错很少是公式本身写错，多半是「同一件事写了两份」：预扣和结算各认一次型号，两个页面各格式化一次阈值，前端和执行端各推断一次模式，明细里两类行各取一次时间。修法都一样：收成一处；测试挑「会出问题的那一态」写，并且放到改动前的代码上先跑红。

## 0. 起因：一条计费链路，规则散在很多地方

我在一个多供应商的 API 网关上做模型接入。一单按量计费的请求大致要过这几步：

1. 入口按「型号 + 用户组 + 渠道」查价，算出预扣，先从余额里扣掉；
2. 执行，失败时可能换一条渠道重投；
3. 结算按实际用量重算，多退少补；
4. 写用量明细，账单导出从明细里取；
5. 页面展示：模型页、定价页、价格计算器、在线试用页的预估。

每一步都可能有自己的一份规则拷贝。下面七个坑，没有一个是「公式写错了」，都是两份拷贝之间对不上。为了不写任何真实价格，文中的型号名、表名、函数名都是我编的通用名。

## 1. 子串匹配：新同族名字在预扣和结算两边落到不同规则

**现象**：接入一个视频生成模型的轻量版之前，我先读了同族已有型号的代码。家族判断有两种写法：预扣、参数校验和倍率策略用子串匹配，结算却用精确匹配。

```go
// 预扣、校验、倍率：子串
if strings.Contains(model, "video-x") { ... }
// 结算：精确
if task.Model == "video-x-preview" { ... }
```

新型号叫 `video-x-mini`。它在预扣时命中了 `Contains`，按老型号的规则预扣；到结算时精确匹配不上，掉进了通用的计价逻辑。两边算的不是同一套东西。供应商 SDK 里还有一处 `Contains(upstreamModel, "-x")`，把新型号支持的两种画面比例当成老型号不支持的，悄悄过滤掉了。

**根因**：型号名是查表的键。子串规则写的时候只有一个型号，它「碰巧」只命中那一个；新增一个同族名字，它就把新名字也吞进来。精确匹配那一处又不认新名字。新名字代进去，一边命中、一边落空。这类判断查不到也不报错，所以问题要到对账时才看得出来。

**怎么找全**：动手前，在网关和供应商 SDK 里按旧型号名和它的前缀各搜一遍，再搜所有按型号名做 `Contains`、`HasPrefix` 的地方。每一处都把新名字代进去问两句：新名字该不该命中这里？实际命中的是哪一条？这类判断通常散在白名单、参数校验、预扣、倍率、结算、超时几类地方，而且不止一个仓库，这次 SDK 里就藏着一处。

**修复**：把散在各处的子串判断收成一个家族判断，配一张按型号的参数表。预扣和结算调同一个函数：

```go
type FamilyParams struct {
    MaxImages int
    TierRatio map[string]float64 // 清晰度档位 → 倍率
}

var videoXFamily = map[string]FamilyParams{ // ← 家族成员只在这里登记
    "video-x-preview": {...},
    "video-x-mini":    {...},
}

func videoXCost(model string, u Usage) (Cost, bool) {
    p, ok := videoXFamily[model] // ← 精确匹配
    if !ok {
        return Cost{}, false // 调用方拿到 false 时打日志或拒绝，不回落通用计价
    }
    return p.cost(u), true // 预扣和结算都走这里
}
```

**验证**：老型号的价格不能变，存量测试和新加的对照用例把它钉住。新的守卫测试先放到改动前的代码上跑，确认会红，再放到改动后跑绿。守卫测试为什么要先跑红，见[守卫测试的三个要求](/blog/testing/guard-tests-three-rules/)；拿名字当键的其他几类情形（改名改一半、别名改指向、默认档变化），见[改名、别名和重定向](/blog/model-onboarding/rename-alias-redirect-ripple/)。

## 2. 查价失败的兜底：按次计费的公式套在了按秒计费上

**现象**：在本地全栈里，我删掉一条新渠道在某个用户组下的定价行，再让任务换到这条渠道上。结算出来的实扣是预扣的好几倍。我给每个按秒计费的型号各写了一条行为测试，修复前全红，实扣是预扣的数倍到十倍以上不等（实测）。

**根因**：三处各自合理，拼在一起出事。

- 入口查价带渠道条件，查不到就直接拒绝。所以在原渠道上缺定价行，反而是安全的。
- 换渠道挑候选时不查定价，只看型号映射、渠道启用、用户组和优先级。
- 结算按任务当前所在的渠道查价。查不到时，落进一段为「按次、按张计费」写的通用推算：单价 = 预扣总额 ÷ 张数，再乘结算倍率。

这段推算对按次计费成立。按秒计费的型号，预扣额里已经含了「秒数 × 档位倍率」，再乘一次就是二次放大，而且没有上限。结算侧只在「实扣超过预扣两倍」时打一条告警日志，照样扣。

**当时的修复**：对已确认的按秒计费策略，查价失败时回落预扣额，避免再次乘时长。这一阶段先处理重复放大；后续又为允许少交付的策略补了份额折算，不能把「回落预扣」理解成所有情况都收满。完整演变见[结算缺价：预扣封顶之后，还要处理少交付](/blog/billing-regression/reserve-fallback-partial-delivery/)。

**修复里又藏了一个坑**：第一版保护按型号名前缀认「哪些是按秒计费」。复核时发现，同一前缀下还有另一家渠道的型号是按条计费的，倍率等于结果条数，走另一套结算。被前缀罩住之后，缺价时会按预扣额再乘一次条数。单元测试复现：请求 2 条、只出 1 条，应收 100 个单位，实收 200 个。改成按渠道的供应商类型认，不按型号名。新加的按条计费对照用例，在旧版上是红的。

这一节的教训是：**认计费方式要按计费配置或供应商类型，不按名字长得像不像。**

## 3. 缺定价行：入口不报错，换渠道后在结算时才咬人

上一节的放大，起点是「新渠道上缺了一行定价」。给一个已上线的模型加一条新渠道时，定价行要覆盖「换渠道能到达的每条渠道 × 每个计费组 × 映射里的每个型号」。这里有两个维度最容易漏。

**组的维度**：用自动选组令牌的用户，计费组是他自己的持久组，路由组是自动命中的子组，两者可以不同。源渠道上常有「不在渠道组字段里、但有定价行」的计费组。只复制渠道组字段里那些组的定价行，这类用户换渠道过来就查不到价。所以定价行要复制源渠道的全部生效行，路由再按「定价齐全的组」收窄，两件事分开做。

**型号的维度**：第一版自检的「型号集合」取自源渠道已有的定价行。某个型号在源渠道上一行定价都没有时，它根本不在这个集合里：组照开、路由照建、自检全绿。结算的查价口径是「型号 + 组 + 渠道」，自检要用同一个口径：

```sql
-- 自检：新渠道上，每个组 × 每个映射型号都要有生效定价，期望 0 行
SELECT c.id AS channel_id, g.grp, m.model
FROM channels c
JOIN channel_models m ON m.channel_id = c.id
JOIN channel_groups g ON g.channel_id = c.id
LEFT JOIN prices p
       ON p.channel_id = c.id AND p.grp = g.grp AND p.model = m.model AND p.active = 1
WHERE c.id IN (SELECT id FROM new_channels)
  AND p.model IS NULL;
```

这里还栽过一次「照旧脚本抄清单」：安装脚本的用户组照同族旧脚本抄，交付时留了一句「上线前按生产库核对」。合并时 leader 一查，生产上这个家族通用的组比抄来的多了好几个，抄来的里面还有一个已经废弃。旧脚本只反映它写成那天的生产状态。现在的做法是开工时就用只读从库查出来，写死进脚本，组清单在脚本里只定义一处。

## 4. 同一个阈值，两个页面各格式化一次

**现象**：一个模型的长上下文分档阈值是一个 2 的幂。助手改分档文案时只改了模型页，我问了一句「定价页是不是没改」，才发现两个页面写的不是同一个数，边界符号也不一样。顺着查又发现，另一个模型有一个整千的阈值，在定价页上显示得比原值小。

**根因**：两个页面各有一个格式化函数。模型页一律按十进制，除以 1000；定价页规定「1024 的整数倍一律按二进制」，除以 1024。用编的数字举个同形状的例子：阈值 262144，模型页写「< 262K / ≥ 262K」，定价页写「≤ 256K / > 256K」；阈值 384000 恰好等于 375 × 1024，定价页就把它显示成 375K。

边界符号也有问题。模型页把「达到阈值就进高档」写死在组件里。计费侧每个模型可以配成「达到」或「严格超过」，这个模型配的是严格超过，标签没跟着走。

两个函数各自的单元测试都是绿的。每个函数对自己的用例都对，只是没有任何测试把两个页面放在一起比。

**修复**：收成一个共享函数，边界语义从计费配置派生：

```ts
type Boundary = 'reach' | 'exceed' // 达到即切档 / 超过才切档，和计费配置一致

export function formatThreshold(t: number): string {
  if (t % 1000 !== 0 && t % 1024 === 0) return `${t / 1024}K` // 2 的幂：262144 → 256K
  return `${Math.round(t / 1000)}K`                           // 整千：384000 → 384K
}

export function tierLabels(t: number, b: Boundary): [string, string] {
  const k = formatThreshold(t)
  return b === 'reach' ? [`< ${k}`, `≥ ${k}`] : [`≤ ${k}`, `> ${k}`]
}
```

动共享函数之前，我把数据里出现过的每个阈值用新旧两个函数各算一遍，逐个比输出，确认只改了想改的那几个。

**同类问题：一个规格数字散在六类地方**。另一次，一个文本模型的上下文长度要改一个数。只改模型注册表会漏掉五类地方：模型页的多语言文案（含 SEO，即搜索引擎优化用的标题、描述和问答）、列表页的本地化描述、其他页面里指向它的相关卡片、合集对比表里它那一行、价格配置里的上下文字段。只改一处，列表页和详情页就各写一个数。有一种语言的 SEO 标题本来就写了数字，改完多出 3 个字符，超过了标题长度契约，全量测试里只红这一条。验证时我让替换脚本对每个文件断言命中次数，再起本地服务取渲染后的页面，把剩下的旧写法逐条归到别的模型名下，才算闭环。

## 5. 明细的时间字段：两类行，两个口径

**现象**：一次回归要导出账单，想让它包含一笔正在输出的长文本请求。导出按「创建时间」筛，范围到受理时刻为止。负责协调的 AI 会话读了导出代码，推断这笔请求早就创建了，不管什么时候结束都在范围里，就定了到点提交。同时开着的另一个 AI 会话实测推翻了这个推断：文本请求在途时，明细里根本没有它的行；结算后出现的行，创建时间等于完成时刻（实测）。

**根因**：明细是两个来源合起来的。同步文本请求的行来自结算时写的消费日志，创建时间就是写日志那一刻。异步媒体任务的行来自任务表，提交时就建行，状态和金额之后再更新。协调会话先接触的是媒体任务，把它的口径套到了文本行上。

**修复**：对每类记录，找到它插入明细来源表的那一处，看时间字段在哪里赋值。零成本的实测是：发一笔请求，在途时查一次明细，结束后再查一次。要让在途的同步请求进导出，就等它入账后再提交，并设一个最晚时刻兜底。

## 6. 前端推断模式锁价，请求却发了用户显式选的模式

**现象**：一个视频模型的在线试用页上，用户先在模式里选了文本模式，又传了 N 张图。页面的规则是图片数 ≥ N 就进入参考图模式，时长锁到最长档，估价也按最长档算。请求体里却带着用户显式选的文本模式。执行端遇到显式的文本模式，直接丢掉全部图片。结果是按最长档扣费，出的是一条忽略了图片的文生视频，而用户本来选的是一个短档。

反方向也有：选了参考图模式但没传图，页面照样锁到最长档；执行端在没有图时什么都不拼，结果也是按最长档出文生视频。

**根因**：推断规则写了两份。前端是「显式选参考图，或者图片 ≥ N」；执行端是「模式为空时才按图片数推断」，显式值优先。两份在「显式非参考 + N 张图」和「显式参考 + 0 张图」两个组合上结论相反。网关还有一条规则：某个型号只要图片数到 N，就强制最长档，不看模式。所以简单改成「前端也尊重显式值」也不对，那个型号会被网关拒掉。

**修复**：先把执行端和网关对「显式值和推断值」的优先级读出来，列成组合表，逐格对照前端的锁定和请求体。不可能一致的组合在前端就不让选：图片数到 N 时，参考图以外的模式选项置灰并给一句原因，之前选的回落到自动；选了参考图但没图，不发请求并提示。测试按行为钉：选文本模式 → 加到第 N 张图 → 断言选项置灰、请求体不带模式、时长锁到最长档；再把回落逻辑去掉跑一次，确认用例变红。

## 7. 页面上每个数字都要说得出来源

最后一类坑不在计费链路里，在展示上。

- **编出来的用量表**：价格计算器里曾有一张为推理档位编的「典型用量」，只是为了让计算器看起来完整。算出来的价格和真实价格长得一模一样，用户分不清哪个有依据。后来删掉了，只算确定的部分，并在旁边说明其余部分按实际用量结算。
- **行为对了却不解释**：页面上的预估价不随画面比例等选项变化，被反馈成 bug。这些选项本来就不影响计费，固定不变是对的。改法是在旁边加一句为什么不变。
- **「官方价」填成了自家暂定价**：页面框架的逻辑是「实时价比官方价低就划线、显示省了多少」。一个没有公开官方价的模型，把「官方价」字段照模板填成了自家的暂定价。今天两价相等，不渲染，测试也绿。我在树外写了一个临时测试，把实时价 mock 得更低，头部立刻输出了划线价和折扣比例，而那个「官方价」是自家的旧价。修法是这类模型的官方价字段留空，并加一条「实时价更低时仍无划线」的测试。原来的测试只覆盖「两价相等」这一态，恰好是唯一不会出问题的那一态。
- **来回换汇推出来的「官方价」**：官方的外币价先换成本币、再按另一个汇率换回来，比官方页面上的原价高了几个百分点，页面宣称的节省比例因此大了一倍左右。修法是直接取官方同币种的原价，必须换算时只换一次，并注明汇率。

审查时我会对每个数字问一句：它来自后端返回、官方原文，还是一个公式？三样都指不到，就不给这个数。

## 8. 一张审计清单

| 查什么 | 怎么查 |
|---|---|
| 型号判断 | 全仓搜家族名的子串判断和精确判断；预扣和结算是否调同一个函数 |
| 查价失败分支 | 按秒、按 token 计费的型号会不会落进按次推算；保护按供应商类型认，不按名字 |
| 定价行覆盖 | 自检按结算的查价口径写：渠道 × 计费组 × 映射型号，期望缺失 0 行 |
| 只有生产知道的清单 | 开工时只读查询写死，脚本里只定义一处，不留「上线前再核」 |
| 阈值和规格数字 | 所有展示面用同一个格式化函数；边界符号从计费配置派生；改数字前全前端搜 |
| 明细时间字段 | 每类记录各核一次写入时刻；在途时查一次明细 |
| 推断与显式 | 列「显式模式 × 素材数」组合表，和执行端逐格对照 |
| 页面数字 | 每个数指得到来源；测试覆盖「会出问题的那一态」 |

## 收尾

1. **一件事只写一份** —— 预扣和结算共用一个计价函数，所有页面共用一个格式化函数。
2. **认计费方式不认名字** —— 名字前缀和子串会吞进新同族名字，按计费配置或供应商类型认。
3. **自检和结算同一个口径** —— 自检从「已有的行」取集合，正好看不见「一行都没有」的那个型号。
4. **兜底推算要问适用范围** —— 「预扣总额 ÷ 张数」只对按次计费成立，套到按秒计费上就是二次放大。
5. **测试挑会出问题的那一态** —— 两价相等、兜底等于实时值，都是看不出问题的态。

这些坑有一个共同的发现方式：接入前先读同族型号的代码，把新名字、新渠道、新组代进每一处查表的地方走一遍。下次碰到计费相关的改动，我会先列出这条链路上每一份规则拷贝，再动手。生产上怎么核计费，见[上线前回归](/blog/billing-regression/pre-launch-regression-real-billing/)；数据脚本怎么验，见[要进生产库的 SQL](/blog/billing-regression/sql-on-prod-shaped-db/)。
