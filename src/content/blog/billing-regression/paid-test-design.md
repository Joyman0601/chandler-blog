> 一句话总结：按次付费的接口，测试设计的目标是「每花一单钱，回答尽量多的问题」。做法是把观测量互相独立的维度合进同一条请求，测极端不穷举，先用一条必然失败的请求看扣不扣费，用同一组金标准在各渠道之间对照；每一单真打之前，先单独做一步不花钱的核对；用例表写成能原样粘贴执行的命令，每条带停止规则。

## 0. 起因：每一单都扣真钱

我做模型接入时，常要测视频、图像、语音这类生成接口。它们按秒或按张收费，有的还不能取消。第一次给一个视频模型写测试方案时，第一版照「一个参数一条请求」排，一个渠道一个版本就要二十来单，几个渠道乘下来又贵又慢。

我给 AI 助手定过一条规则：真实上游调用每天一个总预算，单次请求有上限。在上限以内，助手自己决定发不发，每一单记进任务目录的台账（时间、用途、预估、实扣）；超出任一上限才来问我。这条规则把「要不要花钱」变成了「这笔钱值不值」，逼着用例设计得更省。

下面是两周里在几类付费测试上攒下的做法，和两个让测试白花钱的坑。

## 1. 合并维度：观测量独立，就放进同一单

### 判断能不能合

关键问题是：**每个维度的结果，能不能从输出里单独读出来。**

以视频生成为例：

| 维度 | 从输出里读什么 |
|---|---|
| 画面比例、分辨率 | 画布宽高 |
| 时长 | 帧数和帧率 |
| 首帧、尾帧 | 第一帧和最后一帧是不是输入的图 |
| 音频 | 有没有音轨 |

这几项互不干扰。一条请求可以同时改比例、时长和音频，各读各的结果。设计时我先写一张覆盖表：每个维度的每个取值落在哪条请求里，保证每个取值至少出现一次。

| 请求 | 比例 | 时长 | 首尾帧 | 音频 |
|---|---|---|---|---|
| R1 | 横屏最宽 | 最短 | 只给首帧 | 开 |
| R2 | 竖屏 | 最长 | 首尾都给 | 关 |
| R3 | 方形 | 中间值 | 不给 | 开 |

### 哪些不能合

- **会让整条失败的维度单独放。**超长提示词、未知字段、可能不支持的模式（比如只给尾帧），合在一起失败了，说不清是谁导致的。单独放，或者放在「失败不花钱」的位置。
- **会互相干扰的参数分开放。**语音合成里，语速和语调都会改变音频时长。靠时长判语速时，语调就不能放在同一单。
- **主观量不合并归因。**画质会被多个维度同时影响，只放在金标准里横向比，不从合并单里归因。

### 测极端，不穷举

取值由公式决定的维度，比如短边固定、边长对齐、面积上限，我只测横、竖、最宽三个极端。时长只测最短、中间、最长。极端出了问题，再补中间值。

### 只有非默认值能证明参数生效

leader 在会上举过一个例子（转述）：传了 16 kHz 的采样率，就要在输出文件里量到 16 kHz，而不是看请求体里有没有这个字段。传默认值的话，生效和没生效在输出上一模一样。

一次语音合成模型的上线回归里实测过这条。语速要靠时长判，就需要一单同音色、同文本、不带语速参数的基准单。第一次时长反常，补了一单对照才判清方向。那次一共跑了 8 单，覆盖格式、采样率、语言、语速、音量、语调和几个专属参数（实测）。事后复盘推算，按「格式 × 采样率 × 音色来源 × 语言」交叉排成 3 单就够，语速、音量、语调取近极值搭车（推断，没有按 3 单重跑过）。

## 2. 先跑负向：失败扣不扣钱

正式排单之前，我先发一条必然非法的请求，回答三个问题：上游是同步拒绝，还是先受理、跑到一半再失败？失败扣不扣费？报错里有什么？

这一单往往很值。

- **同步拒绝通常不扣费**。那负向用例可以放心多测几条；如果受理后失败也扣费，就只测最影响网关校验写法的一两条。自家网关本来就会做参数校验，上游怎么拒绝只影响报错文案。
- **非法枚举能免费拿到允许值**。故意传一个不存在的型号或档位，上游同步拒绝时常在报错里列出允许的取值。不花钱就知道这个站点支持哪些档位。
- **并发上限顺带读**。核心用例并发提交，超出账号并发的那几单会被同步拒绝、不扣费，正好读出上限，不用专门压测。
- **一单分清取整方式**。按秒取整计费的接口，我选一段视频流和容器时长相同、时长特意取 x.4 秒的素材。四舍五入和向上取整差 1 秒，一单就能分清。

## 3. 金标准跨渠道对照，后续渠道只测差异

同一个模型常有几条供应商渠道，还有官方线。我准备一组金标准请求：同提示词、同素材、同参数、同随机种子，在每条渠道和官方线上各跑一次，横向比规格、耗时、实扣和画质。每条请求都拿账单和「秒数 × 单价」对一次。一组样本同时回答好几个问题，还能揪出偷偷降配的渠道。

第一条渠道摸清版本能力以后，同版本的其他渠道只跑金标准和最容易出差异的两条。第一条输出就不像目标版本（帧率、帧数、尺寸不对），立刻停。

有一次是给已上线的上游加一个新站点，代码、参数映射和计费策略都和老站点共用。我只测站点能带来的差异：站点（错误文案、审核）、账号（凭证格式、资源包、并发）、网络（它拉我们的素材、用户拉它的结果）、成本（按什么秒数扣）。参数映射已经由单元测试和老站点的生产流量覆盖，不按参数重测。老站点已有的真实单，原样搬到新站点当跨站金标准，不另付费跑基线。

需要说明：这套视频方案按上面的思路重新设计后被采纳了，但写这篇时还没在真实渠道上跑完，次数能降到原来的三分之一左右是按方案估的。语音回归那部分是实测过的。

## 4. 花钱之前，单独做一步不花钱的核对

同一类坑踩过三次。核对没有单独成一步，或者改错了地方，又没有一步能发现。

**案例一：渠道指向测试桩，任务照样打到真上游。**助手想零成本验证一条结果转存的链路，起了本地假上游，把渠道表里的上游地址改过去，重启网关，直接提交了一个生成任务。任务一直处理中，假上游的日志里一条请求都没有；执行端日志里写的还是真实上游地址。原来网关把任务派给 worker 时，上游地址取自另一张型号映射表，渠道表里的地址在这条链路上不参与。渠道里留着真实 key，于是真上游建了一个按秒计费、不能取消的任务。

**案例二：改了优先级，请求没落到测试渠道。**助手临时建了一条假 key 的测试渠道，把路由表里它的优先级调高，期望请求都走它、触发 401。实际两次请求都落到了真渠道。网关开着内存缓存时，选渠道按渠道表自己的优先级分层，路由表里的优先级只在直查数据库那条路径上用。

**案例三：素材没核对就提交。**助手请我上传一段 5 秒左右的视频跑付费生成，预算按 5 秒报过。我传了一个 12 秒的文件。助手的脚本把「量时长」和「提交两个任务」写在同一条命令里，时长打印出来时任务已经发出去了。这次碰巧 12 秒在所选模式下被上游拒绝，没扣费；换一个模式，就会超出已同意预算的一倍多。

三次的共同点是：核对写成了日志输出，而不是闸门。现在的做法是拆成两条命令，第二条带断言：

```bash
# 第一步：只核对，不提交
duration=$(ffprobe -v error -show_entries format=duration -of csv=p=0 sample.mp4)
echo "素材时长：$duration 秒（预算按 5 秒）"
tail -n 1 mock-upstream.log      # 指向测试桩时：桩的日志里必须已经有一条免费请求

# 第二步：看过上面的输出再执行；脚本里合并时用断言挡住
python3 - "$duration" <<'EOF'
import sys
d = float(sys.argv[1])
assert 4.5 <= d <= 5.5, f"素材 {d} 秒，和预算前提不符，停"
EOF
./submit_paid_task.sh sample.mp4
```

还有两个习惯：

- 留着真实凭证的环境里做桩测试，先把渠道 key 换成占位串。改道失败也只会鉴权失败，不会扣费。
- 报预算时写明它依赖的素材属性，比如「按 5 秒估」。属性一变，就知道预算要重报。

## 5. 用例表写成拿着就能跑

### 第一版写成了流程文档

我给一个 agent 类接口写测试方案，第一版有总览、术语、阶段编号、月度成本估算、备选方案和人天。leader 逐段看完给了意见（转述）：测试方案是拿着就能测的东西；开头只答两件事，选哪种方案、测一遍花多少钱，数字之前先写前提；每条用例要写具体发什么请求、预期什么、怎么判定。

重写以后，用例表成了主体。每条至少有这几列：编号、要验证什么、在流程哪一步、怎么做、预期、判定、花费、何时跑。

### 「怎么做」写成可以整段粘贴的命令

写成「用乙的身份查甲的会话」这种描述，读者还得自己翻译成请求，翻译这一步最容易错。我的做法是：开头一段准备命令，定义几个 shell 函数（按租户切身份、拼消息体、新开会话），每格只调用它们，收成一两行。

交付前我会空跑一遍：从渲染后的页面取出全部代码段，用假的外部命令按页面顺序整段执行，逐条核对每次调用用的身份、请求头、请求体。假命令要按调用次数返回不同的 ID，否则两个租户的会话 ID 相同，引用错了也看不出来。

### 每条付费用例写停止规则

付费用例在跑之前就写好「看到什么就停」。有一次测长输出，第一版用例让模型「写够 7 万 token」。模型直接拒写，只扣了很少一点，停止规则触发，没有继续烧钱。我把用例改成「翻译一篇长文」，第二版才真正触发了要测的行为。所以第一版用例本身就该当成探测，先用最便宜的一单验证设计。

停止规则还要能执行。排练后的复核发现一个问题：付费块被中途打断后，执行工具不保存这一块里的 shell 变量。照停止规则补发取消时，用到的还是上一块的执行器编号，结果可能停错对象，或者什么都没停到，日志却照样写「已停掉」。改法是在停止规则里写明：会话号、执行器编号、起算时刻都从本块日志里抄，不用 shell 变量。

## 6. 两个让测试白花钱的环境坑

### Mac 闲置睡眠，冻住了本地守护脚本

一次云端 agent 会话的长上下文付费测试，助手在本机跑了一个守护函数：每 20 秒查一次会话状态，约每分钟查一次用量，累计花费到上限、或单轮超过 600 秒就发取消。某一轮提交以后：

- 守护日志停了 15 分钟，一行轮询都没有。醒来第一次查询报 `SSLEOFError`，紧接着按「已过 600 秒」判超时，发了取消。
- 这次取消其实是空操作：会话早在这期间自己跑完、回到空闲了。只看守护日志，会读成「这一轮超时，被取消」。
- 本地执行器（挂在云端会话上的长连接）在睡眠时断开，醒来重连回 401，进程退出了。

`pmset -g log` 里，提交后 22 秒出现了这一行：

```text
Entering Sleep state due to 'Idle Sleep'
```

`pmset -g` 显示 `sleep 1`，闲置 1 分钟就睡。守护在跑、人在等结果时，键盘鼠标都不动，系统就当作闲置。云端的会话不睡，照常推理、照常计费。

修法是付费块开跑前在后台挂 `caffeinate`，跑完按 PID 停掉：

```bash
caffeinate -s -i -t 7200 &   # -i 拦闲置睡眠，-s 接电源时拦系统睡眠，-t 到时自己退出
CAF=$!
# …… 付费块 ……
kill "$CAF"
```

醒来以后，先核三样再下结论：会话现在的状态、睡眠期间的用量、执行器进程和它的日志。执行器退出了就重新挂上，等日志里出现新的连接成功行再提交下一轮。正式环境的花费熔断要放在服务端或常开的机器上，开发机上的脚本只当测试辅助。

### 推理档位校准，被输出上限压平了

另一次要判断推理模型的 `thinkingBudget` 这类参数落在哪一档。设计是先用显式的 low、medium、high 各跑一单做校准，再拿思考 token 数去判别。为了省钱，助手把输出上限设成了 2,048。

结果三档的思考 token 是 1,965、1,962、1,962，几个固定预算的写法也都在 1,963 左右。看上去「档位不起作用」，其实是这道题在每一档都想用超过上限的思考，被上限截平了。只有动态写法不一样：思考 3,929 token，冲破了上限，回答被截断。等助手发现校准失败时，后面的落档单已经花掉了。

改法是：

1. 校准前先花一单，用最高档、不封顶，量出自然的思考用量，上限设在它的 1.5 倍左右。预算放不下就换一道更短的题。
2. 校准单跑完立刻检查，相邻档位相差不到 30%，或者各档都贴着上限，就停下改设计，不接着跑落档单。
3. 每单都看结束原因。没有思考的单，思考 token 字段可能整个不出现，按 0 处理，并用实扣印证。

这和第 1 节是同一个道理：观测量被某个上限压平了，就失去了区分能力。

## 7. 一张付费测试的检查清单

设计时：

- [ ] 写覆盖表：每个维度的每个取值落在哪条请求；观测量不独立的不合并。
- [ ] 每个参数取非默认值，从输出量，不看请求体；需要时备一单基准。
- [ ] 第一单是必然失败的请求：同步拒绝还是受理后失败，扣不扣费。
- [ ] 每条付费用例写好预估、上限和停止规则；第一版用例当探测，先跑最便宜的一单。

每一单真打之前：

- [ ] 素材属性单独量过，和预算前提一致。
- [ ] 指向测试桩时，桩的日志里已经有一条来自这条链路的免费请求；真实 key 换成了占位串。
- [ ] 今天的台账加上这一单，仍在每日预算和单次上限以内。
- [ ] 本机跑的长付费块挂了 `caffeinate`。

跑完以后：

- [ ] 实扣和公式对过，记进台账。
- [ ] 校准类测试先看各档有没有拉开，再往下跑。

## 收尾

1. **按观测量合并** —— 能从输出里单独读出来的维度放进同一单，会让整条失败的单独放。
2. **先问失败扣不扣钱** —— 一条必然失败的请求，常常顺带给出允许值和并发上限。
3. **核对单独成一步** —— 改配置不等于流量改道，素材不一定是约定的那个，先看到核对结果再提交。
4. **用例写成命令** —— 可粘贴、空跑过、带停止规则，ID 从本块日志里抄。
5. **防止观测量被压平** —— 机器睡着时守护失灵，输出上限太小时档位分不开，都要先确认测量本身有区分力。

回头看，最省钱的一步永远是「先花一单最便宜的，验证设计本身」。下次排付费用例，我会先写覆盖表和停止规则，再写第一条命令。上线前在生产上怎么排这些用例，见[上线前回归](/blog/billing-regression/pre-launch-regression-real-billing/)；agent 类接口的花费怎么估，见[估 agent 类接口的花费](/blog/billing-regression/agent-api-token-cost/)。
