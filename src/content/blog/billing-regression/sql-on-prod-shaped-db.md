> 一句话总结：开发库、开发库导出的「生产」夹具、sqlite、ORM 自动迁移建出来的库，都不是生产形状。手写数据脚本里有一类错只在整份真跑时才报，只读评审看不出来。所以要进生产库的 SQL，提交前在生产形状的表结构上、按几种可能的排序规则、用固定场景整份跑一遍，再从生产实际用的网页通道复跑一遍。

## 0. 起因：三次验收全绿，三次被审出来

接入一个新模型，最后一步是一份数据初始化脚本：建渠道、挂型号映射、写定价、开路由。脚本由有生产权限的人在 phpMyAdmin 网页里执行，我自己碰不到生产库。

短短几天里，三份这样的脚本都是验收全绿、交出去以后才被审出问题：

1. **列宽**。一个新供应商的注册名，超出了生产任务表里存供应商名那一列的宽度，生产又开着严格模式。上线后一个任务都建不出来，报 1406。生产列比本地窄，本地库那一列宽得多；单元测试用的 sqlite 根本不查长度。
2. **缺列、缺键**。脚本用 `ON DUPLICATE KEY UPDATE` 保证重跑不重复，子句里引用了本地表有、生产表没有的一列，所以在生产上报 1054，装一半停住。生产表同时还缺本地有的唯一键，就算把列换成生产有的，这个子句也永远不会触发。
3. **排序规则**。脚本只在一种排序规则的夹具上验过。线上排序规则和夹具不一致时，第一条跨表比较就报 1267，整份装不上。

三次的原因是同一个：验证用的表结构来自开发库。

## 1. 为什么开发库不算生产形状

开发库和生产库的差别，比想象的多：

- 缺代码新加的列：ORM 里有，开发库没迁出来。
- 缺生产的遗留列：生产脚本一直在写，代码从没声明过。
- 排序规则不同。
- 多出生产没有的主键和唯一键。
- 列比生产宽，sqlite 和内存库不查列宽、不开严格模式。
- ORM 自动迁移可能漏建表。有一次网关在临时库上起来，日志写着「database migrated」，中间夹着几行 `Error 1091 (42000): Can't DROP '...'`。ORM 顺着关联字段先迁移被引用的表，删一个索引失败后放弃了这次迁移，带关联的任务表一起没建。

第 2 个问题里还有一个更隐蔽的坑：那份夹具的文件名里写着「prod」，七个场景全绿。打开文件头一看，写的是 `Host: localhost`，其实是开发库导出的。开发库导出的表结构比生产多出了列和键，脚本在它上面当然全绿。

下面用编的表名复现这两层问题（MySQL 8.0 实测）。`routes` 按生产形状建：没有子句里引用的那一列，也没有任何键；`tmp_routes` 里放 2 行。

```sql
-- 改前：子句引用了生产表没有的列
INSERT INTO routes (grp, model, channel_id, enabled)
SELECT grp, model, channel_id, 1 FROM tmp_routes
ON DUPLICATE KEY UPDATE routes.route_id = routes.route_id;
-- ERROR 1054 (42S22): Unknown column 'routes.route_id' in 'field list'

-- 把列换成生产有的 enabled：不再报错，但没有唯一键，子句永远不触发
-- 跑一次 2 行，原样重跑变成 4 行

-- 改后：不依赖任何键
INSERT INTO routes (grp, model, channel_id, enabled)
SELECT t.grp, t.model, t.channel_id, 1 FROM tmp_routes t
WHERE NOT EXISTS (
  SELECT 1 FROM routes r
  WHERE r.grp = t.grp AND r.model = t.model AND r.channel_id = t.channel_id
);
```

目标表没有唯一键时，换成哪一列都没用，只能改成上面的 `NOT EXISTS`，重跑仍是 2 行。

现在建夹具时，每张表的表头写上出处和日期，可信度从高到低是：线上实查的建表语句 > 有权限的人本机的线上副本 > 代码里的 ORM 定义 > 推断。改夹具之前，先用改动前的脚本跑一次，确认能复现当时的报错，证明新夹具确实「更像生产」。

## 2. 排序规则：说法矛盾，就把几种都跑一遍

### 为什么只和字面量比较的旧脚本从没出过事

仓库里历届上线脚本对渠道表排序规则的说法互相矛盾：MySQL 8 上最常见的两种 utf8mb4 排序规则，各有脚本这么写。

MySQL 比较两个字符串时，要看两边的「强制性」（coercibility）。临时表的列、用户变量、表列都是同一级。两边排序规则不同就报 1267。字面量的强制性最弱，会跟随另一边。所以旧脚本只拿表列和字面量比，从来没出过事；我的脚本用了 `@变量` 和临时表，就撞上了。

三招：

1. 常量写字面量，不用 `@变量`。
2. 同一张表里能比的，用同表自连接。
3. 剩下的跨表、临时表比较，两侧都显式写 `COLLATE`，ASCII 名字用 `utf8mb4_bin`。

```sql
SELECT c.id
FROM channels c
JOIN tmp_slots s ON s.name COLLATE utf8mb4_bin = c.name COLLATE utf8mb4_bin;  -- ← 两侧都写
```

只把一张表换成另一种排序规则还不够，测不到「定价表和目录表之间」这类比较。我最后做了四套变体：全 0900、全 unicode、以及两种几张表交错的组合。

### 自检段的 UNION 报 1271

一份脚本的安装段四套都过了，只有文末自检那条「十行 `UNION ALL` 拼起来的 SELECT」在三套 unicode 变体上报：

```text
ERROR 1271 (HY000): Illegal mix of collations for operation 'UNION'
```

每个分支的输出列，一边是字面量（连接的排序规则），一边是表列（表的排序规则）。`UNION` 要求各分支同一列的排序规则能合并，比较两侧加 `COLLATE` 救不了输出列。

改法是先建一张列排序规则写死的临时结果表，每项检查一条 `INSERT … SELECT`，最后整表输出：

```sql
CREATE TEMPORARY TABLE chk (
  seq INT, item VARCHAR(64) COLLATE utf8mb4_bin, ok VARCHAR(4) COLLATE utf8mb4_bin
);
INSERT INTO chk SELECT 1, '每个新渠道都有映射', IF(COUNT(*) = 0, '✅', '❌')
  FROM new_channels n WHERE NOT EXISTS (SELECT 1 FROM channel_models m WHERE m.channel_id = n.id);
INSERT INTO chk SELECT 2, '定价无缺行', IF(COUNT(*) = 0, '✅', '❌') FROM missing_prices;
SELECT * FROM chk ORDER BY seq;   -- ← 最后一条语句输出结论
```

`INSERT` 会做隐式转换，不报混合排序规则的错。网页工具通常只显示最后一张结果表，正好。

## 3. 只读评审看不出的几类错

下面这些错，读脚本时都觉得没问题，整份一跑就红：

| 报错 | 原因 | 改法 |
|---|---|---|
| 1137 `Can't reopen table` | 临时表在一条语句里出现了两次（自连接、两个子查询各引用一次、UNION 两边） | 拆成独立语句；自检改用 CTE，CTE 在一条语句里可以引用多次 |
| 1046 `No database selected` | 「表名都带库名」漏了临时表；多表 `DELETE a FROM db.t1 a JOIN …` 全带库名也报 | 每处都带库名；多表 DELETE 改成单表 `DELETE … WHERE id IN (SELECT …)` |
| 1052 列名歧义 | `INSERT … SELECT … ON DUPLICATE KEY UPDATE col = …`，来源里有同名列 | 引用目标表的列一律写 `目标表.列` |
| 1064 语法错 | 回滚段整段注释，给人看的说明行也只有一层 `-- `，按「整段去注释」执行就成了裸文本 | 段内说明行写 `-- -- `，去一层仍是注释 |

1052 那次助手还犯了一个流程错：按审查意见改了来源表，没等检查跑完就提交了，结果四套排序规则加网页通道全红。现在的规则是看到「❌ 0」再提交，不并行提交。

还有两条判定上的坑：

- **自增值**。`INSERT … ON DUPLICATE KEY UPDATE` 撞键时行不变，自增照样前进。判「重跑没改数据」要按行内容比；判「前置失败零写入」要连自增一起比。读 `information_schema` 里的自增值前，先执行 `SET SESSION information_schema_stats_expiry = 0`，否则 MySQL 8 默认缓存 24 小时，读到旧值。
- **软删除**。回滚段按名字删渠道，没带「未软删除」的条件，把种子里一条软删除的同名旧渠道也删了。回滚后校验和对不上，才发现。

## 4. 按型号认渠道，不按名字

一份给已有模型加一组新地域渠道的脚本，原来按名字找几条源渠道，新渠道命名为「源名 + 后缀」，重跑、自检、上线开关、回滚都靠名字配对。四套排序规则、十几个场景全绿。leader 看方案时问了一句（转述）：渠道名运维随时能改，后端用的是型号，型号不会变，为什么用名字？

我在生产形状的临时库上验证了这个问题：首装前把一条源渠道改个名，整份脚本找不到源、什么都不写；装好后把新渠道改个名再重跑，自检报 3 个 ❌；一类型号挂了两条源渠道，旧脚本照样写数据。

改法：

1. 一张临时表定义「类别 × 供应商类型 × 型号」，型号清单只写在这一处。
2. 源渠道 = 挂着这类型号的启用映射、地址不在新地域的渠道，每类恰好一条；新渠道 = 映射地址在新地域的同类渠道，每类至多一条。
3. 一类有多条源渠道、渠道跨两类、新地域地址却没有映射（手工建了一半）、新建的名字撞名，任一情况整份不写。
4. 新建行要拿 id 时，在同一事务里紧接着按「刚起的名字 + 新地域地址 + 还没有映射」认一次。映射建好以后，就一直按映射认，名字再改也无所谓。

改完以后又出过一次事。上线开关和回滚段是装完以后单独执行的，不受前置检查保护。它们只按「有一条映射地址在新地域」认新渠道，没核渠道自身的地址。于是构造一个状态：一条原有地域的渠道有一条映射被改成了新地域地址。安装段被守卫拦住、零写入；同一状态代进回滚段，会把这条原有渠道连同映射、定价、路由一起删掉。助手只测了安装段，就以为这个状态安全；复核时把同一状态代进上线和回滚段，在生产形状的临时库上才跑红。

修法是这两段也按映射认，而且条件不能比安装段宽：再要求渠道自身的地址也在新地域；回滚先把要删的 id 记下来，再按 id 删子表、最后删渠道。新加的 4 个场景，在按名字认的旧版上都是红的。

## 5. 锁范围：按 data_locks 实测，不凭直觉写

一份补用户组的脚本，注释里对锁的描述改了三版。第二版写的是「只锁目标模型相关的行和间隙；网关运行时不写这两张表」。新上下文的复核拿同一份锁快照推翻了它：按组过滤走了组索引，共享锁覆盖了其他模型在这个组下的全部行；而网关在自动禁用、启用渠道时，会更新路由表的启用状态。

**根因**：可重复读隔离级别下，`INSERT INTO t SELECT … FROM s` 会给 s 上扫描到的行加共享的 next-key 锁。扫描范围由优化器选的索引决定，WHERE 里的其他条件不缩小加锁范围。

**实测方法**：在临时库里让事务停在 COMMIT 之前，另开一个连接查：

```sql
-- 连接 A：执行脚本，在 COMMIT 前插一句 SELECT SLEEP(30);
-- 连接 B：
SELECT object_name, index_name, lock_type, lock_mode, lock_data
FROM performance_schema.data_locks
ORDER BY object_name, index_name;
```

把每一行 `lock_data` 对回种子数据，看锁到了哪些「不该碰」的行，写进注释。再在代码里搜运行时对这张表的写入，包括错误处理、定时任务和后台保存。想缩小锁范围，可以把只读计算挪到事务外先存进临时表，事务里只做写。夹具上的锁范围不等于生产，索引选择随数据量变，所以注释里写「夹具实测，生产可能不同」。

## 6. 回滚测试：要有一个去掉事务的对照

验证「中途出错会整体回滚」，常见做法是在中间插一条必错语句，看前后快照是否相同。相同只说明「最后没变」。如果报错点前面的语句本来就没写任何东西，快照也不变。

所以要再跑一个对照：同一份注入脚本去掉 `START TRANSACTION`，快照应该变成「做了一半」的样子。

```bash
snap > before.txt
mysql app < inject.sql                    # 在「删旧行之后、重建之前」插了一条必错语句
snap > after.txt
diff before.txt after.txt && echo "有事务：不变"

restore_installed_state
sed '/^START TRANSACTION;$/d' inject.sql > inject_notx.sql
mysql app < inject_notx.sql
snap                                      # 预期：删除留了下来，目标行数变成 0
```

两个结果一起，才证明是事务在起作用。注入点要放在「已经写过东西、还没写完」的地方。DDL 会隐式提交，对照证明不了脚本里没有这类语句，要另外读。

反过来，脚本没有事务时要写清楚。有一份改价脚本就没有事务，中途失败不会撤回已执行的语句。报告里写明「本地检查通过不等于生产操作完成」。

## 7. 只认网页通道：用 Playwright 驱动 phpMyAdmin

生产只能在 phpMyAdmin 网页里执行，所以命令行跑通还不算。我起一个临时 phpMyAdmin 连临时 MySQL，用 Playwright 把整份脚本粘进 SQL 框执行：

```bash
docker network create tmp-net
docker run -d --name tmp-mysql --network tmp-net -e MYSQL_ROOT_PASSWORD=pw mysql:8.0
docker run -d --name tmp-pma --network tmp-net -e PMA_HOST=tmp-mysql \
  -e PMA_USER=root -e PMA_PASSWORD=pw -p 127.0.0.1:18081:80 phpmyadmin/phpmyadmin
```

```js
await page.goto('http://127.0.0.1:18081/index.php?route=/server/sql'); // 服务器级 SQL 页，不选库
await page.waitForFunction(() => [...document.querySelectorAll('.CodeMirror')]
  .some((e) => e.CodeMirror?.getTextArea?.()?.id === 'sqlquery'));
await page.evaluate((sql) => {
  const el = [...document.querySelectorAll('.CodeMirror')]
    .find((e) => e.CodeMirror?.getTextArea?.()?.id === 'sqlquery');
  el.CodeMirror.setValue(sql);
  el.CodeMirror.save();
}, sqlText);
await page.click('#button_submit_query');
await page.waitForLoadState('networkidle');
// 只在结果表里数 ✅ / ❌：页面会回显整段 SQL，脚本里的字面量也会被数进去
const results = await page.$$eval('table.table_results', (ts) => ts.map((t) => t.innerText));
```

几个坑：

- SQL 框背后的 textarea 是隐藏的，等「可见」永远等不到，要写进 CodeMirror 实例。页面上有两个 CodeMirror，要按 textarea 的 id 找。
- 结果里的 `#1051` 可能只是 Note（`DROP TEMPORARY TABLE IF EXISTS` 第一次执行时出现），不是错误。
- 网页只渲染最后一条语句的结果。有一份脚本的自检以 `DEALLOCATE PREPARE` 收尾，单独贴自检时页面上 0 个 ✅、0 个 ❌。自检段的最后一条必须是输出结论的 SELECT。
- 页面截在「Loading…」时，结果表 0 张、错误 0 条，照样会被判成通过。判定要求结果表数量大于 0。

## 8. 一条命令跑完：场景清单

上面这些后来做成了一条命令：生产形状的表结构 + 四套排序规则 + 固定场景 + 网页通道复验。

| 场景 | 判定 |
|---|---|
| 首装 | 自检全 ✅ |
| 原样重跑 | 行内容不变 |
| 运维改值后重跑 | 运维改过的值保留 |
| 删一行后重跑 | 只补回那一行 |
| 三种前置失败 | 零写入，自增也不变 |
| 回滚 | 回到首装前，校验和一致 |
| 事务对照 | 有事务不变，去掉事务变成「做了一半」 |
| 不选库执行 | 照样落到正确的库 |
| 网页通道 | 整份首装、单独贴自检、原样重跑，结果和命令行一致 |

每份脚本还要声明一个「基线红」：旧版本或故意改坏的副本，跑出来必须是红的。有一次我做了一个删掉路由段的副本，跑出 4 个失败，说明这些场景抓得住缺陷。拿当年出事的旧脚本重跑，也能复现当时的 1054 和 1267。

固化以后第一次用，就在一份已经验收过的脚本上查出了问题：它当时只在一种排序规则的夹具上验过，换到另外三套变体上，首装都报 1267。按最近的线上实查记录它能装，按另一种说法装不上。我没有自己判成「不影响」，默认照常上线，附了一条上线前确认排序规则的只读查询，交给有权限的人决定。

## 9. 写入与回滚：对象范围必须相同

后来一次复审又补出一个边界：安装脚本给符合某些外观条件的对象写了子记录，归属登记却只收集活跃且属于本次安装的对象。外来的软删除对象没进登记表，却已经被写入。回滚只清登记范围，于是留下残留，下一次安装又被冲突检查挡住。

原来已有软删除回滚用例，仍没有覆盖这个方向。它验证的是「回滚别删外来对象」，新缺陷是「安装别给外来对象新增内容」。两条预期需要分别成立。

可以把集合关系写出来，给评审一个独立预期：

```text
本次允许变更集合 = 当前有效对象 ∩ 本次明确认领的对象
写入、归属登记、自检、回滚都按这份集合核对
```

实现可以因表关系使用不同语句，但语义范围不能各自扩宽。登记发生在写入后时，还要能证明没有对象已经被写入、却未被认领。

我现在会在种子里同时放入：本次目标、外来同名对象、外来软删除对象和运维改过值的对象。运行安装、重跑、回滚、再安装，对比目标内外的行内容；不仅看安装结果表有没有红字。

历史补修使用合成库存验证了这条链路，并用分别撤掉两处筛选的变异抓住遗漏。它不代表生产真实库存已经核过。生成器输出的脚本还要重新生成、重新检查，不能只修生成源后继续交旧文件。

## 10. 自检完整性：分别出现过，不代表组合齐全

另一次自检分别统计规格和分组：所有规格都出现过，所有分组也出现过，就显示齐全。实际上缺的是组合。

用一个自编例子看更直观：规格 A、B、C，分组 x、y。实际只有 A-x、B-y、C-x，规格和分组的并集都齐了，但六个应有组合只有三个。

```python
from itertools import product

expected = set(product(["A", "B", "C"], ["x", "y"]))
actual = {("A", "x"), ("B", "y"), ("C", "x")}
assert expected - actual == {("A", "y"), ("B", "x"), ("C", "y")}
```

真实系统还可能有可达渠道、工具角色或地区。先从有效路由和已确认的开放策略导出应有集合，再逐组合查缺、查重。不是所有维度都应无条件做笛卡尔积：某渠道本来不开放的组合，应由独立策略说明为什么排除。

缺失检查也不能只从现有价格行出发。如果某个组合连第一行都没有，内连接根本枚举不到它；要从应有集合反查实际数据。写入前发现缺失应阻断，单独运行自检也应报出同一缺口。

这两轮补查让我把「脚本能跑」「对象归属正确」「组合覆盖完整」分成三项。前两项通过，第三项仍可能为空；总行数符合某个数字，也可能同时包含重复与缺失。

## 收尾

1. **表结构要来自生产** —— 夹具写明出处和日期，文件名叫「prod」不算数，先看文件头。
2. **说法矛盾就都跑** —— 排序规则说不准时，做几套变体，交错的组合也要有。
3. **整份真跑才算** —— 临时表引用、库名、同名列、注释层数这几类错，只读评审看不出。
4. **认对象按不会变的键** —— 名字给人看，型号映射才是代码用的；不在门控里的段，条件不能比安装段宽。
5. **「没变化」要配对照** —— 回滚测试去掉事务再跑一次，锁范围按 data_locks 逐行对回种子。

回头看，这三次问题都是「验证的东西和生产不是同一个」。下次写要进生产库的脚本，我会先把表结构的出处写在第一行，再写第一条语句。计费链路上相关的坑见[计费规则的几个暗坑](/blog/billing-regression/billing-rule-pitfalls/)；Playwright 走查页面的更多细节见[用 Playwright 走查页面的一串坑](/blog/testing/playwright-walkthrough-gotchas/)。
