> 一句话总结：付费回归里最贵的错误往往出在执行上。前置检查失败时，下游的付费发送次数必须真的是零，靠代码分支保证，不靠「顺序写对了」；要拿余额差当实扣，先取得账号独占交接，自己按明细核费时也别闯进别人的独占区间；预扣和结算是两套口径，「完成了、扣得不比预扣多」证明不了扣对了。

## 0. 起因：三天里的几次回归，坑都在自己这边

那几天连着做了几次上线后的付费回归：一个文本模型的请求整流修复，一个视频模型新出的轻量变体，一个图像模型新加的「一次请求产出多张图」能力的预装，还有一个管理后台日志筛选的修复。回归的做法沿用[上线前回归](/blog/billing-regression/pre-launch-regression-real-billing/)那一套：普通账号、真实扣费，每一单让历史记录、任务日志、余额差和独立公式对上。

回头复盘时，产品缺陷只占一小部分。更多的问题出在执行：AI 编程助手的前置检查失败了，付费请求照样发了出去；两个窗口共用一个账号，各自的余额差互相污染；预扣按上限冻结、结算按实际产出收，被当成一个数核。还有几处是用例本身没验：构造的「非法」输入其实返回 200，错误文案被网关改写后正则误报失败。

这些不是新知识，回归手册里大多写过。它们还是发生了，说明「写在清单里」和「执行时真的做到」之间有距离。下面按三条纪律整理，每条讲现象、为什么会这样、现在怎么做，最后给一段可以直接拿走的发送前检查脚本和一张清单。

## 1. 前置检查要让发送真的为零

**现象**：文本模型那次回归，我和另一个回归窗口共用同一把密钥。助手的计划是：等对方停手，做一次零探测（发一条必然被拒、不该扣费的请求，确认余额不动），核预算，再发付费单。三步写在同一个批量执行里。结果零探测那一步退出码是 1，付费进程照样启动了。等助手拿到整批输出、看到失败时，付费请求已经发出去。

**根因**：批量脚本里 `await` 等到的是结果对象，不是成功。非零退出码不会自动抛异常，只是被打印出来。整批只保证了「先后顺序」，没有保证「前一步失败就停」。助手读过账号独占的规则，也确实把等待写在了发送前面，可是顺序写对不等于条件写对。

这件事不能写成「助手看到失败后又决定继续发」。准确的说法是：同一批脚本没有按前置结果分支，主会话收到输出时请求已经发生。把原因写准，修法才找得对：要改的是脚本，不是「下次看仔细点」。

**修复**：前置检查做成闸门，放在下一步启动之前，并且在读取密钥之前就拒绝。任何一项缺失、失败或未知，都让后面的付费发送次数为零。判定要「默认关」：拿不到结果和拿到失败结果一样处理。

```python
# paid_gate.py：付费发送前的最小闸门（示意，按自己的任务改字段）
import json
import sys
import time


class GateClosed(Exception):
    pass


def check_gate(preflight: dict, handoff: dict, now: float) -> None:
    # 1. 前置步骤必须真的结束且成功；缺字段按失败处理
    if preflight.get("finished") is not True:
        raise GateClosed("preflight unfinished or missing")
    if preflight.get("exit_code") != 0:
        raise GateClosed(f"preflight exit_code={preflight.get('exit_code')}")
    # 2. 零探测的用量差必须是 0（不是「接近 0」）
    if preflight.get("probe_usage_delta") != 0:
        raise GateClosed("zero-probe delta is not exactly 0")
    # 3. 账号独占要有明确确认，写明来源和有效期
    if handoff.get("exclusive_confirmed") is not True:
        raise GateClosed("no exclusive-use confirmation")
    if not handoff.get("source"):
        raise GateClosed("confirmation has no source")
    if now > handoff.get("expires_at", 0):
        raise GateClosed("confirmation expired")


def main() -> int:
    preflight = json.load(open(sys.argv[1]))
    handoff = json.load(open(sys.argv[2]))
    try:
        check_gate(preflight, handoff, time.time())
    except GateClosed as e:
        print(f"[gate] closed: {e}", file=sys.stderr)
        return 2  # ← 在读密钥、建客户端之前就退出
    cred = load_key()  # 闸门通过后才碰密钥
    send_paid_cases(cred)
    return 0
```

闸门本身也要测，而且测的是「下游发送次数」，不是「打印了 FAIL」。最小的做法是把发送函数换成计数器，喂一组坏输入：

```python
# test_paid_gate.py：每种坏前提，发送次数都必须是 0
BAD_CASES = [
    {},                                                    # 缺回执
    {"finished": True, "exit_code": 1, "probe_usage_delta": 0},
    {"finished": False, "exit_code": 0, "probe_usage_delta": 0},
    {"finished": True, "exit_code": 0, "probe_usage_delta": 3},  # 零探测不为零
]
# 另加：确认缺失、来源为空、确认已过期；再加一条全部合格的放行对照，
# 证明测试不是因为闸门永远关着才通过。
```

放行对照这一条不能省。全是拒绝用例的测试，闸门写成 `raise` 永远关着也能全绿。

还要说清这道闸的边界。它只保护这个任务自己的入口。同一账号上别的工具、别的窗口如果不经过它，照样能发。所以它解决「我自己别在前提不成立时发」，解决不了「账号上只有我在发」，后者是第 2 节的事。

## 2. 余额差对账要独占账号

### 2.1 读数稳定不等于只有我在发

**现象**：还是那次共用密钥的回归。零探测本该净差为零，读出来却有一笔不小的差额。随后一条普通请求，按响应复算应扣一个数，余额差却比它大出一截。第一反应容易是「重复扣费了」。等对方窗口停手、给出分段读数，才核出多出的那截正是对方同一时段的一条请求。

**根因**：账号余额差 = 本次调用 + 同区间别人的调用 + 迟到的结算。前两次读数相同，只说明那一小段时间余额没动，不能证明账号上没有别的发送者。发一条「我要开始了」的通知、自己单方面加一把文件锁，也约束不了不使用这把锁的窗口。

**修复**：

1. 一个账号同一时间只留一个发送者。拿到对方或我本人明确的「已停止、可以独占」确认后，再取基线。确认要记下来源和时间，过期的确认不能拿来恢复付费调用。
2. 已经被污染的样本，原始读数原样保留，不计入逐单通过数。独占之后换一个新的样本名重测，不覆盖旧的。
3. 不做「减到预期」。有了对方完整的分段账务，可以解释总花费；但在不知道其他交易是否齐全时，拿总差额减掉一个「看起来像别人的数」凑出预期，等于用结论倒推证据。

### 2.2 我按明细核费，也会污染别人

视频模型那次回归更隐蔽。同一个账号上，另一个窗口在跑一单图像生成，它不看余额差，只按任务明细核费，自己的那一单对得严丝合缝。可我这边正在用余额差逐单对账，其中一单的区间增量比任务费多出一截，多出的部分恰好等于那一单图像任务的费用。

对方发送之前，其实能读到我在台账上写的「本窗口已确认独占账号」。助手的判断是：我只按任务明细核费，不受余额影响，于是继续发了。错在把「我的取证方法不依赖余额差」推成「我的请求不会影响别人的取证」。自己的结果没受影响，不代表没破坏别人的前提。

复盘时还有一处时间线要摆正。我这边发协调消息，是在对方那单已经发出、甚至已经完成之后才到的。所以「对方漏读了协调消息才发单」不成立。真正的执行缺口有两个，要分开记：发送前读到了独占声明却没先协调；收尾时没回读消息，也没及时回传「已停止、无在途」。

现在的做法：

- 任何付费发送前，先看同账号的登记、其他窗口的台账和收件箱。有人声明独占，先协调出一个时段交接，再决定各自怎么对账。
- 收尾时重读收件箱，明确回传三件事：全部生成已停止、刚才发了哪几单、有没有还在途的任务。
- 被污染的那一单，双方都保留原始值，不计余额差逐单通过；出片和任务费照常记。

### 2.3 测试窗口和生成耗时分开记

两次复盘里都出现了同一种时间口径的混淆。「测试窗口」包含人工登录、准备素材、协调等待；「单条生成耗时」只是从提交到终态；报告、清理、复盘又是另一段。把整个窗口写成「测一次要这么久」，会让人以为接口慢；把串账排查算进生成耗时，又会冤枉上游。计时要按段落盘，各段可以重叠但不能相加，细节见[缩短上线回归](/blog/billing-regression/regression-core-set-single-key/)。

## 3. 预扣和结算口径分开核

### 3.1 按上限预扣，按实际产出结算

那个图像模型的多图能力，请求里的 `n` 是「最多产出几张」的上限，并不保证真产出那么多。提交时既不知道实际张数，也不知道每张的尺寸，所以预扣按「1 张输入 + n 张高档」冻结；完成后按每张图的实际像素判高档还是低档，分别计费，多冻结的部分退回。

这里有三个容易混的地方：

- **单位不同的字段不能互相替代**。请求的 `n`、实际输出张数、每张的像素数、上游回执里的 token 数，各说各的事。回执只有图片地址是不够的，还得保留结算需要的逐张像素信息。
- **第一张高档不代表每张都高档**。同一次请求产出的多张图尺寸可以不同。按「最高档位 × 张数」估结算，会系统性偏高。
- **兜底分支会伪装成「扣对了」**。缺价或渠道信息缺失时，专用分支按整笔预扣额结算并告警。这避免了总价再乘一遍数量，却也不退本该退的差额。所以「任务 completed、实扣不超过预扣」这两条都成立，费用仍可能是错的。

核这类计费，要把图下载下来自己量尺寸，独立数出高档、低档各几张，按公式算出应扣，再去对历史记录、账单和独占区间的余额差。另一条边界也要写清：同步请求 400 净扣为零，只说明这条请求最后没扣钱，证明不了「任务预扣后又退款」的那条路径走通了。

文本模型那次有个同类的点：原生流式响应的首帧带一个「估算」的用量，末帧才是结算用量。只用末帧计费并独立复算，两帧不能相加。

### 3.2 同族共用估价函数，取整规则可能不同

视频模型的新变体复用了同族旧型号的「计费秒数」函数，只换了单价和最大时长。函数内部却固定向上取整，而新变体的契约要求四舍五入。3.4 秒的视频，契约算 3 秒，旧函数算 4 秒。线上页面的估价因此高于实扣：参考生视频一单、编辑时不传时长一单，两处都是。

这个错能活到线上，有两个原因：

1. **整数时长的素材让两种规则结果相同**。用 3 秒、5 秒的素材测，向上取整和四舍五入算出来一样，测试全绿。要用 3.4、3.6 这种小数时长，才分得开。
2. **实现和预期用的是同一个函数**。好几个组件共用这个 helper，它们一致地错，彼此对得上。复用计费逻辑时，要把时长来源、取整方式、最小值和上限都列成契约，用一个独立写的公式给出预期，再去对页面估价和结算。

还要分清「哪条证据证明了计费数量，哪条只证明了费用归属」。这次没拿到上游的用量原文，公开的任务费用和余额对齐，只能说明钱扣在了这单上，不能升级成「已经核过官方回执」。

## 4. 用例自己也要先验

### 4.1 构造的「非法」输入，实际返回 200

为了测「失败退款」，助手构造了一条把输出上限参数设得极大的请求，预期上游拒绝。实际返回 200，正常出结果。这条用例因此什么也证明不了，既不能证明失败退款，也不能证明输入大上游就必拒。后来改成提交一个不存在的文件类型，拿到参数 400，再观察一段结算时间，最终净扣为零。

教训是：负向用例的「负向」本身要先确认。先用一单看清它真的失败、在哪一层失败，再拿它测退款。另外，最终 200 区分不了「上游直接接受」和「整流后救回」，要证明整流真的触发，需要日志、统计或一组有效的对照。

### 4.2 错误文案被网关改写，正则误报失败

那条参数 400 的判定，最初用正则去匹配上游错误里的字段名。网关会把上游错误标准化成自己的文案，字段名不在里面，于是判成失败。改判定条件后，直接离线重读保存下来的同一份响应，没有再花钱重发。

两点可以带走：原始响应一律落盘，判定逻辑改了就离线重算；如果「错误里能看到字段名」本来就不是验收要求，就别把它写成断言。

### 4.3 素材预检漏掉一项

视频回归里，助手拿了一张公共示例图当输入，它的边长低于上游要求的最小值，任务直接失败。换一张合规的图才成功。付费前要单独量一遍素材的 MIME、大小、宽高和时长，对照当前模式的限制，再提交同一份素材。这一步不花钱，省的是一单白跑。

## 5. 先确认阶段和入口，再谈回归

最后两件事，和计费无关，却决定了回归该不该开始、按什么标准判。

**预装不是放量**。那个图像模型的新能力，发布说明写得很清楚：这一阶段只预装、还没对用户开放。我后来说了一句「已上线，回归一下」，助手就按「已对用户开放」的标准去判，把「模型列表里看不到」当成阻塞，还提前问起付费账号能否独占。我把发布说明重新贴回去，它才改正。停用预装的阶段，模型不可见恰恰是对的。

这个阶段能独立验收的是：代码和节点版本、安装自检、数量与停用状态、计费规则和缓存。真实生成、各项附加能力、多张产出和完整账务，留到开放验证之后。当时没法签完整预装，直接原因是后台证据没核到，不能笼统说成「没真机所以不能通过」。

取证里也有一处要剔除：助手一开始请求的计费规则路径写错了，拿到 404。后来查对了单模型的规则端点，返回 200 且价格与发布说明一致。它能证明公开的默认规则，不能证明所有分组的价格行。批量模型列表缺项和单条规则可读，是两个视图，前后又隔了一段时间，不能据此倒推规则何时发布、缓存何时刷新。

**入口不通就早停**。管理后台日志筛选那次，修复已经合并，要我在浏览器里补验关键字大小写、特殊字符这些点。助手先投入了不少流程准备，最后才问「后台地址是什么、有没有管理员登录态」。我访问不了线上后台，这次回归就此暂停。正确的顺序是开工第一件事先确认入口能不能进。

顺带要分清四层状态：源码合并了、检查通过了、制品发布到了目标实例、页面上实测过了。每一层只接受它能证明的结论。分支策略检查通过，不等于编译和测试过了；合并了，也不等于线上已经换版。缺哪一层的证据，就把它转成一条具体的交接：谁能看到、需要他确认什么。

## 6. 一张付费发送前的清单

每次发付费单之前过一遍，任何一项答不上来就不发：

| 检查项 | 合格的样子 |
|---|---|
| 阶段 | 说得出现在是预装、小范围验证还是已放量，判据跟着阶段走 |
| 入口 | 用户入口或后台入口已经实际打开过 |
| 前置结果 | 已结束、退出码为 0，由代码分支判定，失败时发送计数为 0 |
| 零探测 | 用量差严格等于 0 |
| 账号独占 | 有明确确认，记了来源和有效期；同账号其他窗口的台账和收件箱已看 |
| 素材 | MIME、大小、宽高、时长已量，符合当前模式的限制 |
| 负向用例 | 已确认它真的失败、在哪一层失败 |
| 预期公式 | 独立写，不调用被测的 helper；覆盖取整能区分的小数输入 |
| 口径 | 预扣、估价、结算分开列预期；流式只取结算帧 |
| 收尾 | 原始响应已落盘；已回传停止和在途状态 |

## 收尾

1. **顺序不是条件** —— `await` 拿到退出码不等于成功，前置失败要靠显式分支让发送次数为零，并用计数器测它
2. **稳定不是独占** —— 余额差要归给一条请求，先取得账号独占交接；污染样本保留原值、剔除通过数、换名重测
3. **别人的区间也要保护** —— 自己按明细核费，照样会污染别人的余额差，发前协调、收尾回传
4. **预扣不是结算** —— 按上限冻结、按实际产出收，兜底分支让「没超预扣」失去意义，要独立量产出、独立算公式
5. **用例先自证** —— 「非法」输入先看它真的失败，判定改了就离线重算，素材先量再交
6. **阶段和入口先确认** —— 预装、小范围验证、放量各有判据；入口不通，第一时间停

回头看，这几次的错几乎都不是「不知道」，而是「知道但没落到执行的那一层」。清单上写着要独占，读过还会漏；写着前置失败要停，批量脚本照样发。我现在的做法是：能写成代码的约束就写成闸门，并且测「发送次数」这一个数；写不成代码的，比如跨窗口协调，就把它变成发送前必须产出的一份记录。付费测试的整体设计见[按次付费接口的测试设计](/blog/billing-regression/paid-test-design/)，计费规则本身的暗坑见[计费规则的几个暗坑](/blog/billing-regression/billing-rule-pitfalls/)。
