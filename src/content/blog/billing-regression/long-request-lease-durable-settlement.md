> 一句话总结：预扣要覆盖后端实际工作的生命周期；结算失败要留下可恢复的事实；持久记录还要有真正运行的消费者。最终余额正确，只能证明这条链路的一部分。

## 0. 起因：内容还在输出，冻结已经被清走

我复盘过一条长请求链路：请求开始时先预留费用，结束后按实际用量结算。冻结记录有固定期限，超过期限就由清理任务回收。

常规请求没有问题。请求足够长时，上游仍在执行，冻结却先过期了。等真实用量回来，结算再也找不到可以确认的待结算记录。

最直接的想法是延长期限。但如果客户端允许更长请求，或者根本没有总超时，换一个更大的常量只是把缺陷往后推。后来补上持久重试，又发现记录确实写入了，消费循环却跟另一个子系统一起被关闭。

这些问题共同指向一件事：不能让几个不同的生命周期共用一个「请求结束」概念。

## 1. 先把四个时钟画到同一条线上

| 时钟 | 表示什么 | 结束条件 |
|---|---|---|
| 客户端连接 | 用户是否还在接收响应 | 断开、取消、响应完成 |
| 后端工作 | 这次上游执行是否仍在进行 | 工作完成、失败或被明确取消 |
| 预扣租约 | 待结算冻结是否继续有效 | 续租停止后到期，或进入账务终态 |
| 持久补扣 | 已知用量是否仍需恢复结算 | 确认成功，或进入明确人工处理状态 |

客户端断开不自动证明后端停止。有的出站请求绑定客户端取消，有的会继续处理；要读实际构建请求的分支，再判断租约跟谁走。

Go 的服务端请求 context 会在连接关闭、请求取消或 handler 返回时取消；出站请求的 context 控制其取消。两者是否相连，要看应用怎样传递。[Go Request.Context 文档](https://pkg.go.dev/net/http#Request.Context)

因此不能把一个框架请求对象放进后台循环，等它随连接消失；也不能为了续租，顺手改变上游原有的取消策略。先确定谁持有真实工作，再把租约绑定到它。

## 2. 估算、风险缓冲、输出上限和实扣是四层

在另一轮输入估算复盘中，我还看到「把 token 估算乘一个倍率」被当成完整止血方案。倍率能改善某批样本，却不能保证预扣覆盖所有风险。

至少要拆成四层：

1. 输入估算尽量贴近实际模型和内容结构，文本、历史、工具定义与媒体分别处理。
2. 风险缓冲用于表达估算不确定性，不能冒充更精确的 tokenizer。
3. 余额不足以支撑任意输出时，要约束真正发给上游的输出上限。
4. 最终结算采用契约认可的实际用量，估算倍率不应混进实扣。

缓存写入、长上下文或其他价格档位，也要进入预留预算。同样数量的输入，不同角色可能有不同成本。某次事故样本在加倍率后仍能越过余额边界，说明应检验完整预算，而不是只检查倍率已经写进配置。

这类估算仍有误差边界。没有原请求、实际模型映射和用量回执，就只能说明本地保护机制已实现，不能宣布事故已完整重放。

## 3. 租约要续得上，也要停得下来

我采用的通用判断是：实际工作活跃时定期延长待结算租约；工作结束后停止续租；崩溃后由有限期限回收遗弃冻结。

更新还要满足三个条件：只更新待结算状态、只延长期限、数据库操作本身有独立的有界超时。迟到续租不能让已退款或已确认的记录重新变成 pending。

可以把核心状态转换写成下面的检查表：

| 当前状态 | 收到什么 | 允许的结果 |
|---|---|---|
| 工作活跃、待结算 | 续租 | 延长到期时间 |
| 已确认或已退款 | 迟到续租 | 保持终态 |
| 工作已结束 | 后续 tick | 不再续租 |
| 进程已崩溃 | 长期无续租 | 到期后可回收 |

测试长时行为可以推进可控时钟。历史验收用它证明超过初始期限仍保持冻结，工作退出后又能回收。这个结果是状态演算，不能写成真实连续跑了对应时长，更不能替代生产长连接的网络验证。

## 4. 结算失败后，保存事实而不是换一种价格重算

上游工作已经完成，账本写入却失败时，重新生成通常不合适。退款后再用另一条旧价格路径扣款，也会让同一次执行前后采用不同口径。

恢复记录应保存这次执行已经确定的结算事实：稳定账务标识、实际用量、锁定的价格依据，以及完成结算所需的最小上下文。敏感凭据不应随恢复快照长期保存。

随后由独立消费者完成确认，重复处理同一标识仍只产生一笔费用。确认、退款和过期清理发生竞争时，也要通过条件更新或事务维持终态唯一。

这里的幂等是业务性质：第一次处理成功后，再次收到同一条记录，余额、冻结和消费明细都不应变化。仅仅「第二次没有报错」不够。也不能为了恢复，把已经退款的终态强制改回待结算。

## 5. 写进队列不代表有人会消费

我遇到过一轮复审：测试里手动调用消费者，恢复成功；真实启动流程却把这个消费者绑在媒体分发开关后面。只使用同步文字请求的节点没有开启媒体分发，也就没有运行补扣循环。

结果是持久记录存在、数据库也恢复正常，冻结仍长时间不收敛。手动消费一下又好了。缺陷在启动接线，单独调用处理函数的测试看不到。

现在我会把三层分开验证：

- 处理函数能正确结算；
- 节点在目标配置下确实启动消费循环；
- 故障恢复后，无人工调用也能最终收敛。

要覆盖没有可选队列服务、只启用同步入口、从节点默认关闭和显式启用等配置。它们不是随意扩大的测试矩阵，而是消费者实际启动条件的几条分支。

## 6. 原请求统计不能被补扣时间改写

恢复可能发生在原请求结束很久以后。如果用「现在减开始时间」记录耗时，结算等待会变成模型耗时；重放时再记一次渠道用量，还会让流量指标翻倍。

我把它分成两个事件：原请求完成时记录执行耗时、渠道用量和必要会话事件；补扣成功时记录账务恢复结果。补扣不重复记原执行指标。

这也提醒我，共享日志入口往往有隐含职责。把某类结算从公共函数挪走，金额仍然正确，但原本顺带写出的成功事件可能消失。重构时要核业务动作清单，不能只比较返回金额。

消费者升级同样属于生命周期。新生产者写入新类型记录之前，至少要有能处理它的消费者；旧消费者抢到不认识的记录，可能把它变成失败积压。回滚流量节点时，也要给已产生的新记录保留处理能力。

## 7. 可直接拿走的验收不变量

| 场景 | 应观察的结果 |
|---|---|
| 超过初始租约，工作仍活跃 | 冻结保持有效 |
| 客户端取消，上游按既有语义继续 | 租约跟随真实工作 |
| 工作返回或 panic | 续租退出，遗弃状态最终可回收 |
| 已退款后迟到续租或补扣 | 终态不复活、不再次扣费 |
| 账本写入失败后恢复 | 无人工消费也最终结算 |
| 重复消费、并发确认、清理竞争 | 一笔消费、冻结收敛、余额自洽 |
| 故障后较晚恢复 | 原耗时不被拉长，统计不重复 |
| 新旧消费者交错 | 新记录有明确可处理方 |

我在历史本地回归中见到这些状态、并发与负向对照的通过记录；生产消费者是否同库、节点是否全部升级、线上补扣是否实际收敛，仍需要各自的运行证据。不能拿本地金额正确替代这些结论。

## 收尾

1. **租约跟工作走** —— 客户端连接和后端执行可能不同步。
2. **预留分四层** —— 估算、缓冲、出站上限、最终实扣分别验证。
3. **持久化还要接线** —— 恢复函数正确以后，再验消费者确实启动。
4. **重放只补账务** —— 保留原请求统计和耗时，避免恢复过程污染指标。
5. **终态保持唯一** —— 迟到续租、重复消费与清理竞争都不能复活已结束的账。

下次排查长请求漏收，我会先把四个时钟放到一起，再看哪个事件提前结束或没有接上。更一般的少交付结算问题见[预扣缺价与部分交付](/blog/billing-regression/reserve-fallback-partial-delivery/)。
