> 一句话总结：上线前回归是在生产上用真实账号、真实扣费，从用户视角把能感知到的路径走一遍。最值钱的三样是：用故意写错参数的请求零花费判断「能不能路由」；每一单让历史记录、任务日志、余额差和独立公式四个数相等；兜底值恰好等于实时值时，用本地改写代理把实时值往两个方向推，看页面跟不跟着变。

## 0. 起因：代码上了生产，离对外开放还差一步

我所在的团队维护一个多供应商的 API 网关，接了不少上游模型。一个模型从接入到对外开放，前面有本地验收：在验收环境里审代码、跑参数矩阵、对预扣和实扣。验收过了，代码合并、部署到生产，但还没对外公告。这中间有一段空档，要有人在生产上拿真实账号再走一遍。

第一次做这件事，是给某厂商的语音合成（TTS）模型做上线回归。之前的验收全在本地和 mock 上游上做，这次第一次碰真钱：每一单都从测试账号的余额里扣。后来又给一个文本大模型做了一次，流程在两次之间补了不少。

leader 在会上给过几条原则（转述）：清单是活文档，每次回归沉淀一点；重点是用户能感知到的东西，后台配置的核对单独列出，交给有权限的人；历次出过的问题不用单列，一次完整的回归自然会覆盖；AI 把脚本跑完不等于回归完，要登录、要看界面的部分得人亲手点。

这篇把两次回归沉淀下来的流程和三个最有用的技巧写出来。

后续回归已开始按有效的验收证据缩小范围：未变化的文档和页面检查可以复用，核心请求按必要端点和计费角色选择。本文保留完整核对方法，具体怎样减少重复、安排单密钥串行和并行对账，见[缩短上线回归](/blog/billing-regression/regression-core-set-single-key/)。

## 1. 整体流程：准备加十步，每步写清依据

我把回归拆成下面的准备加十步。每一步后面标了依据：「实测」是两次回归里真跑过的，「转述」是会上口述、我还没完整跑过的。

| 步 | 做什么 | 依据 |
|---|---|---|
| 0 准备 | 记余额基线（读接口，不读页面）；每个价格分组备一个账号；记下对照的代码版本；写用例表并估价 | 实测 |
| 1 上线判定 | 每个模型 ID 用故意写错参数的请求零花费探可路由 | 实测 |
| 2 页面 | 多语言语义不冲突；整页价格处处一致；按钮跳对；对外内容不出现内部概念 | 转述 |
| 3 Playground | 用在线试用页同时验前端和后端，接口只补它覆盖不到的参数 | 部分实测 |
| 4 计费 | 历史记录、任务日志、余额差、独立公式四个数逐单相等 | 实测 |
| 5 错误 | 前端拦截、同步 400 / 404、执行失败的错误码、失败退款 | 实测 |
| 6 文档 | 参数和限制与接口对齐，报错示例逐字对，对外承诺不高于实际 | 实测 |
| 7 下线 | 旧模型 ID 各打一次，按 404 / 400 / 200 判 | 实测 |
| 8 后台 | 渠道配置链、错误码规则、自动禁用、跨账号隔离 | 转述 |
| 9 待跟进 | 有时效的行为记下时间点，到点复测 | 实测 |
| 10 报告 | 每块两栏「要验证什么 / 目前有什么问题」，每个问题标阻塞与否 | 转述 |

第 0 步有一条后来补上的：**接口地址按文档站给这类接口写的默认地址测**。同一个网关常有两个入口，一个经 CDN（内容分发网络），一个直连。只测了一个，报告里就写明另一个没测。这条的来历见[经 CDN 的非流式长请求](/blog/billing-regression/cdn-524-long-non-stream/)。

下面挑第 1、4 步和一个页面取数的技巧细讲，最后讲人工走查和报告。

## 2. 上线判定：一分钱不花，判断能不能路由

### 原理

网关处理一条请求的顺序大致是：鉴权 → 选渠道（这个模型对这把 key 所在的分组可见吗）→ 参数校验 → 建任务、预扣。

所以一条故意写错参数的请求有两种结局。模型能路由，它会走到参数校验，回 400，不建任务、不扣钱。模型不能路由，它在选渠道那一步就回 `404 model_not_found`。用这个就能判断「已经上线了吗」「公告下线的旧型号真的下了吗」，全程零花费。

前提是这个端点确实「先选渠道、后校验」。所以每个端点都要先做一条对照：拿一个不存在的模型名，缺同样的参数，打同一个端点。

| 用例 | 请求体 | 预期 | 读法 |
|---|---|---|---|
| 对照（每端点一条） | 不存在的模型名 + 缺必填参数 | 404 | 这个端点先选渠道，下面两行的读法成立 |
| 新模型 | 合法模型名 + 一个它会拒的参数 | 400，且错误码和文案正好是你埋的那一处 | 已上线 |
| 下线的旧模型 | 旧模型名 + 缺必填参数 | 404 | 下线生效；回参数 400 就是仍可路由 |
| 拼错的模型名 | 近似名 | 404，最好带「你是不是要找」的建议 | 错误提示不诱导重试 |

对照回 400 怎么办？说明这个端点先校验参数、后选渠道，这个方法在这里不成立，要换办法。

一个最小的探测脚本长这样：

```bash
probe() {  # $1 = 端点路径，$2 = 请求体
  curl -s -o /tmp/probe.json -w '%{http_code} ' "$BASE$1" \
    -H "Authorization: Bearer $API_KEY" -H 'Content-Type: application/json' -d "$2"
  head -c 160 /tmp/probe.json; echo
}
probe /v1/chat/completions '{"model":"no-such-model-0000","messages":[]}'   # 对照，要 404
probe /v1/chat/completions '{"model":"new-model","messages":[]}'           # 要 400，且是 messages 的错
```

### 两次回归里碰到的情况

第一次（TTS 模型）的回归里，我在音频端点和图像端点各做了一条对照，都回 404。于是几个已经公告下线的旧型号回了参数 400，就能判成「仍可路由」：下线只在公告里，没在路由层生效（实测）。这条按「延期」进了待跟进，不按缺陷记。

第二次（文本模型）碰到一个新情况：有一种错误输入回的不是 400，是 500。乍一看像是方法失效了。想清楚以后：同一请求换成不存在的模型名回 404，说明请求已经过了「找模型、选渠道」这一关，500 发生在后面。所以 500 也能证明可路由，500 本身按错误路径另查（实测）。

第二次还加了一条：发一个比上游上限大 1 的参数，比如最大输出长度。它会回上游原文的 400，说明改名和转发都通到了上游，仍然不花钱（实测）。

### 边界

- **可路由不等于能出结果**。上游 key 失效、上游已经下线这个型号，零花费探测都看不出来。要知道合法请求能不能成功，得付费发一单最便宜的。报告里写「只做了零花费探测，没发合法请求」。
- 结论只对这把 key 所在的分组成立，可见性按分组算。
- 404 也可能是渠道被全部手动禁用，不一定是从没配过。
- 判「零花费」本身也要实证：整批跑前、跑后各读一次余额。

## 3. 计费三处对齐：四个数逐单相等

### 四个数

每一单要对上四个数：在线试用页历史记录的终态金额、控制台任务日志里的费用、调用前后的余额差，以及我自己按计费公式独立算出的应扣。前三个是系统给的三处，第四个是我的预期。四个相等才算这一单对上；失败的单要全额退款。

这里有两个细节决定了能不能对准。

**余额读接口，不读页面。**页面上的余额常做了取整，差一点看不出来。生产上开着批量记账时，扣费会晚几秒才落到余额里，所以要轮询，等连续两次读到同一个值再记：

```python
import time

def stable_balance(read, interval=2.0, tries=15):
    """read() 返回当前余额；连续两次相同才返回，避免批量记账还没落账。"""
    last = read()
    for _ in range(tries):
        time.sleep(interval)
        cur = read()
        if cur == last:
            return cur
        last = cur
    raise RuntimeError("余额一直在变，先别记")
```

**页面金额的预期要按前端的取整方式算。**有一次核用量页，助手默认页面金额是四舍五入，写好预期一对，14 单里有 3 单差末位一个单位。它去读前端的格式化函数，才发现是末位向上取。按向上取重算，14 单全对（实测）。反过来也危险：只拿两三条举例核，可能正好挑中两种算法结果相同的几条，就把口径写错了。所以预期要逐单按格式化函数的规则算，不凭直觉写。

### 按 token 计费的请求

文本模型按 token 计费，对账要多想几层。应扣按计费代码的口径算，不按文档猜：

- 缓存命中从哪个字段读；
- 各协议的输入数含不含缓存；
- 输入、输出、缓存各角色是分别向上取整，还是合计后取整；
- 最低计费在哪一步套。

协议之间的差别是实测出来的。OpenAI Chat Completions 和 OpenAI Responses 的输入数含缓存命中，命中数放在 details 里；Anthropic Messages 的 `input_tokens` 不含缓存读，缓存读单列。流式请求的 usage 从最后一个带 usage 的事件取：Chat 是末块，Responses 是完成事件，Messages 要把开头和增量两个事件拼起来。对账脚本按协议取字段，写错一个就全错。

**最低计费会把小单盖成同一个数。**一单只有几十个 token 时，不管公式写对写错，扣的都是最低计费。所以公式要靠大单验：长前缀、长输出、缓存命中。我验缓存的做法是在系统提示开头放一个随机串，避免命中别人留下的前缀缓存；再用一万 token 以上的长前缀连发两单。第一单全未命中，第二单命中、只扣缓存部分。这两单同时也是验「分角色取整」的大单。

### 账单导出的时间字段

还有一个坑和对账相关：要让某笔请求进账单导出，先核这类记录的时间字段是什么口径。同步文本请求的行在结算时才写，时间是完成时刻，在途时根本没有行；异步媒体任务提交时就建行。负责协调的 AI 会话差点把媒体任务的口径套到文本请求上，让一笔在途请求落在账单外。细节见[计费规则的几个暗坑](/blog/billing-regression/billing-rule-pitfalls/)。

## 4. 兜底值等于实时值：用改写代理推一推

### 现象

有一项修复要验：页面上的报价改成「用接口返回的实时价，拿不到才用前端兜底价」。我把页面上每条报价和后端快照逐条比，全部一致，看起来修复生效了。

再去看前端的兜底表，所有相关条目的兜底值和后端当前值完全相同。页面不管走实时还是走兜底，渲染出来都是这组数。这次核对什么也没证明。

**根因**：「输出和真实值一致」只说明结果对，不说明结果从哪条路来。两条路给出同一个值时，输出就失去了区分能力。兜底表通常照上线时的真实值抄，没调过价之前两者本来就相等，所以这种情况很常见。

### 修复：本地改写代理

不用等后台改值，也不用动共享后端。起一个本地代理，只改写目标接口里的目标字段，其余请求原样转发。然后用环境变量把页面服务端的后端地址指向它：

```python
import json, sys, urllib.request
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

PORT, FACTOR = int(sys.argv[1]), float(sys.argv[2])
UPSTREAM, TARGET = "http://<后端地址>", "/api/catalog"

class Rewrite(BaseHTTPRequestHandler):
    def do_GET(self):
        hdrs = {k: v for k, v in self.headers.items() if k.lower() not in ("host", "accept-encoding")}
        with urllib.request.urlopen(urllib.request.Request(UPSTREAM + self.path, headers=hdrs)) as r:
            status, body = r.status, r.read()
        changed = 0
        if self.path.split("?")[0] == TARGET:
            doc = json.loads(body)
            for item in doc["data"]:
                item["value"] *= FACTOR       # ← 只改这一个字段
                changed += 1
            body = json.dumps(doc).encode()
        print(f"{self.path} -> {status} changed={changed}", flush=True)  # ← 日志证明真的取了数
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

ThreadingHTTPServer(("127.0.0.1", PORT), Rewrite).serve_forever()
```

用法：

```bash
python3 rewrite.py 18101 2.0 &                     # 涨价方向，端口 A
BACKEND_URL=http://127.0.0.1:18101 npm run start   # 进程环境变量优先于 .env 文件
# 请求页面，解析报价，和「原值 × 2，再按页面的取整规则」逐条比
# 换 0.5、端口 B 再来一遍；最后去掉变量重启，确认回到原值
```

几个要点：

- **涨、降两个方向都测**。另一个页面的报价是一个区间，取所有候选的最小和最大。候选里一部分来自实时值，一部分写死在页面数据里。把实时值调低，低端跟着变了，像是「跟随实时值」；调高时两端都不动，因为写死的候选卡住了两端（实测）。只测一个方向，就会把「只跟降价」误判成「跟随实时值」。
- **每个方向换一个代理端口**。服务端框架的数据缓存按 URL 做键，换端口就是新键，不会拿到上一轮的缓存。
- **代理要打日志**。日志里要有目标接口的请求，而且改写条数大于 0。没有这行日志、页面却「对了」，说明页面根本没取这份数据。
- **预渲染的页面要触发重新生成**。静态生成的页面换了后端地址也不会变，要像生产改值后那样调一次重新验证。
- 这个办法只对服务端取数有效。浏览器端直接请求的接口要在浏览器里拦截改写。

两种办法都没做时，报告里如实写「实时值路径只由 mock 测试证明」，不写「已核对」。

## 5. 人亲手点的部分，和报告怎么写

### 人工走查清单

回归脚本没有登录态，覆盖不到在线试用页、用量明细和任务日志。这几样我列成人工走查清单交给人点，每项写清要看什么、拿哪个请求 ID 去对。生成中的状态也要人盯着：任务日志在转圈、余额已经预扣，脚本替代不了这一眼（转述）。

在线试用页还有几条值得逐项过：

- 参数集合满足「试用页 ⊆ 文档 ⊆ 后端」，可以少，不能多。
- 参数取非默认值、近极值，从输出本身证明生效，不看请求体。
- 历史记录先显示预扣，完成后变成实扣；结果区的 JSON 和查询接口的响应体逐字段一致。
- 文档声称的每项能力各打一单。文件输入就在文件里放一个暗号，回答对上才算读到；内置工具看响应里的工具痕迹字段，不看「返回 200、有回答」。

### 错误和下线

新模型报了意外的错，先拿同一请求换同端点的几个其他模型打。都一样，就是网关的存量问题，记成疑似缺陷进待跟进，不算到这个模型头上（实测）。

下线判定按旧模型 ID 的返回码读：404 是不可路由，不做重定向时正常；400 是仍可路由；200 是仍可用。还能用的进待跟进，按「延期」记。

### 待跟进要带时间点

TTS 模型那次有一个自建资源（自定义音色）带有效期。回归当天测不到过期，我就在待跟进里写下到期时间，到点复测：合成要被拒，上游资源要被清掉（实测）。延期事项、疑似缺陷、不阻塞的优化、条件不足没测的，各列一节，每条带时间点或负责人。

### 报告

报告每块分两栏：「要验证什么」和「目前有什么问题」，每个问题标阻塞或不阻塞，结尾是待跟进。没过的条目附浏览器 console 的报错、复现步骤、能不能稳定复现、截图（转述）。

「只有英文」这类问题可以不阻塞上线，但不能预设「用户可以接受」。阻塞与否的判断写清依据，留给决策人改。

## 收尾

1. **零花费先探路由** —— 故意写错一个参数，每个端点先拿不存在的模型名做对照，回 404 才能读懂后面的 400 和 500。
2. **四个数逐单相等** —— 历史记录、任务日志、余额差、独立公式，余额读接口并等它稳定，页面金额按前端的取整规则算预期。
3. **公式靠大单验** —— 最低计费会把小单盖成同一个数，长前缀、长输出、缓存命中才能区分公式对错。
4. **结果一样时换一个能区分的对照** —— 兜底值等于实时值时，用改写代理把实时值往两个方向推。
5. **机器跑完不等于回归完** —— 要登录、要看界面的部分列成清单交给人点，没过的附 console 和复现步骤。

回头看，这套流程里最省事的是第 1 步，最容易出错的是第 4 步。下次做回归，我会先把四个数的读取脚本和取整规则写好，再开始花钱。长输出类请求在 CDN 上的行为另写了一篇：[经 CDN 的非流式长请求](/blog/billing-regression/cdn-524-long-non-stream/)；付费用例怎么排，见[按次付费接口的测试设计](/blog/billing-regression/paid-test-design/)。
