> 一句话总结：累计快照描述「目前一共多少」，完成条目描述「具体哪次完成」。分别保存来源、按契约派生最终值，才能避免同一次用量重复计数；要用 `max` 精确合并，两路覆盖还须存在包含关系，仅仅范围相同或部分重叠不够。

## 0. 起因：两条正确回执合起来，次数反而错了

我复盘一段工具计费实现时，碰到了一个很小的时序问题。同一次响应先报告「目前完成一次」，随后补回那一次调用的完成条目。前一条正确，后一条也正确，合并后却可能变成两次。

原来的总计数器承担了两种职责：收到汇总时，把总数更新为汇总值；收到完成条目时，再加一。只看每个分支都说得通，放到同一时间线上就重复了。

我追问助手：既然是这样，让上游只给累计值，或者完成时不自增，不就够了吗？问题的关键还差半步：到底停止增加哪个数，以及没有累计值时怎么办。

## 1. 先给数据写定义，再给字段起名字

这次我把三类数据分开记：

| 数据 | 回答的问题 | 应怎样更新 |
|---|---|---|
| 累计快照 | 当前统计范围内，报告方目前一共记录多少 | 按契约替换或保留最新快照，重发不增加 |
| 完成条目 | 哪一个具体调用已完成 | 按稳定调用标识去重，维护独立集合 |
| 权威计数 | 最终计费应采用哪个来源的数量 | 来源存在且有效时采用，包括显式零 |

「权威」和「累计」是两个维度。一个字段可以既是权威计数，又是累计汇总。前者说的是采用谁，后者说的是数怎样形成。

同样，完成动作数不必等于可计费次数。供应商可能将一些操作合并计价，也可能排除不收费的动作。把动作数看成金额依据之前，要先核它究竟统计什么。

我现在会为每个来源补四项定义：属于哪个请求或资源、覆盖哪个时间窗、单位是什么、和其他来源是否重叠。两个字段都叫 `count`，没有这些定义也无法决定该相加还是选一个。

## 2. 「不自增」说对了一半

假设下面两种回执都描述同一响应中的相同工具用量：

| 到达的回执 | 快照 | 去重条目数 | 此时采用的次数 |
|---|---:|---:|---:|
| 累计一次 | 1 | 0 | 1 |
| 调用 A 完成 | 1 | 1 | 1 |
| 调用 B 完成，汇总尚未更新 | 1 | 2 | 2 |
| 累计两次 | 2 | 2 | 2 |

第二行不能再给最终总数加一，否则 A 被计了两遍。第三行仍要记录 B，否则快照没更新时会漏掉新用量。

所以完成事件应停止修改累计快照，继续更新自己的条目集合。最终数从两份独立状态派生。只写一句「有累计值以后不再计完成条目」，会把重复计数改成漏计。

反过来，只依赖汇总也需要来源保证：它是否一定出现、是否覆盖完整输出、是否可能被中间层裁掉。兼容多个回执格式时，不能要求每个上游都按同一个理想格式返回。

## 3. 合并规则有前提，不能直接背一个公式

下面是一份自编契约，不代表任何厂商的完整接口：权威值存在就采用；缺失时，累计快照与去重条目都是同一累计序列的前缀视图，覆盖集合存在包含关系，较长的前缀覆盖较短的前缀。

```text
若存在有效的权威计数：采用它
否则：max（累计快照，已去重条目数）
```

这不是通用计数定律。快照包含 A、B，条目却只有 C 时，即使都属于同一请求，`max(2, 1)` 仍漏掉一次；快照包含 A、B，条目包含 B、C 时，部分重叠也不足以求出正确并集。只有数量没有成员，就无法恢复这些关系。

因此需要契约保证包含关系，或明确选择某一来源、接受何种兼容计量政策。不能把一个防重复的保守规则描述成任意乱序下的精确合并。来源描述不同工具、不同请求或互斥分区时，更需要另定规则。

快照包含计划调用、条目只含成功调用时，连计量单位都不同，也不能照搬。

显式零还必须区别于缺失。契约明确返回零，表示来源做过判断；字段没有给，表示没有这个信息。如果都用整数默认值零表示，后面的回退逻辑就会把「明确不收费」误当成「没收到，改用动作数」。

非法值也单列处理。负数、非整数、错误类型和字段缺失是不同情况，应该按约定拒绝、忽略并告警，不能在转换失败时偷偷变成零。

## 4. 用独立状态表达这份抽象契约

下面的 Python 示例为文章单独编写。对象只服务一个响应；两路均满足上节的前缀包含契约，快照单调增加，权威值是终态完整值。代码不负责从数量推断包含关系，跨请求必须新建对象。

```python
from dataclasses import dataclass, field

@dataclass
class Usage:
    snapshot: int = 0
    item_ids: set[str] = field(default_factory=set)
    authority: int | None = None

    def observe(self, kind, value):
        if kind == "item":
            if not isinstance(value, str) or not value:
                raise ValueError("stable item id required")
            self.item_ids.add(value)
        elif kind in ("snapshot", "authority"):
            if type(value) is not int or value < 0:
                raise ValueError("nonnegative integer required")
            if kind == "snapshot":
                self.snapshot = max(self.snapshot, value)
            else:
                self.authority = value
        else:
            raise ValueError("unknown source")

    def total(self):
        if self.authority is not None:
            return self.authority
        return max(self.snapshot, len(self.item_ids))
```

稳定标识很关键。同一个调用可能重复报告，同样的内容也可能由两个不同调用产生。按内容哈希去重会把后者合并，按事件条数计数又会放大前者。没有足够标识时，应记录无法精确去重的限制，不能假装集合已经解决问题。

这个例子也没有处理统计窗口回退、修正历史用量或并发写入。真实系统如果允许快照向下更正，就不能永远取历史最大值，要给版本和替换关系另定规则。

## 5. 测试要交换顺序，不能只重复发同一条

这次复盘保存的八个抽象场景中，分来源方案符合固定预期；混用总计数器的方案有五个不符。这是助手运行的抽象实验，只证明所设契约和演算，不能代替业务网关回归。它也没有证明任意来源都满足前缀包含关系。

可直接复用的用例清单是：

| 输入 | 固定预期 | 要防的错 |
|---|---:|---|
| 快照 1 → 条目 A | 1 | 汇总与明细重复相加 |
| 条目 A → 快照 1 | 1 | 到达顺序改变结果 |
| 快照 1 → 条目 A → 条目 B | 2 | 汇总存在后忽略新条目 |
| 重复条目 A、重复快照 | 1 | 重发重复计数 |
| 只有条目 A、B | 2 | 缺汇总就当零 |
| 只有快照 2 | 2 | 没有完整明细就少计 |
| 非零明细加权威 0 | 0 | 显式零被当成缺失 |
| 明细 A 加权威 2 | 2 | 裁剪明细覆盖权威数 |

预期应来自已确认的计量契约，用独立字面值表达。把被测 `total()` 再调用一次生成 expected，验证不了计量规则。

## 6. 次数正确以后，费用还有自己的规则

计量层回答「发生了多少」，收费层还要回答「这次由谁付、什么条件下收」。整体失败后是否收已完成工具用量、缺价是否拒绝、退款如何处理，都是需要明确的政策。

我经历过同一条链路先补齐失败回执计量，后来又调整失败收费规则。旧测试在旧契约下成立，不等于新政策必须保留旧金额；新政策改变，也不能抹掉旧计数器曾有的重复问题。两类变化要分别写清。

资源复用又多一层：记住资源的规格，不等于已经认领某次收费窗口。首个请求暴露资源编号后失败，后续请求可能继续复用；如果只在付款成功时记录规格，就可能按错误档位计算后续费用。元数据、计量状态、收费归属应分别保存，再按各自的生命周期清理。

## 收尾

1. **先定义来源关系** —— 范围、时间窗、单位和集合包含关系明确以后，再选择合并方式。
2. **分开保存来源** —— 快照不承接条目增量，完成条目按稳定标识去重。
3. **零不是缺失** —— 权威值的存在性要有独立状态。
4. **按顺序验收** —— 相同回执换个顺序，结果仍应符合契约。
5. **计量和政策分开** —— 执行次数、可计费次数、最终费用各有依据。

这次追问让我意识到，画数据流之前也要先写清数据含义。只有箭头和名字，仍然可能把两份正确数据加成一个错误结果。相关的金额与取整问题见[计费规则的几个暗坑](/blog/billing-regression/billing-rule-pitfalls/)。
