> 一句话总结：缩短回归，先找出上线后必须重新取得的证据，再安排请求。只有一把密钥时，短文本串行常常已经足够快；并行能缩短等待，却可能把逐单实扣降成整组推定，报告必须保留这个区别。

## 0. 起因：流程越来越全，等待也越来越长

连续做了几轮模型回归之后，我发现流程里多了很多合理的检查：文档、页面、参数、能力、计费、错误、历史问题。每次遇到新问题，就往清单里补一项。清单越来越完整，下一次开工也越来越慢。

我让助手重新估时，得到的仍是按小时计算的计划。我指出，报告准备可以单独计时，测试要尽快给出关键结论，测试集也不必每次铺满。助手最先想到的是并行付费请求，再同时检查文档和页面。

接着我补了两个现实条件：手里只有一把可用密钥；文档和页面在上线前已经核过。于是问题变了。需要压缩的既有网络等待，也有重复工作。多开几个执行任务，只解决其中一部分。

这篇依据当时的会话、流程修订和保存的彩排结果整理。历史上的一次通过，只证明当时那组样本；这里不把它写成所有模型的固定耗时承诺。

## 1. 核心集：每一单都要补上一块必要证据

我先把检查分成三类：上线前已验证且没有变化的、生产环境才会变化的、这次改动直接影响的。第一类保留原证据和版本，后两类进入本轮重点。已有证据缺版本、对应不上当前实现时，就不能直接复用。

例如，同一份静态说明已经审过，发布时内容没变，就不必重新逐句研究；生产渠道是否可达、真实账户是否按预期扣费，却必须重新取证。若这次恰好改了域名、页面取数或文档参数，相应检查又要加回来。

付费请求也按证据覆盖来选。一条长前缀请求可能同时覆盖普通输入、输出和缓存写入，后续命中请求再覆盖缓存读取。若另有一条短文本请求只重复输入、输出，它就可以降为可选。先保留依赖链，再看哪些请求重复覆盖。

我用下面这张表压缩范围。表里的用例是泛化示例，并非原任务清单。

| 必须回答的问题 | 需要的证据 | 可以合并的部分 |
|---|---|---|
| 合法请求能否完成 | 真实终态、可读取结果 | 可与基础计费用例合并 |
| 独立计费角色是否正确 | 用量、独立公式、实际扣费 | 一单可覆盖多个角色 |
| 每个公开端点是否可用 | 对应端点的成功响应 | 相同模型名不能代替端点覆盖 |
| 改动是否破坏旧路径 | 一条有区分力的旧路径对照 | 无变化的参数排列可留给验收 |
| 错参是否被拒且无费用 | 对照错误、账务读数 | 已验证拒绝的探测可成批执行 |

最后一行有前提：错参真的会被拒。有的参数会被忽略或归一化，发过去仍然成功。探测意外受理后，要停下并记录它的实际费用，不能继续把它当作无费用的轮询。

## 2. 计时：把测试、准备和交付分别量出来

过去的估时把读资料、编请求、等待上线、测试、截图和写报告放在一起。这个总时间有价值，但看不出哪里最慢。我改为至少保留三个时间段：准备完成前的工作、开测到结论落盘、结论到报告交付。

测试起点也要说清。自动探测第一次判定可用，是本机观察到的时刻；服务真实开放可能更早。若探测间隔为一段固定时间，还应单列检测延迟，不能把它悄悄算成零。

文档和页面从本轮测试时钟移出去，是因为它们已有有效证据。若仍有阻塞性的人工检查未完成，最终交付就仍未完成。分开计时只是为了分析流程，不能通过挪走工作来宣布整体提速。

当时彩排还额外保留了一段观察窗口，用来量扣费是否晚到。记录里的完整运行时间包含这段等待；把它扣掉得到的是下一轮估时，不能再称为本轮实测。保存完整起止时间、各阶段耗时和额外等待，比只写一个「大约几分钟」更有用。

## 3. 一把密钥：先保住逐单对账

只有一把密钥，而且可读取的只是累计用量时，最直接的逐单测法是串行：记开始读数，发请求，等结算，核结束读数，再进入下一单。前提是这个计数范围里没有其他并发消费。

上一单已经对上账，可以把它的结束读数作为下一单的开始读数，省掉一次重复等待。如果上一单未对上、超时或仍可能有延迟结算，就不能直接沿用。此时重新读取也未必足够，还要确认旧请求的终态，避免把晚到的费用算到新请求上。

保存的历史彩排里，短文本核心请求确实逐单执行，并逐单对上了独立预期。请求本身并没有占掉原估时里的大部分时间。减少重复检查，再按真实结算轨迹调整读数，已经能缩短主要流程。

「连续两次读数相同」只是观测规则，不能从逻辑上保证后面再也不变。它要结合响应终态、记账机制和异常超时使用。当时量到的结果仅来自一次非流式文本彩排，所以没有直接拿同一等待参数套到视频任务上。

## 4. 并行对账：总额相等不代表每单相等

多把密钥也不自动带来逐单隔离。用量接口可能按密钥统计，也可能所有密钥都读到账户总量。若不先确认统计范围，程序甚至会把多扣解释成正常。

举一个完全虚构的例子：两笔请求的独立预期都是一个单位。两把密钥的读数都增加两个单位，有两种解释：账户总共正确扣了两个单位，两次读取看到了同一个总量；或者按密钥统计，每笔都被多扣了一倍。只看这两条读数，无法区分。

一种辅助方法是放一把本波不发请求的密钥作参照，结合已知配置和读数判断统计范围。这个方法仍依赖同一账户、相同统计口径和稳定记账，条件不足时只能记「范围未知」，不能挑一个能对上的解释。

媒体任务并行生成时，同一账户的总量差可以核整组合计。各任务自报的费用能帮助定位，但它们可能和最终账务走同一套实现，不能代替独立的账户读数。一个多扣、另一个少扣，合计恰好相等，整组检查也看不出来。

因此，我会把结论写成明确的层级：逐单实测、整组实测、逐单按比例推定，或者尚不能判断。合计对上时不自动给每一单盖章；需要逐单确认的关键路径，单独执行或使用已验证的隔离计数器。

## 5. 已知问题：保存基线，也保留复测触发条件

回归缩短之后，历史问题表更有用了。它记录问题在哪个版本、哪个入口和哪组条件下出现，现有证据是什么，什么时候需要重跑。已经确定的存量问题，不必每次从零研究；相关路径变化时，又能立刻找到对应样本。

这张表也不能替新异常免责。今天的错误文案和上周相似，不代表根因相同。请求结构、渠道、版本或终态不一致，都应重新核对。旧问题只有在条件和证据仍适用时，才能作为基线引用。

对不上账时，脚本可以按常见取整、缓存和重复扣费方式重新计算，列出恰好匹配实际读数的候选解释。但这些只是排查线索。助手算出一个相等的式子，不足以证明生产实际走过这个分支。

## 6. 把彩排做到的和没做到的放在一起

历史记录中，一把密钥串行跑文本、并发做拒绝探测，以及单张图像的账务核对都有保存结果。我回读结果行，确认文本的独立预期与实际读数逐条相等。它们可以支撑本次流程调整的局部结论。

同一阶段，多密钥并行主要由本地假网关验证；视频的真实耗时没有量过。自动探测彩排时，目标本来就已开放，第一轮便通过，所以也没有证明真实的「尚未开放到开放」切换行为。这些空白需要原样保留。

后续再用这套方法，我会先确认五件事：复用证据对应哪个版本；核心集是否覆盖每个必要端点和计费角色；累计读数属于谁；异常时怎样停止追加请求；测试时间和交付时间是否分别记录。答案齐了，再选择串行或并行。

## 收尾

缩短回归最有效的变化，是把重复工作移出本轮，把必要证据安排进更少的请求，并保留对账结论的准确范围。并行只是执行方式，覆盖和证据才决定结果能否使用。
