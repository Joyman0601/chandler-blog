> 一句话总结：跨仓新增字段，完成条件要包括所有消费者能读到它，以及发布产物确实包含它。本地兄弟目录一起升级，只能证明这一组本地代码能配合运行。

## 0. 起因：字段发出去了，另一端仍走旧行为

一次修复给共享的 SDK（软件开发工具包）增加了配置字段。网关设置它，再通过 JSON 发给任务执行器，希望执行器按新的隔离规则处理上游错误。

网关和 SDK 都改了，本地也能编译。但执行器在发布时依赖的 SDK 仍是旧版。旧结构体没有这个字段，解码过程没有报错，后续继续按旧行为执行。

我复盘时发现，这类问题有两种表现。直接在源码里引用新字段的一方，用旧依赖会编译失败；仅通过 JSON 接收配置的一方，可能正常编译、正常响应，却无法理解新增信息。

后者很容易被「接口返回成功」掩盖。提交说明记录了线上问题；我核对了字段新增、下游升级和解码测试的差异，并回看当时保存的本地发版模拟。下面用通用例子说明机制，不包含原业务代码。

## 1. JSON 兼容，不等于新语义已经生效

Go 的 `encoding/json` 提供了拒绝未知字段的显式选项。使用普通解码方式时，发送方增加字段，并不会自动迫使旧接收方升级。严格解码的行为可查[官方文档](https://pkg.go.dev/encoding/json#Decoder.DisallowUnknownFields)。

下面的例子模拟一个新发送方和旧消费者。字段名为本文自编，程序只使用标准库：

```go
package main

import (
    "encoding/json"
    "fmt"
)

type OldConfig struct {
    Limit int `json:"limit"`
}

type NewConfig struct {
    Limit         int  `json:"limit"`
    SeparatePools bool `json:"separate_pools"`
}

func main() {
    wire := []byte(`{"limit":4,"separate_pools":true}`)
    var old OldConfig
    var current NewConfig
    if err := json.Unmarshal(wire, &old); err != nil {
        panic(err)
    }
    if err := json.Unmarshal(wire, &current); err != nil {
        panic(err)
    }
    fmt.Printf("old limit=%d\n", old.Limit)
    fmt.Printf("new separate_pools=%t\n", current.SeparatePools)
}
```

旧消费者读到了它认识的限额，整个解码成功；新增开关没有进入它的结构体。协议层面允许这种演进，但业务要求可能已经变了。

因此，需要分别回答两个问题：旧消费者能否继续运行，新行为是否必须由所有消费者同时支持。前一个答案为「能」，不能代替后一个答案。

也不能把全局启用严格解码当作唯一修法。滚动升级时，新旧进程并存是正常情况。是否拒绝新字段、增加协议版本、显式协商能力，或者先升级消费者，都要按兼容契约选择。这里的最低要求，是把旧消费者忽略字段的结果明确写出来。

## 2. 本地替换让两个不同问题看起来像一个

多仓开发常把依赖指向兄弟目录，方便同时修改接口两侧。假设有这样一份通用配置：

```go
require example.org/task-sdk v1.2.0

replace example.org/task-sdk => ../task-sdk
```

`require` 中记录的版本，与本地真正使用的源码可能不同。`replace` 可以用本地目录替换模块内容，这是 Go 模块机制本身的行为，见[模块参考](https://go.dev/ref/mod#go-mod-file-replace)。

如果兄弟目录已经包含新字段，本地编译自然会通过。发布环境如何取依赖，则取决于自己的脚本：可能按锁定版本下载，也可能检出指定提交，再生成 `vendor`。不能笼统地说持续集成一定忽略 `replace`，必须看实际构建步骤。

这次问题正是本地组合与发布组合不同。我现在会把它们分开记录：

| 组合 | 要证明什么 |
|---|---|
| 本地多个仓库的工作版本 | 开发中的接口两侧可以协作 |
| 清单锁定的依赖版本 | 将要发布的代码包含必需变更 |
| 持续集成检出的版本 | 自动检查使用了预期的依赖 |
| 最终二进制中的依赖 | 交付产物与前面的记录一致 |

这几行可能恰好一致，也可能不同。写成一行「SDK 已升级」会丢掉最有价值的信息。

## 3. 从字段出发，列全编码方和解码方

审查时我会从新字段出发画一条数据路径：谁创建它，谁序列化，经过哪些缓存或队列，谁解码，最终哪个分支读取它。

HTTP（超文本传输协议）接口只是其中一种传输方式。JSON 还可能被写进数据库、缓存或任务消息。另一个进程从历史消息恢复任务时，也可能成为消费者。

对应的检查表应该按消费者列，而不是按修改文件列：

| 消费者 | 使用共享类型的方式 | 最低验证 |
|---|---|---|
| 网关 | 直接构造包含新字段的结构体 | 按发布依赖编译 |
| 任务执行器 | 解码远端配置 | 新字段解码后值正确 |
| 恢复或重放程序 | 读取持久化消息 | 新旧消息各有明确结果 |
| 旁路工具 | 只关心少量旧字段 | 明确允许忽略哪些信息 |

表里的后两行是通用排查方向，不表示这次事故涉及这些程序。列清单的目的，是主动找出可能没有改源码、却已经受到协议变化影响的一方。

对每个消费者，再记录其依赖版本是否包含字段变更。在线性或保留祖先关系的历史中，可以用 `git merge-base --is-ancestor` 检查包含关系。压缩合并或挑选提交会改变祖先关系，这时需要核内容和行为，不能只靠提交哈希判定。

## 4. 解码夹具直接断言新字段

原来的接口测试可能只断言请求成功，以及某个旧字段值正确。这样的用例对新增字段没有约束，旧版 SDK 同样能通过。

这次下游修复在配置响应夹具里加入新字段，并直接断言解码后的值。引用该字段的测试在旧类型下会编译失败，也就不会再默默忽略这次依赖升级。

我更倾向于保留两层验证：第一层断言新字段确实解出来，第二层验证它驱动的行为。例如，在本文的虚构例子里，不能只看 `SeparatePools` 为真，还要检查两个资源池是否按新规则隔离。

旧消息也需要独立预期。字段缺省时继续沿用旧行为，还是拒绝执行，应由兼容要求决定。测试不要从当前实现里读取默认值再当答案，否则实现和测试可能一起错。

最小验证矩阵可以这样写：

| 发送内容与消费者 | 预期 |
|---|---|
| 新消息、新消费者 | 新字段被读取，新行为生效 |
| 旧消息、新消费者 | 按约定的缺省行为处理 |
| 新消息、旧消费者 | 记录实际兼容结果，限制不安全组合 |
| 只升级本地目录，发布仍锁旧版 | 发布预检或目标测试明确失败 |

这和[守卫测试的三个要求](/blog/testing/guard-tests-three-rules/)是一件事：测试需要识别错误组合，失败位置还必须能说明它在守什么。

## 5. 按发布入口复现，能区分三种失败

保存下来的发版模拟很有帮助。它没有只跑一次本地构建，而是比较了不同依赖组合：

| 组合 | 当时的实际结果 | 能得出的结论 |
|---|---|---|
| 本地依赖较新，清单仍锁旧版 | 版本一致性预检失败 | 本地组合不能直接当发布组合 |
| 本地依赖退回清单版本 | 预检通过，编译报告缺少新字段 | 清单版本不满足源码要求 |
| 清单和依赖更新到兼容版本 | 预检与构建通过 | 这组本地发布输入可构建 |

这三行比一句「构建失败」清楚。第一种要处理依赖来源不一致，第二种要升级必需版本，第三种仍不能直接证明线上部署完成。

如果项目使用 `vendor`，还要核生成步骤。它是依赖源码的一份快照，旧快照不会因为兄弟仓改了就自动更新。Go 会检查部分清单一致性，但不能替代对实际构建过程的核对，见[官方 vendoring 说明](https://go.dev/ref/mod#vendoring)。

在排查副本里，可以记录 `go env GOWORK`、`go list -m -json` 的结果，以及 `go version -m` 输出的产物模块信息。它们分别帮助确认工作区影响、模块选择和二进制元数据。具体能读到什么，要以实际构建方式为准。

## 6. 持续集成状态要读到步骤层

CI（持续集成）显示失败，也不代表新字段已经被测试发现。流程可能在检出依赖、读取凭证或启动执行环境时就停了，编译和测试根本没开始。

反过来，一个绿色任务如果只检查格式，也无法证明发布依赖正确。判断检查是否有效，需要找到负责这项契约的具体步骤，看它是否执行、用了什么版本、产生了什么结果。

本地执行发布脚本，能补上对构建输入的验证；它不能代替托管平台上的真实运行状态。我会把「本地模拟通过」和「远端检查已执行」写成两个结论，避免自动化的图标掩盖证据缺口。

## 收尾

1. **列消费者** —— 新增字段影响的不止写字段的仓库，还有每个解码进程。
2. **区分依赖来源** —— 本地替换、版本清单、持续集成和产物要分别核。
3. **直接断言字段** —— 响应成功和旧字段正确，不能证明新信息已被消费。
4. **模拟真实发布** —— 用发布入口验证依赖组合，再确认自动检查确实执行。

这次让我把「跨仓改完了」的判断往后移了一步。字段存在于源码只是开始；它穿过序列化边界、进入正确版本的消费者，并在实际产物里驱动预期行为，才算完成。
