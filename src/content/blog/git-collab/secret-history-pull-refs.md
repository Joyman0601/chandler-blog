> 一句话总结：敏感文件从当前主分支消失，只回答了一个很小的问题；检查公开暴露，要沿着保留它的引用继续查，同时独立确认凭据已经撤销。

## 0. 起因：目录里找不到，旧链接却能打开

我整理公开仓库时，发现一个容易误判的状态：当前主分支已经没有旧配置脚本，普通目录浏览也找不到它，看起来已经处理干净。

继续检查历史引用，情况变了。旧提交不属于当前主分支的祖先，却仍被一个拉取请求（Pull Request，PR）的引用保留。按旧提交访问静态文件，不带登录凭据也能下载，返回内容与本地 Git 对象一致。

这是当时保存的实测结果。它证明文件仍公开可读，没有证明文件里的凭据仍然有效，也没有证明有人使用过那些凭据。我没有拿发现的值调用真实服务。

后来我确认旧凭据已撤销，接着处理残留历史。到本轮整理采用的记录为止，本地清理副本已验证，平台侧残留仍待处理。文章里的例子都重新编写，不包含原仓库、路径、提交标识或凭据。

## 1. 四种状态：先把「删了」说清楚

我现在会把检查结果拆成四行，避免用一句「已经删除」概括所有层次。

| 层次 | 实际要问的问题 | 检查通过的范围 |
|---|---|---|
| 当前版本 | 文件还在当前检出的目录里吗 | 当前工作树和选定提交 |
| 提交历史 | 当前主分支能否到达那个旧提交 | 指定分支的祖先链 |
| 引用集合 | 其他分支、标签或 PR 是否保留它 | 实际取得并检查的引用 |
| 对外访问 | 无认证访问旧内容会得到什么 | 当次请求的 URL、时间和响应 |

例如，删除文件并提交，可以让当前版本不再包含它；旧提交仍然存在。把文件加进 `.gitignore`，也不会自动移除已经被 Git 跟踪的内容。这一点可见[Git 的忽略规则说明](https://git-scm.com/docs/gitignore)。

这四行还要加一条独立状态：凭据是否已撤销。即使远端暂时看不到旧文件，也不能用它推断凭据已失效。反过来，凭据作废后，私人过程文档是否仍公开，也是另一个要处理的问题。

## 2. 找保留者：核引用，而不是只搜文件名

我先定位旧提交，再问哪些引用包含它。下面只读命令应在专门的核查副本里运行，变量值由实际调查结果提供。

```bash
git for-each-ref --format='%(refname)'
git merge-base --is-ancestor "$OLD_COMMIT" main
git for-each-ref --contains "$OLD_COMMIT" --format='%(refname)'
git rev-list --all --objects
```

第二条命令以退出状态回答祖先关系。返回非零后还要核实是「不是祖先」，还是参数无效、对象缺失等命令错误，不能一律当成历史已清理。

第三条命令列出包含指定对象的引用，参数语义见[Git 的引用遍历文档](https://git-scm.com/docs/git-for-each-ref)。最后一条列出本地引用可达的对象和已知路径，用来扩大历史检查范围。

这里的「全部」仍有前提：它只覆盖本地已经取得的引用。普通克隆、浅克隆和只抓默认分支的检出，不能直接当作平台全部历史。核查记录应写明实际取得了什么，缺哪些引用，而不是只写「全仓扫描通过」。

我这次遇到的关键现象，就是主分支祖先检查与引用包含检查给出不同答案。两者没有矛盾，它们问的是不同范围。

## 3. 验公开可读性：验证文件，不动用凭据

为了确认公开暴露，我只需要证明无认证请求能拿到相同文件。检查应保存状态码、内容长度和文件摘要，敏感值按字段遮掩，不打印到终端或报告里。

**文件可读与凭据可用，需要分别取证。** 静态文件返回 200，说明当次能取到文件；它不说明 API 服务会接受里面的值。拿旧值发真实业务请求，还会引入权限、费用和访问日志，不能顺手当成核查步骤。

摘要也有边界。整份文件的摘要适合比较两次下载是否一致；短密码等低熵值的摘要仍可能被猜测，不应公开发布。我只把必要证据保存在受限的本地记录里，公开文章只留判断方法。

还要避免把暴露证据变成新的暴露入口。正文不需要提供真实旧文件 URL，更不需要展示带凭据的几行原文。读者理解这个问题，靠的是引用关系和检查条件。

## 4. 处置顺序：先撤销，再分清本地与远端

发现疑似真实凭据后，先由有权限的人确认撤销或轮换，再评估历史清理。GitHub 也把撤销或轮换列为处理密钥暴露的第一步；仅重写历史并不能收回外部副本。[官方处理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

我的本地清理验证只说明：在选定副本的可达对象里，已知敏感脚本与目标值不再出现，原本应保留的主分支内容没有改变。这没有修改远端状态。

平台的 PR 引用有自己的权限边界。GitHub 将 `refs/pull/` 标为只读，无法通过普通推送直接覆盖；涉及残留引用和缓存的处理，要遵循平台现行流程，是否受理由平台判断。[GitHub 的清理边界](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

因此，记录应分开写「本地验证通过」「远端分支已更新」「平台已处理残留」「匿名链接复核结果」。哪一步没有证据，就保留未知。

## 5. 平台回复：材料完整不等于工单已提交

这次还有一处助手执行错误。平台的提交前助手给出了材料建议，助手一度把下一步入口说得不够清楚，随后又按模糊的「删除」分类引导，进入了整个仓库删除表单。

我把实际表单选项反馈后，助手纠正了方向。这里需要核的是具体操作对象：保留仓库、清理敏感历史引用，与删除整个仓库有不同结果。不能因为两个入口都有「删除」二字，就认为它们等价。

我把后续状态检查改成了三个问题：是否产生正式工单记录，平台是否明确给出处理结果，处理后是否重新核过旧访问路径。提交前建议只能说明材料准备到了哪一步，不能升级成正式受理，更不能升级成残留已清除。

界面名称会变化，文章不固定某一屏的按钮顺序。实际操作时，应以官方说明、当前页面的问题和最终确认对象为准。

## 6. 复查清单：每一行都能对应证据

| 要记录的事 | 最小证据 | 不能顺带推出 |
|---|---|---|
| 当前文件已移除 | 指定提交的文件列表 | 旧版本已消失 |
| 主分支不含旧提交 | 祖先关系与有效对象检查 | 所有引用都不含 |
| 某引用保留旧提交 | 引用名与包含关系 | 凭据仍有效 |
| 旧文件匿名可读 | 无认证下载和内容比对 | 已发生滥用 |
| 旧凭据已撤销 | 账户持有人或管理记录 | 历史内容已清除 |
| 本地清理成功 | 清理副本的对象与保留内容对照 | 远端也已清理 |
| 平台处理完成 | 明确处理结果与后续复核 | 所有外部副本被收回 |

预防措施也要对应入口：敏感配置从一开始就不进版本库，提交前审实际暂存内容，公开仓库前再核历史范围。扫描器能发现一批模式，不能保证识别所有私人资料或业务信息。

## 收尾

1. **范围写清** —— 当前目录、分支祖先、其他引用和公开下载分别检查。
2. **凭据独立处理** —— 先确认撤销，静态内容核查不动用旧值。
3. **状态逐步取证** —— 本地清理、工单提交和远端处理各留自己的证据。

下次公开或整理仓库，我会先问「检查了哪些引用」，再判断是否完成。路径不再出现在首页，是检查的起点。
