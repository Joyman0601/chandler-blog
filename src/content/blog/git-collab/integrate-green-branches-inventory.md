> 一句话总结：每条分支的测试都假设别的分支不存在，所以「每条都绿」推不出「合起来是对的」，交叉的地方要专门列出来、专门写会红的守卫；盘点没合入的分支时，「已解决」「没变化」都是结论，要先说清依据是哪一种、数据是不是刚取的。

## 0. 起因：同一天的两件事

那天做了两件和分支打交道的事，都由 AI 编程助手执行，我负责提要求、要利弊、做选择。

第一件是整合。围绕某音乐生成模型，几条修复分支散在前后端、SDK、worker、文档五个仓库里：一条给老客户做回调兼容，一条加逐词时间戳，一条在返回给用户之前过滤掉内部字段，一条修生成过程中的进度推送。每条分支单独看，测试都是绿的。我让助手把它们合成一套整合分支，五个仓库用同一个分支名，审视、修复都在整合分支上做完再推送。

第二件是盘点。我让助手把五个仓库里「没合入主干、问题也还没解决」的分支列一份清单给 leader，原话的意思是「已经解决的可以不写」。清单做到一半，整合那边推了新提交，清单要跟着更新。

两件事暴露的问题是一类：**一句「是绿的」「已解决」「没变化」，背后的依据到底是什么**。下面按顺序讲。

## 1. 每条都绿，合起来不一定对

整合过程中，审视和全量测试找出几处问题，其中三处正好是三种典型的交叉。

### 一条的输出是另一条的输入

过滤分支在返回结果前，把每个条目里下划线开头的内部字段剥掉，这些字段里有歌词和实际使用的引擎。兼容分支要给老客户的回调补一组旧格式字段，歌词和实际模型这两个值，它是从**过滤后**的结果里取的。合在一起，这两个字段永远是 `null`。

两条分支各自的测试都是绿的。原因很简单：过滤分支的测试里没有投影这一步，兼容分支的测试里没有过滤这一步。每条分支都在「另一条不存在」的世界里测过了。

修法是投影改成按序号从库里的原始结果读，过滤照旧。助手写了一条守卫用例，把投影放回修复前的写法，4 处断言失败；修复后通过。这一步很关键：守卫用例要先证明自己能红，才算守住了这个交叉点。

### 两条分支的测试互相矛盾

进度推送分支的测试断言：生成中的阶段不出现歌词。兼容分支所依据的接口契约却要求：查询的每个阶段都给歌词。两条测试对同一个字段下了相反的断言，合在一起只能留一条。

这种冲突 git 看不见，两边改的是不同的测试文件，文本上毫无交集。最后按契约文件改了测试：生成中给歌词，但不给内部字段和上游原始链接。判断依据是契约，不是「哪条分支先写的」。

### 源分支自己的头就是红的

兼容分支的前端部分删了旧版本的一组配置行，旧名字改成解析到新版本。主干上有 5 个测试文件还钉着旧行为，于是这条分支**自己的头上**就有 8 条 Jest 失败，其中 7 条是钉着旧行为的测试。

「这条分支是绿的」原来只是一句说法，没人在它自己的头上按 CI（持续集成）的范围跑过。整合时看到红，第一反应是「合出问题了」，其实问题在合之前就有。

### 一个不算交叉、合起来才看得见的

兼容分支把七种语言的契约文案整包打进了客户端，那个页面的首屏 JS 从约 408 KiB 涨到约 422 KiB（同一台机器本地构建）。改成只传当前语言后回到约 407 KiB。单条分支的体积检查未必报警，几条叠在一起才显出来。CI 上的数字这次没核。

## 2. 先列交叉点，再给每个点写会红的守卫

上面三处是审视和全量测试里撞出来的，不是开工前列出来的。复盘时我把「下次先列」的部分整理成三类交叉点：

| 交叉类型 | 怎么找 | 守卫写什么 |
|---|---|---|
| 两边都改过的文件 | 各自从 merge-base 出文件清单，取交集 | 合并后的行为，不只看有没有文本冲突 |
| 一边写、另一边读的数据 | 列每条分支新增或改动的字段、函数返回值，搜另一条分支读它的地方 | 端到端走一遍「写 → 读」，断言读到的值 |
| 两边测试都断言过的字段 | 搜两条分支新增测试里出现的同名字段 | 以契约为准，只留一套断言 |

第一类可以直接用命令算：

```bash
# 两条分支都改过的文件
TRUNK=origin/main
comm -12 \
  <(git diff --name-only "$TRUNK"...feat/a | sort) \
  <(git diff --name-only "$TRUNK"...feat/b | sort)

# 两条分支新增测试里都出现的字段名（粗筛，按项目习惯改正则）
fields() {
  git diff "$TRUNK"...$1 -- '*_test.go' '*.test.ts' \
    | grep '^+' | grep -oE '"[a-z_]+"' | sort -u
}
comm -12 <(fields feat/a) <(fields feat/b)
```

第二类最难靠命令找全，「过滤 → 投影」这种链条要读代码才看得出。我现在的做法是让列清单的人对每条分支回答一句：**这条分支的输出，另一条分支在哪里当输入用？**

每个交叉点的守卫用例写完，都要做一次反向验证：把修复临时还原，确认用例会红，再恢复。这一步不做，守卫可能根本没覆盖到那条路径。

源分支的头也要单独跑一遍，用干净的 worktree，按 CI 的范围：

```bash
git worktree add --detach /tmp/check-a origin/feat/a
cd /tmp/check-a && <按 CI 的安装和测试命令跑全量>
git worktree remove /tmp/check-a
```

拿到每条源分支头上的失败集合，再和主干的失败集合逐个名字比。整合分支上出现、源分支和主干都没有的失败，才是合出来的问题。

## 3. 整合时的修复，先预演能不能补回源分支

整合分支上修了好几处。接下来要定的是：这些修复要不要补回各自的源分支？

我让助手列出利弊，选了「前端 4 个修复补回兼容分支，第一节那个投影修复只留在整合分支」。决定的依据是 **leader 怎么合**：他开着的几个 PR 都是按源分支一条条合的。兼容分支单独合进去，会带进这些红测试和多出来的首屏体积；补回之后，这条分支的失败从 8 条降到 1 条，新增失败 0，剩下那条是别的页面的路由守卫，与这次无关。如果合并人只合整合分支，补回就没必要。

投影修复为什么补不回去？它改的文件，一部分只在兼容分支上有，一部分只在进度推送分支上有，往哪边摘都缺另一半。这个结论是先预演出来的，不是摘了再撤回。

预演 cherry-pick 用的是 `git merge-tree` 的 `--merge-base` 参数（git 2.40 起）：一次 cherry-pick 就是以「提交的父提交」为基的三方合并，可以在内存里演完：

```bash
FIX=<整合分支上的修复提交>
for b in feat/a feat/b; do
  git merge-tree --write-tree --name-only --merge-base="$FIX^" "$b" "$FIX" >/dev/null
  echo "$b: exit=$?"        # 0 = 能干净摘过去；1 = 有冲突
done
```

不碰工作区，不碰任何分支。补回之后，再核一次补回的提交和整合分支上的原提交是不是同一份补丁：

```bash
git show "$FIX"     | git patch-id --stable | cut -d' ' -f1
git show feat/a     | git patch-id --stable | cut -d' ' -f1   # 两行相同才算同一份
```

patch-id 相同，两条分支先合哪条，git 都能认出是同一处改动，不会在这里冲突。补不回的修复，在给合并人的说明里写明「只能走整合分支」。

用 merge-tree 预判 rebase 冲突的基本用法，见[出 diff 前先定主干和起点](/blog/git-collab/diff-range-trunk-merge-base/)第 4 节。那篇第 5 节讲的按提交日期生成的文件，这次也碰到了：兼容分支合主干的预演在一个 sitemap 生成文件上冲突，那是重算就行的生成物，不是两边逻辑打架。

## 4. 清历史前，先看提交号有没有被别处钉着

整合时还发现，SDK 的两条分支里混进了一个审视工具的产物：一个缓存目录，加上几处源码注释，里面有本机路径。要去掉，有三个选项：不动；每条分支加一个删除提交；改写历史再强推。

只看产物本身，改写历史最干净。同一天另一轮工作里，碰到同类产物，选的就是重建历史、强推。这次我选了加删除提交，原因在产物之外：

- **SDK 的提交号被别处钉着。** 后端、worker 的 `go.mod` 用伪版本引用 SDK 分支上的提交，CI 也按这个版本拉。改写 SDK 历史，下游几个仓库都要重新钉版本、重新审、重新推，只为去掉两处本机路径。
- **主干合 PR 用的是合并提交。** 助手查了最近几十次合并，都是普通合并提交，不压缩。所以删除提交只能让主干上的**文件**干净，**历史**里那几行还在。这一点要写进说明，由合并人决定要不要重建。

查「有没有被钉着」，在下游仓库搜提交号前缀就够：

```bash
# 列出 SDK 分支上的提交号前缀，在各个下游仓库的 go.mod / go.sum 里找
for c in $(git -C sdk rev-list origin/main..feat/a); do
  grep -l "${c:0:12}" backend/go.mod backend/go.sum worker/go.mod worker/go.sum 2>/dev/null \
    | sed "s/^/${c:0:12} 被引用于 /"
done
```

删除提交也要核，确认它「只删不增、删的都是想删的」：

```bash
git diff --numstat HEAD^ HEAD | awk '{a+=$1} END {print "新增行数:", a}'   # 应为 0
git diff -U0 HEAD^ HEAD -- '*.go' | grep '^-[^-]' | grep -vE '^-\s*//' # 应无输出：删的全是注释
gofmt -l .                                                              # 应无输出
```

这次两条 SDK 分支的删除提交是同一份补丁，删掉的 `.go` 行全是注释。所以清不清历史、怎么清，**除了看产物本身，还要看提交号有没有被别处引用**。

## 5. 盘点没合入的分支：「已解决」有四种依据

第二件事。范围的定法和[推送和 PR 状态只问远端](/blog/git-collab/push-status-ask-remote/)第 2 节一样：从远端现取全部分支，按「`主干..分支` 里有没有我的提交」筛，主干按最近的 PR 合进了哪条分支来认。几十条分支里，有一批按「已解决」没有列入。复核时发现，「已解决」的依据强弱差得很远：

| 依据 | 说明到哪一步 | 怎么判 |
|---|---|---|
| 分支提交已是主干的祖先 | 代码确实在主干里，最强 | `git merge-base --is-ancestor` |
| 主干里有等价补丁 | 内容进了主干，提交号不同；要核每个提交都有等价的 | `git cherry`，行首是 `-` 的有等价 |
| 另一个 PR 修了同一个问题 | 分支本身没合；要对着问题描述的失败，在主干上核 | 读代码或复现，命令给不出结论 |
| 转给别人 | 只是归属变了，不算解决 | 单独标「转他人」 |

前两种可以批量算：

```bash
TRUNK=origin/main
for b in feat/a feat/b feat/c; do
  if git merge-base --is-ancestor "$b" "$TRUNK"; then
    echo "$b: 已在主干（祖先）"
  elif ! git cherry "$TRUNK" "$b" | grep -q '^+'; then
    echo "$b: 每个提交在主干都有等价补丁"
  else
    echo "$b: 还有 $(git cherry "$TRUNK" "$b" | grep -c '^+') 个提交没有等价物"
  fi
done
```

后两种只能写成文字，清单里要把依据也写出来。读清单的人看到「已解决」，能一眼知道是哪一种，就知道还要不要追。

## 6. 「没变化」要先证明数据是新的

清单交出去以后，整合那边在几个仓库都推了新提交。助手 fetch 之后重跑枚举，新旧结果差集为 0，差点回复「推送不影响清单」。

我问它拿什么对照过。它用 `ls-remote` 一查，那几条分支的远端 head 都换了。

**根因**：盘点用的镜像是 `git clone --bare` 做的部分克隆。裸克隆不写 `remote.origin.fetch`，之后的 `git fetch origin` 退出码 0、照常打印 `From ...`，但只把远端 HEAD 写进 `FETCH_HEAD`，本地的 `refs/heads/*` 全停在克隆那一刻。第一版清单用的是刚克隆的镜像，所以没出错；隔几小时再跑第二版，才暴露。我在本机拿一个 `file://` 源仓库复现过：裸克隆后源仓库前进一个提交，`git fetch --prune origin` 之后本地 `main` 还是旧的。

**修复**：fetch 时显式写 refspec，或者建镜像时就配上；fetch 完拿远端对一次再继续：

```bash
M=/path/to/mirror.git
git --git-dir="$M" config remote.origin.fetch '+refs/heads/*:refs/heads/*'   # 建镜像时配一次
git --git-dir="$M" fetch --prune origin

# 镜像的本地分支必须和远端逐条一致，否则别重跑
diff <(git --git-dir="$M" ls-remote --heads origin | sort) \
     <(git --git-dir="$M" for-each-ref --format='%(objectname)%09%(refname)' refs/heads | sort) \
  && echo "镜像已是最新" || echo "镜像没更新，先别下结论"
```

用 `+` 是因为镜像只读：别人强推过的分支也要跟上。`git clone --mirror` 会自带 `+refs/*:refs/*`，但会连代码托管平台的 PR refs 一起拉，量大，所以盘点时常用 `--bare`，也就常踩这个坑。

道理和「推没推只问远端」一样：**差集为 0 只说明两份数据相同，不说明数据是新的**。下「没变化」的结论之前，先证明输入是刚取的。

## 7. 手写的结论回到数据里核，提更正先读原句

清单页面的分支行，由脚本从枚举数据生成，脚本还断言了「每条分支恰好归类一次」。机器检查全过。可页面上手写的部分，首屏、小结、卡片说明，是助手凭印象写的。我让一个新上下文的子代理复核，交回的问题里，有 8 处是手写文字和同页数据对不上：

- 「落后主干约 400 个提交」只对一个仓库成立；
- 「全部没有 PR」有反例；
- 「没有冲突」所在的那一组里，有一条分支试合并有一串冲突文件；
- 「没发给您」的依据只是「没有发送记录」；
- 标题把暂放的几项也算成了「问题」。

都在发出前改掉了。规律是：带「全部」「都」「没有」的句子、带数字的句子，最容易和明细打架。我现在看 AI 写的小结，会挑一两句回到明细里找反例。

复盘时还有一个小插曲。上下文被压缩过，压缩摘要里写着「已发的清单把 SDK 的删除提交当成已清理，需要更正」。助手准备照着提更正。我让它先回去读页面原句：页面写的是「已用一个删除提交去掉，没有改写历史」，正是第 4 节的选择，和事实一致，不用更正。摘要是转述，原句才是证据。要说已发出的东西有错，先引出原句，再说依据的规则。

## 8. 一张清单

整合几条分支之前：

- [ ] 每条源分支在自己的头上，用干净 worktree 按 CI 范围跑一遍，记下失败集合
- [ ] 列交叉点：两边都改的文件、一边写另一边读的数据、两边测试都断言的字段
- [ ] 每个交叉点在整合分支上写一条守卫，并确认还原修复后它会红
- [ ] 互相矛盾的断言，以契约文件为准，只留一套

整合分支上修了东西之后：

- [ ] 每个修复用 `merge-tree --merge-base` 预演能不能摘回源分支
- [ ] 按合并人的合并方式定补不补：一条条合就补回，只合整合分支就不必
- [ ] 补回后用 `patch-id` 核和原提交是同一份补丁
- [ ] 补不回的，在合并说明里写「只能走整合分支」

要清理历史时：

- [ ] 先查提交号有没有被下游的依赖清单或 CI 钉着；钉着就先考虑删除提交
- [ ] 删除提交核「新增 0 行、删的都是目标内容」
- [ ] 主干若用合并提交，说明里写「历史里还在」，由合并人定要不要重建

盘点没合入的分支时：

- [ ] 每条「已解决」写明依据属于四种里的哪一种
- [ ] 镜像 fetch 后和 `ls-remote` 对一遍，对不上不下「没变化」
- [ ] 手写的小结里，带数字和「全部」「没有」的句子回到明细找反例
- [ ] 要更正已发出的内容，先读原句

## 收尾

1. **各自全绿不等于合起来对** —— 每条分支的测试都假设别的分支不存在，交叉处要专门列、专门测
2. **守卫先证明能红** —— 还原修复后不红的用例，守不住任何东西
3. **「绿」要在源分支自己的头上跑出来** —— 不然合出来的红分不清是谁的
4. **补不补回看合并方式** —— 先用 merge-tree 演，补回后用 patch-id 核
5. **清历史看提交号有没有被钉着** —— 被钉着，改写的代价落在下游所有仓库
6. **「已解决」分四种** —— 祖先、等价补丁、别处修了、转给别人，强弱不同
7. **「没变化」先证明数据是新的** —— 裸克隆的 fetch 不更新本地分支，差集为 0 是假的

回头看，这些问题都不是我理解错了，是助手在执行和起草时省了一步：没在源分支头上跑、没核镜像、没回到数据、照摘要说话。能发现它们，靠的是几个固定的追问。下次看到 AI 说「是绿的」「已解决」「没变化」「要更正」，我先问一句：拿什么核的，数据是什么时候取的？这几个问题和[推送和 PR 状态只问远端](/blog/git-collab/push-status-ask-remote/)是同一个道理：状态只认现取的证据，不认记录和转述。
