> 系列第 2 篇，整条路线的招牌。很多 RAG 系统停在「纯向量检索」，这是最容易踩的一个坑。这一篇把检索质量拆成「召回」和「精排」两段，讲清为什么要用混合检索、为什么召回之后还要重排。

## 检索两段式：召回 → 精排

好的检索不是一步到位，而是分两段：

- **召回（Recall）**：从海量文档里快速捞出可能相关的候选（几百条），目标是「全、别漏」。手段是向量 + BM25 的混合检索。
- **精排（Rerank）**：对召回的候选逐条精细打分，挑出真正最相关的 top-k（几条），目标是「准」。手段是 Cross-Encoder。

记住这个分工：**召回求全、精排求准**。后面所有技术都围绕这两段展开。

## 为什么纯向量不够 → 混合检索

向量检索（Dense）理解的是**语义**，强在近义词、换一种说法也能命中。但它有个明显短板：**在精确关键词、编号、专名、缩写上会翻车**。

举个典型例子：query 是订单号 `A12345`，纯向量可能召回一个语义很近但编号是 `A12346` 的文档——对语义模型来说这俩几乎一样，但对用户来说是完全错误的答案。

补这个短板的是 **BM25（Sparse）**：传统的关键词精确匹配，命中的词越多、越稀有，得分越高。它懂「字面」。

> 记忆锚点：向量懂「意思」，BM25 懂「字面」。编号、型号、人名这类必须靠 BM25 兜底。

把两路结合起来，就是**混合检索（Hybrid）**。

### RRF 融合

两路检索的分数量纲不同（向量是相似度，BM25 是词频得分），不能直接相加。RRF（倒数排名融合）的做法是**只看排名不看分数**：一个文档在某一路里排第 r 名，就得 `1/(k+r)` 分，两路得分相加后重新排序。k 通常取 60。

这样无论两路的打分尺度差多少，都能公平融合。

## 重排：Bi-Encoder vs Cross-Encoder

这是检索里最值得讲清的一组概念。

- **Bi-Encoder（双塔，用于召回）**：query 和文档**分别**编码成向量，再比相似度。因为文档向量可以提前算好存进库里，检索时极快。代价是 query 和文档之间没有交互，精度有限。
- **Cross-Encoder（交叉，用于精排）**：query 和文档**拼在一起**送进模型，内部逐词做注意力交互，直接输出一个相关性分数。精度高，但每一对 query-文档都要实时过一遍模型，慢。

**为什么不直接用 Cross-Encoder 召回**：全库可能有几十万篇文档，挨个和 query 拼起来过模型，慢到完全不可接受。所以正解是分工——先用 Bi-Encoder 快速召回几百条，再用 Cross-Encoder 只精排这几百条。

## 分块策略 Chunking

文档要切成 chunk 才能检索，chunk 大小直接影响召回质量：

- **chunk 太大**：一块里塞太多内容，语义被稀释，匹配不准。
- **chunk 太小**：句子被腰斩，**语义不完整**，检索到也用不了。

一个好用的策略是**父子分块（small-to-big）**：用小块去检索（定位精准、命中准），但喂给 LLM 时返回小块所属的大块（上下文完整）。兼顾了「准」和「全」。

## 中文 Embedding 选型

中文 RAG 的 embedding 主流首选是 **bge（BAAI）系列**：开源、可私有化部署，而且配套有 bge-reranker，召回和精排能用同一家。

选型时主要看几个维度：

- MTEB 中文榜上的效果。
- 向量维度（影响存储和检索速度）。
- 能否私有化（合规要求）。
- 中文支持程度。
- 成本与合规。

## 一次完整的检索改造

把上面拼起来，一次典型的检索升级是这样的：

1. 在原有向量检索旁边接入 BM25，两路结果用 RRF 融合 —— 得到混合检索。
2. 混合检索召回几百条候选后，接一个 Cross-Encoder（如 bge-reranker）重排，取 top-k 喂给 LLM。
3. 工程上给重排做失败降级：rerank 调用失败时自动退回 RRF 融合的顺序，不报错、不中断链路。

这套改造让检索从「只懂语义」变成「语义 + 字面 + 精排」三重保障。但它到底带来多少提升、代价是多少延迟——光说没用，得有数据。下一篇就讲怎么用 RAGAS 把这些量化出来。
