> 系列第 6 篇。纯应用方向最容易被贴的标签是「只会调 API」。这一篇补上微调和本地部署的直觉：不要求真的训出 SOTA，但要能讲清 LoRA 为什么省显存、量化在换什么、vLLM 快在哪。

## 微调谱系

从一个会说话的模型是怎么炼成的看起：

- **预训练**：海量文本上预测下一个 token，产出 Base Model。它只会续写，不会对话。
- **SFT（监督微调）**：用「指令 → 回答」配对数据训练，把 Base Model 变成 Chat Model。
- **RLHF**：人工标注偏好 → 训练奖励模型 → 用强化学习对齐。效果好但复杂。
- **DPO**：用「好答案 vs 坏答案」的对比数据直接微调，不需要单独训练奖励模型，是近年主流的 RLHF 替代。

> 一句话记忆链：预训练（学语言）→ SFT（学服从指令）→ RLHF/DPO（学对齐价值观）。

## LoRA：为什么能省显存

**问题**：全参微调一个 7B 模型需要 100GB+ 显存（参数 + 梯度 + 优化器状态都要存）。

**洞见**：参数的更新量 ΔW 是**低秩**的——真正有信息量的更新方向只有少数几个（秩 r，比如 8）。

**做法**：冻结原始权重 W，在旁边加两个小矩阵 A（d×r）和 B（r×d），**只训练 A 和 B**。参数量从 d² 降到 2dr，比如 r=8 时只剩约 0.4%。推理时 `W_new = W + A×B`。

**显存为什么降**：原始 W 冻结、不求梯度；A、B 很小，它们的梯度和 Adam 优化器状态同比缩小，从数 GB 降到几十 MB。整体显存从 100GB+ 降到 10~20GB。

**代价**：效果略低于全参微调（通常差距很小）；好处是多个 LoRA adapter 可以随时切换。

### QLoRA：再往下压

在 LoRA 基础上，先把 Base Model 量化到 **NF4（4bit）**，显存再缩小约 4 倍（7B 从约 14GB 降到约 3~4GB），然后再跑 LoRA。总共只需 **6~8GB 显存**，一张普通游戏显卡就能微调 7B。

代价是量化引入精度损失（4bit 低于 FP16），效果略低于 LoRA；量化/反量化也有额外计算开销，训练稍慢。

## 量化：用精度换显存

量化就是把参数从 FP16（2 字节）压到更少的 bit：

| 格式 | 7B 模型显存 | 精度损失 |
|---|---|---|
| FP16 | ~14GB | 极小 |
| INT8 | ~7GB | 小（生产常用折中） |
| INT4 / NF4 | ~3.5GB | 中等 |

一个实用细节：**8GB 显卡不能选 INT8**。因为模型权重约 7GB，再加上激活值和运行时开销 1~2GB，加起来就 OOM 了。只看权重不够，要算上运行时开销，所以 8GB 卡应该选 INT4 才有余量。

**GPTQ / AWQ** 是量化**算法**（不是精度格式），解决「如何把 FP16 聪明地压到 INT4 而尽量少损精度」：GPTQ 逐层校准；AWQ 考虑激活值分布、保护重要权重，精度通常略高。

## vLLM 与 PagedAttention

**问题**：传统推理框架按**最大序列长度提前分配一整块连续显存**。比如按 2048 token 分配，实际只用了 200 token，剩下 1800 token 的显存被占着却给不了别人——这叫内存碎片化。

**PagedAttention**：把 KV Cache 切成小页按需分配，用多少要多少，消灭碎片。显存利用率从约 20~30% 提升到接近 90%，同样的显存下吞吐量提升 10 倍以上。

> 一句话：PagedAttention = 给 KV Cache 做操作系统式的分页管理，消灭显存碎片。

## Ollama：一句话拉起本地模型

```bash
ollama run qwen2.5:7b
```

自动下载 + 量化 + 启动，并暴露一个 OpenAI 兼容 API（`http://localhost:11434/v1`）。把应用的 base URL、model、api key 三个配置一改就能接进来。

- **vs vLLM**：Ollama 面向个人 / 开发者，简单、单用户；vLLM 面向生产，高并发高吞吐，但部署复杂。
- **vs 调云端 API**：本地部署数据不出机（合规、隐私）、无网络延迟、无调用费用；代价是受限于本机显存，只能跑小模型。
- **一个落地坑**：有些应用用的是 Responses API（`/v1/responses`），而 Ollama 只支持 chat/completions，接入时还得改客户端适配。

## RAG vs 微调：什么时候选哪个

这是最该想清楚的判断：

| 场景 | 选 RAG | 选微调 |
|---|---|---|
| 知识动态 / 频繁更新 | ✅ | ❌ 微调后知识固化 |
| 知识库很大 | ✅ | ❌ 装不进参数 |
| 需要引用来源 | ✅ 天然有 sources | ❌ 参数知识无法溯源 |
| 改变输出风格 / 格式 | ❌ Prompt 治标 | ✅ SFT/DPO 改模型行为 |
| 领域专有术语深度理解 | 🔶 | ✅ |
| 安全 / 合规约束 | ❌ Prompt 可被绕过 | ✅ RLHF/DPO 对齐更可靠 |

> 一句话判断：**知识问题用 RAG**（快、可更新、可溯源）；**行为 / 风格 / 深度理解问题用微调**。两者也可以叠加——微调改行为，RAG 补知识。
