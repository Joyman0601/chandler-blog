> 系列第 3 篇。上一篇把检索从纯向量升级成了混合检索 + 重排，但「升级了」和「升级有用」是两回事。这一篇用 RAGAS 给几种方案打分，把优化前后的差异落到数字上——也顺带揭示一个反直觉的结论。

## 为什么必须有评估

加了混合检索、加了重排，效果到底好了多少？如果回答不上来，那这些技术就只是「听起来很厉害」的名词。**没有评估的 RAG 等于玄学。**

评估的真正价值不是给系统打个分发朋友圈，而是**避免盲目堆技术**——有些技术在你的数据上根本没用，没有量化你永远不知道。

## RAGAS 四大指标

RAGAS 把 RAG 质量拆成检索和生成两层，对应四个指标：

| 指标 | 衡量什么 | 属于哪层 |
|---|---|---|
| Context Recall | 该检索到的相关内容，是否都检索到了（够全） | 检索 |
| Context Precision | 相关的内容是否排在前面（排序准） | 检索 |
| Faithfulness | 答案是否忠于检索到的资料（不编造） | 生成 |
| Answer Relevancy | 答案是否切题 | 生成 |

其中 **Faithfulness 和 Answer Relevancy 都是用 LLM 来打分的**——也就是 LLM-as-Judge。

## LLM-as-Judge 的范式与局限

LLM-as-Judge 就是让一个（通常更强的）模型来当裁判，按规则给生成答案打分。它的好处是能评估「忠实度」「切题度」这类没法用字符串匹配判断的软指标。

但它有局限：

- 裁判模型本身也会出错、有偏好。
- 对短答案、特定语言可能系统性偏低或偏高。
- 裁判模型太小会因为输出被截断而打分失败。

所以解读 LLM-as-Judge 的分数时，要结合数据集特点判断，而不是把绝对值当真理。

## 一组真实对比数据

拿主线项目实测一遍。配置：生成模型走 OpenAI 兼容端点，embedding 用 bge-m3，重排用 bge-reranker-v2-m3，RAGAS 裁判用 Qwen2.5-72B-Instruct。语料是一份 51 篇的标准化 FAQ，26 道测试题。

**检索与端到端延迟**

| 模式 | Hit@K | retrieval p50 | e2e p50 |
|---|---|---|---|
| vector | 100% | 95ms | 3363ms |
| hybrid | 100% | 99ms | 3447ms |
| hybrid + rerank | 100% | 665ms | 3852ms |

**生成质量（RAGAS）**

| 模式 | faithfulness | answer_relevancy | context_precision |
|---|---|---|---|
| vector | 0.942 | 0.486 | 0.967 |
| hybrid | 0.954 | 0.443 | **1.000** |
| hybrid + rerank | 0.915 | 0.508 | 0.989 |

## 关键解读（这部分才是重点）

1. **三种模式 Hit@K 都是 100%** —— 这不是「混合检索把召回提到了 100%」，而是**这个数据集的召回已经饱和（天花板效应）**。FAQ 太规范、问题和答案几乎一一对应，纯向量就够用了。如果有人写「Hybrid 把召回率提升到 100%」，那是误读。
2. **context_precision 从 0.967 提升到 1.000** —— 这才是混合检索在这个数据集上真实可见的增量：相关上下文被排得更靠前了。
3. **faithfulness 稳定在 0.92~0.95** —— 说明 RAG 的防幻觉约束确实有效。
4. **answer_relevancy 偏低（~0.5）别单拎出来下结论** —— 中文短答天然会被这个指标打低，这是评测方式的产物，不代表答案质量差。
5. **延迟代价要如实记录** —— 开启 rerank 后检索 p50 从约 95ms 涨到 665ms。懂得这个 trade-off、据此决定「是否按需开启重排」，比无脑全开更重要。

## 最反直觉、也最有价值的结论

在这个**召回已经饱和的简单 FAQ 集**上，混合检索和重排对召回率没有任何提升空间。

这听起来像是「白做了」，但恰恰相反——**这正是评估的价值所在**：如果不做量化，就会想当然地以为「加了混合检索 + 重排，效果一定大幅提升」，然后把这套复杂方案无脑铺到所有场景。评估告诉你：在这种数据上它不划算，把延迟预算省下来。

> 一句话：评估不是为了证明技术有用，是为了知道**技术到底在什么场景下才有用**。

## 工程落地的几个坑

- 裁判模型用 7B 会因为 max_tokens 截断导致打分全部为 nan，必须换成 72B，并调大 max_tokens、降低并发。
- 评估脚本最好放独立虚拟环境，钉死 ragas 和 langchain 的版本，避免被主项目的依赖污染。
- 不同厂商的端点能力不一样，生成端和 embedding 端可能得分开走不同服务。
