> 系列第 3 篇。上一篇把检索从纯向量升级成了混合检索 + 重排，但「升级了」和「升级有用」是两回事。这一篇用 RAGAS 给几种方案打分，把优化前后的差异落到数字上——也顺带揭示一个反直觉的结论。

## 为什么必须有评估

加了混合检索、加了重排，效果到底好了多少？如果回答不上来，那这些技术就只是「听起来很厉害」的名词。**没有评估的 RAG 等于玄学。**

评估的真正价值不是给系统打个分发朋友圈，而是**避免盲目堆技术**——有些技术在你的数据上根本没用，没有量化你永远不知道。

## RAGAS 四大指标

RAGAS 把 RAG 质量拆成检索和生成两层，对应四个指标：

| 指标 | 衡量什么 | 属于哪层 |
|---|---|---|
| Context Recall | 该检索到的相关内容，是否都检索到了（够全）；需要标准答案才能算 | 检索 |
| Context Precision | 相关的内容是否排在前面（排序准） | 检索 |
| Faithfulness | 答案是否忠于检索到的资料（不编造） | 生成 |
| Answer Relevancy | 答案是否切题 | 生成 |

RAGAS 默认这四个指标**都用 LLM 来打分**，也就是 LLM-as-Judge。Faithfulness、Answer Relevancy 让 LLM 判断答案；Context Precision、Context Recall 让 LLM 逐条判断检索片段和标准答案（或生成的答案）是否相关。RAGAS 也提供不用 LLM 的版本，按字符串相似度或片段 ID 比对，但要事先准备好标准上下文。

## LLM-as-Judge 的范式与局限

LLM-as-Judge 就是让一个（通常更强的）模型来当裁判，按规则给生成答案打分。它的好处是能评估「忠实度」「切题度」这类没法用字符串匹配判断的软指标。

但它有局限：

- 裁判模型本身也会出错、有偏好。
- 对短答案、特定语言可能系统性偏低或偏高。
- 裁判模型太小会因为输出被截断而打分失败。

所以解读 LLM-as-Judge 的分数时，要结合数据集特点判断，而不是把绝对值当真理。

## 一组真实对比数据

> 更正：后来同一项目、同样 26 道题的评估，数字和这一节对不上。[进阶 RAG 范式](/blog/llm-learn/05-advanced-rag-patterns/)和[给 RAG 搭一套评估](/blog/rag-evaluation/)里，Hit@K 是 vector 69.2%、hybrid 88.5%，context_precision 是 0.653 → 0.843。所以下面「召回已饱和」「混合检索没有提升空间」的结论不再成立，以后文的数据为准。两次差这么多，主要是评测口径变了：这一节的 Hit@K 按弱标注的关键词判命中，检索结果里出现过关键词就算中，口径很宽，三种模式自然都是 100%；后来加 Query 改写时，我把采集改成走 Java 侧的真接口、导出冻结的数据集再交给判官，命中的判法也收紧了。喂给判官的上下文换了一批，context_precision 和 faithfulness 跟着变。两次的数字不能直接对比，只能各看各的。

拿主线项目实测一遍。配置：生成模型走 OpenAI 兼容端点，embedding 用 bge-m3，重排用 bge-reranker-v2-m3，RAGAS 裁判用 Qwen2.5-72B-Instruct。语料是一份 51 篇的标准化 FAQ，26 道测试题。

**检索与端到端延迟**

| 模式 | Hit@K | retrieval p50 | e2e p50 |
|---|---|---|---|
| vector | 100% | 95ms | 3363ms |
| hybrid | 100% | 99ms | 3447ms |
| hybrid + rerank | 100% | 665ms | 3852ms |

**生成质量（RAGAS）**

| 模式 | faithfulness | answer_relevancy | context_precision |
|---|---|---|---|
| vector | 0.942 | 0.486 | 0.967 |
| hybrid | 0.954 | 0.443 | **1.000** |
| hybrid + rerank | 0.915 | 0.508 | 0.989 |

表里没有 Context Recall：这 26 道题当时是弱标注，没有标准答案，这个指标算不了。标准答案后来在 [给 RAG 搭一套评估](/blog/rag-evaluation/) 里才补上。

## 关键解读（这部分才是重点）

1. **三种模式 Hit@K 都是 100%** —— 当时我的解读是「这个数据集的召回已经饱和（天花板效应）」。但后来同样 26 题的评估里 vector 只有 69.2%，这个解读站不住。能确定的只有一点：即使三种模式都是 100%，也不能写成「Hybrid 把召回率提升到 100%」。
2. **context_precision 从 0.967 提升到 1.000** —— 相关上下文被排得更靠前了。后来的评估是 0.653 → 0.843，方向一致，幅度差很多。
3. **faithfulness 在 0.92~0.95** —— 这次运行里看起来防幻觉约束有效；后来换了采集方式，vector 只有 0.854，hybrid 是 0.948。按后一次的数字，「防幻觉约束有效」要加一个前提：检索得给出相关的上下文。
4. **answer_relevancy 偏低（~0.5）别单拎出来下结论** —— 中文短答天然会被这个指标打低，这是评测方式的产物，不代表答案质量差。
5. **延迟代价要如实记录** —— 开启 rerank 后检索 p50 从约 95ms 涨到 665ms。懂得这个 trade-off、据此决定「是否按需开启重排」，比无脑全开更重要。

## 当时的结论和回头看的教训

当时的结论是：在这个简单 FAQ 集上，混合检索和重排对召回率没有提升空间。这个结论已被后来的评估推翻，见上文「一组真实对比数据」开头的更正。

回头看，这次评估真正的教训在另一面：**一次评估的结论要能复现才算数**。同一批题跑出两组差别这么大的数字，根子在评测口径前后不一致：判命中的规则和采集上下文的方式都变了。只跑一次、口径又没固定，就下结论，不可靠。下结论之前，先把评测口径写死（怎么判命中、上下文从哪来），同一配置重跑一遍，确认数字稳定。

不过评估的价值本身没变：如果不做量化，就会想当然地以为「加了混合检索 + 重排，效果一定大幅提升」，然后把这套复杂方案无脑铺到所有场景。

> 一句话：评估不是为了证明技术有用，是为了知道**技术到底在什么场景下才有用**。

## 工程落地的几个坑

- 裁判模型用 7B 时，输出被 max_tokens 截断，打分全部为 nan。真正的修法是调大 max_tokens，让裁判能把判断写完；当时我同时换成了 72B、降低了并发，换大模型是做法之一，不是必须。
- 评估脚本最好放独立虚拟环境，钉死 ragas 和 langchain 的版本，避免被主项目的依赖污染。
- 不同厂商的端点能力不一样，生成端和 embedding 端可能得分开走不同服务。
