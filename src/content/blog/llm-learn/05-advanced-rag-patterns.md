> 系列第 5 篇。RAG 的进阶技术一大堆，单个记很容易乱。这一篇用一个「三层优化框架」把它们串起来：每一层解决什么问题、代价是什么、什么时候才该上。

## 检索侧增强：在检索之前把 query 变好

很多检索质量问题的根源不在检索器，而在 query 本身——用户的问题往往口语化、模糊、缺关键词。这组技术的核心思想是：**在检索之前，先把 query 改造成「检索友好」的形式。**

- **Query 改写**：让 LLM 把口语化问题改写成关键词更精准的检索 query。一个角度，一条 query。
- **Multi-Query**：从同一个问题生成**多个不同角度**的 query，分别检索再取并集。适合「问题能从多维度解读」的场景，比如「请假要注意什么」可以拆成流程、材料、天数三路。
  - **和 Query 改写的核心区别**：Query 改写是「一个问题换一个更好的表达」，Multi-Query 是「一个问题拆成多个维度」。区别在覆盖面，不在调用次数。
- **HyDE（假设性文档嵌入）**：query 是问句，文档是陈述句，两者在向量空间里天然有 gap。HyDE 的解法是让 LLM 先生成一段假设性答案（陈述体），用这段答案的向量去检索——**以陈述找陈述**。假设性答案对不对不重要，它只是个检索「探针」。

## 文档与生成侧

- **父子检索（small-to-big）**：用小 chunk 检索（定位精准）→ 返回所属的大 chunk 给 LLM（上下文完整）。「用小块定位，用大块回答」。
- **上下文压缩**：检索到文档后，先让 LLM 提炼出只和 query 真正相关的句子，再喂给生成模型。省 token、减噪音、降幻觉。代价是多一次 LLM 调用。

## 自适应范式

### Self-RAG（自反思检索）

普通 RAG 有两个问题：不管问题简单与否都去检索（浪费），而且不审查生成的答案有没有文档支撑（幻觉）。

Self-RAG 在生成过程中插入反思 token 让模型自审：

- `[Retrieve?]` —— 防**不必要的检索**：简单问题不触发检索。
- `[Supported?]` —— 防**答案超出文档范围**：没有依据就说不确定。

一个管检索入口、一个管生成出口，把 RAG 链路两端的质量都管起来。局限是：它需要专门微调过、能生成反思 token 的模型，不是随便哪个 LLM 都能用。

### GraphRAG（知识图谱 + RAG）

普通 RAG 是「局部检索」，对**跨文档、需要推理关系**的问题无能为力。GraphRAG 先把语料里的实体和关系抽取出来建成知识图谱，检索时沿图谱推理，而不只是找相似文本。

- **适用**：多文档跨文档推理（「A 和 B 有什么关联」）、实体关系密集的语料（组织架构、代码依赖）、需要全局摘要。
- **不适用**：FAQ 这类简单场景——每个问题对应独立文档，没有关系网络要推理，上 GraphRAG 是过度设计，构建和维护成本都很高。

> 一句话：普通 RAG 是「语义搜索」，GraphRAG 是「关系推理」，解决的是不同层次的问题。

## 三层优化框架（把上面全串起来）

> **第一层 · 检索方式**：BM25 + 向量混合检索（RRF 融合）+ Cross-Encoder 精排，解决召回率不全、排序不准。
>
> **第二层 · Query 侧**：Query 改写 / Multi-Query 把口语化问题转成检索友好形式；HyDE 用假设性答案弥补问句和文档的向量空间 gap，解决 query 本身质量差的问题。
>
> **第三层 · 文档与生成侧**：父子检索兼顾定位精准和上下文完整；上下文压缩减噪音省 token；Self-RAG 自审要不要检索、答案有没有依据；GraphRAG 解决跨文档关系推理。

这三层可以叠加，但**每多一层都增加延迟和 LLM 调用次数**，要按场景权衡。

## 一个反直觉的实测：Query 改写反而降低了召回

给主线项目加了 Query 改写后（检索用改写后的 query，作答仍用原问题），跑了一组量化对比：

| 模式 | Hit@K | faithfulness | context_precision |
|---|---|---|---|
| vector | 69.2% | 0.854 | 0.653 |
| hybrid | 88.5% | 0.948 | 0.843 |
| hybrid + rerank | 88.5% | 0.917 | 0.889 |
| **vector + 改写** | **61.5%** | 0.881 | 0.811 |

注意 **vector + 改写的 Hit@K 反而比纯 vector 低（61.5% vs 69.2%）**。原因：

1. 语料是标准化 FAQ，问题本身已经很简洁（「病假需要提交什么材料？」），改写反而可能引入偏差或过度泛化。
2. 改写用的大模型和检索目标语料的语义空间未必对齐，改写后的 query 向量可能偏离了正确答案文档的方向。
3. Query 改写真正的价值场景是**口语化的长问题、带省略和指代的问题**（「我那个请假材料的事儿」），这类在规范 FAQ 测试集里占比很少。

**结论**：Query 改写的价值是场景依赖的。适合口语化、省略多的真实用户问题，不适合本身已经精炼的 FAQ。没有量化就不知道该不该开这个开关——这又一次印证了上一篇评估的价值：**做技术不是为了堆，是为了知道哪些技术真正有用。**

工程上把改写做成可降级的开关：LLM 调用失败时自动退回原 query，链路不中断。下一篇换个方向——跳出「只会调 API」，看看微调与本地部署。
