> 一句话总结：给 leader 的报告，读者要拿它做决定或去验收，不是去了解过程。第一屏逐条回答他点名要的东西在哪、结论是什么；待拍板只放非他不可的，最多三条，其余写「已按默认处理，不同意再改」；测试方案的主体是能原样粘贴执行的用例；状态和数字现量现写，报错了当场更正。

## 0. 起因：报告是交给一个要做决定的人

我给 leader 的报告，大多由 AI 编程助手起草，我改过再发。助手起草时的默认习惯，是按做事的顺序写：背景、过程、发现、结论、附录。读起来逻辑很顺，可 leader 拿到以后要自己去找他关心的那几样。

第一次暴露这个问题，是一个拆给几个窗口并行做的任务。任务原文里 leader 写了「今天发我」哪几样，以及「我会重点核对」哪三点。助手给每个窗口写了一份派生简报，简报里自拟了报告结构。各窗口都照简报交，结构整齐，但读者要的那三点散在不同章节里。我收稿时指出了这一点。

改法很直接：在总体状态下面加一张表，三个核对点一行一个，每行写结论和证据在哪。这张表后来成了我所有报告的第一屏。

那之后几周，同样的问题换着样子又出现了好几次。下面按问题类型排。

## 1. 第一屏：现状结论，加验收点逐条对应

**一次具体的错**：一份调研配了证据索引页。助手把核对时发现的几十条「原来写的 → 改成」也放进了索引页，想显得透明。我指出：leader 从没看过初版，这些对他只是噪音，还把内部来回暴露了出去。

**根因**：改动明细只对看过上一版的人有意义。助手不知道读者看没看过，就默认他看过。读者看没看过，只有我知道，而我没有给它任何记录可查。

**做法**：

1. 每个任务目录记一份「发出去的记录」。我说「发了」，就把当时的交付文件存一份快照。
2. 没有记录，就按「没看过」出结论版，只给现状和出处。
3. 看过上一版且本轮需要核变更时，先给现状总览，再在后面放差异和旧基线。三段是当时采用的版式，后续是否保留，按这次读者的任务决定。
4. 交出去前问一句：只看第 0 节，能不能把当前方案讲给别人听？

一份方案改了三轮时，顺序上也错过两次：先是只放增删数字（新增几条、删除几条），没有当前完整列表；补上基线以后，又把基线和改动放在了最前。读者的第一个问题永远是「所以现在是什么」。增删数字是过程结论，现状总览才是结果本身。

## 2. 待拍板最多三条

**一次具体的错**：一次交付的初稿，列了 13 条「需要您定」。每一条单看都有道理：这个默认值要不要改、那个文案用哪种说法、某个边界情况怎么处理。

**根因**：「拿不准的」和「必须由 leader 定的」混在了一起。13 条摆在 leader 面前，他得逐条读懂背景才能判断哪条重要；真正需要他权限的那几条，反而被淹没了。

**做法**：只留两类，一类要他的权限（一个对外价格、一条文档口径、要不要偏离规范），一类要他手里的数据（生产流量、后台配置）。其余的按最保守的默认先落地，写成「已按默认 X 处理，不同意再改」，放在后面的一张表里。那次筛下来是 3 条必须定的，加一张默认处理表。

每条待拍板的写法也有要求。后来助手起草的一条交接消息被我退回：真正要 leader 动手的那条，只写了做法（「按请求 ID 查一下走了哪条渠道」），没写为什么要查、查到不同结果各意味着什么。读者不知道为什么，就排不了优先级，也没法把事情转述给别人。重写后是这样：

```markdown
**请您查**：按请求 ID 查这次调用走的是哪条渠道。
- 为什么：单看一次失败，分不清是流程坏了还是没路由到。
- 查到渠道 A：说明路由正常，问题在流程，我来修。
- 查到渠道 B：说明路由配置有问题，需要您在后台调整，文档那句先不改。
```

同一条消息里，「逐项校验明细」「没改的页面清单」这些有没有都行的东西，删掉。留下的每个改动跟一句依据，比如「实测读不了这类文件」。可以抽象、简短，但依据不能没有。

## 3. 结论要自己站得住

**一次具体的错**：一份测试方案的结论段，放了一个月度成本估算。一次对齐会上，leader 逐句问下来（转述）：这个数基于正文后面才讲、而且没选的备选方案，读者连那个方案是什么都不知道；估算用的业务量是拿厂商文档的示例凑的；它和这次要定的事也没关系。他还说了一句，大意是一个结论要靠很多前提才看得懂，就不算结论（转述）。另一个问题是单位：结论里写的是内部计费单位和一串型号名，读这份结论的同事既不认识这个单位，也不认识这些型号。

**根因**：「以小白视角汇报」被理解成了多铺一层背景，结果把前提都塞进了结论。会后整理时的归纳（推断，不是会上原话）：小白视角是把理解成本降下来，不是多讲前提。

**做法**：结论段写完，逐个圈出里面的名词和数字，问：读者只读这一段，认不认识它、知不知道它从哪来？

- 没选的方案不进结论；
- 内部单位换成读者使用的单位；业务总量可用类别概括，选型则保留能识别对象的完整型号和版本，首次出现补短解释；
- 估算缺业务数据就找有数据的人要，不拿示例凑；
- 和本次目标无关的数字，有没有都行的，就不放。

同一次对齐会上，leader 对清单类文档（回归 SOP、验收单）的写法提了三点（转述）：

1. 每个模块分两栏：「要验证什么 / 目前有什么问题」。混在一段里，读者分不清哪句是要求、哪句是这次的发现。
2. 检查项按类抽象，比如「多语言语义一致」「整页价格统一」「按钮跳转」，不按对象逐个罗列。
3. 每个问题标阻塞不阻塞上线，不阻塞的进结尾的待跟进，带时间点。

照这个重写时，会上提到的要求逐条编了号，再写一个自检脚本：每条要求在文档里都有落点，没有一条缺来源或示例。回归报告的第一屏也照这个思路，只答三件事：能不能上线、阻塞项是什么、这一轮花了多少（在预算内还是超了）。

## 4. 测试方案：用例表是主体

**一次具体的错**：一个新接入服务要设计计费测试。第一版写成了流程文档：总览和术语、阶段编号、月度成本、备选方案、人天。leader 看完的意见（转述）可以归成一句：测试方案是拿着就能测的东西，必须知道每条发什么请求。

重写时又量出两处没到位（实测）：

- 首版用例表的文字只占全页 42%。删掉和对照表重复的说明以后，用例表才过半，终版 65%。
- 不少「怎么做」格子还是一句描述，比如「用乙的身份查甲的会话」。描述读者还得自己翻译成请求，而翻译这一步最容易出错，本该由写方案的一方做掉。

改法：开头放一段一次性的准备命令，定义几个 shell 函数（切身份、拼消息体、新开会话），每格只调用它们，一两行就够。交付前从渲染后的页面取出全部代码段，用假的外部命令按页面顺序整段空跑，核每次调用的身份、请求头和请求体。假命令要按调用次数返回不同的 ID，否则两个身份的会话 ID 相同，引用错了也看不出来。

我过目时又指出一处排版问题：8 列宽表定了 1240px 最小宽度，正文栏只有约 910px，右边几列藏在横向滚动后面，滚动条又在几千像素高的表底部。助手的自检报了「无横向溢出」，因为脚本只量整页宽度，把表格的滚动容器排除了。改成每条用例一块：块头放编号、要验证什么、花费、何时跑，中间整宽放命令，底部两栏放预期和判定。改完在 1280、1440、1920 三个桌面宽度下重量，每个宽度都从 4 处溢出降到 0（实测）。

查溢出要把容器也算进去，在浏览器控制台里跑一句就够：

```js
[...document.querySelectorAll('table, pre, div')]
  .filter(el => el.scrollWidth > el.clientWidth + 1)
  .map(el => `${el.tagName}.${el.className} ${el.scrollWidth}/${el.clientWidth}`)
```

几个桌面宽度和手机宽度各量一次。

## 5. 状态要能追溯，报错了当场更正

**一次具体的错**：助手按一周的工作记录生成周报，我看后指出「很多任务其实已经做完了」。它回去实测核对，查出三类问题：

1. 「后续重点」15 项里，11 项是等 leader 决定、等上游上架、等别人核对，和我方能推进的混在一起，读者以为是 15 件没做完的事。
2. 把记录的归档日期写成了完成日期：前一天晚上推的修复，被写成了第二天推的。
3. 记录写完到周报生成之间，有几件事状态变了，周报只依据记录，没有再实测。

**做法**：

- 待办分「我方待办 / 等待他方」。等待项写成「当前等 X；满足后由我方做 Y」。助手改的第一版把等待项一律写成「我方无待做」，我纠正了：那会把后续仍要承担的工作也盖掉。
- 记录之外新补的事实单独标「补核 · 时间 · 依据」。
- 汇总报告里会变的状态（远端分支、合并、别人的提交），生成时再实测一次。

时间戳也是数字。有一次长任务的状态文件里，七个阶段是做完后一次性补记的，助手凭印象把时间列写成了间隔均匀的一串时刻，最晚的一个比写入那一刻还晚。收尾时用 `date` 一对才发现，只能如实改成时间窗，并加一行更正。

```bash
# 每轮尝试结束，往状态文件追加一行；时间用命令取，不凭印象
printf '%s | %s | %s | %s\n' "$(date '+%F %H:%M')" "做了什么" "结果" "下一步" >> STATUS.md
```

发现报错了，马上更正，格式固定：「之前说 X，实际是 Y，原因是 Z，影响范围是……」。说清原因，别人才能判断其他数字有没有受影响。

## 6. 后续修订：每个关键章节也要能直接做判断

到月底，一份持续更新的选型报告又暴露了同一个问题。首页已经有推荐，比较章节却先讲计算器、公式和长表；最重要的建议放在事实卡片后面，视觉上像一条注解。我指出，结论前置也要落实到章节，主建议的分量还要在版面上看得出来。

之后我转述带教的反馈，进一步补齐了理由：推荐后紧接一两句抽象说明，解释素材条件或需求为什么对应这个选择，再给同条件例子和证据。先比较同类型号的适用范围，再比较渠道；不能先默认一个型号最好，后面只找它的低价入口。

**结论、依据和下一步要连在一起。** 一段能复用的写法如下，内容为自编示例。

```text
当前建议：先验证方案甲，方案乙留作文字密集素材的备选。
理由：甲的控制项覆盖当前输入，乙的目标能力仍有一项待测。
同条件例子：两者都用同一份原图、目标尺寸和质量门槛比较。
边界与下一步：目前只有文档证据，先做小样，再定生产选择。
```

这里也纠正了我之前对「通俗」的一种过度理解。主层不能只写一个供应商简称，让读者猜比较的是哪个产品；也不必把完整请求字段塞进每个表格单元。面向读者的型号、版本和条件留在主层，精确端点及请求选择放在就近可展开的映射里。对象可识别，阅读负担也可控。

两项交付检查随之变得更具体。

- **截图核支持范围。** 图片能加载、链接能打开，只能说明入口有效。还要确认它来自哪个产品和页面，截图上实际可见的文字是否支撑旁边那条结论。引用错页时，补更多截图不能修复原判断。
- **覆盖核来源清单。** 新增许多候选，不等于指定搜索范围已查全。清单按搜索来源、已查看结果、独立平台和可用接口分别记账；未覆盖的范围单列。最终报告合并去重后的当前选择，不按「原有」和「新增」展示整理过程。

那轮我还删掉了一批解释探索过程的句子，例如「按刚才的反馈补齐了某表」。读者没有参与这些对话，知道了也不能多做一个判断。正文保留当前结果、依据和会改变选择的限制；内部来回留在过程记录里。

这些是当次明确反馈和后续整理得到的方法。本次写作没有重新检查全部历史截图，也没有证据证明新版已被读者接受。实用的核法是从目录逐章进入最终页面，在桌面和手机看：第一眼能否找到建议，紧接着是否知道原因，证据能否支持那条判断。

## 7. 一份能套用的第一屏

```markdown
## 0. 现状

**一句话结论**：可以上线 / 有 1 个阻塞项 / 方案选 B

| 您要的 | 结论 | 在哪 |
|---|---|---|
| 核对点 1（原文照抄） | 通过，证据 3 张截图 | §2.1 |
| 核对点 2 | 有 1 处不一致，不阻塞，周五前修 | §2.3 |
| 今天发我的 X | 已附 | 附件 A |

**需要您定（不超过 3 条）**
1. 一个对外价格的取值口径。为什么要您定：……；选 A 会……，选 B 会……

**已按默认处理，不同意再改**
| 事项 | 默认 | 理由 |

**我方待办 / 等待他方**
| 事项 | 当前等谁 | 满足后我方做什么 |
```

交出去前对一遍：

- [ ] 第一屏逐条回答了任务原文点名要的东西，用的是原文的说法
- [ ] 每个需要做判断的章节也先给结论，主建议视觉上最突出，理由就近
- [ ] 读者没看过上一版，就没放改动明细和「原来写错了」
- [ ] 待拍板不超过三条，每条写了为什么、各结果意味着什么
- [ ] 结论里没有读者不认识的单位、型号、没选的方案
- [ ] 清单类文档分两栏，问题标了阻塞与否
- [ ] 测试方案的「怎么做」能原样粘贴执行，空跑过
- [ ] 状态、日期、数字都是交付前现量的
- [ ] 每个判断标了依据：实测、文档，还是转述
- [ ] 截图支撑邻近结论，覆盖范围有来源清单，正文没有无用的探索过程

## 收尾

1. **按读者的验收点组织** —— 第一屏逐条回答他点名要的，不按做事的顺序。
2. **待拍板只留非他不可的** —— 要他权限或他手里数据的才问，其余按保守默认落地并写明。
3. **结论自己站得住** —— 读者只读结论段，也认识里面的每个名词和数字。
4. **测试方案是用例** —— 「怎么做」写成能粘贴的命令，交付前空跑。
5. **状态现量现写** —— 报错了当场更正，说清原因和影响范围。

这几次退稿，单看都是格式问题，背后是同一件事：初稿在写「做了什么」，读者要的是「他接下来怎么做」。助手不知道读者是谁、看过什么，这些信息得由我给它。现在每份报告交出去前，我先只读第一屏，假装自己是 leader，看能不能直接做出决定。
