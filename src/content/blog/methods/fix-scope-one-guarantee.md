> 一句话总结：修一个缺陷，先写一句「这次修复保证什么」，并且对着问题单里报的那个失败写；之后每条审查意见先判它破坏的是不是这件事，是就在这件事里修，不是就写成已知限制。要改的数被好几处共用时，只改点名的那一处，其余读取方逐个锁住或写明。

## 0. 起因：三次修复，两种方向的跑偏

这两周我和 AI 编程助手一起修了三个缺陷，都在一个多上游的 API 网关和它的两个前端上。三次都被 leader 打回过一轮，打回的理由听起来各不相同：

- 第一次是登录态问题。助手为了回应一轮轮审查意见，陆续加了好几层机制，leader 的意见大意是「整体侵入性有点强，可以简化」（转述）。
- 第二次是大文件传不上去。第一批修了旁边几个缺陷，问题单报的那个失败一点没动，leader 回「这个没有解决掉」（转述）。
- 第三次是预扣估少了。第一版把能想到的低估来源全补了，leader 列了三条副作用，建议「做减法，只把预扣估准」（转述）。

第一次和第三次是改多了，第二次是改偏了。回头看，三次缺的是同一样东西：开工时没写清这次修复要保证的那一件事。有了它，审查意见该不该接、改动该停在哪、交付时该怎么交代，都有了尺子。

下面按「先定一件事 → 判审查意见 → 对准报的失败 → 共用的数」的顺序讲，最后给一张清单和一个最小示例。

## 1. 先写一句「这次修复保证什么」

这句话要满足三个条件：

1. **对着问题单里报的那个失败写**。问题单说「某类渠道传一张二十多 MB 的图失败」，那这句就是「这张图经这类渠道能传」，不是「大文件处理更健壮」。
2. **可以验证**。读的人能想出一个用例来判它过没过。
3. **短**。一句话，放在报告第一屏和提交说明里，审查的人一眼能看到。

写下来以后，它管三件事：

| 时机 | 拿它做什么 |
|---|---|
| 开工 | 决定改哪几处，旁边顺手的缺陷能不能一起交 |
| 收到审查意见 | 判这条意见是不是在破坏这件事 |
| 交付 | 第一屏回答这件事现在成没成立，没成立卡在哪 |

我以前觉得「问题单就是范围」，不用另写。三次下来发现不够：问题单往往描述现象，原因和修法夹在一起，读的人各取一段，就各自理解出一个范围。写一句话的成本很低，分歧在开工时就暴露了。

## 2. 审查意见逐条判范围：登录态那次怎么越改越大

### 问题本身

问题是：账号在后台被封禁以后，浏览器里存着的登录态还能接着用。

我一开始把它归成「前端数据和后端数据不同步」。这个大类没错，但还要往下分一层，看不同步发生在哪：

- **管理后台**：服务端按登录那一刻的账号状态快照判权限，后续请求不再查库。封禁以后旧会话照样能用，请求真的被放行了。
- **官网**：业务接口每次都查库，本来就会拒绝。但前端拿不到业务资料时，会退回用第三方身份服务给的资料拼出一个「已登录」的样子。业务请求没成功，页面显示却是登录着的。

前者是真放行，要在服务端改成按当前账号状态判权；后者是假登录，要在前端把「外部身份已认证」和「业务账号有权限」分开。清浏览器缓存修不了前者，服务端查库也修不了后者。拆开看是三件事：凭据还在、外部身份认证通过、业务账号当前有权限。封禁只改了数据库，前两样都还留在浏览器里。

### 机制是怎么堆上去的

前两轮实现都是助手写的。每轮审查都会提出一些边界情况，助手的处理方式是每条加一层机制：

- A 账号的迟到请求可能把新登录的 B 账号登出，于是加了会话编号；
- 多个标签页同时登录退出会打架，于是加了跨标签锁（浏览器的 Web Locks）；
- 再往后是全局登出开关、登录前先清凭证、后台定时刷新角色、后端一层新的错误归类。

每一条单看都有道理，我也没拦。但每加一层机制，它自己就成了下一轮要审的对象：锁有没有死锁、编号什么时候换、开关谁来关。审查意见没有收敛，改动却一直在长。到 leader 看的时候，非测试代码在两个仓库里加起来改了六十多个文件，增删共三千多行。

### 简化版只做一件事

这一轮我先写下那句话：**封禁后立即退出，拦在浏览器外**。然后从主干重新做，只改这件事需要的地方：

- 后台每个请求按主键查一次当前账号状态，不再信会话里的快照；
- 前端收到明确的「账号已封禁」才清业务登录态，并且不让第三方身份自动恢复。

非测试代码降到十几个文件、一百多行。上面那串机制全部去掉，leader 深度审查报告里针对它们的一批条目跟着不再成立，跨模块的风险只剩一条发布顺序：先换完后端全部节点，再发前端。

### 简化不等于少修

简化版做完，我又让一个新上下文的审视跑了一遍，还是查出两条范围内的问题：

- 刷新重试的过程中换了账号，旧请求的拒绝会把新账号登出；
- 页面冷启动时没有退出第三方身份。

两条都破坏「封禁后立即退出」这件事本身，所以照修，并补了在修复前会失败的用例。同一轮还有十来条小问题，其中一多半不影响这件事，按默认不修，逐条写进报告。代价也写明：后台每个请求多一次主键查询。

判断的那一下，就是问一句：**这条意见破坏的是我要保证的那件事吗？**

- 是，就在这件事里修，修法尽量不引入新概念；
- 不是，就写成已知限制和默认处理，由 leader 决定要不要另开问题。

为了让审查清零去加机制，是这次最贵的错误。归谁定、默认怎么取，见[归别人定的事](/blog/methods/others-decision-default-log/)。

### 一个没料到的尾巴

最终 diff 小了，提交历史却没变干净。简化版是在旧提交上叠了一个大删减，按提交合并的话，原来那版侵入式实现会原样进主干历史；更早的提交里还带进过本机分析工具写进工作树的产物，后来才删掉。要连历史一起干净，只能从主干重建，经同意后强推，分支里其他人提交的哈希也会跟着变。所以「改动变小」要同时看最终 diff 和提交列表。

## 3. 「一件事」要对着报的那个失败

第二次的问题正好反过来。

### 现象

问题单报的是：经某个云厂商模型平台的渠道，用对话接口传一张二十多 MB 的图失败。正文连原因都写了：本该把大素材转存到对象存储、用引用传给上游的那条分支，它的识别条件依赖一项线上没有填写的配置，所以分支从没生效，大图全走「下载后内联」，卡在网关的下载上限上。

### 第一批修了什么

第一批是助手提的方案，我回了一句「按你做」。它修了旁边几个确实存在、但不涉及取舍的缺陷：超限时返回明确的 400、发请求前预检大小、下载的取消和超时、日志里的地址脱敏。转存那条路径被列为「需要拍板的取舍」，留给后续。

给 leader 的说明照实写了：这批还不能让那张图通过。leader 的回复大意是：问题单要解决的是这类渠道传大素材，没有解决掉，可以去看文档里每个模型最大支持多少（转述）。

### 根因

第一批有一点是对的：不能为了让大图通过就直接放大网关的下载上限，大文件不该进网关内存。错在把整条核心路径推到了「后续」。

那个取舍其实不需要别人定：每个模型、每类素材的上限，平台文档里都写着。查文档就能定一个保守默认，标上「不同意再改」交出去。

### 第二批

第二批照文档逐个模型、按素材类型定上限：

- 小文件照旧内联；
- 内联放不下的，交给文件服务转存到渠道自己的对象存储桶，用存储引用传给上游；
- 网关下载上限不动，大文件不经网关内存。

### 没测的部分怎么交代

这一批真实上游和文件服务都没跑过：没有凭据，按规则不绕；全部测试是本地假服务。助手起草给 leader 的话时，把这几项写成「需要您帮忙确认」三条：文件服务的上限和渠道登记、线上配置、真实发一张大图。

我改成先明说「没做实际测试，全部是本地模拟」，三条改成「上线前需要您这边测」。「请帮忙确认」读起来像只差几个配置值、改动本身已经验过；写「没做实际测试」，读的人才知道上线前还缺一次真实验证，也知道该谁来做。

我还问过能不能用自己在主站的账号测。不能：主站跑的是已部署的主干，分支没合并之前，主站上还是旧逻辑（分支的起点就是当前主干，这是实测；主站按主干部署是推断）。主站账号适合上线后回归，替代不了上线前的验证。

## 4. 共用的数只改点名的那一处

第三次是计费上的问题。

### 现象

网关给一个文本大模型做预扣：发请求前按估算冻结一笔押金，跑完按上游实际用量结算。估算输入用的是本地分词器，数出来比上游实际计费的少。问题单给了分布（转述）：真实 ÷ 本地的中位数约 1.43，p75 约 1.53，p99 约 1.78。押金不够覆盖实际用量时，结算就会出现缺口。

第一版是助手实现的，把能想到的低估来源全补了：计数默认乘 1.8 且可按模型覆盖、押金再加 25% 缓冲、按缓存写入价和它的长上下文档位估、按余额压低出站的输出上限、缺价时告警。

leader 的意见有三条（转述大意）：

1. 计数接口会更早触发上下文压缩，不好；
2. 预扣的数额过犹不及；
3. 输出预算拉高后，余额充足时的简化冻结规则被废掉了。

建议做减法，只把这个模型的预扣估准。

### 根因：一个数喂着好几处

三条背后是同一个原因：本地数出来的输入数，不止押金一处在用。我们读代码列出了它的读取方：

| 读取方 | 怎么用 | 计数放大以后 |
|---|---|---|
| 对外的 token 计数接口 | 有的编程助手客户端靠它决定什么时候压缩上下文 | 对话提前被压缩 |
| 预扣押金 | 发起前冻结 | 问题单点名要改的就是这一处 |
| 简化冻结 | 余额相对估算额充足时，走更轻的冻结方式 | 估算额变大，判断门槛跟着变，原本走简化冻结的用户被拉回完整冻结 |
| 低余额规划（按渠道开） | 按余额倒推出站的输出上限 | 出站上限变小 |

第三行最容易漏：它读的不是计数，是用计数算出来的押金估算额。搜计数变量的读取处找不到它，要从押金再往下追一层。

### 减法版

只在押金那一处乘一个系数，默认 150%，可调，设成 100% 等于关闭。取 p75 附近，不取 p99：取 p99 的话，大部分请求都会多冻。校准后的数单独存，原始计数继续给计数接口和缺用量时的回退结算。其他几处保持原样，各配一条断言守着。

### 两个要心里有数的结果

**这一版单独拦不住那张事故单**。按问题单里的数字复算，校准后的押金仍不足以单独拦下那一单；剩下的缺口来自输入估算以外的部分，归另一个问题单处理。给 leader 的话里照实写了这一点。

**新上下文复核又找出四处被动跟着变的**：

- 价格分档按传入的输入数选档；
- 请求没带输出上限时，输出估算按输入的倍数算；
- 配了低余额策略的渠道，「付不起最低输出就拒」会更早触发；
- 结算取不到价时按冻结额收的那条规则。

都是原有逻辑换了一个输入数，代码没改，但不能不说，在说明里单列，交 leader 判断。

### 理由要拿实测对一遍

同一轮复核还发现，助手草稿里一条「已按默认」的理由和实测例子相反。草稿说「不这样做，配了策略的渠道冻结反而更少」，可手头唯一的实测例子里，两种做法冻结的数几乎一样，校准后的还略少一点。余额不够时，两边都约等于「余额减预留」。真实的理由是另一条：规划按偏小的输入，会多放行约 4% 的输出。

写完理由，拿手头的实测数字对一遍，比交出去被问住便宜。

## 5. 最小示例：读取方清单和断言

下面是一个自编的最小例子，和任何实际业务代码无关。一个本地估算被三处使用，修复只动押金。

```python
DEPOSIT_FACTOR = 1.5  # ← 唯一的校准点：真实/本地比值的 p75 附近


def local_count(prompt: str) -> int:
    return len(prompt.split())  # 示意：本地分词器


def count_tokens_api(prompt: str) -> int:
    # 读取方 1：客户端据此决定何时压缩上下文，不该跟着变
    return local_count(prompt)


def deposit(prompt: str, price: float) -> float:
    # 读取方 2：问题单点名的那一处
    return local_count(prompt) * DEPOSIT_FACTOR * price


def hold(balance: float, estimate: float, floor: float = 1.0, n: int = 100) -> float:
    # 二级读取方：读的是押金估算额，不是计数
    return floor if balance >= n * estimate else estimate
```

对应的测试分三类：点名的那一处要变，不动的要锁住，被动变化的要写出前后值。

```python
prompt = "a b c d"  # 本地计数 4
price = 1.0

# 点名的那一处：押金按系数放大
assert deposit(prompt, price) == 4 * 1.5

# 不动：计数接口原样返回
assert count_tokens_api(prompt) == 4

# 被动变化：豁免门槛随押金抬高。不改代码，但把前后值写进说明
old_estimate, new_estimate = 4 * price, deposit(prompt, price)
balance = 500
assert hold(balance, old_estimate) == 1.0      # 原来：500 >= 400，享受豁免
assert hold(balance, new_estimate) == 6.0      # 现在：500 < 600，完整冻结
```

最后两条断言不是在说「这是对的」，而是把一个被动变化钉在纸面上：读的人一看就知道，余额在原门槛和新门槛之间的用户，冻结方式变了。要不要接受，由决策人定。

## 6. 判断清单

开工：

- [ ] 写下一句「这次修复保证什么」，对着问题单报的那个失败，能想出一个用例判它过没过
- [ ] 旁边顺手修的缺陷可以一起交，但不拿它代替那件事
- [ ] 想把核心路径留到「后续」之前，问一句：能不能查文档定一个保守默认？能就落地，标「不同意再改」
- [ ] 要改一个数，先列它的读取方，再从读取结果往下追二级读取方

收到审查意见：

- [ ] 逐条标「在范围内 / 范围外」：它破坏的是那件事吗？
- [ ] 范围内的照修，修法尽量不引入新概念；范围外的写成已知限制和默认处理
- [ ] 为这条意见新加的东西，下一轮要不要再审一遍？要的话，先想有没有更小的修法

交付：

- [ ] 第一屏回答那件事现在成不成立；不成立，卡在哪、归谁
- [ ] 侵入性看非测试代码的文件数、行数，和新加了几个跨模块的概念（开关、锁、编号、新的错误层）
- [ ] 读取方清单三栏齐：点名的改了、不动的有断言、被动变化的写了前后值
- [ ] 没在真实环境跑过，直接写「没做实际测试」，再写上线前要谁测、看到什么算通过
- [ ] 「已按默认」后面的理由，拿实测数字对过
- [ ] 最终 diff 和提交列表都看过，没有不属于这次改动的东西

## 收尾

1. **先定一件事** —— 开工写一句「这次保证什么」，对着报的那个失败写。
2. **审查意见判范围** —— 破坏那件事的就修，其余写成已知限制，不为清零加机制。
3. **简化不等于少修** —— 范围内的问题照样修，简化版也查出了两条。
4. **核心路径不推后** —— 查文档能定的默认，自己定，标「不同意再改」。
5. **共用的数只改点名处** —— 列读取方，追到二级，不动的锁住，被动变化写明。
6. **没测就说没测** —— 「请帮忙确认」和「没做实际测试」是两种信息量。

三次里，助手逐条加机制，单看都说得通：会话编号、跨标签锁、1.8 倍系数。我也没拦，没先给它一把尺子，它就拿每条审查意见、每个想得到的风险当尺子。现在接一个修复，我先自己写那一句话，再让助手动手；审查意见回来时，先拿那句话去对。函数改动该追到哪一层，可以参考[函数职责记录](/blog/methods/function-contract-impact-checks/)里「在行为保证未变的边界停下」的思路，这里的读取方清单是它在一个共用数值上的用法。
