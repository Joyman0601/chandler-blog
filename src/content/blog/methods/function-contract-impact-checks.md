> 一句话总结：函数记录只描述自身职责和所依赖的具体保证；实现变化先复核本层，只有影响调用者使用的保证才继续向上传播。版本检查能指出旧记录过期，首次漏写的职责和新分支遗漏仍要靠阅读及独立预期发现。

## 0. 起因：主要结果对了，隐藏动作却没发生

一次重构把部分请求改走新的处理入口。测试检查了主要状态和结果，全部通过；后来复盘发现，新路径绕过公共函数，也绕过了它原来负责补充上下文、发送成功事件的动作。

问题不在于「测试通过」这件事是假的。它确实证明了被检查的结果正确，只是没有观察那条事件。函数名称也没有直接暴露这些附带职责。

助手最初建议让我每次读出旧函数的完整功能，再逐项检查。我指出，这会把大量重复理解转嫁给我。代码持续增加，旧函数也会变化，仅靠记忆维护不了。于是我提出把职责记录在函数附近，读过一次后复用，同时把有限的关联检查接进现有审查。

这篇讲那次讨论形成的设计和边界。首版已有本地机制及历史对照记录，我在本次写作时只回读来源，没有重新执行业务回归，也没有测量它在所有后续任务中的收益。

## 1. 函数名、调用索引和职责记录回答不同问题

函数名给一个粗略意图，调用索引回答谁可能调用谁，职责记录说明调用者可以依赖什么结果。

一个自编的例子是：业务入口调用 `finish()`，它再调用 `save()`。名称和关系都很清楚，却仍不知道保存失败后是否重试、什么时候发通知、重复调用会不会发两次。

职责应当写到可以验证的程度。

| 要写什么 | 通用例子 |
|---|---|
| 最终结果 | 成功时保存结果，状态变为完成 |
| 生效条件 | 只有有效订阅者存在时发送通知 |
| 前置数据 | 调用者提供当前操作的上下文 |
| 失败语义 | 保存失败不标完成，保留可重试状态 |
| 重复语义 | 同一操作重复执行不重复产生通知 |

**职责描述可观察的保证。** 不必把循环、局部变量和每一行实现再写一遍。否则代码一改，注释也要跟着大改，记录很快失去可读性。

记录还要区分草稿和已核内容。自动生成了一段说明，只证明文本存在；「已核」至少要有来源、对应版本、检查条件和证据。

## 2. A 不复制 B，只写需要 B 保证什么

最初方案有一个容易变重的方向：B 新增职责，A 的注释也增加同样内容。若 B 再调用许多函数，整条链的功能会一路复制到顶层。

我继续追问，为什么 A 要介绍 B 的全部功能。最后采用的边界是：A 记录自己的结果，以及它使用 B 的哪些保证。

下面是自编的职责拆分示意，和任何实际业务代码无关。

```text
A：完成一次导出
  自己保证：文件可取得后才返回成功。
  使用 B 的保证：保存文件；对有效订阅者记录一次完成通知。
  前置责任：把本次操作的订阅上下文传给 B。

B：保存结果并记录通知
  自己保证：保存失败则不产生完成通知；重复操作不重复记录。
  使用 C 的保证：写入可以原子提交。

C：持久化
  自己保证：提交成功后数据可读取；失败返回明确错误。
```

A 不需要知道 C 具体怎样写存储，却要知道自己必须把通知所需的数据交给 B。只写「调用 B」仍然过粗，因为丢失的恰好可能是那项附带保证。

如此分工后，职责说明有一个主要维护位置。调用关系由工具生成，目录页只是入口。多个层级再人工维护相同功能简介，会重新制造同步问题。

## 3. 复用需要有效期，哈希不证明理解

如果每次都相信上一次的说明，只是把相信函数名换成相信旧注释。实现、相关类型、配置和依赖变化后，记录需要重新判断是否有效。

代码指纹适合做变化检测，但它的结论应很窄：对应内容是否和审阅时一致。

| 当前情况 | 应怎样处理 |
|---|---|
| 没有记录 | 读实现及必要下层，建立职责与证据 |
| 记录有效且本次未受影响 | 复用边界说明，再读当前实际改动 |
| 本函数实现变化 | 复核职责、条件和出口 |
| 使用的依赖保证变化 | 判断当前调用是否仍满足自己的保证 |
| 关系无法识别 | 标出未知，补显式关联或继续阅读 |

指纹相同不能证明第一次没有漏写；指纹变化也不能证明业务一定变化。一个只换内部算法的重构，可能仍兑现全部保证。此时记录保证未变的理由与证据即可，不需要为了消除提示随意改几个字。

同样，零条记录不是零风险。检查器对空集合返回成功，最多说明没有登记项可查；不能据此宣称仓库已经完成职责审查。

## 4. 何时停止向上传播影响

这是整个方案最关键的边界。若 B 一改就要求从 A 追到所有入口，每次微调都可能扩展成全仓阅读；若只看 B，改变调用者行为的修复又会漏掉。

我采用的判断顺序如下。

1. 先复核 B，确定它对外提供的保证是否变化。
2. 找出 A 实际使用的保证。
3. 所用保证未变，A 的已有审阅可以继续复用。
4. 所用保证变化，检查 A 是否仍兑现自身保证。
5. A 对上层的保证未变，就在 A 这一层停止扩散。

举例说，B 换了压缩实现，仍保证内容可还原、失败语义不变，A 不一定需要改。若 B 改成后台保存、提前返回成功，而 A 承诺返回时文件已经可读，A 就受到直接影响。

因此，停止的依据是行为保证，而非函数名、签名或者调用集合。增加一次外部写入，即使参数和返回值没动，也可能改变时延、错误、重试和重复执行的意义。

这里仍需要判断。工具可以指出依赖变化，却不能仅凭两段自然语言自动证明行为相等。未建立保证边界的下层，只能保守展开；随着实际任务逐步补齐，不必一开始把全仓统一标注完。

## 5. 调用集合没变，也要看每个出口

我最初的案例还有一个特点：旧公共函数仍在代码里，有些分支也仍调用它。只生成调用图，可能看不出新分支提前返回时漏掉了什么。

下面用一个原创小例子说明。

```python
def complete(fast_path, events):
    saved = True
    if fast_path:
        return saved
    events.append("completed")
    return saved

normal_events = []
fast_events = []
assert complete(False, normal_events) is True
assert complete(True, fast_events) is True
assert normal_events == ["completed"]
assert fast_events == []  # 主要结果相同，通知行为不同
```

这个例子不是正确实现，也没有模拟业务全链。它只表明：两条路径都返回成功，不足以证明两条路径完成相同职责。若独立契约要求都通知，目标断言就应要求快速路径也记录一次；上述代码会失败。

所以新增分支、错误返回、重试和绕过公共入口时，应有一张「出口 × 应有结果」的表。既检查主要状态，也检查必要的事件、统计和上下文；哪些能延期、哪些必须随主动作完成，都要有来源。

## 6. 关联项有限时，直接形成可执行检查

函数职责不是唯一关联。某些遗漏的范围相对明确，更适合直接列出最终对象并执行。

例如退役一个接口，要同时看运行路由、接口描述和面向调用者的使用文档。检查目标是还有没有地方把它当成有效入口介绍；迁移说明合理提到旧地址，应当允许。

又如源内容改变后，生成文件没有出现在修改列表里，恰好可能是忘记生成。触发条件应来自源内容变化，再调用现有生成器比较最终产物，而不能只看生成文件自身有没有变化。

这类检查我更愿意接入现有审查入口。另开一套只写「已确认」的清单，不能增加多少判别力。本地历史对照可以证明某个检查识别了那次旧错误；不能自动推广成所有退役接口、所有生成物都被覆盖。

## 7. 一次修改可以怎样使用

我会按下面的轻量清单执行。

- 定位关键函数，读取已有职责及其版本依据。
- 缺记录或相关内容变化时，读必要实现，不把理解责任转交给读者。
- 列出这次新增出口，逐条对应原有保证。
- 沿实际使用的依赖保证传播影响，在稳定边界停下。
- 为动态调用、回调、事件和跨进程关系补明确关联。
- 用独立业务预期检查最终结果，保存条件、实际结果和证据。

首次理解仍然需要成本。调用索引可能有误匹配，也可能漏动态关系；说明自身也会漏写。这个方案主要让已核且未变的理解可以复用，让变化有落点，不是把审查变成一次哈希比对。

## 收尾

1. **记录行为保证** —— 自身结果、条件、失败和重复语义都要清楚。
2. **依赖写具体** —— A 使用 B 的哪些保证，不复制整条调用链。
3. **稳定边界停止** —— 是否继续追查，取决于对调用者的保证有没有变。
4. **新出口重新核** —— 调用集合不变，也可能提前跳过必要动作。
