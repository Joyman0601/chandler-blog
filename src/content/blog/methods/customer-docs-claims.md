> 一句话总结：对外文档里每一句承诺，等式、范围、「只需 / 不用改」、支持哪些格式、计费怎么取整、谁比谁好，都要过四道对照：官方文档的限制条款、真上游的实测、实际扣费的代码、同一页里的其他规则。写得顺口的、从旧页面或同族文档沿用的句子最容易错。文案可以和旧页面不一致，不能和实际行为不一致。

## 0. 起因：上线前被逐句改掉的三句话

一个视频生成模型的页面上线前，leader 重写了一批文案。拿他的改动和我们的版本逐句对，错在三处：

1. **照抄理想句**。我们写「输出和输入素材一样长」。官方文档的参数说明里，有一条限制和这个等式直接矛盾，这份文档就在我们自己的调研存档里。验收时也测到了：输出比输入短了约一成。两条证据都在手边，文案还是写成了等式。
2. **同页自相矛盾**。介绍区写「切换版本只改模型 ID，其他都不用动」；同一页的参数表又写「本版本传某个字段会被拒绝」。
3. **没证据的比较**。对比表写「上一版人脸更稳定」。谁测的？没有人测过。改成只陈述能力差异，并且立了一条规矩：不写没有复现实测的质量结论。

**根因**：写文案时脑子里转的是「这个模型能干什么」，不是「哪句话可能不成立」。调研存档和验收数据都在，写完之后没人拿它们回头对一遍。

## 1. 四道对照

之后文案写完，都先做一轮「证伪」：

| 对照项 | 怎么做 | 会抓到什么 |
|---|---|---|
| 官方限制条款 | 把调研存档里官方文档每一条「注意」「限制」「例外」列出来，逐条问页面上有没有和它矛盾的句子 | 理想化的等式 |
| 真上游实测 | 验收报告里的输入、输出、计费数字，逐个代进文案里的等式和范围；声明支持的每种格式各打一单 | 「支持」但其实不收的格式 |
| 实际扣费的代码 | 估价和结算各读一遍，取整方式、计费单位和文案对上 | 和旧页面一致、和代码不一致的口径 |
| 同页规则 | 凡是「只需」「不用改」「保证」的句子，和同页的拒绝规则、参数表对一遍 | 同页自相矛盾 |

比较类形容词（「更稳」「更快」「最」）单独过：每一个都要能指到一次自己的测试，指不到就删掉，只写能力差异。

还有两条是一次对齐会上 leader 讲的原则（转述），后来都照着做：

- **承诺不高于实际，能留余量就留**。上传上限，页面承诺的明显低于后端实际值；结果保存期，对外写的比清理配置实际保留的短。上游或配置收紧时，页面也不会变成错的。
- **不写用户心智里没有的东西**。上游是谁、内部计价单位、「经平台实测」这类概念，都不出现在对外页面上。

先把候选句子捞出来，人再逐句过：

```bash
# 列出文档里所有像承诺的句子，逐句过四道对照
grep -rnE '只需|只要|不用|无需|保证|一样|相同|最多|最少|最长|支持|更稳|更快|最[好快稳]|only|just|no need|same as|up to|supports?' docs/zh docs/en
```

## 2. 格式清单：SDK 收不等于上游收

**现象**：另一个视频生成模型接受图片作首帧。上传框、API 文档、各语种的文案、文档站，都写「支持 JPG / PNG / WebP」。用两张 .webp 做首尾帧打真上游：创建接口返回成功，任务排队，十几秒后失败。上游的报错大意是不支持这种图片格式，只收 JPEG 和 PNG。换成同参数的 .jpg，正常出片（实测）。

更糟的是，网关给用户的错误文案里写死了一串格式清单，其中也有 WebP，等于继续告诉用户 WebP 可以用。预扣费全额退了，所以只看计费核对是全绿的。

**根因**：

- 供应商 SDK 拉图时的类型白名单里有 webp，图片能下载、能内联、能发出去，SDK 层不报错。「SDK 收」和「上游收」是两件事。
- 文档里的格式清单，是从同平台另一条线路的文档沿用过来的。那条线路确实收 WebP，换了上游没人重测。
- 上游不在创建时拒绝，而是受理后在任务里失败。只看创建接口的状态码，会以为通过了。

**做法**：对外口径按实测收窄，只写真上游接受的格式，上传控件按线路分开设置。网关的错误文案是全模型共用的，单个模型改不了，所以记成待定项交了出去，没有顺手改共享文案。声明支持的每种输入格式，都用真上游打一单最便宜的档，并且轮询到终态。

## 3. 计费口径：估价和结算分开写

**现象**：一个新模型的计费展示，前端估价向上取整，后端结算四舍五入。上一版同族页面的文案写的是「向上取整」。验收时有人提出要和上一版一致，于是估价、价格页、各语种文案、文档、更新日志共 45 处都写成了「向上取整」。契约里注明了「展示不低于实扣」，并把「要不要两边统一」列成了待定问题。

上线前，leader 把这句改了回去：估价写按输入时长向上取整，结算写按实际输出时长四舍五入、差额退回。他在修改记录里的意思是：不能故意沿用错误的口径。

**根因**：「和旧页面一致」看起来最保守，其实是把旧页面的错误再复制一份。估价和结算本来就是两个规则，合写成一句话，必然有一句是假的。当时已经发现两者不一致，该做的是把真实版本做成默认，把「沿用旧口径」列为待定，而不是反过来。这条原则在[归别人定的事那篇](/blog/methods/others-decision-default-log/)里有更完整的讨论。

## 4. 加新型号：按能力逐项决定，不按「和某型号同列」

**现象**：一个文本模型家族出了一个新型号，是老型号 A 的新版本。上线前一天，一次文档提交把新型号加进了三页 API 文档：源语言里，每页原本出现「A」的清单有八九处，改后全部加上了新型号，各语种同样处理，diff 非常整齐。

生产回归时按能力逐项实打（实测）：

- **图片清单**：新型号在多种协议上都能读图，没问题。
- **PDF 清单**：一个协议按文档写法传 PDF，直接 400；另一个协议返回 200，但输入 token 数少得只装得下文字部分，回答说读不了文件，照收最低计费。同一请求体发给 A，两个协议都读出了 PDF 里埋的暗号。
- **内置联网搜索**：页面写支持。强制模型调用搜索工具，新型号返回 200，响应里却没有搜索调用的痕迹字段。同族另外两个型号发同一请求体，也都不搜。用 `git log -S` 追到引入那句话的提交，它是两个月前按整个系列写进去的，不是新型号带来的。

修的时候还有两个坑：

- 其中一页有一句合写的话，大意是 PDF 和图片都只有某三款型号能读，其余两款读不了。新型号支持图片、不支持 PDF，放进这句、拿出这句都是错的。要先拆成两句，各带各的型号清单。
- 从 PDF 清单删掉新型号后，清单外从两个型号变成三个，行为还不一样。照原句只删名字，「其余两款」就成了错话。按数量的指代一律改成写出型号名。

**根因**：「新型号是 A 的新版本」被当成了「A 能做的它都能做」，加型号变成了查找替换。整齐的 diff 会诱导评审按「加全了没有」来看，不按能力逐条问「这一项测过没有」。

「200 + 有回答」也不能当成能力生效。静默忽略的工具、静默丢掉的文件都不报错，只有工具痕迹字段、文件里的暗号、输入 token 数能证明。

```bash
# 这句话是哪次提交写进来的：分清「新型号被加进清单」还是「整页早就这么写」
git log -S '内置联网搜索' --oneline -- docs/
# 删型号后找按数量的指代
grep -rnE '其[他余].{0,2}[两三四]款|other (two|three)' docs/
```

## 5. 反方向：官方文档写的限制，经网关不一定成立

前面都是文档写多了，也有反过来的情况。一次多语种文档同步，照上游官方文档补了三处限制：

- 一个文件块参数在某种写法下「必填」；
- 文件块「不能和图片块同时传」；
- 一个内置工具的「第二轮回传步骤」。

拿到真 key 后经网关逐条实打（实测）：

- 不带那个参数，200，暗号读对；
- 文件和图片同传，三种组合都 200；
- 回传步骤换了 7 种写法，全部同步 400，报错说请求分词失败。

三处都得撤回：前两处是把不存在的限制写给用户，第三处是教用户一条走不通的流程。

**根因**：上游文档描述的是直连上游的行为。网关会改写请求（补字段、转格式、按能力选渠道），用户经网关看到的行为可能更宽，也可能更窄。

**做法**：从上游文档搬进对外文档的每条限制和步骤，都经网关实打，正反两面。限制要发一单违反它的请求，看是否真的报错，再配一单合规的对照；步骤要走到最后一步、拿到结果才算通。打不了就不加，记成「待实测」。

## 6. 参数集照同族和同类页面取舍

文档站是给客户看的，不是官方文档或接口契约的翻版。有一个新页的初稿列了 14 个请求参数，说明合计约 2700 字符，3 个请求示例，首段第一条三四百字符。同类型页面一般只给 7 到 11 个参数，每个一句话。全站绝大多数页面的 400 响应只写一句「请求参数无效」，具体规则放在各参数说明里。

所以现在开写前先跑一遍统计：同家族全部页面，加同类型最近上线的五六页，抽这几项：

- 请求参数个数；
- 每个参数说明的长度；
- 首段每条的长度；
- 400 的写法；
- 示例个数。

按统计定口径：

- 参数集取同类页面的交集，再加本模型特有的一两个；
- 首段每条控制在全站 p90 以内（那次统计 p90 约 150 字符，中位数约 75）；
- 400 写一句话；
- 示例给一到两个。

和惯例冲突、又和真实行为冲突的点，单独列出来问决策人。

## 7. 多语言：结构齐不等于内容齐

各语种的键齐、占位符齐，只证明结构对。上线前 leader 补的改动里有三类，结构检查一个都抓不到：

1. **译本丢细节**：回调说明在几个语种里写清了每次重试的间隔，另外几个只剩一句「最多重试几次」。
2. **术语漂移**：同一个概念，前端文案和上一版页面统一过，文档仓的某个译本却用了另一个词。两个仓库各做了一半。
3. **没人读的键**：几个文案键从头到尾没有组件读取，每个语种都白翻了一遍，其中一句还在解释内部映射。

后来写多语种的 OpenAPI 页，改成了脚本生成：结构只写一次（骨架），每语种只填一张字符串表；回调、鉴权、错误码这类全站共用的文案，按语种从同族页里读出来复用，术语自然和上一版一致。生成后用第二个脚本逐字段对要点：

```python
# parity.py：以源语言为基准，逐个字符串字段比要点，不比字数
import re

LOCALES = ["en", "zh", "ja"]  # 按自己站点的语种填
LOCALE_SEG = re.compile(r"/(" + "|".join(LOCALES) + r")/")

def points(s):
    return {
        "items": s.count("\n- "),
        "code": sorted(re.findall(r"`[^`]+`", s)),
        "links": sorted(LOCALE_SEG.sub("/LOC/", m)
                        for m in re.findall(r"\]\(([^)]+)\)", s)),
        "paras": s.count("\n\n"),
    }

def check(src_fields, loc_fields, loc):
    for path, src in src_fields.items():
        dst = loc_fields[path]
        if not isinstance(src, str):
            assert dst == src, f"{loc} {path}: 非字符串值必须逐值相等"
            continue
        assert points(src) == points(dst), f"{loc} {path}: 要点不一致"
```

几个具体的坑：

- 中日韩的句号后面没有空格，`[.!?]\s` 一条都数不到；长度也只有英文的几分之一。「译文太短」的阈值按文字系统分开定，拉丁字母约 0.6，中日韩约 0.2，否则全是误报。
- 一个韩语页面上，同一段里出现了两处裸写的 `1~15` 和 `2~7`。GFM 把两个波浪号之间的文字渲染成了删除线。范围值一律放进行内代码。
- 一次合并冲突的处理，把一个字段的说明混进了另一个字段，每个语种都是。要点对照脚本能抓到，人眼扫很难。
- 生成物会被别人直接改。重新生成之前，先把重生成结果和分支现状逐字节 diff，一致了才能继续用脚本，否则会悄悄回滚别人的修改。
- 合入多语言补丁前，按语言数一遍改动文件：`git diff --name-only | cut -d/ -f1 | sort | uniq -c`。有一次 50 个文件看着齐全，一数才发现只有一类文件改全了所有语种，其余只改了两种。

## 8. 三种验收：结构、内容、上线

文档的「验收通过」至少有三种，互相不能替代：

| 验收 | 工具或做法 | 证明不了什么 |
|---|---|---|
| 结构 | Mintlify 的 `npx mint openapi-check <file>`（CLI 子命令，不是仓库脚本）、整站 `npx mint validate` | 内容对不对 |
| 内容 | 要点对照脚本、四道对照；示例请求体先本地解析，再交给后端真实的参数校验函数跑 | 线上是不是这一版 |
| 上线 | 打开线上页面，看到新内容 | —— |

示例请求体还有一个陷阱：拿假 key 打网关，得到 401，不代表请求体合法。先发一个故意写坏的 body 做对照：坏 body 也回 401，说明网关先鉴权后解析，这个 401 对请求体什么也没证明。

那次一个文档改动，结构检查跑了 119 次全过，各语种的结构 102 项全对，新增的 23 个示例请求全部通过校验函数。即便如此，「已合并」「部署状态显示完成」也不等于线上就是新内容，还是要打开线上页面看一眼。

## 9. 交付前清单

- [ ] 文案里的等式、范围、「只需 / 不用改」，逐条对过官方限制条款、实测数据、同页规则
- [ ] 比较类形容词每个都能指到一次自己的测试，否则只写能力差异
- [ ] 声明支持的每种输入格式，都用真上游打过一单并轮询到终态；SDK 白名单、同族页面不算证据
- [ ] 计费文案和估价、结算代码各对一遍；估价和结算分开写
- [ ] 上限、保存期写的值不高于实际；页面上没有内部概念
- [ ] 加型号按能力分组逐项决定，每组能指到一单实测；合写句先拆开；按数量的指代改成型号名
- [ ] 从上游文档搬来的限制和步骤，经网关正反两面实打过；打不了就不加
- [ ] 参数集、首段长度、400 写法按同族和同类页面的统计定
- [ ] 多语言按要点逐语对过；术语和同族上一版一致；新键都有读取处；范围值没有裸写的波浪号
- [ ] 结构检查、内容对照、线上页面三种验收都做了

## 收尾

1. **四道对照** —— 官方限制、真上游实测、计费代码、同页规则，每句承诺都过一遍。
2. **SDK 收不等于上游收** —— 格式清单按真上游实测写，轮询到终态。
3. **和旧页面一致不是保守** —— 和实际行为一致才是，估价和结算分开写。
4. **按能力加型号** —— 整齐的 diff 最危险，一组能力一组实测。
5. **结构齐不等于内容齐** —— 多语言按要点对，三种验收各做各的。

对外文档的错，很少是写错了一个字，多半是一句本来不该有的承诺。我现在的习惯是，写完一页先不想「它写得清不清楚」，而是逐句问「这句话在什么情况下不成立」。能回答出来的，要么改，要么去测。
