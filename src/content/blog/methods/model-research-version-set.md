> 一句话总结：新模型调研最容易错的不是结论，而是前提：读的是不是正本、版本有没有数全、价格是哪个站点哪种货币、退役日期是哪个平台的。先把这几样核死，再按参数清单、计费因子、迁移路径三个维度写，结论才经得起追问。

## 0. 起因：第一份调研被打回

有一次我接到一个调研任务：某厂商出了一个新的模型系列，平台要不要上、上哪几个，出一份文档给 leader。要求只出计划、不写代码，也不要去找后端要资料，因为这是全新的模型，后端也没有。我让 AI 编程助手去查资料、起草。

一个下午后，交上去的是一份「功能特性 + 推荐方案」。第二天 leader 退回来，意见是方案不完整：没有参数的可选值、范围和默认值，没有计费因子，配套能力的必选信息也没写。这份初稿写的是「这个模型能干什么」，leader 要拿它决定「接不接、怎么接、怎么卖」。

后来又做过几次调研：一个视频模型补上旧版本、一批旧型号的迁移、一个开源模型的竞品对比。每次都在不同的地方差点出错，可错的位置很集中：读错了文档、数错了版本、看错了币种、只看了一个平台。这篇按调研的顺序把这些坑排一遍，最后给一份能直接套用的骨架。

## 1. 找正本：同名的文档可能有好几份

**现象**：调研第一天，助手自己就更正了三次。

- 仓库里有一份「新增模型」的流程文档，助手把它当成了正本。它写的详情页路径，在当前代码里根本不存在；真正在用的是另一份近九百行的合订本。
- 初稿写的接口端点是旧的。官方文档里写得很明白：旧接口已经并到了另一个接口上。
- 初稿列的三个参数名像是上一代模型的，官方文档里这一代的参数名不一样。

**根因**：同一主题的文档常有好几版：旧流程文档没删，官方改了端点没改旧页，搜索结果混着几代模型的说法。哪份是正本，从标题上看不出来。

**做法**：

1. 看更新时间，也看它描述的路径、端点在代码或官网里是否真实存在。路径都找不到的，基本就是过期的那份。
2. 官方文档站抓回来只有一个空壳（纯前端渲染）时，先找 `llms.txt` 和页面的 `.md` 导出，再找站点自己加载的 JS 数据模块，不要急着退到第三方聚合平台的参数页。具体做法见[判断自部署还是转售那篇](/blog/methods/identify-upstream-fingerprint/)的第 4 节。
3. 参数名拿不准的，用实测反推。那次助手写了一个只用标准库的探测脚本：每次只换一个参数名发请求，看服务端的 400 报的是哪个字段。每个请求的请求体和响应各存一份，攒了一百多个证据文件，参数表里每一格都能指到一个响应。

```python
# 用 400 报错反推参数名：每次只换一个候选名，其余字段不变
CANDIDATES = ["max_len", "max_length", "maxLength"]
for name in CANDIDATES:
    body = {"model": MODEL, "prompt": "hello", name: 16}
    resp = post(ENDPOINT, body)   # 自己封装的请求函数，顺手把请求和响应落盘
    print(name, resp.status, resp.json().get("message", "")[:80])
# 报「未知参数」说明名字不对；报「取值非法」说明名字对、值不对
```

这一招有前提：上游会拒收未知参数。有的上游对未知参数一律返回 200 照收，这时要改看输出有没有跟着参数变，做法见[上游接口实测那篇](/blog/model-onboarding/upstream-probe-evidence/)。

## 2. 核对版本全集：公告里的名字不一定能调

**现象**：任务描述里的版本清单，逐个核下来少数了一个。另一边，还查了好几个在发布公告和搜索结果里出现、官方模型列表里却不存在的型号名，白花了时间。更早一次排查一个配套接口时，助手把两个名字几乎一样的模型当成了同一个模型的两种写法，还把代码里的名字改成了另一个，多花了约 2 小时。它们其实属于两套不同的接口，请求结构完全不同。

**根因**：发布公告用的是营销名，模型列表里的才是能调用的 model_id。名字相近不等于同一个东西。凭命名规律推，会推出一个不存在的型号，或者把两个模型合成一个。

**做法**：

- 列出这个系列的全部型号。每个 model_id 都在官方模型列表或枚举里查到过，才写进表。
- 名字相近的，各自查一遍请求结构和所属体系。
- 能力按接口逐个查。一个家族的能力常常分散在好几个接口里，编辑、延长、参考这些次要接口也要打开。复核过的一张能力表写某视频模型「文档没写是否带声音」；在它的视频编辑接口里，其实有一个控制是否由模型生成新声音的开关。
- 在文档里搜能力关键词时，只搜请求参数。全文搜 `audio` 会命中每一个接口文件，因为任务响应里有一个各接口共用的输出类型枚举，和这个模型的能力无关。

下面是一个只在请求参数里找关键词的小脚本，读 OpenAPI 的 JSON：

```python
# req_props.py：只看请求体 schema 下的属性名和说明
import json, sys

def walk(node, path, words):
    if isinstance(node, dict):
        props = node.get("properties")
        if isinstance(props, dict) and ("requestBody" in path or "Request" in path):
            for name, prop in props.items():
                desc = (prop or {}).get("description", "")
                if any(w in (name + desc).lower() for w in words):
                    print(f"{path}/{name}: {desc[:80]}")
        for k, v in node.items():
            walk(v, f"{path}/{k}", words)
    elif isinstance(node, list):
        for v in node:
            walk(v, path, words)

walk(json.load(open(sys.argv[1])), "", [w.lower() for w in sys.argv[2:]])
# 用法：python3 req_props.py openapi.json audio sound
# schema 用 $ref 引到 components 时，按被引用的 schema 名（如 VideoRequest）筛
```

汇总时一个型号一行，不把几个相似型号的结论合成一句。写「文档没写」的格子，也要列出查过哪些文件。

## 3. 按三个维度写：参数、计费、迁移

被退回之后，我把调研固定成三个维度。下表右列是那次漏掉的东西：

| 维度 | 要写到什么程度 | 那次漏了什么 |
|---|---|---|
| 参数清单 | 每个参数的可选值、范围、默认值、是否必填，以及哪些适合暴露给用户 | 只列了功能，没有取值 |
| 计费因子 | 按什么计（字符、token、秒、次）、地域差异、换算规则 | 文档只给了一种场景下的换算规则，另一种场景没写，要实测 |
| 迁移路径 | 和现有同类模型比，接口形态（同步、异步任务、流式）有什么不同，已有代码能复用多少 | 官方主推的接口形态和平台现有同类模型不同，这一条直接决定页面骨架 |

另外两条，后来证明比三个维度本身更能决定结论：

- **同口径比较**。同一个系列里，不同版本的计费单位可能不一样。直接比单价没有意义，要先换算到同一口径；按用量计的，还要实测用量的波动范围。
- **硬约束单独列**。有的版本只在部分地域可用，只这一条就可能把它排除，比所有功能对比都管用。类似的还有只能订阅不能按量付费、条款限制转售、限速很低。

迁移那一维，后来在一次旧型号迁移调研里又补了两列：

- **价格变化拆成「单价差」和「用量差」**。某个新型号看起来比旧型号便宜，拆开一看，主要是因为新型号默认不思考、输出 token 少，不是单价降了。两列相加等于差额，读者才知道便宜从哪来、什么时候会变回去（比如用户自己打开思考）。
- **单列「迁过去会丢的能力」**：某个能力新型号没有，某个输出上限变低了。没有这一列，「推荐迁到 X」听上去没有代价。

## 4. 核价：站点、币种、汇率、路由档

这一节只讲方法，不讲任何具体价格。

**现象一：数字一样，币种不一样**。核对一个按次计费的模型售价时，助手看到配置里的数字和存档的官方价格页上的数字完全相同，判了「一致」。我追问了一句：存档页和配置用的是不是同一个币种？它回去才发现：存档的那一页是国际站，单位是外币；配置里的数是本币。数字相同，实际差一个汇率倍数。同一次还发现两件事：存档页里查不到某个型号的价，是因为国际站根本没上架它；价格页上列价的型号名，和实际调用的上游型号不是同一个。

**现象二：两个汇率**。定价时用一个汇率把外币刊例换成内部单价，展示时又用另一个汇率把内部单价换回外币，再和官方价比。两个汇率差几个百分点，定价表里写的「比官方便宜多少」和页面上显示的就对不上。页面是实算的，没有算错；错在定价时没有在用户看到的单位里验算。

**现象三：同一模型按推理路由分档**。云平台上的同一个模型，区域内、地理跨区、全球跨区几档可能不同价（文档，模型卡原文）。比较「用托管服务」和「自己直接调模型」两个方案时，托管服务不支持跨区推理，只能走贵的那档；自建要便宜，前提是业务允许数据出地理范围。另外，「A 比 B 贵 x%」反过来不是「B 比 A 便宜 x%」，分母不同。

**根因**：价格页按站点分成两套，版式、型号、数字都高度相似，只有货币符号和免费额度所在地域不同。导出成 Markdown 以后，文件名看不出站点，读的一方默认它是自己熟悉的那一套。

**做法**：

1. 拿到价格页，先看域名或文件头确定站点；全文数一下两种货币符号各出现多少次。存档时文件名带上站点和币种，比如 `pricing-<站点>-<币种>.md`。
2. 两个站点都取一份。每个型号一行：国际站的价、国内站的价折算后的值；只在一边上架的单独标出来。
3. 每个单价写明推理路由档。方案对比时，先确认每个方案实际能走哪一档。
4. 差价和优惠幅度在用户看到的那个单位里验算；百分比写清分母。
5. 官方价有多个来源时，取值口径交给决策人定。定下来以后，把来源和口径一起写进价格配置的注释和改价脚本的文件头，不要只写一个结果。

## 5. 退役日期：按我们实际走的平台查

**现象**：一批旧型号要不要迁、有多急。厂商的开发者 API 站写这几个型号还没弃用、没有公布关停日，只是收紧了新用户的使用；同一厂商的云平台写它们两周后退役，并给了替代型号。如果流量走的是云平台、却只读开发者站，结论会是「可以慢慢迁」，两周后就会开始报错。

同一次还碰到两处同站矛盾：一个型号在弃用表里最早要半年后才关停，同站定价页的警告写的关停日却已经过去了；另有两个页面，对同一条计量规则给了两套说法。

还有一处差点写错。两个平台给的「推荐替代」也不一样：云平台的替代列写的是低一档的新型号，开发者站给旧型号的预览版指定的是同档的预览版。报告初稿写的是「官方指定替代是 X」，一次对齐会上 leader 问了一句（转述）：「这是跨档了吧？」准确的说法是「云平台那张表指定的是 X」，同档的选项也要写出来。

**根因**：同一厂商的两个平台各自维护生命周期，日期、替代型号，甚至「弃没弃用」都可能不同。弃用表上的日期通常是「最早可能日期」：两边文档的意思分别是退役日只会推迟、不会提前，以及表里列的是最早可能关停的日期。文档站的多页由不同的人维护，改了一页忘了另一页很常见。

**做法**：

1. 先查清平台自己的流量在哪个平台的渠道上，以及近一段时间各多少量。查不了，就把查询语句交给能查的人。
2. 两个平台的生命周期页都存档，逐型号列一行：开发者站状态、云平台退役日、各自推荐的替代。
3. 截止时间取「我们流量所在平台」的那一个。能把流量挪到另一个平台延寿的，当一个选项写出来，并写清前提。
4. 同站多页冲突时，两种说法和出处都写，按更早、更保守的那个排计划，标「来源冲突」。
5. 「官方推荐替代」写明是哪个平台的推荐。

## 6. 交付前：逐格核出处，再请人盲核

调研表常常是助手派几个子代理并行采集、再压缩成摘要。一次竞品调研交付前逐格核出处，约 15% 的格子要改。错法很集中：推断没标、漏了附加计费项、把「页面没写」当成事实、把别处的话安到这里。子代理交回的东西是线索，不是结论，这一点在[子代理那篇](/blog/ai-workflow/subagent-findings-are-leads/)里有专门的讨论。

逐格核完，再做一个盲核页请人独立核：每题只给直达原文的链接和问题，报告里的值先藏着，看完写下自己看到的再揭开对照。一题不一致，就把同类的格子扩大复核。做法见[盲核页那篇](/blog/testing/blind-crosscheck-page/)。

最后，结论里的每一句都标上依据：实测、文档，还是推断。哪些是推断、靠什么推的，要写在格子里，不要只写在核验记录里。来源怎么分级，见[信息来源分三级那篇](/blog/methods/source-tiers-meeting-transcript/)。

## 7. 一份能直接套用的调研骨架

```markdown
# <系列名> 调研

## 结论
- 推荐：上 A、B；不上 C（一句话原因）
- 硬约束：地域 / 计费方式 / 条款 / 限速
- 待确认：每条写明谁来定

## 版本全集
| 对外名 | model_id（官方列表已查到） | 接口形态 | 可用地域 | 出处 |

## 参数清单
| 参数 | 类型 | 可选值 / 范围 | 默认 | 必填 | 暴露给用户 | 依据（实测 / 文档） |

## 计费因子
| 型号 | 计费单位 | 换算规则 | 站点 · 币种 · 路由档 | 出处 |

## 迁移路径
| 现有型号 | 推荐目标（哪个平台推荐的） | 接口形态变化 | 可复用 | 丢失的能力 | 单价差 | 用量差 |

## 生命周期
| 型号 | 开发者站状态 | 云平台退役日 | 各自推荐的替代 | 我们流量所在平台 |

## 来源冲突与推断
- 同站两页冲突：两种说法都写，按更早的排计划
- 推断：写明靠什么推的
```

交付前对一遍这张清单：

- [ ] 读的文档是正本：路径、端点在代码或官网里真实存在
- [ ] 每个 model_id 都在官方模型列表里查到过；名字相近的分别核过请求结构
- [ ] 能力按接口逐个查过，次要接口也打开了；每格附字段名和原文
- [ ] 参数写到可选值、范围、默认值；关键参数名实测过
- [ ] 价格同口径比较；每个单价写明站点、币种、路由档；差价在用户看到的单位里验算
- [ ] 退役日期和替代型号写明是哪个平台的，和我们实际走的渠道对上
- [ ] 硬约束单独列出
- [ ] 结论区分实测、文档、推断；调研表逐格核过出处

## 收尾

1. **先找正本** —— 路径都找不到的文档是过期的那份；参数名拿不准就用实测反推。
2. **数全版本** —— 公告里的名字不一定能调，每个 model_id 都要在官方列表里查到。
3. **三个维度写到取值** —— 参数写可选值和默认值，计费写到因子，迁移写清复用多少、会丢什么。
4. **价格带四个限定词** —— 站点、币种、汇率、路由档，少一个就可能差一个倍数。
5. **按平台取日期** —— 退役日期和推荐替代都写明是哪个平台说的。

回头看，这几次差点出错，都是把一个「看起来对上了」的数字或日期直接写成了结论，没有问它是在什么前提下对上的。助手很擅长找到一个对得上的数，不太会主动问前提，这一步要我来问。下次接到调研，我会先让它花半小时把正本、版本全集和两个平台的生命周期页存档，再开始写任何结论。
