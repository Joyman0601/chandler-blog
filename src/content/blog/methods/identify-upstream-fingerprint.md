> 一句话总结：判断一个平台是自己部署模型还是转售别家，要按信号强弱取证：托管方标记和内嵌数据最强，参数和素材限制的指纹次之，价格比例再次，「能出 2K」最弱。每条依据都要拿去对照每个候选上游，只有「A 有、B 没有」的才算数；两头都对得上就记「未查到」。

## 0. 起因：一张表要回答「每家背后走的是谁」

那次调研要判断一批竞品平台背后走的是谁。同一个模型，很多平台都在卖，背后大致有三种情况：

- 平台自己租 GPU 部署；
- 平台转售出品方的官方 API；
- 平台转售另一家平台的部署。

调研要交一张表：每个平台一行，写它属于哪种，依据是什么。这张表决定后面怎么比价、比效果。如果把转售判成自部署，后面的价格分析就会把一个中间商当成成本方。

AI 编程助手派了几个子代理并行去采集各平台的页面，再汇总成表；交付前又做了一轮逐格核对和一轮人工盲核。表在这两轮里被改了两次，两次都是判定本身错了。这篇按出错的顺序讲。

## 1. 信号从强到弱分四档

先把最后用的分档放在前面，后面两次出错都能对到某一档上。

| 档 | 信号 | 怎么取 | 能不能单独下结论 |
|---|---|---|---|
| 1 | 托管方标记和内嵌数据 | 模型页上表示官方或合作方托管的徽标；页面内嵌 JSON（如 Next.js 的 `__NEXT_DATA__`、组件 props）里的托管方、渠道、硬件字段；单模型 `llms.txt` 里的 `Provider:` 行；页面上明说自己部署、或明说不是中转的话 | 能，但要和第 2 档不冲突 |
| 2 | 参数与素材限制指纹 | 时长的范围和步长；分辨率档是否有官方没有的档位；比例枚举；有没有 seed；素材限制的写法（一边写一个区间，另一边要求固定值） | 能，前提是有区分力 |
| 3 | 价格比例指纹 | 各档单价之比和某个上游完全一致，或者恰好是上游价乘一个固定倍数；用平台自定点数计价的也能按比例认出来 | 只能辅助 |
| 4 | 能力上限 | 「有 2K 档所以是官方」 | 不能 |

第 4 档最不可靠，原因很简单：自部署方可以把低分辨率结果放大成 2K，照样叫 2K。另一条经验：页面写明跑在 CPU 上的「模型」，基本就是转发。

取第 1 档的命令很朴素，先把页面里的结构化数据捞出来，再看字段：

```bash
# 页面内嵌数据：搜托管方、渠道、硬件相关的字段，按出现次数汇总
curl -s "$MODEL_PAGE" \
  | grep -oE '"(provider[a-z_]*|is_[a-z_]*(official|partner)[a-z_]*|channel|hardware|gpu)":"?[^,"]+' \
  | sort | uniq -c

# 单模型的 llms.txt 常带一行 Provider
curl -s "$MODEL_PAGE/llms.txt" | grep -i 'provider'

# 价格常走页面脚本调的公开接口；先看 robots.txt，禁止抓取的路径不要碰
curl -s "https://example.com/robots.txt" | grep -i disallow
```

## 2. 第一次判错：漏看了托管方标记

**现象**：汇总表最初把平台 X 判成「自部署」。依据是它落地页上的一句营销文案，大意是这个模型在它自己的栈上跑得比官方快。

交付前逐格核出处时，重新打开平台 X 的模型页截图，看到基础端点挂着一个表示合作方托管的标记，内嵌数据里的托管方字段也指向合作方。按平台 X 自己的说明，这个标记的意思就是由合作方托管，不是平台自己跑。再回去查那句营销文案，它出自另一个型号的页面，说的根本不是这个模型。

同一次还发现，平台 X 上同一个模型的另一个端点没有这个标记，是平台自己跑的。

**根因**：

1. 用了第 3 档以下的信号（营销文案连档都算不上），压过了第 1 档的结构化标记。
2. 按模型名给整个平台下了一个结论，没有按端点逐个判。同一平台、同一模型的不同端点，托管方可以不同。

**做法**：

- 营销文案和结构化标记冲突时，以标记为准，把冲突写进依据。
- 引用文案前，先确认它说的是哪个型号、出自哪一页。
- 判定表按「平台 × 端点」一行，不按「平台 × 模型名」。

## 3. 第二次判错：拿两边都有的证据下结论

**现象**：盲核时，有一题问「平台 Y 的这一格依据是什么」，复核的人在页面上找不到表里写的依据。那一格判的是「推断转售自上游 A」，依据有两条：

- 平台 Y 的两个参数说明和上游 A 的文档逐字相同；
- 平台 Y 支持参考图生成，单价和上游 A 一样。

回去重看才发现，平台 Y 的取值范围是按另一个候选上游 B（出品方官方 API）收窄的：时长的范围和步长都和 B 一致，和 A 不同；上游 A 多出的一档分辨率，平台 Y 没有。至于「支持参考图生成」「单价一样」，上游 A 和 B 都是这样。

也就是说，写进依据的东西，要么两边都有，要么只能说明说明文字是从 A 抄来的。说明文字谁都可以抄，取值范围要跟着真实的后端走。

**根因**：只拿依据去对照了心里那个候选，没有对照另一个。一条线索只有在「A 有、B 没有」时才指向 A。两边都有的线索写进依据，只会让推断「看起来有根据」。

**扩大复核**：按「一题不一致，同类扩大」的规则，把表里所有标「推断」的 23 格都重新过了一遍：

- 又有两格改成「未查到」：依据要么两边都对得上，要么两边都有；
- 一格依据没错，但排序有问题，按区分力重排，最有区分力的放第一条；
- 其余维持。

**做法**：写依据前，把候选上游的参数表并排列出来，逐条标「只有 A」「只有 B」「都有」。

| 线索 | 上游 A | 上游 B | 平台 Y | 区分力 |
|---|---|---|---|---|
| 参数说明的措辞 | 原文 | 不同 | 和 A 逐字相同 | 弱：说明文字可以照抄 |
| 时长的范围和步长 | 一套 | 另一套 | 和 B 相同 | 指向 B |
| 多出的一档分辨率 | 有 | 无 | 无 | 指向 B |
| 参考图生成 | 有 | 有 | 有 | 无 |
| 单价 | 相同 | 相同 | 相同 | 无 |

这张表画出来，结论就很清楚：线索两头都有，判定写「未查到」，依据里把两边都写上，可以加一句「倾向 B」，但不按倾向记成「是」。

还有一类话要特别小心：描述模型来历的话，比如「经过某家调优」。这是在介绍型号怎么来的，任何转售方都会照抄到自己的页面上，说明不了谁在跑这个模型。

## 4. 文档是纯前端渲染时，怎么拿到原文

取第 2 档信号要读各家的接口文档，而很多文档站是单页应用，直接抓只能拿到空壳。按这个顺序试三条同源的路：

1. 站点根目录的 `llms.txt`：全站页面清单，每页附一个 `.md` 链接。
2. 页面 URL 后加 `.md`：逐页的 Markdown 导出，内容和页面同源，可以当正本引用。
3. 都没有时，找站点自己加载的 JS 数据模块。旧版接口页常常没有 `.md` 导出，参数表打包在前端的数据模块里：路由对应一个 JS 文件，里面是参数名、类型、默认值、枚举的原始数据。路由到模块的映射在一个 loader 脚本里，从页面入口脚本的依赖里能找到。

```bash
# 1. 索引
curl -s https://docs.example.com/llms.txt | grep -i 'video'
# 2. 页面导出
curl -s https://docs.example.com/api/video/foo.md -o foo.md
# 3. 没有 .md：从 HTML 找入口脚本，再在脚本里找数据模块的文件名
curl -s https://docs.example.com/api/video/foo | grep -oE 'assets/[^"]+\.js'
curl -s https://cdn.example.com/assets/index-xxxx.js | grep -oE 'api-[A-Za-z0-9_-]+\.js' | sort -u
```

这条路还有一个副产品。同一厂商的国内站和海外站要不要分别对照？两站走不同的 CDN、不同的 loader，但同一路由加载的模块可以逐个比 md5。那次 7 个模块的 md5 全部相同，结论是同一份接口规格、只差域名。这比逐字段对照两份文档快，也更有说服力。

几个容易踩的点：

- `.md` 导出可能比页面少一截。模型页上由前端从内嵌数据渲染的卡片（按档位的单价、限速）不在导出里，`.md` 只剩一句总价。看到「文档没列分档价」先别下结论，去页面 HTML 的 `<script>` 里找内嵌的模型 JSON。
- `.md` 导出的响应头可能标成 `text/html`，内容其实是 Markdown；同一地址有时又回空壳。判断抓没抓到要看内容，不看 content-type。
- 搜索引擎的 AI 摘要会把原文的意思说反，比如原文说某版本「保留」某参数，摘要写成「移除」。关键结论一律回原文核对。
- 数据模块文件名带构建哈希，下次构建就变。只能当快照，存档时写明来源 URL 和抓取日期。

## 5. 交付前的两道核对

这张表是子代理采集、助手压缩成摘要的，所以交付前做了两道核对。

**逐格核出处**。458 格，每格回原文找依据并截图存档，结果如下：

| 结果 | 格数 |
|---|---|
| 一致 | 367 |
| 推断，已标 | 19 |
| 不一致 | 43 |
| 来源冲突 | 22 |
| 无出处 | 5 |
| 无法截图 | 2 |

要改的约占 15%。错法很集中，下次可以直接按这几类去找：推断没标；漏了附加计费项；页面其实写了，表里却写「未写」；把「免费额度」读成了「免费」。

**人工盲核**。逐格核是自己核自己，还要请人独立核一遍。做法见[盲核页那篇](/blog/testing/blind-crosscheck-page/)，这里只说出题：

- A 层：关键判定（是不是自部署、转售谁）全部出题；
- B 层：其余格子按平台分组随机抽；
- C 层：计数类和有无类的问题；
- 规则：任何一题不一致，同组扩大复核。

84 题，83 题一致。不一致的那一题，就是第 3 节的平台 Y。

## 6. 判定表模板和开工前清单

判定表每行一个「平台 × 端点」：

```markdown
| 平台 | 端点 | 判定（是 / 否 / 未查到） | 依据（原文或推断，标档位和区分力） | 来源存档 |
|---|---|---|---|---|
| 平台 X | 基础端点 | 否：合作方托管 | 第 1 档：模型页的合作方托管标记，平台说明见存档 | x-base-2026-10-07.png |
| 平台 X | 另一个端点 | 是 | 第 1 档：无标记；第 2 档：参数面和自部署推理的一致 | x-alt-2026-10-07.png |
| 平台 Y | 基础端点 | 未查到（倾向 B） | 第 2 档：时长、分辨率只和 B 一致；说明措辞和 A 相同（弱） | y-base-2026-10-07.png |
```

开工前，尤其是要派几个子代理并行采集时，先把这几样定死：

- [ ] 「自部署」的口径，包括边界：上游自己改过、权重不公开、只有它一家托管的版本，转售它算不算自部署
- [ ] 判定只有三个值：是、否、未查到；倾向写在依据里
- [ ] 每条依据标档位；第 4 档不能单独下结论
- [ ] 每条依据都对照过每个候选上游，标「只有 A / 只有 B / 都有」
- [ ] 描述来历的话、营销文案不进依据；和结构化标记冲突时写明冲突
- [ ] 活动价记条件和截止日期；从页面内嵌的活动参数算出来的现价标「推算」
- [ ] 文档原文按 llms.txt、`.md`、JS 数据模块的顺序取，存档写 URL 和日期

最后一条边界要写进报告：这些都是「平台怎么说、看起来像什么」，不是实测。真要对比效果，最终还要实测：输出规格，以及和官方用同一提示词对照的结果。

## 收尾

1. **分档取证** —— 托管方标记和内嵌数据最强，「能出 2K」最弱，弱信号不能压过强信号。
2. **按端点判** —— 同一平台同一模型的不同端点，托管方可以不同。
3. **依据要有区分力** —— 拿每条线索去对照每个候选，两边都有的不算。
4. **两头都有记未查到** —— 说明文字可以抄，取值范围跟着真实后端走；倾向不等于判定。
5. **先核再交** —— 子代理采集的表逐格核出处，再请人盲核，一题不一致就扩大复核。

这次两回判错，都是证据本身没问题，错在用法：一回用弱信号压了强信号，一回只拿证据对照了心里那个答案。以后这类表，我会要求「依据」这一列动笔前，先把候选上游并排列出来，随表一起交。
