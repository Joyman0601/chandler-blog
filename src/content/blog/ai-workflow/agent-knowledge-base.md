> 一句话总结：经验库本身只是一堆 Markdown 加 git，难的是两头。写入端要有门槛和脱敏，不然很快变成流水账；调出端不能指望模型自己想起来：目录常驻上下文，确定的时刻（要执行的命令、要写的文件、出现的报错）带着正文出现，语义判断交给主模型，不交给后台的小模型。

## 0. 起因：同一个坑踩第二次

用 AI 编程助手做开发一段时间后，我发现一个规律：它（和我）踩过的坑，下次照样会踩。会话结束，教训就跟着上下文一起消失了。写进 CLAUDE.md 是一种办法，但那里的每一行都占每个会话的上下文，几十条之后就没人细看；写在笔记里，又没人会在做事的那一刻去翻。

所以我想要的不是一个笔记本，而是满足四个条件的东西：

1. **记得下**：做完一件事，能把可复用的部分记下来，记的时候顺便脱敏，不留公司信息和人名；
2. **调得出**：做到相关那一步时，经验自己出现，不靠谁记得去查；
3. **不越长越没用**：条目多了以后，调出的成本和噪音不能跟着线性涨；
4. **人也能学会**：经验不能只存在 AI 那边，我自己也要掌握。

最后的形态很朴素：一个 git 仓库放 Markdown 条目，一个全局 skill 规定怎么读写，几个 hook 负责在做事时把条目调出来。下面按「条目长什么样 → 怎么写进去 → 怎么脱敏 → 怎么调出来 → 怎么复习」讲。文中的比例和趋势是我自己统计的（实测），库里具体有哪些条目、多少条，不展开。

## 1. 条目结构：一条只讲一个点，标题写结论

条目分六种类型，各放一个目录：

| 类型 | 放什么 | 怎么用 |
|---|---|---|
| playbook（场景手册） | 某类任务的步骤和验收清单 | 做这类事之前调出来照着走 |
| pitfall（踩坑复盘） | 一次踩坑：症状、根因、解法、检查点 | 出问题时按症状查 |
| knowledge（知识与技巧） | 原理和用法 | 查用法、补理解 |
| lab | 可运行的最小复现 | 验证理解 |
| growth（成长） | 方法论、被纠正过的做法 | 定期回看 |
| inbox | 来不及整理的碎片 | 整理时归档 |

几条写法上的硬规定，都是吃过亏才加的：

- **一条只讲一个能复用的点。** 一次排查里有三个独立的坑，就写三条。合在一起的条目，标题概括不了，触发器也写不准。
- **标题写结论，不写事件。** ✗「某日某功能的问题」 ✓「在仓库子目录里跑 git diff 时，按仓库根写的路径会静默命中 0 个文件」。目录里只有标题，标题本身就要能用。
- **每条标证据等级。** `tested`（实测）、`docs`（文档）、`inferred`（推断）、`reported`（转述）。推断和转述的条目以后实测了要回来改。同一条里证据不一时，正文逐句标。
- **每条至少一道自测题，问判断和原因，不问死记的细节。** ✗「上游限速多少」 ✓「上游对未知参数一律返回 200 时，为什么『参数被接受』的探测结论不可信？」
- **踩坑的检查点要回写进相关的场景手册。** 坑是零散的，手册是做事时真正会被打开的。不回写，坑就只能靠检索撞上。
- **不复制业务代码。** 需要代码就自己写最小示例，用通用命名和假数据。

一条踩坑复盘的最小样子如下，字段和真实条目一致，内容是示意：

````markdown
---
title: zsh 里 `echo =====` 会被当成命令路径展开，同一行后面的命令都不执行
type: pitfall
tags: [shell, tooling]
evidence: tested
created: 2026-10-15
updated: 2026-10-15
box: 0
due: 2026-10-16
triggers:
  errors:
    - '= not found'
---

## 一句话教训

zsh 默认开着 EQUALS 选项，以 `=` 开头的词会被当成 `=命令名` 去查路径。
拼接多段输出时用 `printf '%s\n' '====='` 当分隔符，不要用 `echo =====`。

## 症状

`sed -n 1,40p a.md; echo =====; sed -n 1,40p b.md` 只输出了第一段，
然后报 `==== not found`，退出码 1，第二个文件根本没读。

## 根因 / 解法 / 检查点

（略）

## 自测

- Q: 一条用 `;` 串起来的读文件命令只输出了一半、退出码非 0，先查什么？
````

front matter 里的 `box` 和 `due` 给复习用（第 6 节），`triggers` 给调出用（第 4 节）。

## 2. 写入：有门槛，一次最多新建一条

库建起来的第一周，我让 AI 从历史会话里批量提炼，一下子新增了几十条。之后改成每次任务结束时自动记，门槛是「下次遇到能省时间或避免犯错」，几类典型的收获：

- 多轮才定位到的根因；
- 被纠正过的做法；
- 实测推翻了文档或旧结论；
- 新学到的验收标准或工具技巧。

只和这次任务有关的状态、进度、数字不记。

光有门槛不够，AI 对「值得记」的判断偏宽。所以又加了两条限制：

1. **一次对话最多新建一条**，挑最值得的那个；其余候选先看能不能作为案例追加进已有条目（追加不算新建），不能的只在回复最后问一句「要不要记」。
2. **写之前先查**。用一个按标题、标签、正文打分的检索脚本，中英文关键词都试，找到相近的就追加案例、修正结论，不新建。

理由很实际：目录常驻上下文（第 4 节），每多一条，每个会话都要多带一行。按周看，新增数从几十条一路降到个位数：头两周是存量收割，后面降下来，一部分是门槛起了作用，一部分是同类的坑开始作为案例并进旧条目。现在的条目里，踩坑复盘占一半多，绝大多数标的是实测。

## 3. 脱敏：规则、词表、提交前扫描

这个库的目标是条目不含公司信息，可以公开分享：留下知识，去掉公司和人。脱敏分三层。

**第一层：规则文件。** 一张「必须去掉」的表：

- 凭证；
- 公司名和内部仓库、服务、分支名；
- 同事和客户；
- 内网地址、库表结构、内部环境变量名；
- 定价、成本、折扣这类商业信息；
- 业务代码；
- 未公开计划；
- commit、PR 号这类工作痕迹。

还有一张「可以保留」的表：公开的第三方产品和接口、实测得到的第三方行为、通用技术、抽象后的流程。写条目前先读规则，写的时候就脱敏，不先写原文再替换。

规则里最有用的是「泛化的分寸」一段：去掉专名，但保留让这条知识成立的上下文。

- ✗「某系统出了个问题，后来修好了」：泛化到没用了。
- ✓「任务型接口由网关建任务、worker 异步执行；结果只存在创建它的进程内存里，查询落到别的实例上就查不到」。

数字也一样：说明规律的留下，业务性的去掉。

**第二层：本机敏感词表。** 一个不进 git 的文本文件，每行一个词，大小写不敏感，`re:` 开头的是正则，`词 => 替换` 同时给出建议替换。遇到新的内部名随手加。这个表本身就是敏感信息，所以它只在本机，扫描脚本也跳过它。

**第三层：提交前扫描。** 保存脚本在提交前跑一遍扫描：

- **block 级**（阻止提交）：私钥头、各家云厂商和代码托管平台的 key 格式、JWT（JSON Web Token）、Bearer token；形如 `api_key = "..."` 且值不是占位符的赋值；词表命中；
- **warn 级**（只提示）：邮箱、IP、本机绝对路径、反引号里的十六进制串（疑似 commit）、`PR #数字` 这类。

确认无害的行在行尾加一个放行标记。

上线前我拿一组样例测过：10 个应该拦的全拦下；占位符（`<API_KEY>`、`$PROVIDER_API_KEY`）、`max_tokens` 这类参数名、版本号都没误报。发现的一处误报是 noreply 形式的提交邮箱被当成真实邮箱，修了白名单。

扫描能管的边界要心里有数：它只认格式和词表。「某个具体型号哪天上线」「一个业务数字」这类东西，格式上和普通文字没区别，机器拦不住，只能靠写的时候按规则自查。它还会误报：有一次复习记录提交时，条目里一个十位数的参数取值被当成了提交哈希。warn 级就是给这种情况留的，看一眼放过。

## 4. 调出：目录常驻，确定的时刻带正文出现

调出端改了三版。

**第一版：索引页。** 一个列出全部条目的 INDEX.md，让 AI 做事前去读。条目到六十多条时，这一页已经二十多 KB，读一次就占一大块上下文，AI 也开始只读开头。改法是把它变成只列场景手册的路由页，并给它设体积预算；明细挪到单独的目录页，再配一个只返回最相关几条的检索脚本。条目过时就加 `status: archived`，不进索引也不进复习。

**第二版：会话开始时用 hook 注入全部标题。** 约 1.5 万字符，结果被截成 2 KB 预览（hook 单次输出有上限，见[hooks 那篇](/blog/ai-workflow/claude-code-hooks-inject-context/)）。

**第三版（现在）：两层分工。**

- **目录**：每次保存时生成一页全部条目的标题（场景手册另带一句话摘要），在全局 CLAUDE.md 里用 `@路径` 引入，随全局指令进每个会话。它也设了预算，用量接近上限就提示整理。语义上「手头的事和哪条对得上」，交给主模型对照目录判断。
- **触发器**：在确定的时刻，把条目正文直接送进上下文。

触发器写在条目自己的 front matter 里，六类：

| 类别 | 拿什么去匹配 | 命中后 |
|---|---|---|
| `commands` | 将要执行的 shell 命令（已拆成简单命令） | 先拦一次并给出正文，对照后重跑 |
| `gate` | 同上 | 同上，但之前以别的方式出现过也照拦，读过原文才放行；只给 `git push` 这种难撤回的动作 |
| `errors` | 命令的输出 | 注入正文 |
| `prompts` | 我发给助手的消息 | 注入正文 |
| `files` | 将要写入的文件路径 | 先拦一次并给出正文 |
| `skills` | 将要调用的 skill 名 | 随调用结果注入正文 |

```yaml
# 示意
triggers:
  commands:
    - '^git\s+push\b'                  # 以 ^ 开头：从一条简单命令的开头匹配
  errors:
    - 'ERROR 1205 \('                  # 报错写原样格式，不只写错误码
  files:
    - '/[^/\n]*changelog[^/\n]*\.md$'  # 文件名关键词限定在最后一段
```

卡片带的是条目正文（不含自测和修订记录），模型不用再去读文件。限制如下：

- 单张卡片的字数、一次注入的总字数和张数都有上限，放不下的退成一句话摘要；
- 同一会话里一条只出现一次；
- 在库自己的目录里干活时不匹配，否则改条目时满屏都是卡片。

大约一半的条目带触发器，按文件路径的最多，按命令的次之。

触发器上线前，我拿历史会话回放调过噪音，上线后靠命中日志对账（只记时间、会话、规则，不记对话原文）。三周多的日志里，最多的是写文件前拦，其次是命令前拦和报错注入。回放的方法写在 hooks 那篇的第 5 节，这里只说一个教训：「卡片出现后有没有被读」这个指标，在卡片自带正文之后就没意义了，读数接近 0，是因为不需要读，不是因为没用。

## 5. 试过又关掉的：后台小模型挑条目

触发器只能接住有确定信号的场合。「我说要做一次上线前检查」这种语义上的相关，正则写不出来。我试过一个方案：我每发一条消息，后台就起一个小模型，拿全部条目的标题和这条消息，挑出相关的编号，再把这几条的卡片插进对话。它不挡我的输入，结果晚到会通过异步通知插进来。实现细节在 hooks 那篇的第 7 节。

上线前用一组自编的样例测，大部分判对，看起来能用。全开一周多之后对账：

- 触发的消息里，过半是短消息、斜杠命令和通知，脚本直接秒退，真正调用小模型的不到一半；
- 延迟中位数三秒多，慢的十几秒；
- 调用里约四分之三挑出了东西，平均每次插进两三张卡片；
- 不少卡片是在模型干活中途插进来的；也有在模型答完之后才到的，把它叫醒多跑一轮，其中过半因此多做了事。

我抽了一批判断，把被挑中的条目逐条看：明显有用的不到两成，沾边的约三成，不相关的超过一半。几个模式：

- **方法论条目霸榜。** 被挑得最多的那几条，大多是成长类，这类条目和「任何任务」都沾一点边；
- **短消息只能猜。**「继续」「好的」这种消息，小模型也会挑出几条；
- **跨项目误注入。** 一个项目的经验被插进另一个项目的会话里。

结论是关掉。它和常驻目录做的是同一件事（语义匹配），而主模型手里有完整的上下文，比只看一条消息的小模型判断得准；一半以上不相关的卡片，还会让模型学会忽略卡片，连带拖累触发器送来的那些。

关掉后用两样东西补位：

1. **按动作触发**：多写 `files` 和 `skills` 两类触发器，它们比消息内容确定得多；
2. **新任务提醒**：我的消息看起来像在开始一件新任务时，只注入一句提醒，让主模型对照目录，在回复开头写一行「相关条目：…」。判断还是主模型做，提醒只保证它在开头想一下。

这次的教训是：自己写的样例会高估效果。样例大部分判对，线上却一半以上不相关，差的就是真实消息的分布。

## 6. 复习：间隔重复

AI 那边靠调出，我自己靠复习。复习模式每次挑 3–5 条到期条目，一次问一题：用条目的自测题，或者按条目内容现编一道情境题。答完再给评价和要点，不先给答案。

间隔按分箱算：`box` 1 到 5 对应 1、3、7、21、60 天；答好升一箱，答不好回到第 1 箱。

现状不好看：绝大多数条目都处在到期状态，还没有一条升到熟练的箱位。最近一次复习的几道题，没有一题答完整，都回到了第 1 箱。复盘下来，卡住的地方多半不是忘了结论，而是不熟悉背后的机制：有一题问一处参数校验为什么还可能被绕过，结论我记得，可当时没想到另一条传参的路径；讲完一个具体的请求例子，马上就明白了。

所以复习题的写法要跟着改：先把机制讲清楚，再问判断，而不是直接问「这里有什么坑」。条目入库的速度远超人能消化的速度，这部分的欠账是真的。

## 7. 局限：至今量不出来的部分

1. **「照做了没有」量不出来。** 日志能告诉我卡片出现了多少次，告诉不了我模型看到卡片后有没有因此改变做法。能看到的只有零星的个例，比如被拦一次后换了一条命令。
2. **回放会漂移。** 触发器按历史会话调好以后，换了压缩阈值，频率就差了好几倍（经过见[上下文花费那篇](/blog/ai-workflow/context-compaction-cost/)第 6 节）。规则没变，环境变了，回放就得重来。
3. **目录有固定成本。** 几十 KB 的目录每个会话都带着，不管这次用不用得上。预算和整理是在控制它，不是消除它。
4. **扫描只管格式。** 脱敏的最后一道还是写的人自己，第 3 节说过了。
5. **人学得比库长得慢。** 第 6 节的数字就是证据。

## 8. 后续补齐：执行经验之外，还要留人的理解

到后面整理会议和反馈时，我发现，原库虽然有复习题，仍主要服务 AI 执行。我自己的学习常常只在回复里出现，没有独立积累入口。于是把私人理解单独记录，保留概念、真实案例、下一次的用法和来源；公开文章继续脱敏，操作规则仍维护在原处。

这几类记录可以来自同一个案例，却各自回答不同问题。规则保存成功不等于我已学会，学习笔记写完也不等于适合公开。具体分工、学习状态和迁移依赖的处理见[执行规则、个人理解和公开文章](/blog/ai-workflow/rules-learning-and-public-writing/)。本篇前面描述的是原执行经验库的设计，不能据此推断后来所有学习内容仍只存在其中。

## 收尾

如果你也想给 AI 编程助手搭一个类似的东西，我会建议按这个顺序做：

1. **先定写入的规矩**：一条一个点、标题写结论、标证据等级、写自测题；一次对话最多新建一条，先查后写。
2. **脱敏写在入口**：规则文件 + 本机词表 + 提交前扫描，三层都要有；扫描只管格式，业务信息靠自查。
3. **目录常驻，正文按时刻出现**：目录用 `@` 引入，不走 hook；正文只在确定的信号（命令、报错、文件路径、skill）上出现，命令类的要赶在执行之前。
4. **语义匹配交给主模型**：后台小模型挑条目，我实测下来不相关的过半，不如一句提醒让主模型自己对照目录。
5. **每个开关都配日志和回放**：上线前回放，上线后对账，环境变了再回放。

库最大的价值，最后不是 AI 少踩了多少坑（这个量不出来），而是每次踩坑都逼我把「为什么」写成一句结论。写不出结论的，往往是还没真正想明白。
