> 一句话总结：评价一项新流程，先核它补哪个已有缺口，再分别证明规则保存正确、真实任务按预期执行、结果值得增加的成本；三层证据不能互相替代。

## 0. 起因：方法吸收了，效率还不能下结论

我让助手调研公开的技能与工作流，希望吸收有用的方法。筛出来的内容里，既有能直接补进现流程的检查，也有会改变合作方式的方案：持续访谈、严格测试先行、默认多代理，以及整套框架安装。

我的要求是先吸收不影响现流程的部分，其余说明利弊，由我选择。我采用了按需推敲方案、适合独立工作时使用多代理，暂时没有采用全任务严格测试先行。

配置保存后，助手核过结构和原规则是否保留。这是有用的结果。但复盘时我也看到，一次小范围配置用了不少时间，里面有重复阅读、多处同步和留档。此时没有真实新任务的对照，不能因为文件改对了，就说效率已经提高。

这次让我更明确地分开了三个问题：是否写进去了，是否真的执行了，执行后是否更好。

## 1. 采用之前，先把缺口写具体

一份方法看起来合理，很容易被写成通用要求。先查资料再实现、先复现再修复、完成前验证，这些大方向本身没什么争议。真正需要判断的是：现流程是否已有同样的动作，缺口发生在哪里。

我会先填写四项。

| 项目 | 一个自编例子 |
|---|---|
| 已见问题 | 小改也先进入长访谈，明确任务一直等不到实现 |
| 现有覆盖 | 需求不清时本来就会询问，日常实现已有验收标准 |
| 要增加的动作 | 明确要求推敲方案时才进入集中访谈 |
| 完成条件 | 适用任务能暴露关键取舍，明确任务能继续执行 |

**新增动作要能指向具体失败。** 若只写「让质量更高」，后面就很难判断它有没有帮助。若旧流程已有同样要求，下一步应该查为什么没落实，而非再写一份近似规则。

公开项目的关注度可以帮助寻找候选，却不能证明它适合我的任务。文档写得完整，也不能证明和当前权限、上下文、检查入口兼容。采用单位应当是一个有边界的方法，而不是一个看起来很成熟的框架名称。

## 2. 第一层：规则已保存

保存层能做许多机械检查。例如，新入口是否存在，引用是否正确，原先的权限和预算条款是否仍在，触发范围是否被意外扩大。

它回答的是「预期配置是否写成了当前文件」，不是「以后一定照做」。常见的三种误判值得单列。

- 把格式校验通过写成方法生效。
- 把规则被读取写成最终成品已按规则完成。
- 把提醒出现次数写成避免错误的次数。

我遇到过一种直接反例：已有「结论前置」的规则，报告首页也放了结论，但具体比较章节还是先堆公式。规则存在、入口触发、成品仍漏项，可以同时成立。

所以保存层的记录写到文件和结构就停。后续行为还没观察，就明确留空；无需为了让完成报告好看，提前替它补上成效。

## 3. 第二层：在适用任务中真正执行

行为层要看最终对象。报告检查最终页面，测试方法检查实际断言，协作规则检查任务是否被合理拆分、文件是否隔离、结论是否复核。

对一条有条件的规则，我至少想看三类输入。

| 输入 | 应观察什么 |
|---|---|
| 适用场景 | 对应动作被执行，最终对象达到要求 |
| 原来的错例 | 能识别原错误，不能换种写法就全绿 |
| 不适用场景 | 正常放行，没有引入无关步骤 |

例如，「需要推敲方案时集中访谈」应在真正需要决定业务取舍的任务中出现；一处范围明确的小文案修改则应直接完成。只验证前一种，会漏掉规则把所有任务拖进访谈的副作用。

多代理也是同理。适合独立并行的资料核查，可以交给不同执行者；必须先等一个契约才能开始的实现，拆得更多未必减少关键路径。是否启动多个代理，不能作为流程有效的唯一指标。

若需要自动检查，失败条件应落在最终结果上。例如，查每个关键章节是否有当前结论及其依据，比查全文出现过「推荐」两个字更接近目标。机器无法可靠判断的语义，就保留人工复核和可追溯证据。

## 4. 第三层：结果值得增加的成本

行为符合预期以后，还要评估是否有收益。可能更少返工，却多花了等待时间；可能节省主会话上下文，却增加协调和复核。不同目标需要不同观测。

| 想改善什么 | 可以记录什么 | 容易误用的替代指标 |
|---|---|---|
| 正确性 | 漏项、错误结论、独立复核结果 | 工具调用数、报告篇幅 |
| 交付速度 | 从接单到可验收结果的时间 | 单次模型响应速度 |
| 返工 | 原因、轮次、重新打开的范围 | 提交次数 |
| 资源成本 | 同范围下可取得的实际用量 | 不同任务的总 token 直接排名 |
| 可用性 | 读者能否完成判断或执行 | 截图可打开、链接返回成功 |

这次配置过程偏长，是一个可以回查的个案。它包含阅读、思考、工具等待和同步，不能直接当成模型计算耗时，也不能由这一例推断所有文档流程都应精简。

我能做的，是指出具体重复点，在后续真实任务观察。若要比较两种方案，尽量保持任务范围、材料、质量标准和验证条件一致。换了模型又改了流程，结果即使变好，也很难知道原因来自哪一处。

没有可比对照时，记录「本次可观察结果」和「仍未知的效果」，比给出一个没有依据的提升比例更有用。

## 5. 规则存在却仍犯错，先定位断在哪一层

以前我常用「再内化一下」概括这类修正。后来发现，它可能指向四种不同的问题。

| 断点 | 该补的动作 |
|---|---|
| 没触发 | 调整入口和适用信号 |
| 触发了，没落实 | 检查最终对象，明确必须执行的动作 |
| 规则本身不对或太窄 | 修判据，加入边界与反例 |
| 生成后又变化 | 核最终版本，避免旧检查覆盖新产物 |

只增加提醒频率，主要帮助第一种。对于报告逐章遗漏，重复弹出同一张卡片未必解决问题；更直接的是让检查逐章进入最终成品。

修正规则时，也不应把那次任务的所有细节固化为永久步骤。一次报告使用某种卡片排版，不代表所有报告都该用相同卡片。要留下的是视觉重点与决策重要性一致，以及检验这条要求的方法。

## 6. 给流程本身设一个投入边界

小改最容易被流程吞掉。新增一个入口，顺带改多个索引、建立多份状态、重复读一批已经核过且未变化的资料，最后文档建设比实际改动更大。

我现在更愿意按这个顺序做：

1. 找到原来的唯一维护点，先查现有覆盖。
2. 在已确认缺口处增加最少的必要动作。
3. 履行当前必读、权限与必要验证要求。
4. 复用条件未变的已有证据，按实际变化补查。
5. 在真实适用任务中观察，不为证明启用而强造演示。

这不等于降低验证标准。省下来的应是没有增加判别力的重复工作。新版本、相关条件变化或证据仍有疑点，原来的检查就不能直接复用。

一张可套用的采用记录如下。

```text
要解决的旧问题：
现流程已覆盖的部分：
本次只增加的动作与触发条件：
保存层证据：
真实行为证据：适用 / 错例 / 不适用
收益证据：质量 / 耗时 / 返工 / 用量
尚未验证的部分：
下一次在哪个真实任务观察：
```

字段可以合并，关键是未知保持未知。没有真实任务可观察，就停在保存层，不制造一场不必要的工作来填满表格。

## 收尾

1. **先找缺口** —— 已有规则没落实，要修执行位置，未必需要新框架。
2. **证据分三层** —— 保存、执行和收益，各自取证。
3. **检查不适用场景** —— 好规则也要能让明确的小任务顺畅完成。
4. **流程也算成本** —— 按实际变化补查，在真实任务中观察收益。
