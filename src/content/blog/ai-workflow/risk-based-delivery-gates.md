> 一句话总结：交付检查该多重，看错误后果、影响面和能不能撤回，不看前端后端、个人工作或改了几行；负责判级的分流器影响后面所有任务，要按最高级别验。省时间要省在整理返工上，不省在必要检查上；规则生效、真实任务走对、整轮变快是三层证据，备份和阅读减负也一样。

## 0. 起因：三个文件的样式改动，走了四十多分钟

我在给自己的个人博客换字体。试排了几轮，最后定了一套字体和字重，正式改动只有三个文件：字体导入、样式变量和一份设计说明。

我说「可以推送」之后，到助手汇报上线完成，墙钟约 47 分钟。这段时间包括阅读、实现、构建、审视、等待和留档，不是纯编码，也不全是部署等待。里面能指认的额外成本有几处：证据包打好以后又补了一份提示词，清单里的哈希跟着重算；一个页面搜索脚本假设了输入框的选择器，猜错后重跑；还有多份状态文件来回同步。

复盘时，我指出一件事：模型接入这类改动确实需要严密的闸，静态博客的样式不需要同样重。助手回头读了交付检查脚本的代码，结论比我的直觉更细。

- 任务档案里「要不要代码审视」只有要和不要两档。
- 推送前的兜底检查不随「不要」关闭，但说明不适用之后就可以绕过。
- 这次完整审视是助手自己先选的，不全是工具强制。

所以问题有两层：工具缺一个给低风险改动用的档位，助手也没先判断这次改动该走哪一档。

同一轮里还有一处归因要更正。前面几版被我否掉的设计稿，助手在复盘里写成「探索不够有效」。我的看法是设计本来就要多轮，否掉的稿子有参考价值。探索的价值和交付的风险是两件事，要分开评价。

## 1. 分级依据：错误的后果，不是改动的位置

最顺手的分法是按位置：前端轻、后端重，个人项目轻、工作项目重，改动少就轻。这几条都靠不住。

前端页面上展示的价格，改错一个数，用户就按错的价格下单；后端一条注释改错，什么都不会发生。改动行数也一样，一行权限判断比一百行样式危险得多。

我最后用的是三个问题。

1. **错了会怎样**：只是难看，还是会多扣钱、越权、丢数据。
2. **影响多大**：只影响一个页面，还是会被很多调用方、很多后续任务继承。
3. **能不能撤回**：回滚一次部署就恢复，还是数据已经写进去、消息已经发出去。

按这三个问题，交付分成四级。下面这张表可以直接拿去改成自己的版本。

| 级别 | 典型改动 | 必做 | 可以省 |
|---|---|---|---|
| 探索 | 设计样稿、调研草稿、本地实验 | 标明是候选，不进正式分支 | 审视、复核、留档 |
| 静态展示 | 文案、样式、字体、静态页面 | 构建通过、关键页面截图实看、推送前基本卫生 | 完整审视、独立复核、重复构建、用量对账 |
| 功能交互 | 表单、筛选、路由、前端状态 | 交互走查、相关测试、改动范围的审视 | 与改动无关的全量回归 |
| 关键业务 | 计费、权限、模型接入、数据脚本、跨系统接口 | 完整审视、独立复核、付费或生产前的专门核对 | 无 |

表里的「典型改动」只是起点，碰到下面几种行为就往上升级，不管它在哪个目录：

- 涉及价格、额度或任何会显示给用户的金额；
- 涉及权限、登录状态或敏感数据；
- 会持久化，写库、写文件或写缓存；
- 改动跨系统的约定，比如接口字段、回调格式、配置键名。

判不准、或者一次提交里混了几级时，按最高的一级走。推送前的基本卫生每一级都保留：提交身份、目标分支、有没有夹带凭证和本机文件。

## 2. 判级的系统本身，要按最高级别验

分级方案定下来以后，我让助手直接实施，同时说清楚一点：这次改的是检查系统本身，要完整验证。

这两件事并不矛盾。静态改动可以从简，前提是「这是静态改动」这个判断本身可靠。分流器判错一次，后面每个任务都会被带偏：该严查的被放进短路，代价就是事故。所以分流器属于「影响面最大」的那类改动。

助手写了七十多项检查和几个变异测试，全部通过。之后我按惯例让一个新上下文的子代理独立复核，它还是抓到了三处放行遗漏。

**遗漏一：子 shell 里的 `cd`。** 检查脚本要判断一条命令在哪个仓库里推送，于是顺着命令里的 `cd` 跟踪目录。但括号里的 `cd` 只在子 shell 里生效：

```bash
cd /tmp; (cd /; pwd); pwd
# 输出：
# /
# /tmp      # ← 括号结束后，目录回到原处
```

脚本把括号里的 `cd` 当成了全局生效，后面的命令就被归到了错的仓库。

**遗漏二：临时 Git 配置改了推送地址。** 脚本读仓库配置里的远端地址来判断推到哪里。但 `git -c` 可以在单条命令里覆盖配置，配置文件里看不出来：

```bash
git remote get-url --push origin
# https://example.com/a.git
git -c remote.origin.pushurl=https://example.com/other.git remote get-url --push origin
# https://example.com/other.git                         # ← 只对这一条命令生效
git -c url.https://mirror.example/.pushInsteadOf=https://example.com/ remote get-url --push origin
# https://mirror.example/a.git                          # ← 改写规则也能换掉目标
```

**遗漏三：明确要求深审的话被提前过滤。** 我在任务里写明「要深度审视」，但分流逻辑先按旧关键词判成了低风险，后面的规则根本没看到这句话。显式的意图应该排在任何启发式判断之前。

三处都是助手对执行语义的假设和用例覆盖不足，不是需求没说清。为什么七十多项检查没抓到？因为实现和断言出自同一个人，同一个错误的假设同时写进了两边，测试自然全绿。

独立复核绕开盲区的办法，是换预期的来源：

- 目录归属问真实的 shell，像上面那样跑一遍看 `pwd`；
- 推送目标问真实的 Git，`git remote get-url --push` 会把 `-c` 和改写规则都算进去；
- 意图以我的原话为准，不以关键词表为准。

修复后，拿复核用的原始输入重放：修复前三条目标断言是红的，修复后变绿。这一步说明这次复核有具体价值，不是走过场。

## 3. 必要检查和整理返工，分开算

这次实施从会话开始到交付约 57 分钟，同样含阅读、等待、修复和整理。它不能整段算成「严密检查的代价」，因为里面混着不少可以避免的返工：

- 缓存文件误进了审计用的提交，又提交一次删掉；
- 报告里的命令指向旧目录；
- 引用的行号随文件改动偏移，反复校正。

字体那次的哈希重算、选择器猜错，也是同一类。前一天还有一次类似的事：我确认三份样稿都保留，助手顺手同步了好几份说明，收尾时又因为没重读续接模板被拦了一次，整理比实际改动还重。

这些都是助手执行上的取舍，不能用「流程本来就严」一并合理化。反过来，也不能因为整理返工多，就去删必要检查。我后来固定了几条做法。

1. 证据和复核提示词在分发前冻结。冻结后再补材料，前面的哈希、引用都要跟着动。
2. 引用从最终提交里取，不从中间版本取。
3. 没变的文件复用之前的证据。是否「没变」看 Git 对象，不看文件修改时间：

```bash
# 列出两次提交之间真正变了的文件；不在列表里的，之前的检查结果可以复用
git diff --name-only "$VERIFIED_REV" "$FINAL_REV" -- <交付文件清单>

# 单个文件逐项核：两次提交里的 blob 相同，内容就相同
git rev-parse "$VERIFIED_REV:path/to/file" "$FINAL_REV:path/to/file"
```

4. 只对变化影响到的部分补检查。

想删掉某项检查时，先回答两个问题：它防的是什么错，错了后果多大。如果它保护的是成品，就留；如果它只是同一份证据换个格式再存一遍，就是重复留档，可以删。只比检查总数，删掉的往往是错的那一项。

收尾的状态也要分开说。字体上线后，我让助手停掉本地预览服务、清理可重建的目录。「已上线」「预览已停」「临时资源已释放」是三个状态，各自要有证据；被删目录原来占多少空间，也不等于磁盘空闲空间涨了多少。

最后一层：分级规则写进去了、隔离样例里分流也对，这只说明规则生效。它有没有让下一次静态交付变快、有没有误拦，要等真实任务的数据。在那之前，我不说「已经提速」。这三层证据的区分，我在[吸收新流程：先补缺口，再证明实际收益](/blog/ai-workflow/workflow-change-evidence-layers/)里单独写过。

## 4. 备份：上传成功不等于能恢复

同一周我在整理另一件事：把复盘、脱敏改写、发到博客这条链路用到的几个技能和工具备份到一个私有备份仓。

当时我担心技能拆得太多不好维护，想过合成一个大技能，内部用导航文件分流。助手的建议是把三件事分开看：资料在哪里维护、执行时读哪一段、哪些内容能公开。

备份仓可以集中存多个技能，但这不等于把它们合成一个大技能。每个技能保留短入口，按意图只读需要的模块。只放一份目录标题、没有写读取规则，并不能保证按需加载。这次实现了分流，但没有同一任务改前改后的用量对照，所以我不说省了多少。

备份本身踩的坑，我在[知识沉淀分三处](/blog/ai-workflow/rules-learning-and-public-writing/)里写过细节：只存入口文件会漏掉模块、脚本、模板和被引用的规则；同字节但缺执行位的文件会被误判成功；链接落点漏了敏感路径检查。这里只补一条可以直接拿走的验证。

验收不看上传了多少文件，而是从远端的固定版本新克隆一份，用克隆里的工具恢复到一个隔离目录，再逐项核：

```bash
#!/usr/bin/env bash
# 用法：verify.sh <恢复根目录> <清单>
# 清单每行：sha256 权限 相对路径（导出时生成）
set -u
ROOT=$(realpath "$1"); MANIFEST=$(realpath "$2"); bad=0
cd "$ROOT"
while read -r sum mode path; do
  [ -f "$path" ] || { echo "缺失 $path"; bad=1; continue; }
  [ "$(shasum -a 256 "$path" | cut -d' ' -f1)" = "$sum" ] || { echo "内容不符 $path"; bad=1; }
  [ "$(stat -f %Lp "$path")" = "$mode" ] || { echo "权限不符 $path"; bad=1; }   # GNU 用 stat -c %a
done < "$MANIFEST"
while IFS= read -r l; do
  dest=$(readlink "$l")
  t=$(cd "$(dirname "$l")" && realpath "$dest" 2>/dev/null) || { echo "断链 $l"; bad=1; continue; }
  case "$t" in "$ROOT"/*) ;; *) echo "越界 $l -> $t"; bad=1;; esac
done < <(find . -type l)
exit $bad
```

用法是三步：

```bash
WORK=$(mktemp -d)
git clone --quiet <私有备份仓地址> "$WORK/repo" && git -C "$WORK/repo" checkout --quiet "$REV"
"$WORK/repo/<恢复工具>" --target "$WORK/home"     # ← 用克隆里的工具，不用本机原件
bash verify.sh "$WORK/home" "$WORK/repo/<清单>"
```

我在本机拿一个改掉执行位、一个指向恢复目录外、一个断掉的链接各试了一次，三种都能报出来，全对时退出码为 0。还有一条脚本里没写：同一份备份再恢复一次，应该零新增。

这次最终的备份从远端新克隆后，全部文件和链接都恢复了，重复恢复零新增。即便如此，它能证明的也只到一层：

| 已完成的层 | 能说什么 | 还不能说什么 |
|---|---|---|
| 文件和链接恢复 | 选定的材料能完整落到新位置 | 命令能不能跑 |
| 命令在目标环境运行 | 这台机器满足命令的条件 | 宿主是否启用了这些 hook |
| 宿主启用 | 入口被宿主接受 | 真实任务是否按预期执行 |

做了哪层就报哪层。凭证、会话记录和不在白名单里的知识正文，本来就不在这次备份范围内，也要写明。

## 5. 必读材料按模式分流：少读多少和快多少，是两回事

另一个技能是做上线回归的。它的正文和参考资料很长，但跑一次媒体类回归，只需要其中一部分。我让助手按模式分流：媒体和回放模式只读自己那份入口和参考。

结果是，适用的必读材料（含共用的流程文档）少了约四分之一。两个独立上下文对同一个真实媒体样本各走了一遍，覆盖范围和授权边界都还在。这证明了「阅读减负」在这个模式下成立。

但这个比例不能说成「整轮快了四分之一」。算上新方案额外的结构补验和脚本回读，两边的总读取量只差几个百分点；而且两边取证的路径不同，这点差距也不能全部归给分流。耗时、token 和质量上，都还没有可比的数据。

我现在把这类改进拆成三个问题：

1. **适用材料有没有变少**：数正文加实际引用的参考，不只数技能正文。
2. **真实任务有没有仍然做对**：要同类的真实任务、独立定的预期。
3. **整轮效率有没有改善**：还要算准备、补验和整理，并控制比较条件。

只缩短正文不够；反过来，不能因为这轮验证花了成本，就否认入口本身确实减负了。

这次也有助手造成的返工：初版基线漏算了脚本；媒体那份参考里残留了旧的文本命令、缺字段解释、章节转接不完整；报告有两处缺直接证据。最终修好、独立复核通过，不抹掉这些成本。下一次的顺序是：先核完整的可执行基线，再让一个只拿本模式材料的新上下文实际走一遍。只验证了媒体和回放模式，其他模式不外推。

同一周还有一例能说明「规则在」不等于「做到」。一次回归开跑前，助手已经读到「素材先量、用例合并」，还是漏了一项输入尺寸的预检。再加一条同义规则，证明不了这类执行错误会消失；要看下一次发送前的实际检查记录。

## 收尾

1. **按后果分级** —— 交付检查的轻重看错误后果、影响面和可逆性，不看前后端、个人工作或行数；判不准就升级。
2. **分流器从严** —— 决定其他任务走哪条路的系统，本身按最高级别验；预期要来自真实 shell、真实 Git 和原话，不来自写实现的同一个脑子。
3. **返工不算必要检查** —— 冻结后再补、引用旧行号、缓存误入提交，都是整理成本；删检查前先说清它防什么错。
4. **恢复才算备份** —— 从远端固定版本新克隆、隔离恢复、逐项核内容、权限和链接；做到哪层报哪层。
5. **少读不等于更快** —— 阅读减负、做对、整轮提速各要各的证据，比例不能挪用。

这几件事底下是同一个习惯：先选对流程，再把选中的流程认真做完。下次再碰到「小改也跑了很久」，我会先问三件事：这次改动该走哪一级？时间花在必要检查上，还是花在整理返工上？我手里的证据到底证明到了哪一层？
