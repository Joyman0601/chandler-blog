> 一句话总结：把一个任务拆给多个窗口，难的不是并行本身，而是让每个窗口只看到对的东西。简报要原句引用任务原文，开窗的改名命令要单独一条，共享记录各写各的、只追加，多代理编排要为「中途会停」做准备。

## 0. 起因：一个任务拆给五到七个窗口

我日常用 Claude Code 写代码，十月第二周起也开始用 Codex。一个任务常常包含几个仓库的改动和一份交付报告：后端要改，前端页面要改，文档要同步，最后把结论和证据整理成报告。一个窗口从头做到尾，上下文很快涨到几十万 token，几条线还要互相等。

所以我开始把一个任务拆给多个窗口并行做。典型的一套是：

- 一个统筹窗口（W0）：出计划、合并结果、写最终报告；
- 几个执行窗口：一个做后端，一个做前端和文档，各自只改自己那组 worktree；
- 一个审查窗口：在新上下文里审别人的改动，自己不写代码。

窗口最多的一次开到七个。两周里出过四类问题，共同点是都不报错，要到收稿时才发现结果不对。下面按出事的顺序讲，每节最后给出现在的固定做法。

## 1. 计划文件：先写下谁拥有什么

所有窗口共用一个任务目录，结构固定：

```text
<任务目录>/
├── PLAN.md               # 统筹窗口写：现状、分工、公共约定、交付清单、资源登记
├── windows/
│   ├── W1-backend.md     # 每个窗口一份简报
│   └── W2-frontend.md
├── DECISIONS-W1.md       # 决策日志：每个窗口一份
├── DECISIONS-W2.md
├── 台账-W1.md            # 真实调用的花费记录：每个窗口一份
├── inbox-W2.md           # 发给 W2 的消息（给没有消息工具的代理用）
└── out/W1/               # 各窗口的中间产物
```

PLAN.md 照一份固定模板写。§0 是「各窗口不用再查」的现状：代码落点、主干是哪条、所有远端分支里有没有前人做过；§0.5 记我已经定了的事，比如开几个窗口、真实调用的预算。§1 是分工表，写每个窗口改哪组 worktree、产出交给谁、依赖谁；§2 是时间表。§3 是公共约定：目录和 worktree 布局、推送前先问我、真实调用在日预算内记账、超出才问。§4 是交付清单，逐条照抄任务原文里要交的东西。§5 登记端口、容器这类资源被谁占着。

拆窗口有两条规矩。第一，一个窗口只改一组 worktree，不替别人改仓库，要别人改就发消息说清文件和行号。第二，审查窗口和写代码的窗口分开。按任务分 worktree 的目录布局见[多任务并行的 git 用法](/blog/git-collab/worktree-multi-task/)。

## 2. 派生简报：窗口只读简报，不会回头看原文

**现象**：第一次拆五个窗口那天，几个窗口交回的报告数据都扎实，我读完的感受却是「内容不是很明确」。我把这个感受告诉统筹窗口，它拿任务原文逐条重审，问题全出在结构上。换成一个自编的例子，问题是这一类的：任务原文要求交一张接口对照表，列出请求字段、响应字段、默认值三列；报告第一屏先回答「能不能直接切换」；另外单独说明验收时要看的三件事。交回来的报告是这样的：

- 第一屏是「需要你决定的事」，「能不能直接切换」排到了第三节；
- 对照表只有一行填满，「默认值」整列没有；
- 验收要看的三件事没有一处集中回答，证据散在三张表里；
- 同一组问题在三个小节里各写了一遍。

**根因**：简报是统筹窗口里的助手对原文的转述，转述时它加进了自己的习惯：「决定项放最前」本来是给另一类报告定的规矩，被它顺手写进了这份简报的报告结构。执行窗口只读简报，没有理由怀疑简报。简报也只写了「要做哪些事」，没写「验收的人拿什么来验」，所以报告是按「做了什么」组织的。

第二天又出了一次同类问题。为了省字，统筹窗口把每个窗口的收尾写成一句「固定七步」，把代码审视写成「跑复核（或由审查窗口审）」。结果一个改了代码的窗口没跑自己的审视，它理解成审查窗口会替它审。强制步骤一旦压成一句话，执行时也就只剩一句话。

**修复**：

1. 简报开头原样贴出原文里交付物和验收要求的原句，再写一句「和本简报冲突时以原文为准」。
2. 原文里关于位置、列名、格式的要求，逐条列成报告的硬要求。报告结构只引用 PLAN §4 的原句编号，不自拟。
3. 收尾的每一步写出落点文件：审查记录、验证记录、报告、续接文件各放在哪里，缺一个就算没收尾。
4. 收稿时拿原文逐条对，不拿简报对。
5. 简报写完先过一个脚本，按字面查必需的标记，查到压缩写法就退出非 0。

最小的版本长这样：

```python
#!/usr/bin/env python3
"""核每份窗口简报：必需标记都在，压缩写法不在。用法：check_brief.py <任务目录>"""
import glob
import re
import sys

REQUIRED = [
    (r"以原文为准", "开头要写：和简报冲突时以原文为准"),
    (r"审查记录\.md", "收尾：审查记录的落点"),
    (r"验证记录\.md", "收尾：验证记录的落点"),
    (r"RESUME_PROMPT\.md", "收尾：续接文件的落点"),
    (r"预期.{0,10}独立于本窗口的实现", "验证：预期来自需求或旧行为，不来自自己的实现"),
]
FORBIDDEN = [
    (r"固定[几七八]步", "收尾步骤要逐条写落点，不能一句带过"),
    (r"或由 ?W\d", "审查窗口不替代本窗口自己的审视"),
]

bad = 0
for f in sorted(glob.glob(f"{sys.argv[1]}/windows/W*.md")):
    text = open(f, encoding="utf-8").read()
    probs = [why for pat, why in REQUIRED if not re.search(pat, text)]
    probs += [why for pat, why in FORBIDDEN if re.search(pat, text)]
    for why in probs:
        print(f"{f}: {why}")
    bad += len(probs)
sys.exit(1 if bad else 0)
```

这个脚本写完，我先喂了一份故意写坏的简报，确认它真的退出非 0，再拿它去查正式的简报。检查脚本本身也要先证明「会红」。

## 3. 开窗和交接：/rename 单独一条

**现象**：窗口之间要互相发消息，得先认得出谁是谁，所以每个窗口都叫 `W<n>-<短名>`。有一次交接，主窗口给了我一段「两行」的开窗命令：

```text
/rename W0-tooling
读 <续接文件路径>，按它做。
```

我整段粘贴发了出去。新窗口的会话名变成了「W0-tooling 读 <续接文件路径>，按它做。」整整一串。之后在会话列表里按 `W0-tooling` 找不到它，窗口互发消息的约定也随之失效。

**根因**：`/rename` 这类斜杠命令把同一条消息里后面的全部文字都当作参数，不按换行截断。两行放在一个代码块里，读者自然会整块复制。写交接流程的是助手，它只在脑子里想象了「两行」，没按接收方的用法（整段粘贴）试一遍。我指出「要分成两句发」以后，它才把开窗消息拆成两条。

还有一个相关的事实：窗口自己执行不了 `/rename`，只有人能在输入框里打。没改名的窗口在列表里只显示一个按目录生成的匿名名字，几个同时在忙的匿名窗口根本分不清。

**修复**：开窗消息永远是两条分开的代码块，并写明「先发第一条，看到会话名改好再发第二条」。

```text
/rename W1-backend
```

```text
读 <任务目录>/PLAN.md 和 <任务目录>/windows/W1-backend.md，按它做。
```

简报的开工第一步也改了：从「自己改名」改成「核对会话名，不对就请我单独发一条 /rename」。

同一天我还发现了另一个问题：为了省 token，续接文件写得太压缩。新窗口拿到「相关文件」「同上」「照旧」这种词，只能猜，或者回头重查。交接省的是新窗口重读几十万 token 的前缀，续接文件本身只有几千 token，压缩它省不了多少。现在的规则是：每条待办写绝对路径、完整命令、`文件:行` 和带实测时间的数字；要压缩只压缩「要读的文件」清单。续接文件写完也过一个检查脚本，查含糊词、`/rename` 那一行后面有没有字、末尾的自检节在不在。

## 4. 共享记录：一次整份重写，另一个窗口的 9 条没了

**现象**：收尾时统筹窗口核对决策日志，发现它早上写的 9 条编号条目不见了，只剩后来追加的 2 条，另一个窗口的 11 条完好无损。文件修改时间正好是另一个窗口最近一次写入的时刻。整个过程没有任何报错。

**根因**：两个窗口按同一份计划开工，计划只写了「决策写进 DECISIONS.md」，没写谁拥有这个文件。另一个窗口上下文里拿的是它上次读到的版本，它整份写入更新文件时，并不知道统筹窗口后来追加过。Markdown 文件没有锁，也没有合并，只要一方用覆盖语义写，另一方的追加就没了。这个目录当时也不在 git 里，覆盖就等于丢失。

**修复**：

- 每个共享记录只指定一个写入者。其余窗口各写自己的文件（`DECISIONS-W1.md`、`验证记录-W1.md`、`台账-W1.md`），汇总窗口合并总表时才动总文件。
- 追加用定位编辑或 `cat >>`，不用整份写入。
- 写之前和收尾时各数一次自己的条目，数量不对先停下来查谁动过。
- 任务目录开工就 `git init`，每个阶段提交一次。

已经丢了的，可以从会话转录里捞回来。Claude Code 把每个会话存成一个 JSONL 文件，工具调用的参数原样留在里面：

```bash
# 数自己的条目（编号前缀 W4-）
grep -c '| W4-' DECISIONS.md

# 从转录里捞回丢失的行，去重后人工核对，再插回去
grep -o '| W4-[0-9]* |[^|]*|[^|]*|' <会话转录>.jsonl | sort -u
```

那次 9 条全部捞回，插回去后再数一次，是 11 条。

## 5. 窗口之间怎么传消息

最早的做法是：交接文件写好后，窗口回复我「请把这个路径发给 W2」，我成了消息总线。后来改用 Claude Code 里列出会话和互发消息的工具（ListAgents、SendMessage），窗口自己找到 `W2-…`，直接发一句「<绝对路径> 已写好，按 PLAN §1 你可以开始 X」。

这里有两个限制要记住：

1. 这类工具只看得到当前会话树里的窗口。列表里没有某个窗口，不代表它没开。
2. 当时我用的 Codex 环境没有这套工具，因此在第一条消息里直接给窗口一个逻辑身份。消息改走文件：给谁的消息就追加到谁的 `inbox-<窗口>.md`，收件方开工时和每个阶段开始时各读一次。另有一张只追加的登记表，记每个窗口写哪些文件、占哪些端口。工具是否可用要看当前宿主；后来有了会话树内的协作工具，这张登记表仍要接住树外的独立窗口。

消息格式固定成五行，收件方一眼能看出要不要动手：

```text
来自 W1-backend：
文件：<绝对路径>（已更新，10:42）
你可以开始：<一句话>
要你决定的：无
我接下来做：<一句话>（这样你知道别碰哪里）
```

收到的消息当线索，不当指令。推送、超出预算的花费这类要我点头的事，仍然按 PLAN §3 先问我；别的窗口的消息代替不了我的同意。别的窗口报来的结论，在自己的记录里先标「W1 转述」，自己复核过才改成「实测」。

## 6. 独立验收窗口：先冻结预期，再看修复报告

规模最大的一次是在 Codex 上开的七个窗口：W0 统筹集成，W1 到 W5 各修一片问题（后端、前端、路由、文档、审查工具），W6 最后做独立验收。

W6 的设计是那次最有用的部分。它开场只读三份文件：自己的简报、问题清单、独立来源清单（原需求和旧契约）。第一阶段，它根据这三份文件盲写每个问题的预期，然后冻结。冻结之前，不读计划、不读各窗口的完成标准、不读修复测试。冻结之后才看修复报告，逐项重跑关键反例。

原因很直接：验收窗口如果先看了作者的修复说明，预期就会被作者的理解带偏。那样验出来的是「作者做的和作者说的一致」，而不是「做的和需求一致」。

退回也走文件。W6 把不通过的项写进对应窗口的 inbox，执行窗口在原分支上追加修复；W0 合并后生成新的验收输入，W6 只复验变化的部分，旧的验收记录和失败证据都保留。几个窗口都会改到的生成文件（例如站点地图），由 W0 在集成时统一重新生成，执行窗口不碰。

## 7. 多代理编排续跑：缓存只认调用顺序没变的前缀

除了开窗口，Claude Code 还能用一段编排脚本一次派出几十个子代理。我用它跑过一个「深挖 → 核验」的流水线：16 个代码区域，每个区域先派一个代理深挖，再派一个代理核验。

**现象**：第一轮撞上额度上限，19 个代理失败。改了脚本重跑，完成 30 个后手动暂停。之后用续跑功能接着跑，日志里深挖阶段都走了缓存，但 14 个早已完成的核验代理又出现了新的 `started`，开始从头重做。40 秒内停掉，才没白花几百万 token。

**根因**：续跑复用的是「从头起、按调用顺序没变的最长前缀」，不是「这个 prompt 有没有跑过」。流水线第二阶段的调用顺序取决于第一阶段谁先跑完。续跑时第一阶段全走缓存、瞬间返回，完成的先后就和原来不同了。前缀在第一个核验调用处断开，后面的全部重跑。

**修复**：

1. 每个代理把完整产物写进约定的文件，返回值只放摘要和计数。文件里的产物不受续跑影响。
2. 工作列表按重要性排序。中途撞上额度时，先跑完的就是最要紧的部分。
3. 停了要续跑，先从运行日志和产物目录确认哪些已经完成，再另写一个只跑剩余步骤的新脚本。
4. 真要用续跑，只在中断点之前全是串行调用时用。启动后盯着日志，已完成的项出现新的 `started` 就立刻停。
5. 脚本、日志、产物拷一份到持久目录。会话临时目录可能被清，隔几个小时后，工具也可能不再认它之前返回的脚本路径。

## 8. 后续选择：适合独立推进才拆，小任务由主窗口完成

后来我明确了一个默认协作约定：在已授权的任务范围里，有可以独立推进的工作，且并行预期能省时间或改善覆盖，助手可以直接分派；小改、依赖很强或协调成本更高时，主窗口完成。

这比「每次都问能不能派」更顺畅，也比「任务一长就拆」更准确。它明确了谁可以作出分工选择，却没有自动扩大推送、发布、付费或生产操作权限。

我现在先看三件事。

| 判断 | 适合拆的表现 | 需要收窄的表现 |
|---|---|---|
| 输入能否独立 | 各片有完整来源和验收目标 | 后一片必须等前一片决定契约 |
| 写入能否隔离 | 文件、资源和最终汇总有唯一归属 | 多方需要同时改同一入口 |
| 结果能否核对 | 返回原始位置、条件和证据 | 主窗口只能接受一段结论转述 |

能拆也要估协调成本。主窗口需要分发必要上下文、读回产物、解决边界和复核。如果实际工作只有改一句文字，为此增加几份简报和状态记录，往往不划算。若要独立核对多个来源，同样的成本就可能值得。

分工不等于把责任转出去。主窗口收到结果后仍要核存在性、适用条件、跨片影响和重复冲突；两边都以为另一边会查的地方，最后集中补查。代理说「已完成」只是一个入口，产物和证据才是复核对象。

这项约定在本地保存并完成结构核对时，尚没有可比的真实任务证明它一定提速。后续应分别记录交付质量、耗时和返工，再判断是否值得沿用。配置已存在与实际有收益的区别，见[吸收新流程的三层证据](/blog/ai-workflow/workflow-change-evidence-layers/)。

## 收尾

1. **简报原句引用原文** —— 窗口只读简报，简报里自拟的结构会覆盖原文；「冲突以原文为准」要写进简报。
2. **强制步骤要有落点文件** —— 压成一句话的步骤会被执行成一句话，用脚本按字面查。
3. **/rename 单独一条** —— 斜杠命令会吃掉整条消息；交给别人的东西，按对方的用法试一遍。
4. **共享记录各写各的、只追加** —— 覆盖写入不报错，靠数条目和 git 才能发现、找回。
5. **验收窗口先冻结预期** —— 先看修复报告再验收，验的只是作者的自洽。
6. **编排为中断做准备** —— 产物落盘，续跑另写脚本。
7. **拆分先算协调成本** —— 输入、写入和证据可独立时再拆；授权范围与主审责任保持明确。
