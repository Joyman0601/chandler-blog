> 一句话总结：从会话记录汇总当天做了什么，切日期按本地时区、按整段会话判断就够了；真正费事的是归类规则。「从第一次碰到到最后一次碰到全归到笔记类」会把中间的工作调用一起卷走，只看 cwd 会把下一件事算到上一件事头上，按「提到」整轮归类会误伤引用路径的工作简报。这三处都是拿新旧两版脚本对同一批历史回放才发现的，汇总数字本身看不出来。

## 0. 起因：现成的检索工具切不出「今天」

我一天里会开好几个 Claude Code 窗口，到晚上想要一份「今天按时间做了哪些事」的清单，再逐条核对。最开始用的是一个现成的会话检索工具，9 月 22 日那天就发现它不合用（实测）：

- 列表按会话的**最后活动时间**排序，只显示 10 条。那天实际有 8 个会话在活动，列表里却混着前一天的会话，要一个个点开才知道哪些是今天的。
- 会话常常跨零点，有的前一天下午开、今天一直在用。按「会话属于哪一天」分不出来，得按每条记录的时间分。

于是我让 Claude 写了一段 Python 直接解析会话的 JSONL 文件，第二天把它做成了一个 skill：一条命令列出当天每个会话的时间段、消息数和时间线，按项目分好组，写汇总的时候照着它核。

同一天还碰到一件事，后来成了这个 skill 的第一条规矩：会话里说的状态，是说那句话时的状态。有个会话里写着某个 PR 还开着，我拿 `gh` 一查，它早就关了。所以脚本列出来的只是线索，状态类的说法要回到 git、`gh` 上重新查（实测）。这个 skill 的核心是**校对**，排版是次要的。

## 1. 按本地日切：先整段判断，再按日期取

Claude Code 的会话记录每行一个 JSON，带 `timestamp`，是 UTC 时间（结尾带 `Z`）。切日期只要两步：时间先转成本机时区再取日期；归属类的判断（这个会话归哪个项目、某一轮算不算笔记库维护）按**整段会话**做完，最后才按日期取当天的记录。这样一轮跨零点的对话不会被切成两半各判一次。

跨天的会话比我以为的多。用下面的脚本数了四天（实测）：

| 日期 | 当天有记录的会话 | 其中更早就开了的 |
|---|---|---|
| 10-05 | 8 | 5 |
| 10-07 | 18 | 8 |
| 10-15 | 11 | 1 |
| 10-20 | 2 | 1 |

最小可用的版本是这样的：

```python
import json, sys
from datetime import date, datetime
from pathlib import Path


def local_day(ts: str) -> date:
    # 记录里的时间是 UTC（结尾带 Z），先转成本机时区再取日期
    return datetime.fromisoformat(ts.replace("Z", "+00:00")).astimezone().date()


def is_spoken(rec: dict) -> bool:
    """人打的字或助手说的话；工具调用、工具结果、系统记录都不算。"""
    if rec.get("type") not in ("user", "assistant"):
        return False
    content = rec.get("message", {}).get("content")
    if isinstance(content, str):
        return bool(content.strip())
    return any(b.get("type") == "text" and b.get("text", "").strip()
               for b in content or [] if isinstance(b, dict))


def day_report(root: Path, day: date):
    for f in sorted(root.glob("*.jsonl")):
        recs = []
        for line in f.open(encoding="utf-8"):
            try:
                r = json.loads(line)
            except json.JSONDecodeError:
                continue
            if "timestamp" in r:
                recs.append(r)
        today = [r for r in recs if local_day(r["timestamp"]) == day]
        if not today:
            continue
        start = min(local_day(r["timestamp"]) for r in recs)
        spoken = sum(map(is_spoken, today))
        times = sorted(datetime.fromisoformat(r["timestamp"].replace("Z", "+00:00")).astimezone()
                       for r in today)
        first, last = times[0], times[-1]
        note = "（前一天开的）" if start < day else ""
        print(f"{f.stem[:8]} {first:%H:%M}-{last:%H:%M} 说话 {spoken} 条 / 原始 {len(today)} 条{note}")


if __name__ == "__main__":
    day_report(Path(sys.argv[1]).expanduser(), date.fromisoformat(sys.argv[2]))
```

```bash
python3 day_split.py ~/.claude/projects/<项目目录> 2026-10-05
# xxxxxxxx 22:20-22:56 说话 12 条 / 原始 527 条（前一天开的）   ← 会话 id 已替换
```

「前一天开的」只说明这个会话的第一条记录早于当天，可能是前一天，也可能更早。

**消息数要写清口径。** 9 月 23 日第一次跑的时候，同一天的「纯文本消息」是 667 条，「原始条目」是 3084 条，差 4.6 倍（实测）。上面这个最小版本把所有带时间戳的记录都算进原始条目，三天跑下来差 13–21 倍（实测）。两个数都对，只是数的东西不一样。所以脚本两个数都打，并在输出里提醒一句「两种口径能差好几倍」，免得写汇总时拿一个去和另一个比。

## 2. 第一版归类规则：从第一次碰到到最后一次

时间线按项目分组，每件事挂在它所属的项目下。另外有一类单独归：我平时干活时，会顺手往一个个人笔记库里记坑、记做法，这些笔记库的维护归到「笔记」一类，不算进工作项。会话开在哪个项目目录里，整段就归哪个项目，这一条没出过问题。麻烦的是工作会话里夹着的笔记库调用：它们和工作调用混在同一轮里，要单独挑出来。

第一版写得很直接：一轮对话里，从第一次碰到笔记库的工具调用，到最后一次调用的结果返回，这一段都归到笔记类。如果这段之外没有别的工具调用，这一轮整轮归到笔记类。

9 月 29 日我给笔记库加了一个 hook：开始做事前自动提示相关条目。从那以后，「开头读一条笔记、结尾记一条笔记」成了常态。第二天对数时发现不对（实测）：

- 拿改前改后的脚本对同一天各跑一遍，那天 5457 条原始记录里，约 960 条工作记录被归进了笔记类。
- 其中一个会话在工作时间线里显示为「22:50–22:50，7 条」，实际一直做到 23:59，有 838 条。

区间的两个端点用的是同一个判据，「碰到了笔记库」，没有区分查和写。查阅会出现在一轮的任何位置，开头查一次、结尾写一次，区间就被拉到整轮那么长，中间的工作调用全进了区间。而且这个问题在加 hook 之前就有（手动先查再记的那几轮），只是没人对过数。脚本不报错，汇总数字看起来也合理，所以一直没被发现。

改法：**只读的查阅按点归类，只划走那一次调用和它的结果；只有写入类的调用才界定区间。**

## 3. 「查阅」按用途认，不按读写认

10 月 5 日又出了一次（实测）。那一轮开头，我先按「查清单」的模式调了笔记库的 skill，又用 `cat` 读了两本手册，结尾记了两条。当时的脚本只把「读文件工具」和「检索脚本」认作查阅，skill 调用和 shell 里的 `cat` 都没认出来，于是它们又成了区间起点：22:20 到 22:53 这半小时、174 次工作调用整段从工作时间线上消失。

补认这两种查法之后，反方向的问题紧跟着冒出来：记录流程的开头也是只读的，要调 skill、读模板、读脱敏规则。这些被认成查阅以后，区间起点往后挪，起点之前那几句记录旁白（「先按流程查重…」「没有相近的条目，新建两条」）被算成了工作项。

所以「查阅」不能按读还是写来认，要按这次调用是为了什么：

| 这次调用 | 归类 | 划到笔记类的范围 |
|---|---|---|
| 读文件工具、检索脚本读笔记 | 查阅 | 只划这一次 |
| 按查阅模式调笔记库的 skill | 查阅 | 只划这一次 |
| shell 只读命令读条目（`cat`、`grep`、`sed -n`，且没有写文件的重定向） | 查阅 | 只划这一次 |
| 按记录模式调 skill；读模板、读规则文件 | 写入类（写入的准备） | 划区间 |
| 新建、修改条目 | 写入类 | 划区间 |

判断一轮里哪些调用归到笔记类，核心逻辑很短：

```python
def notes_calls_in_turn(calls):
    """calls：一轮里的 [(下标, 类别)]，类别是 None（工作）、"lookup"（查阅笔记）、"write"（写入类）。
    返回 (归到笔记类的下标, 是否整轮归到笔记类)。"""
    out = {i for i, kind in calls if kind == "lookup"}         # 查阅只划走那一次
    writes = [i for i, kind in calls if kind == "write"]
    if not writes:
        return out, bool(calls) and all(kind for _, kind in calls)
    lo, hi = writes[0], writes[-1]                             # 写入类才划区间
    work_outside = any(kind is None and not lo <= i <= hi for i, kind in calls)
    out |= {i for i, _ in calls if lo <= i <= hi}
    return out, not work_outside


# 开头查一次、中间干活、结尾记两条：只划走 0、8、9
print(notes_calls_in_turn([(0, "lookup"), (1, None), (5, None), (8, "write"), (9, "write")]))
# ({0, 8, 9}, False)
```

写入类仍然按区间，是因为一次记录流程（准备、写、写完）中间那几句旁白也属于笔记库维护，按点划会把它们留在工作项里。如果你的场景里写入本身也会分散在一轮的两头，就得给区间再加一个条件，比如两次写入之间隔了工作调用就断开。

## 4. cwd 说明不了这条命令在干什么

会话记录里每条工具调用都带着当时的 cwd。第一反应是拿它判断归属，结果两个方向各错了一次（实测）。

**漏认。** 原规则只认「工具输入里出现了笔记库的路径」。shell 停在笔记库目录里，用相对路径改它的脚本（`python3 _ops/scripts/x.py`、`tail _ops/state/x.log`），命令里看不到完整路径，整整一个改笔记库的会话出现在了工作时间线里。

**误归。** 补成「cwd 在笔记库里的 Bash 调用都归笔记类」之后，多天回放对照下来，三段工作被归错：

- 记完一条笔记，shell 停在库目录，下一条命令是 `cd <工作仓库> && …`；
- 停在库目录里，用检索工具查之前的会话；
- 停在库目录里，处理临时目录下的文件。

根因是 cwd 是 shell 的状态，不是命令的属性。长会话里 cd 到哪儿就停在哪儿，下一件事未必先 cd 回去。改成三层判断：

1. 命令以 `cd X` 开头：按 X 算，不管当时停在哪。
2. 没有 cd，但命令里带了指向别处的绝对路径（`/`、`~/`、`$HOME/` 开头）：按这些路径算。
3. 只有相对路径或不带路径：这时才看 cwd，而且分两种目录：
   - 其他个人项目（做工作时 shell 很少停在那里）：直接按 cwd 算。一轮开始时 cwd 就在那个项目里也算，因为那种轮次常常只有一句「继续」，没有任何路径。
   - 笔记库（记完一条就会停在那里）：只有相对路径指向它特有的子目录，或者是操作它本身的 `git`（不带 `-C`），才算。

写成代码（目录名是示例）：

```python
import re

NOTES = ("notes/",)                                        # 个人笔记库的路径片段（示例）
NOTE_DIRS = re.compile(r"(?<![\w/.])(entries|_ops)/")     # 笔记库特有的子目录（示例）
ABS = re.compile(r"(?:~|\$HOME)/[^\s'\";|&)]*")


def works_in_notes(command: str, cwd: str) -> bool:
    """一条 Bash 调用是不是在维护笔记库。cwd 是 shell 当时停的目录。"""
    m = re.match(r"\s*cd\s+(\S+)", command)
    if m:                                       # 1. 以 cd 开头：按 cd 的目标算
        return any(p in m.group(1) for p in NOTES)
    paths = ABS.findall(command)
    if paths:                                   # 2. 带绝对路径：按这些路径算
        return any(p in x for x in paths for p in NOTES)
    if not any(p in cwd.rstrip("/") + "/" for p in NOTES):  # 3. 只有相对路径：这时才看 cwd
        return False
    # 停在笔记库里：相对路径指向它特有的结构，或者是操作库本身的 git，才算
    return bool(NOTE_DIRS.search(command) or re.match(r"\s*git\s+(?!-C\b)", command))
```

`ABS` 这里只认 `~/` 和 `$HOME/`，真用时把 `/` 开头的绝对路径也加进去。我拿这几条用例跑过（实测）：

| 命令 | 当时的 cwd | 判定 |
|---|---|---|
| `cd ~/work/repo && git status` | `~/notes` | 工作 |
| `python3 _ops/scripts/x.py` | `~/notes` | 笔记库 |
| `git log -3` | `~/notes` | 笔记库 |
| `git -C ~/work/repo log -3` | `~/notes` | 工作 |
| `cat ~/notes/entries/a.md` | `~/work/repo` | 笔记库 |
| `go test ./...` | `~/work/repo` | 工作 |

第一次写这段时我自己也踩了个小坑：测试用例里 cwd 写成 `~/notes`，没有结尾的斜杠，匹配 `notes/` 就落空了，三条该判笔记库的全判成了工作。所以第 3 步先给 cwd 补一个斜杠再匹配。

同一个坑后来在 hook 里又出现了一次（10 月 8 日，实测）。笔记库的监听 hook 规定「cwd 在笔记库里就不匹配」，因为那时多半在记笔记。刚记完一条，下一条命令 `cd <别处> && …` 明明是去干活，hook 拿到的 cwd 仍是库目录，整条被跳过。改成先看命令里最后一次 `cd` 的目标，没有 cd 才用 cwd。

## 5. 「提到」不等于「在做」

为了不让「我去笔记库查一下…」这类旁白留在工作时间线里，还有一条规则：我发的那句话里提到了笔记库的路径，整轮归到笔记类。

10 月 9 日发现它误伤得很厉害（实测）。那几天我在多窗口并行干活，每个窗口的开场提示词固定写一句「先读笔记库的索引」。结果这些窗口的第一轮，连同之后只说「继续」的轮次，全被归进了笔记类：10 月 7 日的工作时间线少了 1,377 行，10 月 8 日少了 187 行，那几天的汇总都得打开「显示全部类别」的开关手工捞回来。

改法：一句话里同时出现了工作路径（工作仓库或任务目录），就不按「提到」整轮归类，只把真正读写笔记库或个人项目目录的那几次调用归过去。会话开在个人项目目录里也同理，先看开场那句话里有没有工作路径。

另外两条兜底规则一直留着：一个会话里说过话的轮次有六成以上是笔记库维护，整个会话归到笔记类；输出工作时间线前，提到笔记库路径的行也归到笔记类。

## 6. 每次改规则：新旧两版对同一批历史各跑一遍

上面三次问题，没有一次是脚本报错发现的，全是拿新旧两版对同一批历史回放、逐行对出来的。汇总数字看起来都合理，只看数字对不出来。后来我把这条做法记进了笔记库；第三次改规则时，自动提示的 hook 先拦了我一下，提醒先做改前改后对照。

我现在每次改归类规则都这么做：

```bash
# 改之前先留一份旧版（我第一次改时目录还没进 git，旧版只存在临时目录里，后来才 git init）
cp sessions.py /tmp/sessions_old.py
# …改 sessions.py…
for d in 2026-09-27 2026-09-28 2026-09-29 2026-09-30 2026-10-01; do
  python3 /tmp/sessions_old.py --day "$d" --timeline > "/tmp/old-$d.txt"
  python3 sessions.py --day "$d" --timeline > "/tmp/new-$d.txt"
  echo "== $d 移出 $(diff "/tmp/old-$d.txt" "/tmp/new-$d.txt" | grep -c '^<') 行，补回 $(diff "/tmp/old-$d.txt" "/tmp/new-$d.txt" | grep -c '^>') 行"
  # 补回工作时间线的行里应该没有笔记库那一类：搜一遍笔记库的路径和关键词
  diff "/tmp/old-$d.txt" "/tmp/new-$d.txt" | grep '^>' | grep -iE 'notes/|笔记' && echo "  !! 有笔记类的行被算进了工作项"
done
```

`--day`、`--timeline` 换成你自己脚本的参数。判定标准是三条：

1. 没有新行为的日子，新旧输出应该逐字相同。
2. 有差异的日子，移出工作时间线的行逐条看，应该全是笔记库维护；补回的行逐条看，应该全是工作项。
3. 补回的行里搜一遍笔记库的关键词，应该是 0。

几次改动的回放结果（实测）：

| 改动 | 回放范围 | 结果 |
|---|---|---|
| 查阅按点归类 | 09-24 到 09-30 | 09-24 到 09-28 输出逐字相同；29、30 两天只有统计数变了，输出里没有笔记库的词 |
| 补认 skill 和 shell 查阅、cwd 三层判断 | 09-27 到 10-05 之间的五天 | 移出的行全是笔记库内容，补回的行全是当天的前端工作 |
| 提到工作路径时不整轮归类 | 10-06 到 10-08 | 补回 1,377 行和 187 行，笔记库关键词 0 条，没有任何行被移出 |
| 多登记一个个人项目目录 | 最近 10 天 | 前 9 天逐字相同；当天唯一的差别是正在改规则的那个会话整段归到了新登记的目录，符合预期 |

## 7. 脚本之外还有一层人工

脚本输出的是候选清单，不是成品。写汇总时我还会再过一遍：归错类的行改过来；会话里说的「已推送」「还开着」这类状态，回 git 和 `gh` 上重新查；拿不准一段算不算工作项，就回会话原文看那一轮实际改了哪些文件。

做成 skill 时我把这一层也写进了步骤，排在「跑脚本」之后、「写汇总」之前。规则写得再细，也有它没想到的情形，人工这层就是给这些情形兜底的。

## 收尾

能直接拿走的几条：

- 切日期：时间先转本机时区；归属判断按整段会话做，最后再按日期取。
- 消息数两种口径都打，并写明各自数的是什么。
- 归类规则里出现「从 A 到 B 之间全部归到某类」时，问一句：A 和 B 会不会分散在两头、中间夹着别的。只读查阅按点归类，写入才划区间；「查阅」按用途认。
- 用 cwd 判断命令归属之前，先想 shell 会不会停在上一件事的目录里；按「cd 目标 → 绝对路径 → 相对路径特征」三层判断。
- 「提到某个目录」和「在那个目录里干活」是两回事；文字里同时出现工作路径时，不按提到整轮归类。
- 改归类规则，就用新旧两版对多天历史跑 diff，逐行看移出和补回的内容，再搜一遍关键词。只看总数对不出来。

这类脚本最难的不是解析格式，是给「这件事归哪一类」划界线。每加一个会在任意时刻触发的新行为（自动提示、新的 hook、新的开场提示词），都要回头看一眼下游按它的痕迹做归类的脚本。相关的 hook 写法见[用 hook 往对话里注入上下文](/blog/ai-workflow/claude-code-hooks-inject-context/)。
