> 一句话总结：验收者的价值在于独立。开发会话说「验过了」的一律重跑；「应该看到」要能指到测试、规范或代码；在被污染的环境里得到的缺陷，先在规范配置下重跑；每条结论附预期依据、实际结果和证据路径，缺一样就不算通过。

## 0. 起因：同一个人，换一顶帽子

我的日常工作里，同一个模型接入经常由两个会话分别处理：一个当开发者，把上游模型接进主后端网关、前端控制台的模型页和文档站的 API 页；另一个当验收者，在开发完成后复核这三个仓库。两个会话都是我带着 Claude Code 在跑，区别只在角色。

验收会话开工时，手里通常有一堆开发会话留下的东西：契约文件、数据安装脚本、调研存档，还有一套脚手架（临时库的表结构、种子数据、mock 上游、截图脚本），外加一份写明「已拍板决定」和「已知已接受项」的验收提示。

最大的诱惑是直接拿脚手架跑一遍，全绿就交。这样做等于继承了开发者的全部盲区：mock 上游只模拟了开发者想到的响应，种子数据只覆盖了开发者想到的情况。所以我给验收定的第一条原则是：脚手架只是工具，结论要自己跑。开发会话说「验过了」的，一律重跑。

有一次验收一个语音模型的接入，开发会话交来时自测全绿。独立验收查出 25 个问题，其中 2 个阻断项，有 1 个还是上一轮修复引入的。这两个阻断项都不在开发者的测试矩阵里。这篇讲那几轮验收里慢慢固定下来的做法。

## 1. 开工前：清单从规范和 leader 的修正里合成

验收清单不能凭印象列。我的做法是开工前合成一份带编号的清单文件，后面每条证据都回指编号。来源有三处：

1. **团队的权威规范**：后端接入规范里的边界情况、验证步骤、数据库约定，前端的页面规范。
2. **自己积累的坑**：过去踩过、记下来的检查点，挑和这次相关的。
3. **leader 改过的同类实现**：读他在同类页面上的评审意见和修正提交，把「他挑问题的方式」变成本页的检查项。leader 挑问题的方式，就是这次验收的真实基准。

还有一件开工前就要做的事：先把预期冻结下来，再去看开发者的期望值。有一次验收一个站点地图生成器，验收会话在看开发者的测试之前，就把「应该出现的 103 个文件」存成了一份清单。之后的每轮复验都对照这份冻结清单，不拿作者测试里的 expected 当预期。原因很简单：作者的 expected 和实现出自同一个人的理解，用它当预期，只能证明两者一致。

## 2. 分轨并行：子代理各管一轨，起服务那轨自己做

跨三个仓库的验收工作量很大，我把它拆成几条轨：

| 轨 | 谁做 | 看什么 |
|---|---|---|
| 文档 | 子代理 | 参数、限制、错误码和后端实际校验是否一致 |
| 前端 | 子代理 | 页面规范逐条、多语言、草稿与深链、价格展示 |
| 跨仓一致性 | 子代理 | 同一个数字、名字、阈值在三个仓库里是否一致 |
| 后端 diff 审查 + 测试基线 | 子代理 | 改动范围、存量失败和新增失败 |
| 后端数据脚本与端到端 | 主会话自己 | 要起服务，最需要连续判断 |

给子代理的指令里写死几件事：只读、不改仓库；临时文件放在哪；结束时按 PID 和端口收拾自己起的进程；报告用什么格式。

子代理报回来的每条缺陷，主会话都用自己的端到端 runner 再发一次，拿到出站 body 或响应，确认了才写进报告。报告里还要标明「本次引入」还是「存量」，存量的附基线复跑证据。子代理的发现是线索，不是结论。

并行也有代价。有一轮助手为了测一个 provider 的队列派发，把网关的派发模式整体切成了队列模式。结果其他 provider 的任务也进了队列，而队列另一头没有对应的消费者。并行跑的前端轨那一轮真实创建全部超时，只能重跑。现在改派发模式、重启网关之前，先确认并行的轨道没有在用它；只测一个 provider 时，只把它列进队列名单。

## 3. 后端：结论要从出站字节和账本里来

后端验收最容易被骗的地方，是拿网关日志或内存里的结构体当证据。网关在请求上补默认值、整流、合并参数，写在结构体上的东西不一定真进了发给上游的 body。所以我的 mock 上游只做一件事：把每个入站请求体原样落盘。出站 body 一律以这里的字节为准。

```python
# mock_upstream.py：每个入站请求体原样落盘；usage 由环境变量控制，方便测分档和缓存
import json, os, time
from http.server import BaseHTTPRequestHandler, HTTPServer

OUT = os.environ.get("MOCK_DIR", "/tmp/mock-bodies")
os.makedirs(OUT, exist_ok=True)

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        name = f"{time.time_ns()}{self.path.replace('/', '_')}.json"
        with open(os.path.join(OUT, name), "wb") as f:
            f.write(body)                                   # ← 出站 body 以这里为准
        usage = {"prompt_tokens": int(os.environ.get("MOCK_IN", "1000")),
                 "completion_tokens": int(os.environ.get("MOCK_OUT", "200"))}
        data = json.dumps({"id": "mock-1", "usage": usage,
                           "choices": [{"message": {"role": "assistant", "content": "ok"}}]}).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

HTTPServer(("127.0.0.1", 18080), Handler).serve_forever()
```

在它上面写一个小 runner，每个用例打印一行：HTTP 状态、上游被调用了几次、上游收到的关键字段、结算日志、用户冻结额。矩阵的维度大致是：

- 端点 × 流式 / 非流式；
- 每一种整流变体：关闭某功能的每种写法、别名、预算档位，以及 `null`、空串、大小写、类型错误；
- 负向用例：缺价、上游做不到的字段、写错模型名；
- 同族的旧模型抽一条，看它的出站 body 没有被这次改动带变。

计费按契约手算。把 mock 的 usage 做成环境变量可配，跑一遍常规用量、一遍超过分档阈值的用量、一遍带缓存写入的用量，和契约的分角色单价逐笔对到个位。单价对、阈值对、取整方式不对，照样会差几个最小单位。

还要拿假 key 打一次真实上游：先直连每个主机、每个端点，拿状态码、错误体和请求 id 头；再经网关打，看用户拿到的文案、日志里有没有上游请求 id、第一条渠道有没有被自动禁用、最后一条渠道有没有被安全闸挡住。这一步零花费，却经常查出「上游原文直接透给了用户」这类问题。

数据安装脚本的「重跑不覆盖运维改过的 key」，要靠真做来证明：先手工把 key 改掉、启用一条渠道，再原样重跑脚本，看 key 和启用状态是否原样保留。读 UPDATE 语句的列清单推出来的结论不算。表结构要用生产形状的库（细节见[要进生产库的 SQL](/blog/billing-regression/sql-on-prod-shaped-db/)）。

回到开头那两个阻断项：

- 一个是「先展开再查长度」：接口允许用户传一组级联替换规则，长度上限按替换后的文本算。一个不到 200 字节、16 项 `{"a":"aa"}` 的请求，让网关构造出 3.2 亿字符，耗时 4 秒，内存从 197 MB 涨到 785 MB，最后才返回那个正确的 400。修复后在每一步替换后判长度，同一个请求 57 ms 返回 400，内存不变。
- 另一个是「通用的附加参数覆盖了已校验的字段」：严格校验过的字段，被附加参数里的同名键改回了非法值，并且真的发到了上游。

这两个用例都不在开发者的矩阵里，一个是放大输入，一个是「顶层合法 + 附加参数里放同名非法值」。网关改写请求时这类漏洞的完整清单，另一篇[网关改写请求的几个漏洞](/blog/model-onboarding/gateway-outbound-body-pitfalls/)讲得更细。

## 4. 「应该看到」要能指到来源

后端之外，还有一部分验收必须交给人在浏览器里点：真实登录、真实生成、肉眼看排版。助手会写一份步骤，每步带一句「应该看到」，我照着执行。助手第一版的预期是从「修了什么」推出来的，我执行时就有好几处和实际不符：

1. **草稿被覆盖**。步骤是「在 B 档填草稿 → 新开标签页打开 A 档深链 → 再打开 B 档」，预期「显示刚才的 B 档草稿」，实际是 B 档的示例词。草稿在浏览器存储里只存一份，键固定；负责保存的 effect 在组件挂载时也会执行，新开的 A 档页面一加载，就把 A 档的首屏状态写进了同一个键。规范只要求「草稿所属的档和落地的档不一致时整份不套用」，没要求保留另一档的草稿。这不是缺陷，是预期写错了。
2. **红字出现的时机**。步骤写「填非法图片地址，应出现红字」。实际上按接口契约的校验只在点「生成」时跑，而且在这之前要先登录；输入时只检查 JSON 语法。
3. **入口的显示条件**。步骤写「在任务日志里点回放按钮」。实际只有已结束的任务才有这个按钮。后来又发现入口不在列表行上，而在任务详情弹窗底部，文案也和验收提示里的叫法不同。
4. **守卫的输入有几个来源**。步骤写「贴链接加入的视频，前端读不到时长，超长也不会被拦」，依据是只看到时长回调挂在上传路径上。实际组件对链接素材也会用 `<video>` 元素探测时长，守卫照样触发。守卫读的那份状态有几个生产者，要把 setter 全部 grep 出来。
5. **显示值的取整**。核用量页金额时，助手把预期写成「四舍五入到 6 位后与结算金额相同」，只拿一两条举例核过就判了通过。后来按前端格式化函数逐条重算，才发现页面是末位向上取（函数注释写明：显示值不能小于实扣），有 3 条差了一个最小单位。

还有一次反过来：我报「切到图生视频，默认提示词却是 a cat」。查下来是助手上一步给的验收步骤里用了这个提示词，同档草稿被正常恢复了。也不是缺陷。

**根因**：预期是从修复描述推出来的，没去核实现的时序和条件。

**修复**：每条「应该看到」旁边标上来源：测试用例名、规范条款或代码行号。标不出来源的，先读代码回答三个问题：

- **写入时机**：持久化是挂载就写，还是用户改了才写？存一份还是按维度分开存？
- **触发时机**：校验在输入时跑还是提交时跑？前面有没有登录、鉴权这类更早的拦截？
- **显示条件**：按钮、提示、徽标在什么状态下才渲染？文案原文是什么（找到组件和它的多语言键）？

执行时和预期不一致，先按这三个问题读代码，再判断是缺陷还是预期写错。报告里把这两种分开列，各附判断依据。

## 5. 被污染的环境里得到的缺陷，先在规范配置下重跑

那份 25 个问题的报告里有一条高优先级：worker 进程被 SIGKILL 硬杀后，处理中的任务 16 分钟无人接管，17 分钟后才由网关超时兜底失败。复现脚本和原始输出都附着，看起来很扎实。

但同一份报告自己记着：那一轮的派发模式被错设成了全量队列，其他 provider 的任务都进了没有消费者的流。网关对队列任务的对账（静默一段时间后重投、绝对超时后接管）是全局扫描，一堆孤儿任务会改变扫描行为和日志。在那种环境下测到的「不接管」，不能归因到被测的这个 provider。

动手改通用的恢复逻辑之前，先按规范配置重跑：派发模式用本地，只把被测 provider 列进队列名单；创建任务 6 秒后杀掉 worker，每 30 秒记录一次：

- 队列里待确认条目的空闲时长和消费者；
- 新 worker 的恢复日志；
- 网关对这个任务的对账日志，以及每轮扫描「同步 N/M 个活跃任务」那一行。

两次结果一致：任务静默 120 秒后网关判定重投，新 worker 接手，分别在 147 秒和 138 秒完成，只计费一次。结论写「按规范配置未复现，不改代码」，并把继续追查需要的日志字段列出来。最后我接受了「硬杀后最长停顿约 120 秒」作为设计口径，没有去改一段影响所有队列 provider 的通用逻辑。

判断规则：一条缺陷如果出自报告自己都标注过「那轮环境有误」的会话，它的复现步骤就不可信。先带观测按规范配置重跑，再决定要不要改代码。

## 6. 结论三样齐：预期依据、实际结果、证据路径

两周后有一次复查，助手交出的报告写着「已核」「已测」「通过」，我逐项走查后指出了五类问题。助手回查执行记录，五类都属实：

| 问题 | 发生了什么 |
|---|---|
| 预期照实现写 | 旧页面默认是高一档，迁移重定向却跳到标准档；测试的 expected 和实现用的是同一张映射表，全绿 |
| 关键边界没测，用数量背书 | 参数矩阵几十条、整套几万项测试全过，但没有一条打到上限和上限加一；实测后发现平台上限是 token 和 UTF-8 字节两重 |
| 原始数据对，成品错 | 媒体探测的原始数据完整，报告生成脚本读错了一层结构，成品表整列显示「None×None」「无音轨」；脚本退出码 0 |
| 复核没重新取证 | 独立复核读了主审报告，核了文件名、行号和提交号，没有自己定预期、跑验证、读成品 |
| 待办当完成 | 能自己测的项归成了「只能交给 leader 测」，其中有的只是单次超预算，不是缺权限 |

这次之后，每个关键结论（通过、已修、已核、已实测、完成）都要附三样：

1. **预期依据**：独立于本次实现的来源，标明是实测、文档还是转述。比如旧版本的实际行为、官方契约原文、需求原文。
2. **实际执行结果**：命令和输出要点。
3. **证据路径**：存盘的输出文件，或者 `文件:行`。

缺一样就写「未验证：缺什么」，不进通过数。写成表大概是这样：

```markdown
| 结论 | 预期依据 | 实际结果 | 证据 |
|---|---|---|---|
| 提示词超上限 1 字节被拒 | 文档：平台限制 4000 UTF-8 字节（契约第 3 节） | 4000 字节 → 200；4001 字节 → 400 invalid_parameter | out/limits/run-03.json |
| 重定向保留旧页默认档 | 实测：改动前检出上旧页初始化选中的档 | 未验证：缺改动前检出的截图 | — |
| 第二张参考图参与生成 | 文档：最多 2 张参考图 | 只换第二张图（蓝色圆环 → 黄色三角），提示词不提颜色形状，两片各取 49 帧对照，输出跟着变 | out/ref2/frames/ |
```

能力类的结论，要对应到一个能观察的结果上。上表第三行就是一例：要证明第二张参考图真的起作用，得控制变量，只换第二张图，提示词里也不提颜色和形状，再逐帧对照。类似的还有：4K 看下载下来的原片分辨率、编码和位深，不看请求参数；联网搜索要看到检索结果和来源，不能只看回了 200；图片数量的边界要用不同的素材，重复的 URL 会被上游去重，充当不了边界。

预期本身也可能错，错了要当场撤回。有一次助手按官方写的总上下文窗口，推断一个百万 token 输入的请求应该成功，失败后还提了「查路由故障」。补查渠道一侧的文档才发现，渠道另外列了一个更小的输入上限：总窗口、输入上限、端点预算是三个不同的数。助手撤回了那条预期和待办，并在报告里写明撤回的原因。

成品由脚本生成的，生成器要对必填字段做断言，缺了就非零退出；生成后解析成品，和原始数据逐行对。对账脚本不能复用生成器的取数规则，同一条规则只会自证。

复核也有讲究。派复核子代理时，只给来源清单（任务原文、契约路径、旧版本入口、成品和原始数据的路径、可免费重跑的命令），不给主审的结论。我还让助手做过一次演练：派复核子代理时，要求子代理先把独立预期存成文件，再打开主审报告。第一轮只口头要求「先写预期」，它在第 15 次工具调用时就读了主审写的发现文件；第二轮要求先落盘，它在第 41 次调用存好预期，第 42 次才第一次打开报告。「先定预期、后看结论」要靠落盘文件加调用顺序来证明，自述不算。

收尾的状态只有三种：完成（有证据）、未完成（自己能做，做完再交）、受阻（写明卡在哪：预算多少、缺什么权限、谁有）。「列进待办」只是换了个地方写，事情没有做。这些核对是交付方的活，不能留给验收的人逐项走查来发现。

## 7. 环境还原：回到开工时的样子

验收会起很多东西：网关、mock 上游、前端 dev server、文档站预览、临时数据库容器、基线检出。结束时按清单来：

```bash
# 开工时记下每个仓库的 HEAD 和状态
for r in gateway console docs; do git -C "$r" rev-parse HEAD; git -C "$r" status --porcelain; done > /tmp/start.txt

# 结束时：按端口停自己起的进程（不要 pkill -f 宽匹配）
for port in 18080 3001 3002; do lsof -ti "tcp:$port" | xargs -r kill; done
docker rm -f accept-mysql 2>/dev/null
git -C gateway worktree list        # 子代理建的基线检出必须已删

for r in gateway console docs; do git -C "$r" rev-parse HEAD; git -C "$r" status --porcelain; done > /tmp/end.txt
diff /tmp/start.txt /tmp/end.txt    # 期望为空；HEAD 变了说明中途有人推了提交
```

HEAD 变了的情况真遇到过：一次验收进行到一半，前端分支上多了一个提交，改的正是一个共享组件。这时要在报告里标明哪些检查是在旧 HEAD 上做的、哪些在新 HEAD 上，机器检查在新 HEAD 上重跑。旧 HEAD 上的结论不能直接沿用。

## 8. 先问：旧实现能不能通过同一观察

后来两轮回归让我补上一个问题：即使结果与预期一致，观察项是否真的能区分修复前后？

一种情况是内部关联编号不一致，但系统还有另一个交易标识兜底。用户能查到任务，扣费与退款也正确，旧实现同样可能做到。修复目标是内部关联一致，验收却只观察了外部结果。

另一种情况是新增了上游账单纠偏。某个正常样本里，本地估算和上游实际值恰好一样。最终金额正确，证明不了新查账路径被执行，也证明不了不同值时会采用上游依据。

我把这类观察分成三层：

| 层次 | 说明什么 | 还缺什么 |
|---|---|---|
| 用户结果正确 | 创建、查询、成功或退款符合公开契约 | 内部目标是否改变 |
| 修复路径确实触发 | 有对应版本和执行轨迹 | 分支行为是否正确 |
| 能区分旧实现 | 构造新旧算法或新旧关联不同的样本 | 生产覆盖与适用边界 |

要验证查账纠偏，优先用「本地值与上游值不同」的可控夹具，再核最终采用哪一个。要验证关联编号，检查两端实际关联字段，而不是再生成更多相同的正常样本。

没有内部只读权限时，可以先完成公开契约回归，保存现有样本和具体缺口。结论写成「用户侧结果通过，内部关联待核」比笼统的「全部通过」更准确；也不需要为了缺一项权限停下所有本地检查。

类似问题还出现在测试桩里。手写一个符合作者猜想的成功响应，能让错误示例自测成功；应尽量让请求经过真实校验器，响应由真实构造器生成，再执行从最终文档提取的示例。输入桩、实现和 expected 都来自同一猜想时，独立跑一次也不够独立。

这几类证据要各司其职。版本证明不能代替执行轨迹，执行轨迹不能代替结果对账，公开接口成功也不能替代内部修复目标。新增用例之前，先找一个旧实现也会通过的解释，再决定缺哪条观察。

## 收尾

1. **脚手架只是工具** —— 开发会话说「验过了」的一律重跑，预期在看作者的 expected 之前冻结。
2. **证据看出站字节和账本** —— mock 上游落盘请求体，计费按契约逐笔手算到个位。
3. **子代理的发现自己复现** —— 拿到出站 body 或响应才写进报告，标明引入还是存量。
4. **「应该看到」标来源** —— 标不出来的，先读写入时机、触发时机、显示条件；缺陷和预期写错分开列。
5. **污染环境先重跑** —— 在规范配置下带观测重跑，复现不了就不改通用逻辑。
6. **结论三样齐** —— 预期依据、实际结果、证据路径，缺一样写「未验证：缺什么」。
7. **环境还原** —— 按端口和 PID 收拾，开工和收尾各记一次 HEAD。

回头看，这几轮验收里最值钱的发现，都来自「不信开发会话那一套」的地方：放大输入、同名键覆盖、换一种写法、换一个入口。下次当验收者，我会先问自己：这条结论如果是错的，我手里哪一份文件能证明它错？答不上来，就说明我还没有自己跑过。守卫测试那一侧的同类问题，见[守卫测试的三个要求](/blog/testing/guard-tests-three-rules/)。
