> 一句话总结：一条守卫测试有效，要拿出的证据是「把缺陷放回去，目标断言执行了、而且失败了」，不是「测试红过」或「测试全绿」。红可能来自别的断言、无效夹具或早退，绿可能来自没执行的代码、被测试准备掩盖的默认值或一份没人调用的副本。

## 0. 起因：三关都过了，还是会空转

之前写过一篇[守卫测试的三个要求](/blog/testing/guard-tests-three-rules/)：放到改动前的代码上会红，断言打在行为和值上，改共享函数时比对全部调用方。那之后我照着这三条要求 AI 编程助手，每个修复都附「旧版红、新版绿」的证据。

11 月头两周，独立复核和推送前的检查又抓出一批问题。它们都过了「旧版会红」这一关，问题出在更细的地方：

- 旧版确实红了，可红在前面一条无关的断言上，目标断言根本没执行；
- 新版确实绿了，可被测函数在前提缺失时提前返回，「没记录失败」是因为什么都没做；
- 测试准备阶段先改了全局默认值，测的是改过之后的分支；
- 测试读回结果用的函数，生产代码里没人调用。

这些错大多是助手写测试时犯的，由新上下文的复核子代理或推送前的检查脚本抓出来，我做的是追问和拍板。文中的数字来自当时保存的测试记录（实测），写这篇时没有重跑。下面按「红」「绿」「范围」三类讲，最后给一张清单。

## 1. 红了，但红在别的断言上

**现象**：主后端网关要下载用户给的文件。修复的目标是：响应头已经声明文件超过上限时，一个字节都不读，直接拒绝。助手写了守卫测试，放到旧代码上跑，红了，于是当作「已知超限零读取」有效的证明。

复核去看旧版的失败输出：测试先断言错误类型，旧代码返回的错误类型不对，测试就在这一行 `Fatal` 退出了。日志里其实打印了「读取了阈值加 1 个字节」，旧代码确实读了，可后面那条「读取量为 0」的断言没有执行。

**根因**：Go 的 `t.Fatal` / `t.Fatalf` 会立刻结束当前用例，之后的断言都不跑。「测试失败」和「目标断言失败」在这里是两件事。旧代码以后要是改成「错误类型对、但照样读了」，这条测试能不能抓住，当时的证据回答不了。

**修复**：把目标断言挪到最前面，前置条件用 `t.Errorf`（记失败、继续跑）而不是 `Fatal`。再放回旧代码，失败信息正好是零读那一行。

```go
func TestKnownOversizeIsRejectedWithoutReading(t *testing.T) {
	body := &countingReader{r: strings.NewReader(strings.Repeat("a", limit+1))}
	_, err := fetchWithLimit(body, declaredLength(limit+1), limit)

	// ← 目标断言放第一条：声明超限时一个字节都不该读
	if body.n != 0 {
		t.Fatalf("known oversize: read %d bytes, want 0", body.n)
	}
	// 次要断言用 Errorf，不挡住别的检查
	var tooLarge *TooLargeError
	if !errors.As(err, &tooLarge) {
		t.Errorf("err = %v, want *TooLargeError", err)
	}
}
```

判断方法很朴素：看旧版的失败输出，找到目标断言自己的那句失败信息。找不到，只看到一个退出码或别的断言的报错，就不算证明。[那篇](/blog/testing/guard-tests-three-rules/)讲过「红在对的那一行」，那里的例子是断言找错了控件；这里更早一步，目标断言压根没轮到执行。

## 2. 绿了，但目标代码没执行：负向断言要配正向对照

**现象**：同一次修复还有一条用例，断言「超限被拒时，不把这次失败记进渠道健康统计」。新代码上绿。复核发现用例没设置模型名，记录健康统计的函数一开头就判「没有模型名，直接返回」。所以「没记失败」成立，原因是函数什么都没做，和超限分类对不对毫无关系。

**根因**：「没有发生 X」这类负向断言，在被测路径没走到时天然成立。前一篇讲过否定断言要加正向对照，那里的问题是目标元素没渲染；这里是前提字段缺失让函数早退，换了个地方，问题相同。

**修复**：补上模型名，读真实的统计存储，同时断言两件事：分类确实发生了（「被过滤」计数是 1），失败和完成计数都是 0。再加一条只改一个因素的正向对照：同样的准备，换成上游 500，失败计数应该是 1。

```python
@pytest.mark.parametrize("status, want_filtered, want_failed", [
    (413, 1, 0),   # 超限：只记「被过滤」
    (500, 0, 1),   # ← 正向对照：同样的准备，确实能记失败
])
def test_health_classification(status, want_filtered, want_failed):
    store = InMemoryHealthStore()
    record_download_result(store, model="model-a", status=status)  # ← 带上模型名，否则函数早退
    assert store.filtered + store.failed == 1      # 先证明分类发生了
    assert (store.filtered, store.failed) == (want_filtered, want_failed)
```

正向对照的价值在于它和负向用例共用同一套准备。它能记上失败，就说明这条记录路径在当前准备下是通的；负向用例里的「没记」才有意义。

## 3. 负例夹具要合法，只让一个因素越界

**现象**：任务 worker 调上游建单时，响应体超过 10 MiB 要按「结果不明」处理。助手的夹具是 10 MiB 多一点的字母 `x`，断言「结果不明」，旧版红、新版绿。

复核指出：一串 `x` 本身就不是合法 JSON。把大小守卫整个删掉，解析也会失败，同样会落到「结果不明」，测试照样是绿的。这条用例证明不了大小守卫在起作用。

**根因**：夹具同时违反了两条规则（太大、格式不对），测试只看最终结果，分不出是哪条规则在起作用。

**修复**：用一份合法 JSON，尾部补空格凑到精确长度。正好 10 MiB 的那份应当成功并返回同一个任务 ID；多 1 个字节的那份应当报大小错误。两种都断言只发了 1 次建单请求。

```python
LIMIT = 10 * 1024 * 1024

def padded_json(size: int) -> bytes:
    base = b'{"id":"task-1"}'
    return base + b" " * (size - len(base))   # ← 仍是合法 JSON，只有长度在变

def test_body_at_limit_is_accepted(fake_upstream):
    fake_upstream.respond(200, padded_json(LIMIT))
    result = create_task(client)
    assert result.task_id == "task-1"
    assert fake_upstream.post_count == 1

def test_body_one_byte_over_is_ambiguous(fake_upstream):
    fake_upstream.respond(200, padded_json(LIMIT + 1))
    with pytest.raises(AmbiguousResult) as e:
        create_task(client)
    assert e.value.reason == "body_too_large"   # ← 断言命中原因，不只看错误类型
    assert fake_upstream.post_count == 1        # 没有重发
```

这里要同时对的有三样：副作用次数、错误类型、命中原因。合法边界（正好等于上限）和超限边界（多 1 字节）也要成对出现，两者只差一个因素。

同一轮还有一个输入错误：端到端测试把上游 SDK 的内部字段当成了对外接口的参数传进去，默认画质让独立算出的扣费预期对不上，首轮红了。当时改的是输入，换成对外文档里的参数名，预期没动。夹具和预期对不上时，先问「我是不是在用真实入口的输入」，再考虑是不是预期写错了。

## 4. 测试准备不能替被测代码做决定

**现象**：我有一个命令执行前注入提醒的 hook，Claude Code 和 Codex 共用：碰到停止 Docker Desktop 的命令，提醒先确认谁还在用；纯查帮助的命令不提醒。我发现提醒卡出现得太频繁，让助手改进。初版修复的 12 项测试全过，独立复核又找到两处缺口。

第一处是命令边界。初版只测了 `docker desktop stop --help` 这一例，正则里的空白能跨过分隔符：

| 输入 | 应有判断 | 初版的问题 |
|---|---|---|
| `docker desktop stop --help` | 只是查帮助，不提醒 | 对 |
| `docker desktop stop && foo --help` | 前一条是真的停止，要提醒 | 后一条的 `--help` 把前一条豁免了 |
| `docker; desktop stop` | 两条独立命令，不构成停止 | 多行统一匹配，把两段拼成了一次停止 |
| 引号里的多行文字提到 stop | 是参数文字，不是命令 | 只检查行首不够，引号内也会命中 |

第二处更隐蔽。hook 里有一个全局变量记录当前客户端，默认值是 `claude`，这个默认值本身是对的。问题在测试：helper 一上来先把这个全局变量改成用例指定的值，再调用入口。于是每条测试证明的都是「改过之后的分支正确」。复核只做了一个变异，把默认值改成 `codex`，12 项照样全绿。

**根因**：测试准备替被测代码做了决定。被测的「默认值」在准备阶段就被覆盖掉了，没有任何断言读得到它。

**修复**：单独一条用例，在任何覆盖之前读原值，并走不带客户端参数的原生入口。同一个单点变异再跑，正好红在这条上。

```python
import hook

def run(cmd, client=None, monkeypatch=None):
    if client is not None:                 # 只在用例明确要求时覆盖
        monkeypatch.setattr(hook, "CLIENT", client)
    return hook.main({"command": cmd})

def test_default_client_untouched():
    assert hook.CLIENT == "claude"         # ← 覆盖之前先核原值
    out = hook.main({"command": "docker desktop stop"})   # ← 原生入口，不经 helper 覆盖
    assert out.reminder_for == "claude"
```

最后新增 15 项、原有 17 项都通过，复核也核了实际安装到本机的文件。这只证明本次覆盖成立，证明不了所有 shell 写法的边界都对了。「实现现在没错」和「测试能阻止它以后改错」是两种证据，后一种要靠变异来拿。

## 5. 从真实构造走到真实出口

这一类在两周里出现了两次，形状一样：测试绕开了生产会走的那一段。

### 中间对象漏字段，消费方把缺字段当空

**现象**：前端控制台的价格页上，有一类「家族卡片」（一个模型家族合成一张卡）不显示按次计费的工具费用行，单个型号的卡片显示正常。后台配置和价格接口里都有这项价格。

**根因**：共用的明细组件按行对象上的「工具费率列表」字段逐项渲染，字段缺失时取空列表，不报错。单型号行的构造函数传了这个字段，家族行的构造函数只传了 token 相关的字段。原有测试只测了「从配置里解析出工具费率」的函数，没有穿过家族行的构造函数，挡不住中间这一跳丢字段。

这里有两层要分开。项目定义决定「有没有这一行」，价格表决定「这一行多少钱」。缺价格时可以显示兜底值，缺项目定义时根本走不到取价那一步。

**修复**：新测试用真实的行构造函数，经过真实的表格组件，一直渲染到明细组件，只替换取价的 hook。覆盖家族卡片和普通卡片两组，各测无实时价、涨价、降价三种情况。放回旧代码上，家族卡片的目标用例全红，普通卡片的对照用例全绿。

助手第一次修的时候，只让变体从自己的配置里找工具费率，漏了有的变体把工具定义放在家族一级，补上「变体优先、找不到再读家族」才全过。这一处是动手前没核完整继承关系。

### 测试读回的是一份没人调的副本

**现象**：任务 worker 在生成过程中回报进度时带上部分结果，主后端网关把其中的流式链接存下来，用户查任务时就能边生成边播放。回调测试断言「用户能看到链接」，读回用的是控制器层一个组装任务响应的函数，审视报告也把它当成了查询出口。

新上下文复核从路由往下追：任务查询接口实际走的是服务层的另一个响应构造函数。测试用的那个函数，除了测试没有调用方。两份判断条件逐行相同，真实 HTTP 的端到端也拿到了链接，所以代码没错。但以后有人只改服务层那份，这条测试照样是绿的。

**修复**：补一个只加测试的提交，读回走服务层那条路，3 个变异都红在目标断言上。确认读回函数有没有生产调用方，最快的办法是排除测试文件再搜：

```bash
# 列出非测试代码里对这个函数的调用；为空就说明测试守的是一份副本
git grep -n 'buildTaskView(' -- '*.go' ':!*_test.go'
```

两个例子合起来是一条规则：「用户能看到 X」的测试，要从生产的构造入口进，从生产的读取出口出。中间每一跳都用真实代码，只在最外层替换外部依赖（价格 hook、上游 HTTP）。这和前一篇「输入形状取自被测出口」是一对：那篇管进去的数据，这里管走的路。

## 6. 「通过」要说清跑完了多少、审的是哪一版

### 开始数要等于结束数

同一次修复，审视报告写「控制器包两边的失败集合逐名相同」。复核亲自跑，两次全量都在中途 panic，各有一千多个用例没开始，通过数却接近，看起来就像可以比。跳过引发 panic 的用例再跑，两边都跑完了，失败数也相同，这才是真的对比。

Go 的 panic 会打断整个包，前一篇第 4 节讲过。这次补一个机械的检查：先列出应有的用例，再数开始了多少、结束了多少。

```bash
go test -list '.*' ./pkg/tasks/ | grep -c '^Test'      # 应有的顶层用例数
go test -json ./pkg/tasks/ > run.json || true
jq -r 'select(.Test and .Action=="run") | .Test' run.json | sort -u | wc -l                  # 开始的
jq -r 'select(.Test and (.Action|test("^(pass|fail|skip)$"))) | .Test' run.json | sort -u | wc -l  # 结束的
grep -c '"Output":"panic:' run.json                                                          # 应为 0
```

三个数对不上，或者 panic 不为 0，这次运行就不能拿来比失败集合。超时也一样：两份日志都超时，先核双方完成的是不是同一批用例。

### 复核结论绑定版本，之后的改动都算没复核

**现象**：第一轮复核报告只记了审视清单文件的修改时间。之后助手照复核意见改了这份清单，又补了上面那个测试提交，这两样都没被新上下文看过。我同意推送后，推送前检查脚本拦了下来：它要求复核报告里写着当前清单的内容哈希。

助手没有把新哈希填进旧报告，补了一轮只看增量的复核，新发现的几条小问题记在复核报告里，不再改清单（免得哈希又变），之后才推上去。

**根因**：复核流程的模板让记修改时间，检查脚本按内容哈希核，两边口径不一致。模板还让「补做直接改回清单」，却没写补完要再复核。修改时间说明不了内容，碰一下文件就会变；内容哈希加提交号，才能说清「复核的是哪一版」。我同意改模板之后，复核报告的标题改成记完整的 sha256，并加了一步：复核之后又改过，推送前补一轮复核。

```bash
# 写进复核报告的抬头
printf 'commit %s\nchecklist sha256 %s\n' \
  "$(git rev-parse HEAD)" "$(shasum -a 256 review-checklist.md | cut -d' ' -f1)"

# 推送前：和报告里记的比，不一致就说明有没复核过的改动
git diff --stat <复核时的提交>..HEAD
```

## 7. 检查脚本本身：放行、误拦、一直红着，都要问走的哪条路

上面那个推送前检查脚本，同一天也被我们查出了自己的三个问题。

### 放行不等于核过

补另一个工具那份复核规则时，助手顺带发现：前一个修复推上去的版本，复核之后清单改过、还多了一个提交，检查脚本却放行了。我让它查。

脚本按任务说明文件的格式分两条路：新格式走严格路径，要求复核报告里有当前清单的哈希；旧格式走兜底路径，只看清单在不在、是不是比最新提交新。那个任务的说明文件没被脚本认到，落进了兜底路径。照复核意见补改清单，正好让清单比提交新，兜底就过了。

我选了两处改动：找不到说明文件时按任务目录去找；兜底路径也核复核哈希，没有就拦一次、原样重发放行。没选「旧格式一律走严格路径」，因为有一批旧任务会被直接拦死。

### 「会误放」要在修复前的代码上跑出来

给上面两处改动写测试时，助手照真实写法用了 `git push origin HEAD:x 2>&1 | tail -6`，一条测试被误拦。原来脚本切命令时把 `&` 当分隔符，`2>&1` 被切成三段。

修的过程中，助手在思考摘要里写「已确认」重定向写在远端前面时会误放，这句没跑过。补的守卫测试在修复前的代码上是绿的：残留的 `2>` 占了远端的位置，和 `origin` 对不上，于是拦下，只会误拦、不会误放。助手当轮改口，在回复开头更正了。

真正会误放的在另一处：判断推送目标的逻辑。执行 `git push 2>&1 upstream HEAD:main` 时，后面的远端和 ref 被切走，脚本按默认远端认错了推送目标，走了较轻的检查就放行。这条用探针和 3 个子用例在旧代码上实测，全红。最后修在切词那一层，再把读参数的几个地方逐个过了一遍。

误拦只是麻烦，误放会出事故，两者要分开说，而且都要在修复前的代码上跑出来。只凭读代码推出来的「会误放」，和「会红」一样，只是假设。切命令时怎么处理重定向，见 [hook 那篇](/blog/ai-workflow/claude-code-hooks-inject-context/)。

### 一直红着的测试，要问从哪次改动开始红

还有一条适配器测试一直报错。助手在旧版脚本上复现了，确认不是这次改出来的，写了「原因还没查」。我让它查下去。

这条测试在临时目录里派子代理，提示词里没有任何工作仓库的名字。几天后脚本加了规则：不碰工作仓库的派发不需要审视。这条测试从那天起就被当成个人事务放行了。脚本是对的，测试过时了。这种红灯挂着不查，以后脚本真坏了，它也不会让人多看一眼。「不是这次引入的」之后，还要追到「是哪次改动让它红的、是测试过时还是代码退化」。

## 8. 交出全绿之前的清单

我现在核 AI 交来的「测试全绿」「已复核」时，逐条问下面这些。每条都要能指到一段输出、一次命令或一个提交。

| 问题 | 要看到的证据 |
|---|---|
| 把这个缺陷放回去，哪一条断言失败？ | 旧版失败输出里，目标断言自己的失败信息 |
| 目标断言之前有没有 `Fatal`、早退、前置失败？ | 目标断言排在最前，或前置检查不中断 |
| 负向断言（「没有发生 X」）的路径真的走到了吗？ | 同一套准备下的正向对照能让 X 发生 |
| 负例夹具是不是只违反了一条规则？ | 合法边界和超限边界成对，只差一个因素；断言命中原因 |
| 测试准备有没有改掉被测的默认值？ | 覆盖之前先读原值的用例；改默认值的单点变异会红 |
| 输入是不是真实入口会收到的那种？ | 对外文档的参数名、实测记录里的输入形状 |
| 读回走的是生产出口吗？ | 非测试代码里的调用方，或从路由往下的调用链 |
| 中间对象是不是由真实构造函数产出的？ | 测试没有手造完整对象绕过转换 |
| 全量跑完了吗？ | 应有数 = 开始数 = 结束数，panic 为 0 |
| 复核的是哪一版？ | 提交号加清单内容哈希；之后的 diff 为空或已补复核 |
| 检查脚本放行时走的哪条路？ | 那条路实际核了哪几样 |
| 「会误放 / 会误拦」跑过吗？ | 修复前代码上的实测结果 |
| 一直红着的测试从哪次改动开始红？ | 引入它的那次改动，以及「测试过时 / 代码退化」的判断 |

## 收尾

1. **找到目标断言自己的失败信息** —— 退出码非 0 不算，别的断言报错也不算。
2. **负向断言配正向对照** —— 同一套准备，只换一个因素，证明路径是通的。
3. **夹具只越一条界** —— 合法 JSON 补空格到精确长度，比一串 `x` 有说服力。
4. **测试准备别替代码做决定** —— 先读原值，再覆盖；默认值要有自己的变异。
5. **从真实构造进、从生产出口出** —— 搜一下读回函数在非测试代码里有没有调用方。
6. **结论绑定范围和版本** —— 跑完多少个用例、复核的是哪个提交和哪份哈希。
7. **检查脚本也要问路径** —— 放行看走的哪条路；误放、误拦都在修复前的代码上跑出来。

回头看，这七种情况里没有一条测试是「写错了断言」那么简单。断言本身都对，错在断言和被测行为之间的那一环：执行到没有、前提成立没有、走的是不是那条路、说的是不是这一版。我现在给自己的规矩比上一篇多了半句：交出去之前要能回答「把 bug 放回去，它红在哪一行，而且这一行确实执行了」。检查流程本身为什么也会全绿却没守住，见[两次「假完成」之后](/blog/testing/fake-done-and-gates/)；复核子代理交回的东西怎么核，见[子代理的发现是线索](/blog/ai-workflow/subagent-findings-are-leads/)。
