> 一句话总结：新测试全绿只证明它和新代码不冲突，证明不了它在守东西。守卫测试要过三关：放到改动前的代码上会红，断言打在行为和值上，改共享函数时比对全部调用方的前后输出。

## 0. 起因：每个修复都带了守卫测试，可它们守住了什么

这一个月我修了不少 bug，几乎每个修复都配了一条「守卫测试」：钉住这次修的行为，以后谁改回去就红。代码大多是我带着 Claude Code 写的，助手写测试很快，提交时测试总是绿的。

问题出在复核上。有几次，审视时把守卫测试放到改动前的代码上跑，结果照样是绿的。也就是说，就算把 bug 原样放回去，这条测试也不会拦。还有几次反过来：测试红了，被测的东西却没坏，是测试自己的前提过期了。

这篇把这些经过按「三关」整理，后面再补三件和守卫测试配套的事：红了以后怎么分清是不是自己引入的、夹具怎么选数据、只验收不改仓库时怎么跑临时用例。

## 1. 第一关：放到改动前的代码上，该红的都要红

### 一条在新旧代码上都绿的界面守卫

**现象**：一次改动要求「实时价更低时，价格表里不出现划线的官方价和 -N% 折扣徽标」。助手写了一条界面用例：渲染价格表，断言找不到划线价、找不到 `-\d+%`。新代码上绿。复核时把三份源文件退回基线再跑，这条照样通过。改动前的那一行明明带着官方价，页面会显示划线和 `−N%`。

**根因**有两层，叠在一起让断言恒成立：

1. 价格表组件默认停在另一个分类的标签页上，目标那一行根本没渲染。「找不到划线价」当然成立。
2. 徽标里的减号是 U+2212（`−`），断言的正则写的是 ASCII 连字符 `-`。就算那一行渲染出来，也匹配不上。

「找不到 X」这类否定断言天然容易空转：目标不在页面上，和目标被正确去掉，测出来一模一样。

**修复**：先切到目标标签页，再加一条正向对照，断言目标行确实渲染出来了；正则把同形字符都收进去。

```tsx
it('实时价更低时不显示划线价和折扣徽标', async () => {
  render(<PriceTable prices={livePrices} />)
  await user.click(screen.getByRole('tab', { name: 'Image' }))   // ← 先切到目标标签
  const row = screen.getByRole('row', { name: /Model X/ })         // ← 正向对照：目标行在页面上
  expect(row.querySelector('del')).toBeNull()                      // 不出现划线价
  expect(row.textContent).not.toMatch(/[−-]\d+%/)                  // ← 同形字符都收进来
})
```

修完再放到改动前的代码上跑，这组 7 条全红，才算过了第一关。

### 怎么在改动前的代码上跑

不要在正在干活的工作区里来回切。开一个改动前代码的临时检出，复用当前的依赖目录，只把测试文件拷进去：

```bash
base=$(git merge-base origin/main HEAD)
git worktree add --detach /tmp/guard-base "$base"
ln -s "$PWD/node_modules" /tmp/guard-base/node_modules     # 复用依赖，不重新安装
cp src/__tests__/priceTable.guard.test.tsx /tmp/guard-base/src/__tests__/
(cd /tmp/guard-base && ./node_modules/.bin/jest src/__tests__/priceTable.guard.test.tsx)
# 期望：每一条都红；没红的逐条查原因
git worktree remove --force /tmp/guard-base
```

用 `./node_modules/.bin/jest` 而不是 `npx`：新检出里如果没有依赖，`npx` 可能去拉一个同名占位包，跑出一个看着正常的假结果。Go 项目不用另外检出，`go test -overlay` 能在编译时把改过的文件换回基线版本，第 4 节会讲。

### 红也要红在对的那一行

过了「改动前会红」也不一定守住了。有一次，表单里不支持某个选项的变体改成不列这个选项，助手加了一条「A 档选了它，切到 B 档不串过去」的用例。它在改动前的代码上确实是红的，但红在「按钮不存在」那一行：旧代码是把按钮置灰显示，不是不显示。

真正守串档的那句，断言的是「切到 B 档后 Auto 处于按下状态」，也就是回到了默认值：

```ts
expect(screen.getAllByRole('button', { name: 'Auto' }).some(isPressed)).toBe(true)
```

页面上另一行（纵横比）也有个同名的 Auto 按钮，默认就是按下的，所以这句在任何代码上都成立。复核子代理做了一个变异：故意让切档时把选项带过去，整份 41 条用例照样全过。

同一轮还有一条「不出现某句提示」的断言，能成立只是因为渲染那句话的上传组件在测试里被 mock 掉了，真实页面上照样有这句。

**修复**：用 `within(行容器)` 把断言限定在目标控件那一行；再补一条行为断言，检查生成的请求体里不带这个参数，然后套上同一个变异，确认它会红。

### 变异要只让被测那一条失效

用变异证明一条断言有效时，还要防一个坑。助手给 changelog 测试加了一条「正文里的生效日期等于常量」，为了证明它有效，把测试里的日期常量从 8 日改成 9 日，7 个语种全红，就当作证明了。

复核子代理指出：同一个常量还驱动着「front matter 日期等于常量」那条旧断言。只改常量，旧断言本来就会红，这次变异证明不了新断言有用。

正确的做法是只让被测断言读的那份输入失效：把其它断言共用的输入一起改到一致，只留正文日期不动；看失败位置，报错行号应当正好是新断言那一行。变异在临时检出里做，不动正在跑全量测试的工作区。

## 2. 第二关：断言打在行为和值上，不打在源码和格式上

### 按源码文本 grep 的断言两头不占

为了保证「站内链接不能丢」，早期写过一条在源码里 grep `href` 的测试。后来卡片改成从数据源派生链接，这条立刻变红，可链接一个都没丢。反过来，数据里的链接真丢了，它也抓不到。源码文本是实现细节，grep 测的是「代码长什么样」，不是「页面上有什么」。改成两条断言：数据源解析出的每个链接都存在，对应区块确实渲染了。

### 「不出现某种格式」会把实现往错的方向推

**现象**：一个新模型的倍率说明串里，一个三分之几的倍率被原样转成字符串，渲染成一长串循环小数（下面用自编的数说明：7/3 会渲染成 `2.3333333333333335`）。修法是改一个多个模型共享的格式化函数，加了一条守卫：「倍率串里不出现 4 位以上的小数」。

问题在于另一些模型的表值本来就是三四位的有限小数（形如 1.125、0.3125）。为了让守卫过，实现顺理成章地对一切做了 `toFixed(2)`。结果是旧模型页面上的倍率从 ×1.125 变成 ×1.13、从 ×0.3125 变成 ×0.31，不再等于实际乘的倍率。套件全绿。

**根因**：守卫断言的是一种格式性质，而不是「显示的值等于表里的值」。格式性质的守卫，会奖励任何满足格式的实现，包括错的那种。

**修复**：只处理真正的无限小数，其余原样输出；守卫改成「渲染串里的每个数，要么等于表值，要么是表值的分数写法」。

```ts
function formatFactor(v: number): string {
  if (Number.isInteger(v)) return String(v)
  const thirds = v * 3
  if (Math.abs(thirds - Math.round(thirds)) < 1e-9) return `${Math.round(thirds)}/3`
  return String(v)                      // 1.125 仍是 1.125；7/3 走上一行，得到 "7/3"
}

const toNumber = (s: string) => {
  const [a, b] = s.split('/')
  return b === undefined ? Number(a) : Number(a) / Number(b)
}

it.each(ALL_FACTORS)('%s 的显示值等于表值', (v) => {
  expect(toNumber(formatFactor(v))).toBeCloseTo(v, 9)   // ← 断言值，不断言格式
})
```

### 期望值不能从实现里抄

还有一种更隐蔽的空转：测试的期望值本身就是从被测实现里抄来的。一次复查旧页面的退役重定向时发现，旧页默认打开的是一个档位，退役映射却把它送到另一个档位。原有的测试把实现里那张错误的映射原样当作 expected，于是一直是绿的。

这条测试守住的是「实现等于实现」。修复时期望值改成从改动之外取：旧页面初始化时实际选中的档位、当初的退役公告。期望值从哪来，验收时同样要问，另一篇[当验收者而不是开发者](/blog/testing/acceptance-as-reviewer/)专门讲。

### 输入形状要取自被测的那个出口

一次给任务 worker 的失败加错误策略：按上游错误码把失败分成「用户请求侧 / 只观察 / 致命」。守卫用例「某个 403 经换渠道出口时不计入渠道健康」在分支上绿、在改动前红，三关看着都过了。

审查时翻本地栈日志，换渠道出口实际收到的文案，末尾没有那段附带状态码和错误码的后缀。用例喂的是终态出口的文案形状，因为写用例的人照着生产样本抄，而生产样本全是终态文案。生产形状下，策略里的锚点一个都不中，按 HTTP 403 直接判致命，正常渠道会被禁用。

红绿都是在错误的输入上得出的，所以「改动前会红」也救不了它。测某个出口时，输入形状要从这个出口的实测记录取：本地栈日志、回调请求体、抓包。记录里没有，就先造一条让它经过这个出口。

同类的还有一条随交测试：它只配置了建任务的地址，没配查询地址，三个子用例因此失败；超时用例又被错误响应体提前判成 failed，根本没走到超时。这种情况要写成「测试夹具错误」，不能写成「业务修复无效」。后来另写了一条接线正确的测试，再拿旧的轮询器做负对照，才确认业务修复本身是有效的。

## 3. 第三关：改共享函数，比对全部调用方的前后输出

上面那个格式化函数，助手第一轮自审写的是「其它模型的显示不变」，只核了两个恰好是有限小数的值。下一轮两个子代理各自查了全部调用方，才发现 6 处调用里有 3 个模型的值被舍入了。

改共享函数的验证流程是固定的：

1. 列出全部调用方（grep 函数名，加上间接引用它的那一层）；
2. 对每个调用方，把改前、改后的输出各打一份；
3. diff 为空，或者每一条差异都解释得了，才算验证完。

「打一份输出」最省事的办法是写一个只负责导出的测试，放在仓库外，改前改后各跑一次：

```ts
// dump-factors.test.ts：只导出，不断言
import { writeFileSync } from 'node:fs'
import { formatFactor } from './format'
import { ALL_MODELS } from './catalog'

it('dump', () => {
  const out = Object.fromEntries(ALL_MODELS.map((m) => [m.id, m.factors.map(formatFactor)]))
  writeFileSync(process.env.DUMP_OUT!, JSON.stringify(out, null, 2))
})
```

```bash
DUMP_OUT=/tmp/before.json ./node_modules/.bin/jest --roots /tmp/checks ...   # 在基线检出里跑
DUMP_OUT=/tmp/after.json  ./node_modules/.bin/jest --roots /tmp/checks ...   # 在当前分支跑
diff /tmp/before.json /tmp/after.json
```

后来一次批量改多语言文案也用的这一招：导出全部文案字段，改前改后一比，147 个字段里只有 6 个变了，而且都是预期要改的那一种语言。这比「我只改了那几行」有说服力得多。

变异测试是同一思路的另一面。一次给错误分类加规则后，做了 19 个变异（逐条删规则、改匹配），新加的 4 个用例抓到 16 个；没抓到的 3 个是「只在代码默认规则里删」，因为代码里还有更宽泛的规则接住，属于预期。这 3 个由另一条测试抓到：它断言代码默认规则和交给运维的配置文件逐字一致。每个变异是谁抓的，都要能说出来。

## 4. 红了以后：先分清存量失败和自己引入的

守卫测试写对了，全量跑一遍还会冒出别的红。「这个失败跟我无关」是一个需要证据的结论。

最基本的证据是在不含自己改动的基线上复跑，按用例名做集合差，不看失败条数：条数相同也可能是一个修好、一个新坏。

```bash
./node_modules/.bin/jest --json --outputFile=/tmp/branch.json || true
git stash -u && ./node_modules/.bin/jest --json --outputFile=/tmp/base.json || true; git stash pop

python3 - <<'EOF'
import json, os
def failed(path):
    d = json.load(open(path))
    return {f"{os.path.basename(r['name'])} :: {a['fullName']}"
            for r in d["testResults"] for a in r["assertionResults"] if a["status"] == "failed"}
base, branch = failed("/tmp/base.json"), failed("/tmp/branch.json")
print("本分支新增的失败：", sorted(branch - base) or "无")
print("本分支修好的：", sorted(base - branch) or "无")
EOF
```

Go 的对应写法是 `go test -json ./...`，取 `Action == "fail"` 且带 `Test` 字段的行，按「包名加用例名」求差集。汇报写成「全量和主干按用例名比，存量失败集合相同，没有新增」，并附上复跑方法。

几个会让对比失真的情况：

- **Go 的 panic 会中断整个包**。panic 之后的用例两边都没跑，失败集合看起来「完全相同」，其实什么也没比；有时还会让分支「看起来更好」，差集里冒出几条「修好了」的用例。先比两边每个包的通过数，少了一大截就是包被打断了。panic 也不一定来自出错的那个用例，可能是前面某个用例起的后台 goroutine 在测试的空数据库上解引用，要从栈里的 `created by` 反查。
- **基线跑不起来**。多仓项目用相对路径的 `replace`，临时目录里的基线编译不过。这时用 `go test -overlay=o.json`：把改过的文件逐个映射成基线版本（`git show <merge-base>:<path>` 导出），新增的文件映射成空串，就地得到一份基线。
- **按日期触发的哨兵测试**。同一棵树上午全绿、下午两套红，失败信息是「到期后必须已改回原值」这类：哨兵在截止时刻之后自动变红。先在主干单独检出上跑同样的套件确认也红，再写「与本分支无关」。
- **负载造成的假失败**。全量测试和构建、另一门语言的测试同时跑，会冒出几条超时或进程被信号终止的失败。原因清一色不是断言不符，就把这几个套件单独重跑；单独跑全过，才能写成「并发负载下的偶发」。

`-overlay` 的映射文件长这样，两边用同一条命令（同样的 `-skip`、同样的包列表）各跑一遍再求差集：

```json
{"Replace": {"/abs/repo/pkg/changed.go": "/tmp/base/pkg__changed.go", "/abs/repo/pkg/added_test.go": ""}}
```

存量失败查清「不是我的」也不算结束，要记下来告诉相关的人。

## 5. 夹具别钉死会变的数据行

有一类假红是夹具自己过期了。我有一份由脚本从远端实况生成、再由对账脚本逐行核对的分支清单页，还配了反向对账：故意篡改页面，看对账能不能抓到。

**现象**：重采数据后，「把一条待检查行改成搁置」那一例报 NOT CAUGHT；校验脚本里「给一条待检查行塞一个打开的 PR，应被记成 PR 已开」的正向用例也在同一轮变红。页面本身没有任何错。

**根因**：两处用例都写死了同一条分支行。前一天它确实是待检查；这一轮它被合入，状态按规则算成了已合并。篡改用的 `replace('data-status="review"', ...)` 在那一行上找不到目标，等于什么都没改，对账当然「抓不到」。夹具把一个会随外部实况变化的事实当成了常量，失效时表现成「被测对象坏了」，于是先去查页面和生成器，白查了一轮。

**修复**：选行按条件算，开头断言前提成立，篡改后断言内容真的变了：

```python
victim = next((r for r in rows if r["status"] == "review" and not r["pull_requests"]), None)
assert victim, "fixture stale: no review row without PR"

before = page_html
after = before.replace(f'id="{victim["id"]}" data-status="review"', f'id="{victim["id"]}" data-status="held"', 1)
assert after != before, "fixture stale: tamper was a no-op"
```

按条件选行也可能一行都选不到。后来有一轮，全部待检查分支都被合了，满足条件的行一行没有，`next()` 直接抛异常，整个校验脚本崩掉。处理方式是让用例按当前状态分支：有可选行时照旧测；没有时改测互补的那条规则（在一条被固定说明的行上塞 PR，期望生成器拒绝）。不能删用例，也不能放宽条件凑一行，更不能静默跳过。

## 6. 只验收、不改仓库：借仓库的 jest 配置跑临时用例

验收别人的改动时，常要补一条仓库里没有的断言，但约定是不改仓库。办法是把测试文件放在仓库外的临时目录，在仓库目录下运行 jest：

```bash
cd <仓库前端目录>
./node_modules/.bin/jest --roots "$TMP/checks" \
  --modulePaths "$PWD/node_modules" \
  --testMatch '**/headerPrice.probe.test.tsx'
```

- `--roots` 让 jest 只在临时目录里找测试；
- `--modulePaths` 把仓库的依赖加进解析路径。测试文件在仓库外时，`react/jsx-runtime` 这类依赖从文件所在目录往上找会找不到，带 JSX 的用例一定要加；
- 仓库配置里的路径别名、转译和 setup 文件照常生效，可以直接 import 仓库里的组件和夹具。

有一次验收就是这样抓到问题的：临时用例把一个模型的实时价改得比兜底价低，页头立刻显示出划线价和一个折扣百分比，而规则要求这里不能出现折扣。仓库里原有的测试只覆盖了「两个价相等」的情况，线上碰巧也相等，所以一直看不出来。

这类用例是验收证据，不是仓库资产。覆盖缺口写成建议交给维护者，不要顺手加进仓库。结束后看一眼 `git status`，确认没有生成物落进去。另外注意可选链返回的是 `undefined` 不是 `null`：`el?.closest(...)` 找不到时，`toBeNull()` 会失败，先写成 `?? null` 再断言。

## 收尾

1. **改动前会红** —— 新测试拷到基线检出上跑，每条都红；否定断言前先加一条正向对照。
2. **红在对的地方** —— 失败行号要正好是被测断言；变异只让它读的那份输入失效。
3. **断言打在值上** —— 「渲染值等于表值」，不是「不出现某种格式」；期望值从改动之外取。
4. **输入取自被测出口** —— 测哪个出口，就从哪个出口的实测记录取输入形状。
5. **改共享函数比全部调用方** —— 改前改后各导出一份，diff 解释得了才算验证。
6. **按用例名比失败集合** —— 不比条数；先看每个包的通过数，排除 panic 中断。
7. **夹具按条件选行** —— 开头断言前提，篡改后断言内容真的变了，选空时有退路。

回头看，这些坑的共同点是：测试的红绿和被测行为之间少了一环证明。我现在给自己定了一条规矩：一条守卫测试交出去之前，要能回答「把 bug 放回去，它红在哪一行」。答不上来，就说明它还只是一条和新代码不冲突的测试。机器闸和检查为什么会「全绿但没守住」，另一篇[两次「假完成」之后](/blog/testing/fake-done-and-gates/)讲的是同一件事在交付层面的样子。
