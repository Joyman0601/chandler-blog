> 一句话总结：要人独立核一份报告的数据，就别让核对的人先看到报告的答案。题目只问「来源里写的是多少」，报告值点了才揭开；决定结论的关键项全核，其余按维度用固定种子分层抽；直达原文的链接要按落点测；抽到一题不一致，就按它的错法把同类全拉出来复核。

## 0. 起因：自己核对证明不了什么

有一份调研报告是我带着 Claude Code 做的，主体是一张几百格的对照表，每一格都是从公开文档、价目页、接口返回里摘出来的事实。为了经得起查，主会话给每一格都配了原文高亮截图，一共几百张，还写了脚本逐格核对出处。

但这些核对有一个共同的问题：做核对的，和写报告的是同一方，都是主会话或者它派出去的子代理。它们最多能证明「我看到的和我写的一致」。如果一开始就看错了地方，比如看错币种、安错平台、读错单位，截图会忠实地把错误也截下来，核对脚本也会判它一致。

要真正交叉验证，得有人独立去看来源，这个人就是我自己。可人工核也有陷阱：如果我先看到报告的答案再去翻页面，就会顺着答案找，看到差不多的数就点「一致」。所以我让主会话做了一个本地单文件 HTML 的核对页，核心规则只有一条：先自己去看来源，再看报告写的。

这个页面先后用在三份报告上，之后我让助手把每次临时写的生成脚本合成了一套固定流程：输入一份题目清单，页面、抽样、作答格式、判分规则都固定。下面讲这套流程的设计和踩过的坑。

## 1. 每道题长什么样

每道题是一张卡片：

1. **问题**：只问「来源里写的是多少 / 是什么」，不问「报告说得对不对」，也不把报告值写进问题。
2. **到哪找**：一句话写清楚在页面哪一节、哪张表、哪一列，或者 JSON 里的哪个字段。
3. **来源入口**：网页链接（带直达原文的定位）、本地文件和行号、钉在某个提交上的代码位置，或者一条可以原样粘进终端的只读命令。
4. **「你看到的值」**：一个输入框，建议先填。
5. **「揭开报告值」**：点了才显示报告值和当时的存档截图。
6. **结果**：四选一：一致、不一致、页面已变、看不懂，可以写备注。

「页面已变」单列出来，是因为线上页面会改。核对的人看到的值和报告不同，但存档截图里是报告写的那样，就说明是页面后来改了，不算报告写错。「看不懂」也单列，因为它指向的是题目或报告的表达问题，和数值对不对是两回事。

题目清单是一份 JSON，一道题大致是这样：

```json
{
  "id": "A03",
  "group": "A",
  "q": "官方文档里，这个接口单次请求最多接受几张参考图？",
  "where": "「请求参数」一节的参数表，images 那一行的说明列",
  "find": [
    {"url": "https://docs.example.com/api/generate", "text": "up to 4 reference images", "label": "官方 API 文档"},
    {"file": "out/archive/generate-2026-10-07.html", "line": "812-818"}
  ],
  "answer": "4 张",
  "shots": ["out/screens/A03.png"],
  "facts": ["F041"]
}
```

`facts` 指回报告里被拆出来的事实编号，判分时靠它找同一章节的其他事实。

## 2. 出题：谁定范围，谁拆事实

### 2.1 分四组，关键项全核

报告里可核的事实往往有上百条，不可能全让人核。题目分成四组：

| 组 | 内容 | 出题方式 |
|---|---|---|
| A | 决定结论和费用的事实 | 全部出题 |
| C | 数量和有无（「有几个版本」「有没有这个端点」） | 全部出题 |
| D | 从代码里得出的结论 | 全部出题 |
| B | 其余事实 | 当候选池，按维度分层随机抽 |

规则写在页首：A、C、D 有一题不一致，整组扩大复核；B 抽到一题不一致，这个维度的全部候选逐条核。

抽查只能发现系统性错误（看错币种、读错单位这类会成片出现的问题），证明不了整体错误率低。所以关键项必须全核；抽查全对，也只能写「没发现系统性错误」，不能写「整体没问题」。

### 2.2 范围由主会话定，两侧都要写

A、C、D 各包含什么，由主会话按任务原文的验收点来定，不交给子代理判断。子代理照字面执行，范围写窄了，它不会替你补。

有一次验证这套流程，报告的结论是「旧方案换到新方案」。助手写 A 范围时只写了旧方案一侧的关键日期，子代理就把新方案一侧的关键日期放进了 B 组候选，而这个日期正好决定一条待定的结论。第一轮出题只覆盖了上一版人工题目里 20 道关键题中的 14 道。把新的一侧也写进 A 范围后，才全部覆盖。所以凡是「从 X 换到 Y」的结论，A 范围要两侧都写。

### 2.3 拆事实和机器核交给不带上下文的子代理

拆事实和出题，交给一个不带本次对话上下文的子代理。它不知道报告是怎么写出来的，所以不会顺着报告去找。要求是：

- 报告里每个可核的事实拆成一条：数字、日期、个数、「有 / 没有」、文件和行号、引用的原话、判定结论；
- 表格逐格拆，一句话里有几个数就拆几条；
- 写完数一遍条数，和各章节的表格行数、列表项数对一遍。

再起一个子代理做机器核，逐条对照来源，判定只能从六种里选：一致、不符、无来源、推算（写出算式并判算式对不对）、来源冲突、不适用。每个判定附原文引用或命令输出，没打开来源就不许写「一致」。主会话复核所有不是「一致」的条目，再按固定种子抽几条「一致」看；子代理的判定是线索，不是结论。机器核的口径和实际跑出来的分布，见[子代理的审查发现是线索](/blog/ai-workflow/subagent-findings-are-leads/)第 3 节。

### 2.4 算出来的值要拆开问

有一次 28 道题里我标了 3 道「看不懂」。这 3 道的报告值都是「基础值 × 档位系数」算出来的，而来源接口只返回基础值。我在接口里看到的数和报告值对不上，只能标「看不懂」，差点就标了「不一致」。

改法是按来源拆开问：① 价目页写的是多少；② 接口里那一行是多少；③ 代码里这一档的系数是多少；④ 相乘。「到哪找」里写明「接口只给基础值，档位系数在代码里」。一道题可以覆盖同一处来源的几个相关值，但不要跨来源拼题。

### 2.5 B 组按维度、用固定种子抽

B 组的候选按维度分层，维度就是报告里的「哪张表 · 哪一列」。每个维度用「种子 + 维度名」单独建一个随机数生成器，抽固定的题数。这样同一份题目清单每次抽到的都一样；某个维度加减候选，也不影响别的维度抽到哪几题。种子用当天日期，写进报告的复核记录里，方便别人复现。

```python
import random
from collections import defaultdict

def sample_b(claims, seed, per_dim=1):
    dims = defaultdict(list)
    for c in claims:
        if c["group"] == "B":
            dims[c["dimension"]].append(c)
    picked = []
    for dim in sorted(dims):
        rng = random.Random(f"{seed}:{dim}")       # 每个维度独立，互不影响
        pool = sorted(dims[dim], key=lambda c: c["id"])
        picked += rng.sample(pool, min(per_dim, len(pool)))
    return picked
```

抽哪几题由脚本按种子决定，不让子代理挑。

## 3. 直达原文：文字在页面上，不等于人能找到

### 3.1 用文本片段定位，但别把片段露出来

网页来源用 Chrome 的文本片段定位：链接后面加 `#:~:text=<片段>`，打开后自动滚到并高亮那段文字。片段要从已核过的存档里原样复制，选短而唯一的句子，不要跨表格单元格；连字符要编码成 `%2D`。

这里有个容易忽略的泄露：片段本身常常就含着答案。如果页面上显示片段，或者鼠标悬停在链接上能看到带片段的完整地址，盲核就失效了。所以 `href` 里只放不带片段的地址，带片段的完整地址放在一个 data 属性里，点击时才拼上去打开。

报告值同理：放在页面脚本的数据对象里，揭开时才写进 DOM。看页面源代码当然能看到，盲核防的是顺手看到，不是防作弊。

### 3.2 落点要实测

第一次用在一份文档类来源很多的报告上，我有一题判了「不一致」。回头查，原文的表格是对的，问题出在跳转：文档站打开后还在继续加载内容、挪动排版，定位被挤到了别的小节，我在那一节没找到报告写的值。

按同一类错法重测，27 个带定位的链接，文字全都在页面上，落点却有 13 个偏了。所以检查链接不能只查「文字在不在页面上」，要真的带片段打开、等页面加载完，再看原文是不是在视口里。

这个测法本身也改了两回才准：

1. 第一版按「整个文本节点在视口里」判。长段落天然超出视口，全被判成偏了。
2. 第二版用 `window.find` 找。它只找第一处，而小节标题往往先命中右侧目录里的同名条目。
3. 第三版找出全部出现位置，跳过导航和目录（但不跳过 `aside`，文档站的提示框就是它），只要正文里有一处在打开时的视口内，就算落点正确。再抽两题截图，确认「偏了」是真偏。

那一次 60 个链接偏了 22 个。落点偏了的题，把「到哪找」写细（右侧目录点哪一节、看哪张表的哪一列），不单靠跳转。

```js
// Playwright：带片段打开，等加载稳定，判正文里是否有一处出现在视口内
await page.goto(urlWithFragment, { waitUntil: 'networkidle' })
await page.waitForTimeout(1500)                    // 文档站常在加载后继续挪排版
const landed = await page.evaluate(needle => {
  const skip = el => el.closest('nav, [role="navigation"], .toc')   // 不跳过 aside
  const w = document.createTreeWalker(document.body, NodeFilter.SHOW_TEXT)
  for (let n; (n = w.nextNode());) {
    const i = n.nodeValue.indexOf(needle)
    if (i < 0 || skip(n.parentElement)) continue
    const r = document.createRange(); r.setStart(n, i); r.setEnd(n, i + needle.length)
    const b = r.getBoundingClientRect()
    if (b.height && b.top >= 0 && b.bottom <= innerHeight) return true
  }
  return false
}, needle)
```

## 4. 页面本身的几条要求

- **进度存浏览器本地**，键名里带标题、种子和题目指纹，换一份题目不会串。读写都包 try/catch，浏览器存储被禁用时页面照常能用，只是刷新后不保留。
- **出口有两个**：导出作答（JSON 下载），复制不一致的题。导出里带题目清单的哈希、生成时间和导出时间，判分时能确认作答对应的是哪一版题目。
- **题目里的命令要能原样粘贴**。不许有行尾 `#` 注释、尖括号占位符、省略号；拦掉删除、移动、重定向写文件、改仓库的 git 子命令、带请求体的 curl。会花钱、会改东西、会打印密钥的命令一律不放；要用密钥就从本地文件读，不打印。生成脚本只能拦常见写法，拦不住的靠出题时的约束。
- **生成后用浏览器脚本自测**：不填也能揭开；揭开前，每张卡上 4 个字以上的报告值都不在页面文字里（更短的「3」「有」到处都有，没法这样查，只能靠题目写法保证）；链接悬停看不到片段、点开带片段；刷新后作答保留；导出题数对；手机宽度不横向滚动；禁用存储时照常可用。全过才交。

自测只测页面和链接，不测题目问得对不对。题目质量靠主会话复核：A 组对照事实清单数一遍，每个 A 范围的事实都要有题。

## 5. 判分：一题不一致，按错法扩大

我做完导出 JSON，交回给主会话，判分脚本按固定规则出下一步清单：

- **A / C / D 有不一致**：整组扩大复核。先写出这题错在哪一类，再按这个错法，把报告里同类的事实全拉出来看。清单里会列出同章节的其他事实。
- **B 有不一致**：这个维度整行逐条核，包括没被抽到的候选。
- **页面已变**：对照存档截图。
- **看不懂**：改题目或报告的表达，不改结论。

扩大复核是这套流程里最值钱的部分。那份几百格的调研报告，一次盲核 84 道题，只有 1 道不一致：那一格只写了结论，推断依据不在页面上，而且这条依据对两个候选都成立，区分不了。按这个错法把全部带推断的格子拉出来重核，又改出好几处判定和依据，经过见[子代理的审查发现是线索](/blog/ai-workflow/subagent-findings-are-leads/)第 3 节。

顺着我的一句备注，主会话还回头扫了全部截图：几百张里，45 张的高亮框可能画偏或没框到原文，3 格挂错了截图。人核的价值在于，它是从生产方的盲区外面进来的，一道题就足以指出一类问题。

还有两条是从备注里学到的：

- **答案里的每个事实都要配截图**。只给关键句配图，我就会在其余每个数旁边写一句「为什么没截图」。按题拆出答案里的每个数和每个判断，逐个配高亮截图；后台数据和代码也一样，从存档里摘录成文本、数值原样，再截，顶栏注明「存档摘录」或「代码 + 提交号」。
- **备注里的疑问也要回答**。我在一题的备注里写过「截图难道不是什么安全检查吗？」，说明那张截图没讲清它要证明什么。这是证据的表达问题，要改，但不影响数值。

结果回写进一张汇总表，每条事实一行：报告值、机器核、主会话复核、盲核题号、盲核结果、建议。要改报告的地方先列出来，我看过、定了再改；判分脚本只出清单，不改报告。

## 6. 「先写下看到的」要不要强制

第一版页面是强制的：不填「你看到的值」，揭开按钮是灰的。

判分脚本拿我两次真实作答试跑，发现两次都是大多数题填了占位的「1」：一次 46 题里有 25 题，另一次 28 题里有 27 题（实测，数的是作答导出文件里「你看到的值」那一栏）。照最初的规则，这两次只能算「看过答案后确认」，不能算独立盲核。

最后我定的口径是：「你看到的值」不强制，填占位或不填，判分时照常算，不降低结论。页面随之改成「建议先填，不填也能揭开」；揭开那一刻输入框里的内容另存一份，只做记录，判分不用它。

这确实削弱了盲的程度，报告的复核记录里要如实写明这一点。但回头看，这套流程查出的问题，几乎都不依赖这个输入框：

- 链接不露片段、报告值点了才出现，「先去看来源」的顺序仍由页面保证；
- 「看不懂」和备注暴露了表达问题和证据缺口；
- 真正改动报告的，是一题不一致之后的扩大复核。

所以我的结论是：盲核页最该守住的是「答案不能先于来源出现」，以及「一题错就按错法扩大」；输入框是锦上添花。

## 收尾

1. **自己核对只能证明一致** —— 要交叉验证，得让另一个人独立去看来源。
2. **题目只问来源** —— 不把报告值写进问题；算出来的值拆成能分别看到的几项。
3. **关键项全核，其余分层抽** —— A / C / D 全出题，B 按维度用「种子 + 维度名」抽；抽查全对只能说没发现系统性错误。
4. **范围主会话定，两侧都写** —— 子代理照字面执行，不会替你补漏掉的那一侧。
5. **机器核是线索** —— 非「一致」的逐条打开复核，再按种子抽几条「一致」。
6. **链接不露片段，落点要实测** —— 带片段真打开、等加载完、看正文是否在视口；「到哪找」写到哪一节哪一列。
7. **一题不一致按错法扩大** —— A / C / D 整组，B 整个维度；页面已变对存档，看不懂改表达。

这套页面本身不复杂，一个生成脚本、一个判分脚本、两个浏览器自测脚本。真正花时间的是出题：把「报告写的」翻译成「来源里写的是多少」，每翻一题，都要先回答一遍「当初是在哪看到的」。答不上来的那几格，往往就是该改的地方。
