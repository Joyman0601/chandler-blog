> 一句话总结：检查全绿只证明尺子量到的部分没问题。交付前先列「哪些需求有机器尺、哪些没有」，没尺子的要么补闸、要么写进人工清单；流程里的每个「必须」都要有落点文件、机器闸和新上下文复核三件套。

## 0. 起因：一大批页面要迁到新框架上

刚接手前端时，我负责的是前端控制台的一次页面迁移：把一大批模型详情页从老写法迁到新的页面框架上。框架管骨架、路由、SEO 和包体，每一页把自己的区块挂进框架留出的插槽（slot）。手边有一份近九百行的页面规范、一个统计迁移进度的状态脚本，还有几十个按页参数化的契约测试。

活主要是我和 Claude Code 一起干：它按规范改代码、跑测试、报告进度，我验收。头两天就栽了两次，栽法一样：报告说「做完了」，所有检查也是绿的，但需求没做完。

这篇按时间讲这两次，再讲后来几周把「检查」做成「闸」时踩过的几层坑。每一层的教训都一样：先问检查量的是什么，再看它是不是绿的。

## 1. 第一次：进度文档说 0%，其实已经迁完

**现象**：第一天接手时，仓库里有一份手写的进度文档，写着某个页面「0%、老架构、未登记」。我让 Claude Code 先去核一遍，实测结果是这一页已经迁完了，只是改动没提交。如果照文档排期，下一个会话会把做完的事重做一遍。

同一次核对里，助手还挖出了自己之前汇报里的两处错：

- 总页数报多了一页；
- 状态脚本的「契约」列只认「每个页面一个独立测试文件」这种写法，漏看了框架目录下几十个跨页参数化的测试（`it.each(PAGES)` 这种）。

**根因**：进度是人手写的，写的人记的是摘要。手写进度的代价不是「有点过期」，而是方向性的错：它会把下一个人领去重做。

**修复**：写一个状态脚本，进度全部从文件实测——有没有接上框架入口、清单里有没有登记、区块文件在不在。手写的只剩「为什么这么定」，进决策日志。

这个修法本身没问题，问题在于我当时以为「进度可实测」就等于「完成可实测」。第二天就被打脸了。

## 2. 第二次：状态 DONE、47 个契约测试全绿，排版还是旧版

**现象**：第二天三页并行。其中一个模型详情页，状态脚本判 DONE，47 个契约测试和页面自己的领域测试全部通过。我在浏览器里打开一看，试用区（Playground）的排版还是旧版：变体选择器挂在整个区块顶部，而规范要求它是左侧参数卡里的第一项。

翻代码找到了一行注释，自己把偏离写得清清楚楚：「变体选择器落在区块顶部，因为插槽够不到框架管的那段布局」。范本页是按规范自己写的试用区，这一页直接把老的共享组件原样接进了新插槽。

三道防线全部放行：

1. **状态脚本**的口径是文件存在性：接没接框架、登没登记、文件在不在。它不看插槽里接的是新布局还是老组件。
2. **47 个契约测试**测的是变体隔离、SEO、包体、价格口径，没有一条测排版。规范里讲试用区布局的那一整节，零覆盖。
3. **偏离的理由**只写在代码注释里，没进决策日志。我没有机会拍板。

同一天另一页也是这个样子：骨架能跑、契约全绿，正文缺了 7 个区块（一个区缺 4 块、另一个区缺 3 块）。这一页是助手自己发现的，但发现得太晚：任务卡上「人工判断」那几项它打了勾，核的却是「链接没丢、变体没串」，没有逐块对规范的区块清单。

**根因**：这些检查是按「什么容易自动化」设计的，不是按「需求是什么」设计的。标题树检查只数二级标题的个数，包体闸只看 KiB，缺整块正文全部绿着过。「规则写在规范里」和「规则在守着页面」是两回事。

## 3. 补闸的顺序：先造闸，再修页

发现问题后的第一反应是去修那一页。我最后没这么做：修页面只解决这一页，剩下几十页会把同一个漏洞复制几十次。顺序换成了下面四步。

### 先造闸，立刻拿问题页试

把「区块齐全」「有没有残留老组件」「结构和范本是否一致」写成一条可执行的检查，三项分别是：

- **丢块检查**：解析老页面引用了哪些区块，对比新页面在插槽里挂了哪些；
- **结构差分**：新页面的领域目录和范本页逐项对比；
- **老组件残留**：已迁页面还在引用老组件目录，或直接用老的共享试用区，就算没迁完。

造好以后第一件事是拿出问题的那一页去跑，确认闸能拦住它。修完这一页的产物，同时就是这道闸的正向用例。

### 在已完成的页上校准误报

接着在已经迁完的几十页上全跑一遍。第一版有 5 处判定会造成系统性误报，校准掉以后，已完成页零误报、FAIL 为零，剩下 8 个 WARN 逐个看。没经过校准的闸，第一次大面积报红就会被人关掉。

「区块齐全」这类能断言的，直接进测试。领域测试从 18 条加到 51 条，缺一块就红。下面是一个通用的写法，关键是用例集合从清单派生，并且多一条「用例集合非空」的断言：

```ts
// 每个区的必备区块，取自页面规范的区块清单
const REQUIRED: Record<string, string[]> = {
  'section-a': ['block-a1', 'block-a2', 'block-a3', 'block-a4'],
  'section-b': ['block-b1', 'block-b2', 'block-b3', 'block-b4'],
}

describe.each(MIGRATED_PAGES)('$slug 区块齐全', ({ slug }) => {
  it.each(Object.entries(REQUIRED))('%s', (section, blocks) => {
    const { container } = render(<ModelPage slug={slug} section={section} />)
    for (const id of blocks) {
      expect(container.querySelector(`[data-block="${id}"]`)).not.toBeNull()
    }
  })
})

// 防空：清单读错导致一个用例都没跑，也是全绿
it('确实收集到了页面', () => expect(MIGRATED_PAGES.length).toBeGreaterThan(0))
```

老组件残留这种「不该出现」的东西，用一段脚本扫就够：

```bash
# 已迁页面还在引用老组件目录，判为没迁完
while read -r slug; do
  if grep -rqE "from ['\"][^'\"]*/legacy/" "src/pages/$slug"; then
    echo "FAIL $slug：仍在引用老组件"
  fi
done < migrated-pages.txt
```

### 断言打在行为和数据上

补测试时顺手重写了一条站内链接的断言。上一版按源码文本 grep `href`，后来卡片改成从数据源派生链接，这条立刻假红。这种写法两头不占：真丢链接时（链接来自数据）抓不到，换实现时反而误报。改成断言「数据源解析出的链接和封面都存在」加「区块确实渲染了」。守卫测试怎么写才不假绿、不假红，另一篇[守卫测试的三个要求](/blog/testing/guard-tests-three-rules/)专门讲。

### 机器判不了的，做成一页人工清单

最后把机器判不了的项做成一张验收清单卡，110 行：只列浏览器里肉眼能判的项，按页面从上到下排，每条附规范的节号。机器能判的不重复列，人只验机器验不了的。

给人的验收物也跟着变了。让验收的人读九百行规范既不现实也没必要，他要的是会验，不是会做。所以交付物改成三样：这张清单卡、老页 / 新页 / 范本页同区块的三栏对照、闸的原始输出。

还有一条写进了决策日志：偏离规范的决定只写在代码注释里，等于没写。那条注释写得再清楚，也在一个验收的人永远不会打开的文件里。

## 4. 结构闸全绿，行为还会悄悄丢

结构闸上线一周后，又冒出一类问题：页面结构完全对，但老组件在背后默默做的事，迁移后没了。

一个例子是页面的 JSON-LD 结构化数据。老页面把原始文案对象直接交给 schema 生成器，生成器从里面取前 5 条功能点填 `featureList`。迁到新框架后，传进去的换成了页面自己整理过的文案对象，里面没有那个字段。生成器找不到就直接省略：不报错，测试不失败，页面上用户也看不到。这是一次「迁移前有、迁移后悄悄没了」的回归。

**根因**：结构闸回答的是「区块在不在、挂得对不对」，回答不了「被替换的组件原来做了哪些事」。一个组件的职责里，看不见的那部分（结构化数据、草稿恢复、深链参数、失败时的提示）最容易在重写时丢。

**修复**：在验收时固定问四个问题，答得含糊或者只说「已对齐」，就当没做：

1. 被替换的老组件原来做了哪些事？每一件在新代码的哪一行？
2. 这段逻辑，共享层里是不是已经有了？
3. 这个数值、参数、文案的来源是哪个文件的哪一行？
4. 你读的是哪个分支上的规范？

同期 leader 在一次评审里改了几十个文件，我没有只问「改了什么」，而是追问「下次怎么保证不犯」。换回来的是一条能机械套用的审查方法：一个 `await` 就是一道缝，缝两侧的状态可能已经不同了。随后它被写成了一个 CI 闸，扫出一个症状完全不同、靠记清单永远抓不到的同类问题。这条方法另有一篇[一个 await 就是一道缝](/blog/frontend/async-seam-url-variant/)。

## 5. 写规范的人也会偏离：补闸要列全适用页型

后来统计评审记录里的违规类别，看到一个很有说服力的例子。规范的维护者（也就是 leader）在一次上线前的修复提交里，同时改了三处页面文案：

| 改动 | 有没有契约 | 结果 |
|---|---|---|
| 页头状态词改成了词表外的写法 | 有 | 契约立刻红，下一个提交改回 |
| 子导航第三个 tab 改了名 | 只对文本模型页断言，多模态页不断言 | 没红，三天后仍在主干上 |
| 新增区块的条目用了 `<dt>` 而不是规定的三级标题 | 标题树只数二级标题个数 | 没红 |

同一个人、同一次提交，三处偏离的命运完全由「这条规则有没有契约」决定。这排除了「新人不熟规范」这个解释：写规范的人改稿时，对规范的记忆也是摘要。偏离一旦进了主干，下一页就会把它当范本抄。

**修复**分三步：

1. 补闸时顺着「这条规则适用于哪些页型」查契约的用例集合，不只看规则有没有测试。这次是在同一个契约里给多模态页补了一组断言，再加一条「确实收集到了用例」的防空断言。
2. 闸抓到的存量偏离分两类：规范明文要统一的，直接改；归别人定的（这里文案由产品定），不改，登记进豁免表，写明原因和日期。
3. 豁免表要有测试盯着：断言「登记的页确实还偏离着」。修好了却没从表里删，这条就红，豁免不会变成永久后门。

```ts
const PENDING: Record<string, string> = {
  'some-page': '2026-10-06 文案由产品定，定稿前保留',
}

it.each(cases.filter((c) => !(c.slug in PENDING)))('$slug', ({ slug }) => {
  expect(subNavTabs(slug)[2]).toBe('tab-c')      // 第三个 tab 的名字
})

it('登记的页确实还偏离着（修好了就从表里删）', () => {
  for (const slug of Object.keys(PENDING)) expect(stillDeviating(slug)).toBe(true)
})
```

## 6. 强制项三件套：落点文件、机器闸、新上下文复核

页面之外，同样的事也发生在流程上。一份写得很清楚的代码审视流程，三次使用都「改不完」。翻会话记录才看清，差别在产出物上：有产出物的强制步骤三次都做了，没有产出物的要么没做、要么一句话带过。这段经过和数字，在[子代理的发现是线索](/blog/ai-workflow/subagent-findings-are-leads/)那篇里展开，这里只留结论和闸的写法。

**根因**：没规定「写到哪、长什么样、谁来对」的步骤，模型会按最省的方式满足字面。「强制」只有落在产出物上才成立。

**修复**是三件套，缺一件就回到老样子：

1. **落点**：开工时用脚本生成一份清单文件，六问、防线、验证表、自审表、发现台账各占一段。报告就是把这个文件填满，聊天里只给摘要。
2. **机器闸**：写完跑检查，核六段齐不齐、每格非空、✓ 行数等于台账条数，同一句话出现在 5 格以上算敷衍。它管「填没填」。
3. **新上下文复核**：派一个全新上下文的子代理，只给方法原文、清单、diff 和子代理的原始交回，逐项判「做了 / 没做 / 敷衍」。它管「填得对不对」。

机器闸的核心逻辑很短，下面是一个通用版：

```python
import collections, re, sys

text = open(sys.argv[1], encoding="utf-8").read()
rows = [l for l in text.splitlines() if l.startswith("|") and not re.fullmatch(r"[|\-: ]+", l)]
cells = [c.strip() for r in rows for c in r.strip("|").split("|")]

problems = []
if any(not c for c in cells):
    problems.append(f"有 {sum(not c for c in cells)} 个空格子")
for s, n in collections.Counter(cells).items():
    if n >= 5 and len(s) >= 6:
        problems.append(f"同一句出现在 {n} 格：{s[:20]}")
for sec in ("## 1.", "## 2.", "## 3.", "## 4.", "## 5."):
    if sec not in text:
        problems.append(f"缺段落 {sec}")

print("\n".join(problems) or "OK")
sys.exit(1 if problems else 0)
```

按新流程干跑的那一次，同一个分支比上一轮多抓出 1 个严重、4 个重要问题，其中 3 个是上一轮就存在、却被漏掉的。

第三件不能省。机器闸只能查「填没填」，主审亲手写错的证据，比如贴错行、行号引错、结论和事实相反、整列填同一句模板话，它一条也查不出，只有拿原文逐项对的新上下文复核能抓回来。具体的错法和案例也在上面那篇里。复核子代理自己也会错，所以它报的每一条，主会话还要再核一次。

同样的思路也用在了别处。要进生产库的 SQL，三次都是验收全绿后被 leader 审出同一类问题：验证用的表结构来自开发库，和生产的列宽、主键、排序规则不一样。第三次之后，「按生产建表语句造库、整份真跑」被做成了一条提交前的命令（细节见[要进生产库的 SQL](/blog/billing-regression/sql-on-prod-shaped-db/)）。同一类问题被审出第二次，就该换成闸了。

## 收尾

1. **先问尺子量什么** —— 测试全绿只证明尺子覆盖的部分；交付前列出哪些需求没有机器尺。
2. **先造闸再修页** —— 造闸、拿问题页试、在已完成页上校准误报、最后出人工清单。
3. **偏离要进决策日志** —— 只写在代码注释里，等于没给验收的人拍板的机会。
4. **补闸列全页型** —— 规则适用的每种页型都要有用例，再加一条防空断言；豁免表要有测试盯着。
5. **结构对不等于行为对** —— 替换组件时，逐条问老组件原来做了哪些事、在新代码的哪一行。
6. **强制项三件套** —— 落点文件、机器闸、新上下文复核，缺一件就会被执行成一行 ✓。

回头看，这两次「假完成」里没有一个检查是坏的，每个绿灯都是真绿，只是它们合起来没有覆盖需求。下次接手一套「检查齐全」的流程，我会先做一张表：左边是需求条目，右边是守着它的那条检查，右边空着的格子就是下一个「假完成」会出现的地方。
