> 一句话总结：跨进程共享状态，既要核对键和算法，也要核对连接指向。本地把两套存储合成一台，会把读错库的代码测成正确；拆开以后，还需要能证明读写路径实际发生的断言。

## 0. 起因：任务完成了，调度却没有按预期工作

我做过一次任务调度改动。每个上游渠道同一时刻能跑的任务数有上限，上限里还空着的位置，下文叫「名额」。网关在派发前检查候选渠道的剩余名额，任务执行器收到消息后再真正领取名额。希望减少明知没有容量还不断投递的情况。

本地有网关、执行器、数据库、Redis 和假上游。任务能创建、执行、回调、结算，相关用例也通过了。后来同事在线上发现，网关选出来的目标仍会频繁领取失败，应该发生的提前换档没有触发。渠道按优先级分成几档，「换档」指当前这一档的渠道名额都满了，网关直接把任务派给下一档，不再在满的那档上空等。

线上现象来自同事的修复提交说明。本文直接核对的是代码差异，以及事后保存的本地复现记录。它们指向同一个原因：网关在业务 Redis 里检查名额，执行器把名额写在另一台任务流 Redis 里。

这件事最值得记下的地方，是错误没有表现成连接失败。两台 Redis 都正常，命令都能执行，查询不存在的键也能得到一个合法结果。系统在使用一份错误的状态，外表却很平静。

## 1. 同一个键名，仍可能是两份互不相干的数据

当时的网关同时持有两类连接。业务连接用于自己的缓存和簿记；任务流连接用于与执行器协作。执行器只连接后者。

本地为了方便，两类连接最终指向同一台 Redis。任务流连接没有单独配置时，还会回落到默认连接。因此，写代码时选错客户端，本地也能读到正确数据。

把拓扑摊开，就能看清这个条件差异：

| 访问行为 | 本地合并存储 | 生产拆分存储 |
|---|---|---|
| 执行器占用名额 | 写入共享实例 | 写入任务流实例 |
| 网关错误地用业务连接读取 | 仍读到同一实例 | 读到另一实例 |
| 查询结果 | 看起来正确 | 键不存在，进入默认状态 |
| 单靠任务成功判断 | 通过 | 仍有机会通过 |

最后一行很容易忽略。网关预判失误后，执行器仍会做真正的准入检查。失败的任务还可能通过等待和重投最终完成。结果正确，并不能说明中间那次调度判断正确。

**根因**是本地环境消除了本来需要验证的差异。检查使用同一段算法、拼出同一个键名，只覆盖了逻辑层；存储位置属于另一层契约。

我现在会把共享状态的位置写成一组信息：实例或集群、逻辑数据库、键空间、读写角色。单独一个连接变量名说明不了这些。即使两个配置项的名字不同，它们也可能指向同一处；反过来，各进程都叫「默认 Redis」，也可能指向不同位置。

## 2. 修复按状态所有者选连接

这次修复把准入状态的连接选择收到了一个专门入口。凡是读取或修改执行器共享状态的地方，都从这个入口取客户端；网关自己的业务簿记继续使用原来的连接。

这里不能只修报错点。准入状态包含令牌、在跑数量、退避时刻，以及网关为后续派发记录的短期放行数量。只改「读在跑数」而留下另一个探测入口，任务换一条路径后仍会出错。

我会先列一张状态表，再沿调用链找所有访问点：

| 状态 | 谁写入 | 谁读取 | 应落在哪里 |
|---|---|---|---|
| 当前占用 | 执行器 | 网关、执行器 | 任务共享存储 |
| 令牌余额 | 执行器 | 网关、执行器 | 任务共享存储 |
| 退避时刻 | 执行器 | 网关、执行器 | 与退避作用域一致的共享存储 |
| 临时放行数量 | 网关实例们 | 网关实例们 | 本系统约定的任务共享存储 |
| 网关内部记录 | 网关 | 网关 | 业务存储 |

这张表不是要求把所有状态搬到一个库。它要求每种状态有明确归属，消费者跟着归属连接。是否共用实例，要由系统的协作关系决定。

专用入口还给审查提供了落点。以后新增共享状态访问时，可以检查是否绕开了入口。静态搜索能提示可疑位置，但遇到跨包封装或间接传入的客户端，仍要追到实际连接。

## 3. 三组对照说明了业务用例的盲区

事后的本地复现保留了三组记录。它们使用同一组业务用例，但第三组拓扑不同。修复后的网关还需要更新配套 SDK，因此这不是只替换单个文件的实验。

| 代码与环境组合 | 业务结果与核账 | 共享状态访问位置 |
|---|---|---|
| 修复前，单台 Redis | 通过 | 两类连接合在一起，无法区分 |
| 修复前，两台 Redis | 通过 | 网关探测与执行器占位分落两台 |
| 修复后，两台 Redis | 通过 | 已覆盖的准入访问落在任务流实例 |

最有用的是第二组。即使已经拆开 Redis，原来的业务断言依旧全绿。说明只改变部署形状还不够，验收需要增加新的观测量。

当时的做法是在本地两台 Redis 上分别记录命令，提取实际访问的键，再按准入状态的前缀归类。下面是一个最小的两台 Redis 环境，键名是示意：

```yaml
# compose.yaml：业务和任务流各一台，端口分开
services:
  redis-biz:      # 业务 Redis：网关自己的缓存和簿记
    image: redis:7-alpine
    ports: ["6390:6379"]
  redis-stream:   # 任务流 Redis：网关和执行器共享的准入状态
    image: redis:7-alpine
    ports: ["6391:6379"]
```

`docker compose up -d` 之后，两个终端分别挂上 `MONITOR`，再让系统跑一轮：

```bash
redis-cli -p 6390 MONITOR > biz.log &
redis-cli -p 6391 MONITOR > stream.log &
# ……跑一轮业务用例……
grep -o '"inflight:[^"]*"' biz.log    | sort -u   # 业务库上碰过哪些准入键
grep -o '"inflight:[^"]*"' stream.log | sort -u   # 任务流库上碰过哪些
```

我用执行器写任务流库、网关错读业务库的组合试了一次，两份记录各有一行：

```text
biz:    "GET" "inflight:ch-a"
stream: "INCR" "inflight:ch-a"
```

同一个前缀两台都出现，就是一边写、一边读在了另一台。`MONITOR` 每行还带客户端地址，可以用来分辨是哪个进程发的命令。它会拖慢 Redis，只在本地用。
旧版中，同一类状态在两台上都有访问：一边是网关的只读探测，另一边是执行器领取名额。修复后，已覆盖的访问集中到了任务流实例。

这里记录的是**访问**，不能只扫描测试结束后还存在的键。只读操作查询不存在的键，不会凭空留下一个键；如果只看最终键列表，就可能漏掉读错位置的那一侧。

前缀交叉也是线索，不是普遍成立的错误判据。两个业务有意在不同实例使用相同前缀，本来就可能合法。检查前应限定本系统要求共享的状态，写清允许重叠的原因，再判断异常。

## 4. 正向证据：确认读过，也确认读对

「错误实例里没有相关访问」是一个否定断言。如果网关根本没执行准入逻辑，这句话同样成立。为避免这种空转，我会同时要求正向证据。

先看这个 bug 本身。下面的 Go 示例把它缩到最小：没配任务流地址时，任务流连接静默回落到业务连接；网关读在跑数时用错了连接。测试用 [miniredis](https://github.com/alicebob/miniredis) 在进程内起 Redis，同一个用例分别跑单台和两台：

```go
type Clients struct{ Biz, Stream *redis.Client }

// 没配任务流地址时，静默回落到业务连接。本地单台 Redis 就是这样
func NewClients(bizAddr, streamAddr string) Clients {
	biz := redis.NewClient(&redis.Options{Addr: bizAddr})
	if streamAddr == "" {
		return Clients{Biz: biz, Stream: biz}
	}
	return Clients{Biz: biz, Stream: redis.NewClient(&redis.Options{Addr: streamAddr})}
}

// 执行器：在任务流 Redis 里占一个名额
func Acquire(ctx context.Context, c Clients, ch string) error {
	return c.Stream.Incr(ctx, "inflight:"+ch).Err()
}

// 网关读在跑数。buggy 为 true 时模拟旧代码：顺手用了业务连接
func Inflight(ctx context.Context, c Clients, ch string, buggy bool) int64 {
	rdb := c.Stream
	if buggy {
		rdb = c.Biz
	}
	n, _ := rdb.Get(ctx, "inflight:"+ch).Int64() // 键不存在时得到 0，不报错
	return n
}
```

```go
func TestInflightSeesWorkerWrite(t *testing.T) {
	for _, tc := range []struct {
		name                string
		twoInstances, buggy bool
	}{
		{"单台，旧代码", false, true},
		{"两台，旧代码", true, true},
		{"两台，修复后", true, false},
	} {
		t.Run(tc.name, func(t *testing.T) {
			biz, stream := miniredis.RunT(t), ""
			if tc.twoInstances {
				stream = miniredis.RunT(t).Addr()
			}
			c, ctx := NewClients(biz.Addr(), stream), context.Background()
			if err := Acquire(ctx, c, "ch-a"); err != nil {
				t.Fatal(err)
			}
			if got := Inflight(ctx, c, "ch-a", tc.buggy); got != 1 {
				t.Errorf("网关读到在跑数 %d，期望 1", got)
			}
		})
	}
}
```

`go test -v` 的结果正是本文的情形：单台上旧代码通过，两台上旧代码读到 0，修复后通过。

```text
--- PASS: TestInflightSeesWorkerWrite/单台，旧代码
--- FAIL: TestInflightSeesWorkerWrite/两台，旧代码
    admission_test.go:29: 网关读到在跑数 0，期望 1
--- PASS: TestInflightSeesWorkerWrite/两台，修复后
```

这个示例只断言了「读」。真实系统的夹具要准备业务实例 A、任务实例 B，目标只留一个名额，再补三条：网关再次申请同一名额时不能立即成功（竞争）；网关写入的共享放行记录出现在 B（写）；A 上没有本轮准入状态的访问。最后做一次对照：把网关访问切回 A，目标断言应当变红。

这些断言分别证明了读、竞争和写的位置。它们比「两个客户端地址相等」更接近实际行为，也能防止代码绕过某个配置入口。

命令记录还要能区分来源。修复后的历史记录核了连接和访问来源，确认网关确实参与了读取。只有执行器访问正确实例，不能替网关证明任何事。

本轮没有经过的路径也要列出来。例如，只跑到某一类任务的创建与结算，就不能宣称所有重试、恢复、取消入口都已覆盖。两台 Redis 的记录只说明这轮真正走到的代码。

## 5. 切版本复现，还要核实际运行的二进制

复现过程中还碰到一个很实际的问题：切到了修复提交，但配套依赖没有同步，编译失败了。重启脚本仍然拉起磁盘上残留的旧二进制。

这时如果只记录 Git 当前提交，报告就会把旧程序的表现记到新版本名下。服务能启动、进程有新时间戳，都不足以证明编译产物更新过。

我现在把前后对照的顺序固定为：确认依赖组合，构建成功，记录产物身份，重启，确认进程实际使用该产物，最后刷新证据里的版本信息。任何一步失败，都不进入下一轮结论。

这次双实例复现也没有顺便证明执行器所有新逻辑正确。历史记录明确写了执行器版本的限制。因此，文章里只把它作为「网关读写位置」的证据，跨仓字段兼容另见[SDK 字段与发版依赖](/blog/git-collab/sdk-field-release-dependency/)。

## 6. 可以带走的跨进程状态检查表

| 要回答的问题 | 最小证据 |
|---|---|
| 状态由谁维护 | 写入调用链与连接配置 |
| 所有消费者读哪里 | 实例、逻辑数据库、键空间的并列表 |
| 本地是否保留了生产的存储边界 | 至少一次拆分存储的测试 |
| 目标路径是否真的执行 | 带来源的命令记录或行为断言 |
| 错误版本能否被识别 | 同一夹具下的修复前后对照 |
| 测的是哪份程序 | 构建结果、产物身份、进程与版本记录 |
| 结论覆盖到哪里 | 实际经过的入口和未覆盖项 |

这张表可以用于共享缓存、锁、会话和任务恢复。具体实现会变，但「谁写、谁读、是否读到同一份状态」始终需要回答。

## 收尾

1. **保留存储边界** —— 本地环境越方便，越要确认它有没有消除要测试的差异。
2. **增加行为观测** —— 任务完成之外，还要证明中间决策读取了正确状态。
3. **同时核正反两面** —— 错误位置没有访问，正确位置也必须有目标路径的访问。
4. **绑定实际产物** —— 编译失败后的重启，可能只是再次运行旧程序。
