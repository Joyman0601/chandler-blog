> 一句话总结：这周做了三件事：审一批推了但没开 PR 的分支，修完审出的问题；在生产用真实账号做了一轮上线前回归；后半周开几个窗口并行改重试和渠道禁用。最大的收获是两条规矩：分支状态只问远端，结论要经得起第二天的复核。

## 0. 这周在做什么

周初是上周的尾巴，四件小事，各有一个坑：

- **旧模型页下线后的跳转**。只看「301 落到 200」不够，还要核用户落到的那一档对不对：URL 参数、接口返回的模型、价格档位、页面实际渲染的变体，四样逐个看。同族页面返回 200，默认选中的却可能是另一档。
- **登录组件的白框**。Google One Tap 在暗色模式下多出一块白框。站点给页面设了暗色的 `color-scheme`，浏览器就给 iframe 原本透明的画布垫了一层不透明底色。修法是只对 One Tap 的 iframe 设 `color-scheme: normal`，初始化时把站点当前的配色传进去。视觉正常、回调拿到凭证、真实会话登录成功，是三个分开的验收点。第三个第二天就出了问题，见第 3 节。
- **韩语文档页的删除线**。段落里裸写的 `1~15` 在 GFM 下被渲染成了删除线，DOM 里多了一个 `<del>`。把数字范围写成行内代码就好。发布后要看最终渲染出来的 DOM，源码看着没问题不算数。
- **异步任务的退款回归**。第一轮有两单在采样结束时还是 pending，账本后来却退款正确。问题出在观察窗口，不在业务：隔离部署起成了非主节点，没有跑重试兜底；worker 重新认领任务的等待时长，也比测试脚本的采样窗口长。判业务 bug 之前，先查调度配置和终态有没有记账。

周二到周四是主线：审一批分支（第 1 节），在生产做一轮上线前回归（第 2 节）。周五起开了三个并行窗口，各做一个后端任务：上游报「账户欠费」时换渠道、同一渠道上的任务重建重试、渠道自动禁用。同时把一批已推送的分支追上各自的主干。周末所有窗口停了一天半，恢复后又碰上主干前进。

## 1. 分支审计：先把事实钉在远端，再审代码

拿到的是一份清单：哪些分支推了、还没开 PR。我没有直接审 diff，先把每一条的事实重新钉了一遍：远端上到底有没有、指向哪个提交，和主干的 merge-base 在哪，主干是不是已经包含了它。清单是前几天生成的，本地的 `origin/*` 也可能过期，这一步省不得。结果有几条早已被主干包含，不用再审；剩下的一大半和当时的主干冲突。

钉事实就这几条命令，每条分支都跑一遍：

```bash
git fetch origin --prune
git ls-remote --heads origin "$BR"                              # 远端到底有没有、指向哪
git merge-base --is-ancestor "origin/$BR" "origin/$TRUNK" \
  && echo "已被主干包含，跳过"
git log --oneline "origin/$TRUNK..origin/$BR" --author="$ME"   # 主干之外还有没有我的提交
```

审出的问题按类型归，比按分支归有用：

- **异步归属泄漏**：上传还没回来，用户切到别的档又切回、点了重置、或者组件已经卸载，回调回来照样把旧图写进状态。三条路径要分别测。
- **三种长度混用**：字符数、token 数、UTF-8 字节数在同一条校验链上被当成一回事。UTF-8 里常用汉字占 3 个字节，同一个数字当上限，松紧能差三倍。
- **失败后继续往下走**：参考图下载失败时，旧代码丢掉这张图、照样提交生成。改成直接返回错误，回归里断言「失败时提交次数为 0」。
- **依赖钉在旧版**：消费方钉住的 SDK 版本里没有这次的修复。本地组合能过，不代表发布出去的版本能过。

修完做了一轮独立验收。15 个业务验收点，第一轮 11 过、3 不过、1 个没法验证。3 个不过里，有一个是随交的测试夹具自己写错了。我把它和业务修复分开记：业务修复已经证明有效，夹具另修。补完之后 14 过、0 不过，剩下那 1 个要等依赖先发布。

这一轮最有用的，是回头查自己漏检的地方。有一处迁移用例，预期值和实现取自同一张映射表，实现错了，测试跟着一起错。我补了四类检查：

1. **预期要有独立来源**。迁移后的预期从旧行为和当初的决策里取，不从实现或修复说明里推。
2. **最小超限用例**。只测「远超上限」会漏掉边界，要有「刚好多一个字节」的用例。
3. **失败之后的副作用**。请求失败了，状态有没有残留、钱有没有退、计数有没有回滚。
4. **交付物对原始数据**。报告里的数字从原始输出重新取，不从中间稿抄。

审查工具也修了两个洞：证据引用只查格式，不查文件在不在、行号对不对；一条只读的查看命令，会把审查绑到一份历史报告上。

周五到周末又做了一次批量追主干。分支都已推送，不能 rebase，做法统一成：从远端头开一个 detached worktree，`git merge --no-ff origin/<目标分支>`，推送时仍是快进。坑出在一个按提交日期生成的 sitemap 文件上。生成器对每个页面取 `git log -1 --format=%cI -- <路径>`，而 git log 遇到合并提交，会沿第一个「这条路径没变」的父往下找。我的合并提交第一父是分支，PR 的 CI 却跑在平台合成的合并 ref 上，第一父是主干。两棵树一模一样，算出的日期却不同。解法是合成一个「主干在前」的提交，在它上面重算：

```bash
SIM=$(git commit-tree "$(git rev-parse 'HEAD^{tree}')" -p origin/main -p HEAD -m sim)
git worktree add --detach "$TMPDIR/sim" "$SIM"   # 在这里重跑生成器，把结果搬回分支
```

测试失败按用例名和目标分支的头比，只认我引入的那部分。

## 2. 生产回归：两个平台问题，一个第二天被收窄

周三到周四，用真实账号在生产跑了一轮上线前回归：从用户视角把能点的都点一遍，每一笔扣费都和账本对上。功能本身没有阻塞性的缺陷，碰到的是两件平台层面的事。

**入口 403**。一个新加的下载接口，浏览器和命令行打开都是 403。响应来自 CDN（内容分发网络）入口，没到后端。我做了一组对照：不带签名打几个路径，已有的另一个下载接口能回后端的 404，新路径和随手编的路径都在入口 403。这说明入口按白名单放行，新路径没登记，上线手册的运维步骤里也没有这一步。改入口配置不归我，我把它列成待定项，然后隔一段时间用一个不存在的编号零成本探一次：

```bash
# 403 = 还在入口被拦；404 = 已经到了后端（编号不存在，后端回 404）
code=$(curl -s -o /dev/null -w '%{http_code}' "https://api.example.com/v1/exports/does-not-exist")
echo "$(date '+%m-%d %H:%M') $code" >> probe.log
```

第 8 次探到了后端的 404，放行发生在第 7、8 次之间。放行后，我再用真实链接把下载内容逐列核了一遍。

**非流式长请求 524**。经 Cloudflare 的非流式请求超过约 100 秒，客户端收到 524，拿不到结果，也拿不到请求 ID，源站却照常跑完并扣费。当天我写的是「用户照文档用就会碰上」。第二天复核才发现，文档写的默认地址根本不经过 CDN：同一个请求体打过去回 200，跑了 165.8 秒。测试脚本里写死的是备用地址，没写为什么。结论收窄成「只影响走备用地址的长请求」，当天发了更正。细节见 [经 CDN 的非流式长请求](/blog/billing-regression/cdn-524-long-non-stream/)。

还有一处口径值得记下：账本的时间字段在不同类型的记录里不是一个意思。同步文本请求在结算时才写行，时间是完成时刻，请求在途时根本没有这一行；异步媒体任务在提交时就建行，时间是提交时刻。按时间窗判断一笔请求进不进账单之前，先按类型分开。整轮回归的做法见 [用真实账号做上线前回归](/blog/billing-regression/pre-launch-regression-real-billing/)。

## 3. 卡住的地方

- **三个并行任务，各卡在一处时序上**。换渠道的目标是：A 失败换 B，只换一次、只结算一次。最后的分工是 SDK 碰到渠道级的致命错误就不再重发，worker 的完成路径请求换渠道，网关没有候选时直接失败并退款。验证用假上游按端口数命中次数；B 更贵，实扣也要跟着变。同渠道重建重试那边，旧任务迟到的失败回调消耗了新任务的重试次数；我第一版定的阈值，也被真实的失败分布推翻了。渠道自动禁用那边查出三处：跨供应商重派时提前返回，A 的失败没上报；一条 403 排除规则误伤了别的供应商；进程内 5 分钟的去重在手动启用后没有清，启用过的渠道再也不会被禁。前两处修了，第三处在多实例下只能清当前进程，作为限制写进交付说明。
- **窗口停摆，还改了名**。周六上午起所有窗口停了一天半，周日晚上才恢复。恢复后会话名变了，按旧名字发的消息对方收不到。之后交接一律先查对方现在叫什么，再发。
- **两边都加了同一件事**。主干前进了一大截，leader 在同一段代码里也加了「重派时上报源渠道」。冲突两边都留，就会上报两次、甚至重派两次。最后合成一个出口，保留业务代码那一侧。go.mod 里的 SDK 版本冲突，要换成一个同时包含两边改动的版本。复核的窗口在看合并结果之前，先写下了 T1–T11 共 11 条预期。
- **只在 UTC 零点后才红的测试**。在基线上同样红，是存量问题，不是我引入的。
- **机器扛不住**。几个窗口同时构建，load average 一直在 45 到 65。构建改成串行，每次先删 `.next`。文档站的整站校验在主干上也会卡住，判为环境问题。macOS 没有 `timeout`，卡住的命令用 perl 的 `alarm` 兜底。
- **登录的第三个验收点**。真实登录时，选完账号提示框就静默消失。助手先猜根因是「某个 0×0 元素」，我拿后来的反馈一对，对不上，就把这个猜测撤回了。这一项当周没有查完。

## 4. 学到的

- 推送和合并状态只问远端，不看本地的 `origin/*`，也不看几天前的清单。见 [推送和 PR 状态只问远端](/blog/git-collab/push-status-ask-remote/) 和 [出 diff 前先定主干和起点](/blog/git-collab/diff-range-trunk-merge-base/)。
- 验收预期要有独立来源，测试夹具的错误和业务修复分开记。见 [当验收者而不是开发者](/blog/testing/acceptance-as-reviewer/)。
- 清掉站点 cookie，撤不掉 Google 那边的授权。账号选择器不是首次同意页，想复现首次的条款提示，要去 Google 账号设置里撤销授权。见 [Google One Tap 的暗色模式白框](/blog/frontend/google-one-tap-dark-mode/)。
- 估代理类接口的 token 花费，大头是缓存读，不是输入输出。我拿本机 150 个会话一算，输入侧 97.6% 是缓存读。见 [估 agent 类接口的花费](/blog/billing-regression/agent-api-token-cost/)。
- 别人要我撤回某个改动时，先 `git log -- <路径>` 列出这次撤回会连带撤掉哪些修复，再动手。
- 交付附件和报告正文走同一套敏感词扫描，附件不是例外。

## 收尾

1. **事实钉在远端** —— 本地的 `origin/*` 和几天前的清单都会过期，`ls-remote` 加 `merge-base --is-ancestor` 才算数。
2. **结论按复核收窄** —— 524 那条第二天被默认地址的实测推翻了一半。当天就该先问一句「用户默认走哪个地址」。
3. **预期不从实现里推** —— 预期和实现同源，测试就只是在复述实现。
4. **两边都留不等于都对** —— 两边各加了同一件事，保留两份就会执行两遍。

这周的错大多出在「我以为的现状」和「真实的现状」之间：清单是旧的、地址是写死的、会话名换了。下周开工前，先把要依赖的事实重新问一遍真实来源，再往下做。
