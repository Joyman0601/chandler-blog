> 一句话总结：这周最有价值的进展，是把「已经完成」重新拆成触发条件、可观察结果和证据范围，发现了几处原先成功用例没有覆盖的路径。

## 0. 这周在做什么

这一周跨过月末，工作主要围绕一个多供应商 API 网关展开：补计费和流式收尾、核模型接入的发布依赖、做已经合入改动的回归，同时继续媒体接口调研。

我没有把每天的测试次数直接累加成成绩。重复执行、独立场景、父测试与叶测试不是一个统计单位；同样的历史调用也不该在下一份记录里再算一次。

更值得记录的是，几次复审让原来的完成结论收紧了。发现边界后，能在本地复现和修复的继续完成；缺少生产权限的部分，则把需要的现有样本和具体字段交清楚。

## 1. 计费与恢复：成功请求掩盖了失败路径

工具调用的正常结算补齐后，复审又发现一种组合：整体响应失败，但回执已经报告工具完成。如果在读取这份用量前就按失败全退，已经产生的工具费用仍会漏掉。次数怎么算和失败后收不收是两条规则，要分开写清，见[多源用量计数那篇](/blog/billing-regression/usage-snapshots-items-authority/)第 6 节。

补扣恢复的问题更直观。一轮复审里，结算失败后的补扣记录已经落库，数据库也恢复了，冻结却迟迟不收敛。手动调用一次消费者，马上结清；测试里一直是手动调用，所以恢复从来都是成功的。顺着启动流程看才发现，补扣消费者被绑在媒体分发开关后面，只跑同步文字请求的节点不开这个开关，也就没有补扣循环（见[长请求计费那篇](/blog/billing-regression/long-request-lease-durable-settlement/)第 5 节）。

修法是把消费者的启动条件单独拆出来，再在目标配置下起节点，不手动调用，看冻结能不能自己收敛。写进待处理表，不代表有人会消费。

这些问题让我把链路分成几个独立问题：原请求完成了什么，账务需要结算什么，失败记录由谁恢复，恢复时是否重复记录统计，旧版本失败记录怎样升级处理。

相关修复有本地账本与负对照证据，但本地模拟没有回答全部消费者是否已升级、是否共用预期数据库、生产积压是否收敛。记录里继续保留这些边界。

## 2. 流式收尾：终态、用量和连接结束各有信号

流式响应里，内容结束、用量完整、扫描结束和保活停止并不同时发生。把其中一个信号当作全部完成，可能造成两种相反现象：请求已经读完却迟迟不结束，或者连接先关闭导致迟到用量丢失。

我先碰到的是「结束太晚」：终端已经显示完整内容，连接还在等。读取协程读到 EOF 后，往一个普通 channel 发一次 stop，主循环和保活协程都在收。一次发送只会被一个接收方拿走，保活先拿到，主循环就继续空等。对照只差一行（见[流式收尾那篇](/blog/model-onboarding/stream-terminal-usage-eof-lifecycle/)第 2 节）：

```go
stop <- struct{}{} // 一次发送：只有一个接收方拿得到
close(done)        // 关闭通道：所有接收方都能看到
```

反方向是「结束太早」：终态一到就开始短宽限，用量行还有半行在路上，最后文本完整，用量却成了零。

所以这周的后续验证没有只盯耗时。需要同时看 EOF 是否及时传播、迟到用量是否留下、原超时是否仍约束请求，以及保活是否干扰完成通知。我还故意做了两次最小变异：去掉「先拿到有效用量」这个前置条件，慢传用量被归零；恢复竞争消费的完成通知，EOF 又被拖住。两条断言各自能抓到旧缺陷，才说明它们守得住。

维护者的后续修改和我做的验证分别记录。新版本到来后，旧版本的通过结果不能直接移过去；用同一组目标场景补验，才知道修改后的行为。

## 3. 验收反例：页面能显示也可能点不对

前端有两处让我印象很深，都写在[页面可见与动作生效那篇](/blog/frontend/visible-page-interaction-contract/)里。第一处是语言链接。用法语浏览器打开 `/fr/`，拦住交互脚本，在它接入前点「English」：原生链接正常跳到 `/en/`，保存手动选择的处理却还没接上。目标页的自动识别读不到选择，又把人送回 `/fr/`。浏览器语言一直没变，丢的是「这次是用户主动选的」这条信息。

第二处是手机上的长下拉。数据和日期计算都正确，列表向上展开后进入固定导航的区域，导航层级更高，顶部选项在 DOM 里，手指却点不到。想知道某个选项的中心点被谁占着，可以在控制台跑这几行：

```js
const r = option.getBoundingClientRect();
const hit = document.elementFromPoint(r.left + r.width / 2, r.top + r.height / 2);
console.log(hit !== null && option.contains(hit)); // false：上面盖着别的元素
```

修后验证开始围绕实际动作：外部脚本没有就绪时点击语言，是否先保存再跳转；不同视口里选择顶部和底部选项，实际命中的是否就是目标项。负对照也按动作做：只删掉新增的早期保存脚本、其他不动，最终地址回到 `/fr/`；恢复旧下拉组件，手机上被遮挡的场景再次失败。下拉在竖屏、横屏和桌面三种视口里，各点列表首、中、末三处。

## 4. 调研纠正：算式正确，需求也可能理解错

媒体接口和图像增强调研里，资料数量增加并没有自动带来正确结论。10 月 30 日的会上，leader 在一个网页计算器上演示怎么算价，随手选了「720p 放大到 1080p、2 秒视频」这组参数，原话带着「随便选一个」「比如说」。助手整理会议时把这组参数写成了必须支持的接入门槛，后面的推荐和排除理由都是从它推出来的。

11 月 1 日我要求回看原话，才把演示和业务要求重新分开。另一次会上也有一处：我说某个方向「先放一放」，leader 当场纠正「不是先放」。只凭记忆复述，这种紧跟着的更正最容易丢。读法还是[来源分级那篇](/blog/methods/source-tiers-meeting-transcript/)第 3 节的老办法：逐字稿按话题切段，读到话题结束，以最后的口径为准；一个举例只是演示，不能直接升级为要求。由错误门槛推出来的推荐、排除理由和测试计划也一起更正，不能只改一段说明。

供应商资料中的参数、单位和截图也要逐项核对。两份调研意见一致，仍可能共同漏掉一个入口或抄错计费单位。公开估价和网页计算器只能支撑报价比较，质量、速度和账单还需要真实对照。

## 5. 学到的：完成一项检查，要知道它排除了什么

我把这周的方法收获归成三个问题。

1. **旧实现也能通过吗** —— 如果能，当前观察项不足以证明修复生效。第 2 节的两次最小变异、第 3 节只删早期脚本的负对照，问的都是这个。
2. **最后一步真的发生了吗** —— 写入补扣表、收到终态、展示链接都只是中间状态。第 1 节的补扣记录落了库，消费者却根本没启动。
3. **证据覆盖的是哪一层** —— 源码合入、本地通过、用户侧成功和生产运行分别取证。第 1 节的本地账本正确，回答不了生产节点是否都已升级。

## 收尾

1. **覆盖失败组合** —— 正常成功路径之外，还要组合回执、终态和恢复条件。
2. **按动作验收** —— 看实际请求、账本和点击结果，不以存在某段代码代替。
3. **保留真实限制** —— 没有生产运行证据，就不把本地结果升级成上线闭环。
