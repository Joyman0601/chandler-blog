> 一句话总结：节后第一周线最多，接入、重定向、生产回归、写 SOP 交替着做。最贵的教训来自数据脚本：验收全绿之后被审出三次问题，每次是不同的原因，最后把「在生产形状的库上整份真跑」做成了一条命令。

## 0. 这周在做什么

假期回来，手上同时有这些事：

- **接入**：两个视频生成模型、一个图像模型（两条供应商渠道），外加给一个视频厂商新开一条供应商渠道；
- **重定向**：把一个旧模型名指到新型号；
- **调研**：一份旧模型的迁移方案（上游平台公布了退役计划），一份「别家平台的某个模型是自部署还是转售」的判断；
- **上线后**：上周那个语音模型的生产回归，以及从回归里长出来的第一版回归测试 SOP；
- **返工复测**：leader 重做了语音模型的方案，在新契约上复测，本地派发 28/28、stream 派发 4/4，官方音色全部通过；
- **前期阅读**：一个运营后台的需求，只读不写。

## 1. 接入和数据脚本：代码的坑能测出来，数据脚本的坑测不出来

接入这一块，开工前先在所有远端分支里搜了一遍模型名。前人做过两次，都没合进主干，基线早就过期了。里面的决策（对外名、契约）可以沿用，代码只能在当前主干上重做。

然后是名字。新模型的营销名在代码里已经被占用了：一个中转渠道的 Beta 版借了这个官方名。全库按名字做子串匹配的规则一共 25 处，逐条代入新名字，命中 11 处。新名字一律带来源后缀，用精确匹配，并锁住存量模型的返回值。另一个视频模型也是名字的问题：预扣用子串判断家族，实扣用精确匹配，新名字在两边落进了不同的家族。改成一张家族表，预扣和实扣共用一个函数。

上游的行为也有几处和文档对不上（实测）：

- 不支持的分辨率、非法的时长，上游先返回 200 受理，过一会儿任务才报错。网关改成本地先拦，直接 400；
- 不认识的参数照样 200；
- 官方页面写着不支持图片输入，实测首帧、首尾帧都能用；
- 结算回退的路径会把倍率乘两次。守卫是名单式的，新成员不会自动受到保护，默认档被多乘了一次倍率；
- 图像模型的两条渠道，在「什么都不传」时默认行为不同：出图档位、搜索开关、比例映射各不一样。列成表之后，由网关显式统一，不靠渠道默认值；
- 裸请求能通，经网关走 SDK 却失败。SDK 固定下发的一类安全设置被新上游拒收，而这个 4xx 被当成瞬时错误重试了 3 次，其中一次等满了 480 秒。

数据脚本的问题更难受。同一份初始化 SQL，验收全绿之后连着被审出三次问题：

1. 列宽：本地库的同一列比生产宽得多，在本地写得下的值，到生产上写不下；
2. 生产表缺一个本地有的列，也没有唯一键，脚本报 `ERROR 1054`；
3. 排序规则不一致，报 `ERROR 1267`。

三次的原因各不相同，共同点是本地库不是生产形状。只读评审看不出来，只有拿生产的建表语句整份真跑才行。后来把它做成了一条命令：按线上建表语句建库，覆盖四套排序规则，跑固定场景，最后通过 phpMyAdmin 网页通道执行一遍，因为生产上就是从那里执行的。详见 [在生产形状的库上跑 SQL](/blog/billing-regression/sql-on-prod-shaped-db/)。

顺带改了两处脚本逻辑。第一，安装脚本按「型号映射」认渠道，不按渠道名，因为运维随时可能改名。第二，上线段、回滚段认渠道的条件比安装段宽，会误伤别的渠道，改成和安装段一样窄。重跑测试也要按「运维改过之后」的状态来测。

重定向的坑在「旧键」。改了别名的指向之后，按解析后名字存的端点规则会改去管新目标。多变体页改了默认落点后，所有不带变体参数的旧入口（301 跳转、价格页的链接、旧公告）都静默落到了新默认。改之前要把入口和存量配置列全，逐个按原意核对。见 [改名和重定向的涟漪](/blog/model-onboarding/rename-alias-redirect-ripple/)。

## 2. 生产回归和第一版 SOP：真扣费，四层核对

上周的语音模型上线后，用我自己的账号在生产上真扣费跑回归，分四层核：

- **付费单**：每一单都核三个数，预扣等于公式、实扣等于公式、实扣等于余额差；
- **失败单**：全额退回；
- **有时效的资源**：自建音色到了有效期，回的是过期错误，不是笼统的失败；
- **旧名下线**：按计划该下线的旧模型名，是不是真的不可路由了。

最后一层要零花费地判断。办法是利用「先选渠道、后校验参数」的端点：故意不传必填参数，回 400 说明还选得到渠道，回 404 才是真下线。前提是先拿一个不存在的模型名做对照，它必须回 404，否则这个端点的校验顺序就不是预想的那样：

```bash
# 对照：不存在的模型名必须回 404，证明这个端点先选渠道、后校验参数
curl -s -o /dev/null -w '%{http_code}\n' https://api.example.com/v1/images/generations \
  -H "Authorization: Bearer $API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"no-such-model-xyz"}'

# 被测：故意不传必填的 prompt。400 = 还有可用渠道，404 = 真下线了
curl -s -o /dev/null -w '%{http_code}\n' https://api.example.com/v1/images/generations \
  -H "Authorization: Bearer $API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"old-model-name"}'
```

这一层判出几个旧名仍可路由。leader 在会上口头说过下线延期（转述，没有书面记录），所以我没写成缺陷，改列为「待跟进」。

回归里还查到一个渠道的健康度明显偏低。原因是复刻时几种跟录音有关的用户侧错误，只有渠道专属规则认得，而健康度只认全局规则，这些错误就被当成未知错误计进了失败。用 git blame 查到，「渠道规则不进成功率」是有意的分层设计；全量改会动大半条规则的计入口径，所以默认窄修，全量方案交给 leader 定。测试要按「只加载线上那份配置」来跑，因为代码里的默认值会被线上配置整类覆盖，做了 19 个变异来验证测试守得住。顺手还发现，渠道探活的间隔在代码里按分钟算，注释写的是秒，差 60 倍。配置项的单位，以读它的那行代码为准。

还有一个小坑：回归脚本用 Python urllib 拉一个 CDN 上的文件，回 403，正文是 `error code: 1010`。这不是链接过期，是 Cloudflare 按客户端签名拦了 urllib 的默认请求头，换一个 User-Agent 就是 200。

回归做完，从会议逐字稿里整理出 92 条需求，写成第一版回归测试 SOP：通用 10 段加一个音频细分，共 75 个检查点。顺序是先静态页面，再 Playground，接口只补前端测不到的。每个检查点写成两栏：

| 左栏：通用检查点 | 右栏：这次的实例 |
|---|---|
| 要验证什么 | 这次具体测了哪个页面、哪个请求 |
| 在哪里、怎么做 | 原样可粘贴的步骤或命令 |
| 判定：什么算过 | 实际看到了什么 |
| 出处：需求的哪一条、会上谁说的 | 证据截图或响应文件 |
| 阻不阻塞上线 | 结论：过 / 不过 / 待跟进 |

另外配了一页回归流程演示：14 个步骤、31 张截图，截图上用红框编号，每步配「看什么 / 应该是什么 / 这次结果」三栏。后来重读逐字稿，又整理出 56 条口径，其中有几处是讨论到后面被改口的，只读第一句就会写反。见 [上线前回归：生产真扣费](/blog/billing-regression/pre-launch-regression-real-billing/) 和 [来源分级和会议逐字稿](/blog/methods/source-tiers-meeting-transcript/)。

## 3. 卡住的地方

- **派生简报和任务原文冲突**。助手把任务拆给几个窗口时，在简报里自拟了一个报告结构，和任务原文要的不一样，窗口照简报交了。我读完觉得内容不明确，对照原文重审才找到原因。之后简报逐条引用原文的交付物和格式要求。见 [多窗口并行开发](/blog/ai-workflow/multi-window-parallel-dev/)。
- **推送前的代码审视是追问后才补的**。助手没把审视当成固定一步，我追问后才补做，补出来的几条修复落在已经发出去的包之后。
- **守卫测试空转**。浏览器走查脚本断言页面表格里的数值，测试是绿的，但它其实什么都没测到：表格默认停在别的标签页上，要测的那张表根本没渲染；页面上的负号是 U+2212，断言里写的是 ASCII 连字符，永远匹配不上。之后每条否定断言都先配一条正向对照。
- **假 key 的 401 证明不了请求体合法**。拿假 key 打文档里的示例请求，回 401，就当成示例没问题。后来发现故意写坏的 JSON 也回 401，鉴权先于解析。要先拿坏 body 做对照。
- **上游回「型号未注册」的 404**。拿到 key 之后先做一次零成本预检，把「key 不对」和「型号还没上架」分开，不要等到付费请求才知道。
- **推理档位分不出来**。测思考档位时输出上限设得太小，三档都贴着上限，看起来一模一样。要先用一单不封顶的最高档量出自然用量，再定上限。

## 4. 学到的

- 数据脚本的验收不能只在开发库上跑。开发库、导出的库、迁移出来的库都不是生产形状。
- 报告第一屏按 leader 的验收点组织，待拍板的只留必须定的 3 项，其余写成「已按默认处理，不同意再改」。见 [给 leader 的报告](/blog/methods/report-for-leader/)。
- 调研表要逐格有出处。由子代理采集、再人工压缩的表，交付前用盲核页复核：每题只给原文链接和问题，先写下自己看到的，再揭开报告值。见 [盲核页](/blog/testing/blind-crosscheck-page/)。
- 判断别家平台的模型走的是谁，要按信号强弱取证：页面原文最强，参数和素材限制的指纹其次，价格比例和能力上限最弱。见 [从指纹判断上游](/blog/methods/identify-upstream-fingerprint/)。
- 新上游的错误原文，要逐条过一遍网关的错误分类器，没命中的会把上游原文直接透给用户。

## 收尾

1. **数据脚本整份真跑** —— 在生产形状的库上跑，只读评审看不出列宽和排序规则。
2. **名字代进每一处查表** —— 子串规则会把新名字误归别类，营销名可能早被占用。
3. **零花费判断可路由** —— 故意缺参数，先拿不存在的模型名做对照。
4. **转述不写成确认** —— 会上口头说的事，列为待跟进，标明来源。

这一周比前两周杂得多，但规律是一样的：每一次「验收全绿之后又被审出问题」，都指向一个没有被机器量过的地方。这次补上的是数据脚本那一块。周末把这版 SOP 交给了 leader，下一步拿下一个模型的上线来验它。
