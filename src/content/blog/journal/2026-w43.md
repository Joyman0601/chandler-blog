> 一句话总结：这周先补齐回归与能力证据，后半周再压缩重复检查，并核对计费和结果交付的边界。共同的教训是：「回了 200」「控制动作回了成功」和「真的做到了」之间，隔着一个能证明它的字段。

## 0. 这周在做什么

这篇覆盖 10 月 19–25 日。前半周侧重取证和页面框架，后半周把注意力移到回归效率与异步任务的收尾边界。

周一、周二主要在后端这边：给几个文本模型做上线前回归，把每条结论的证据补齐；同时复查给客户看的能力文档，凡是写了「支持」的，都拿真上游打一遍。

周二到周五，每天抽一段时间，给一个托管代理接口跑付费测试。模型在服务端跑，命令在本地挂的执行器里跑。测的是隔离、用量口径和控制动作，花费都在每日预算内。

剩下的时间都在一个运营后台上。上周做了 React 加 Go mock 后端的原型，这周接上真实的本地服务。周四 leader 看完，第一句反馈是「最大的问题不在细节，在框架」，于是整体重排；周五凌晨接上主服务已有的接口。

## 1. 取证：200 和回执都不等于做到了

### 回归和能力文档

回归里最常见的误判，是把状态码当结论。回 200 不等于模型读了 PDF，接受了搜索工具的参数也不等于真的去搜了。每条结论都要找到证明它的那个字段：PDF 要问只有文件里才有的细节，搜索要看响应里有没有搜索痕迹。同族模型做对照，要同一个请求、同一个版本、同一个时间窗。客户端 900 秒超时以后，还要去后端查这一单的终态，这次是失败、零扣费。

这周撤回过一个说得太宽的结论。长输入测试用的是极端重复的字符，请求失败了，我写成了「长输入不可用」。第二天换成有意义的长文本，一直到约 98 万 token，六项检查都通过，原结论撤回。失败样本只能说明它自己，结论的边界要按样本画。

另外两处值得记：视频理解在 fps=1 时失败，换成 fps=5 就过了，输入 token 从 865 涨到 3,637；我本想当无效探测用的 `n=0`，被受理了，还扣了费。所谓零成本探测，要先确认它真的会被拒。

能力文档那边改了四处，每一处都来自实测：

- 示例缺了一个必填字段，网关直接拒，补上；
- 第二轮回传工具结果，七种写法全部 400，文档改成写明这个限制，不再给操作步骤；
- 「PDF 不带文件名也能用」，这个字段改回可选；
- 「文件和图片混在一条消息里也能用」，撤回原来「不能一起发」的说法。

还有一个被重定向的模型：模型目录里声明它支持几种接口格式，真调用时有的回 500，有的回「不支持」。目录会驱动客户端自动选格式，声明错了比不声明更糟。这个模型还有一处用量统计的口径偏小。查这类问题要分清：上游的原始用量、计费用量和成本是三层口径，彼此不能互相代替。

### 托管代理接口

四天测下来，最反直觉的是「控制动作回了成功」和「状态真的变了」经常不是一回事：

- 断开进度流不会停掉任务，重连也不补发错过的事件；
- 执行器断线重连，可能把一条命令重跑一遍；
- 取消大约 6 秒结束这一轮，但已经开始的本地命令可能还在写文件；
- 执行器离线时提交超时，等它连上，那条提交照样跑了。

用量口径上，会话接口拿不到单个会话的用量，要逐单算钱，只能先按预估算。

成本结构也和直觉不同。命令等 4 分钟，期间模型仍在周期性地被调用；会话空闲 36 分钟，零调用。成本跟着命令跑多久走，不跟会话活多久走。但隔了 36 分钟再继续时，缓存已经过期，整段上下文按缓存写的价格重写一遍，那一轮的成本约是平时的 5 倍。长上下文在约 30 万 token 时还能正常用；第 6 轮自动压缩，上下文从约 36 万降到 18 万，只留最后两段加一段约 200 token 的摘要。压缩只能从用量骤降看出来。之后让它报一个早期内容的校验值，它回答「无法确定」，没有编一个。

## 2. 一个运营后台：先定框架，再填细节

原型阶段处理的都是「半成功」：多步操作第一步成了、第二步失败；请求发出去不知道结果；两个人同时处理同一条记录；详情刷新失败；跨时区的日期。周二接上隔离的 MySQL 和本地主服务，加了请求 ID、超时和中文错误信息。规矩只有一条：真实调用失败，绝不静默回落到假数据。

接真实服务的头两天修了一串问题：

- 服务只监听回环地址，启动检查也拒绝别的地址，光改 URL 不够，加了一个要显式打开的局域网模式；
- 旧的异步响应不能覆盖新会话的状态；
- Go 把空切片序列化成 `null`，列表页直接白屏，后端改成永远返回 `[]`，前端也兜一层；
- 一条「保存成功」的提示被随后「打开新表单」的清空吃掉了，测试之前能过，只是赢了竞态；
- 种子数据的生效时间写成 `1`，页面显示成 1969/12/31；
- 会话池满时注册回 500，用户却已经写进了库，改成先占容量再写库。

还有一处只解释、没改：按「加 6 个月」算到期时间，起点是凌晨 02:30，终点恰好落在春季拨快时钟那天。那天 02:30 不存在，代码算出 01:30，比合理的 03:30 早一小时。

周四的框架重排，要点是：拆成 8 个页；列表统一成紧凑表格，顶部一个搜索框；详情从右侧滑出，分标签页，当前这一步该点的按钮固定在底部；状态名全站统一；页面上不出现原始的状态码、Unix 秒和内部单位；调试工具只在本地模式出现，不进生产构建；后台不直接读主服务的库，接口没好的地方先用假数据。

实现时碰到的两处值得拿走。手机布局里，外层 grid 设了 `min-height: 100vh`，自动行被拉高，顶部导航条撑到了 240px：

```css
.app {
  display: grid;
  min-height: 100vh;
  grid-template-rows: auto minmax(0, 1fr); /* ← 新加：只让内容行吃掉剩余高度 */
}
```

周五凌晨接主服务时，有的路由主服务还没实现。框架对没注册的路由回一句纯文本的「404 page not found」，处理函数根本没跑，所以连写操作也能安全地当成「还没实现」，映射成 501。判断时不能只看 Content-Type：测试里的 httptest 服务没设 Content-Type，JSON 的 404 也会被嗅探成 text/plain。

```go
// 只有「框架层的纯文本 404」才算未实现；业务层的 JSON 404 照常当「不存在」
func routeMissing(resp *http.Response, body []byte) bool {
	return resp.StatusCode == http.StatusNotFound &&
		strings.HasPrefix(resp.Header.Get("Content-Type"), "text/plain") &&
		!json.Valid(body)
}
```

另外几处：主服务给的一份 CSV 是长短不齐的 RFC 4180 格式，页面解析后展示，同时提供原文件下载；表头严格校验，列名一变就提示「和约定的格式对不上」，不读半张表。停用接口在类型没变时直接返回已有记录，「本来就停了」和「这次才停」区分不出来，写进待确认。两份文档对同一条规则说法冲突，我读了 leader 写的实现代码才定下来，原来的 mock 用错了规则。被 leader 夸过的「写失败时保留输入」，在重写中丢了测试覆盖，我用 Playwright 的 `page.route` 注入 503 补了一条，并做了变异验证：去掉保留逻辑，它会红。

## 3. 后半周：范围缩小了，证据要更清楚

回归流程越补越长，我要求把测试时间和报告准备分开，关键点尽快给出结论。助手最先提出多密钥并行，我补充实际只有一把密钥，而且文档、页面上线前已经核过。最后保留单密钥文本串行，复用已确认的上一单结束读数，已覆盖且未变化的检查不在开测后重做。

这轮也明确了证据层级：账户总量只能证明整组合计，任务自报费用只能辅助定位，不能把并发后的每单推定金额当成逐单实测。保存的彩排中，文本逐单对账通过；多密钥并行、视频和真实的上线切换仍有未验证部分。详见[缩短上线回归](/blog/billing-regression/regression-core-set-single-key/)。

预扣修复暴露了另一个边界：预扣已含时长，缺价时再当单价乘一次就会放大；限制上界之后，少交付还要退回对应部分。后续提交曾尝试使用任务参数里的价格，又因来源和规格口径不可靠撤回。详见[结算缺价与少交付](/blog/billing-regression/reserve-fallback-partial-delivery/)。

结果存储的修订则提醒我区分生成完成、文件存好、网关确认。已经存好的结果遇到回报失败，仍需保留；旧投递结束时，只能清理自己的登记。这里依据的是代码与测试记录，没有把它们写成一次新的生产验收。详见[结果保留到确认](/blog/model-onboarding/result-retention-until-ack/)。

## 4. 卡住的地方

- **范围按需求文档定，不按排期定**。周三之前，我一直照完整的需求文档做。真正该定范围的是排期：谁在什么时候交什么。8 个模块里 7 个已经有了，于是改成删减而不是重写。还没做的路由在本地模式下回 501「等待主服务」，以后只换后端实现。
- **演示服务在评审人眼前变了**。给 leader 看的演示服务读的是我 worktree 里的构建产物，我每重新构建一次，leader 看到的就变一次。周五凌晨改成了冻结快照。之前替换另一个窗口的共享演示服务时，我先在空闲端口上试，再导入它的启动模块复现环境变量，不打印密钥，只换掉一个进程，然后给对方的收件箱留言。
- **付费块中途被打断**。一个付费测试块断在中间，shell 变量没保存，取消请求发给了上一个块的执行器，日志却写着「已停止」。之后 id 一律从本块的日志里取。另外三条也写进了执行手册：停掉的容器不能 `exec` 取日志；被杀掉的后台任务可能来不及发取消，要显式发取消再查状态；会话停在一个等外部输入的非空闲状态时就停，不往下提交。
- **Mac 睡着了**。本机的花费上限和单轮时限守护脚本，在机器闲置睡眠时整个冻住了 15 分钟，服务端的会话照常跑。醒来后执行器重连回 401，进程退出。周五凌晨又碰到一个小坑：一条带行尾注释的命令粘进 zsh，报 `#: No such file or directory`，因为 zsh 交互模式默认不认 `#` 注释。下面这几行我现在固定在付费块前后跑，注释单独成行，也是为了能整段粘贴：

```zsh
# 防闲置睡眠和系统睡眠，2 小时后自己退出
caffeinate -s -i -t 7200 &
CAF=$!
python3 run.py
kill $CAF
```

- **自己的 hooks 太贵**。回头对账发现，我给 Claude Code 配的检查闸拦下后引起的额外花费，约占全部会话花费的 13%，大头是自动压缩后同一条又拦一遍、同一份文件又读一遍。数字和改法见 [上下文花费的大头是重读前缀](/blog/ai-workflow/context-compaction-cost/) 第 6 节。
- **机器负载**。两个早已没人用的浏览器实例空转了约 3 周，父进程已经是 launchd，调试端口也不应答，杀掉后 load 从 17.9 降到 14.3。Docker Desktop 的虚拟机默认占了约 8 GB 内存，改成 4 GB 后 load 降到 2.8，交换区从 12.0 GB 降到 4.6 GB。

## 5. 学到的

- 探测判通、判拒，都要看证明它的那个字段。见 [上游接口实测](/blog/model-onboarding/upstream-probe-evidence/)。
- 给客户看的文档，每一句「支持」都要有一条真上游的实测，失败样本只能撤回它自己那一句。见 [对外文档里的每句承诺](/blog/methods/customer-docs-claims/)。
- 按次付费的测试要先设计，再花钱；控制动作之后，再查一次真实状态。见 [按次付费接口的测试设计](/blog/billing-regression/paid-test-design/) 和 [估 agent 类接口的花费](/blog/billing-regression/agent-api-token-cost/)。
- 交出去的命令块，要按对方的用法实测：会被整段粘进 zsh。见 [zsh 的展开坑](/blog/tooling/zsh-expansion-gotchas/)。
- Mac 的高负载先按应用汇总 CPU 和内存，再找父进程是 launchd 的孤儿。见 [Mac 开发机的日常排障](/blog/tooling/mac-dev-machine-ops/)。
- 「应该看到」要对着测试断言核。演示报告里 4 处写错的词，都是这样抓出来的。

## 收尾

1. **回执不等于状态** —— 取消、断开、超时之后，都要再查一次真实状态。
2. **结论的边界按样本画** —— 一个极端样本失败，只撤回它自己那一句。
3. **范围看排期** —— 需求文档说的是全部，排期说的是这一轮。
4. **演示的东西要冻住** —— 评审人看到的版本，不该跟着我的构建变。

这周最后留下的改进方向，是把每个结论的边界写清楚：哪些来自实测，哪些来自代码，哪些仍是推算。回归可以缩短，历史结论也可以修订，但两者都要留下足够的依据。
