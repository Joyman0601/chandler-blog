> 一句话总结：这周只有三个工作日，主线是把一个语音模型的「音色设计 + 声音复刻」合成一个接口。独立验收查出的两个阻断，一个是修别的问题时引入的，一个是通用合并入口绕过了校验，都是「修完一处、没想到另一处」。

## 0. 这周在做什么

工作日只有周一到周三。周四起是假期，没有工作，这里不写。

三天里同时开着几条线：

- **主线**：一个语音模型的统一接口。音色设计和声音复刻合到同一个模型名下，再接一个按 token 计费的配套 TTS 模型。从契约、SDK、网关、worker 到数据初始化，五段都要走（分段的做法见 [接入一个新模型的五段](/blog/model-onboarding/onboarding-five-stages/)）。
- **并行验收**：一个文本大模型、一个视频生成模型的新版本，按清单逐条复核。
- **零碎**：模型列表页的标签和筛选改版、一页的 Lighthouse 分数、leader 改过的三页回归。

## 1. 语音模型统一接口：两个阻断都修了，修法各自换了思路

接口按参数分流：带音色描述走设计，带参考录音走复刻，两者互斥。另一模式的字段一律严格 400，不静默忽略。

为什么要这么严，有实测依据：两种字段混着传时，上游不报错，而是把试听文本当成录音的逐字稿，降级建出一个音色，照常计费。用户以为自己在做 A，其实做成了 B，还付了钱。

复刻方案中途返工了一次。方案是照文档推出来的「复刻上游 + 合成模型」组合，实测时合成模型用不了复刻出来的音色，引擎直接报错，只好换另一个复刻上游，前后端一起返工。教训是「A 建的资源 B 能不能用」，要在定方案之前端到端跑一次，不能照文档推。

实测还纠正了上周调研的三处结论：

1. 上游对所有不认识的参数都返回 200，所以「参数被接受」什么都说明不了，要看输出有没有变；
2. 指令参数是单数形式，上周写成了复数；
3. 同一段文本、同一个音色，输出 token 最多相差 3.6 倍。预扣不能按「一个字对应几个 token」这种固定比例算死。

然后是验收查出的两个阻断。

**B1：长度检查放在展开之后。** 走查时修了一个文本替换规则的问题，修法是先把所有规则展开替换，再检查总长度。验收者构造了一个不到 200 字节的请求：几条规则逐级放大，展开后撑到 3.2 亿字符，接口耗时 4 秒，容器内存从 197 MB 涨到 785 MB。长度上限在展开之后才检查，展开这一步本身就能把服务打爆。

修法是每一步替换之前先预算：「出现次数 × 长度差」加上当前长度，超限直接 400；规则总数也设上限，最多 200 条。修完同样的请求 57 ms 返回 400，内存不动。最小示例：

```python
def apply_replacements(text: str, rules: list[tuple[str, str]], limit: int = 5000) -> str:
    """逐条替换；每一步替换之前先算出替换后的长度，超限就拒绝，不先展开再检查。"""
    if len(rules) > 200:
        raise ValueError("too many rules")
    for old, new in rules:
        if not old:
            raise ValueError("empty pattern")
        n = text.count(old)
        projected = len(text) + n * (len(new) - len(old))
        if projected > limit:
            raise ValueError(f"replaced text would exceed {limit} chars")
        text = text.replace(old, new)
    return text
```

**B2：通用合并入口覆盖了已校验的字段。** 网关有一个通用的「附加参数」入口，用户传的额外键会合并进上游请求体。合并发生在校验之后，所以已经校验过的字段可以被同名键再覆盖一次。验收实测用它建出了另一个模型的音色。修法是复刻分支不走通用合并，只下发契约里列出的字段。新模式要严格，就要么不走合并入口，要么合并时拒绝同名键。

预扣系数也被验收打穿了一次。第一版把小写字母当成逐个字母念，英文的预扣高估约 10 倍；第二版改用实测系数。验收在两个非默认音色上，用不带空格的乱码测出实际用量是预估的 2.25–2.41 倍，超过了「实扣不超过预扣 2 倍」的设计保证。后来提高了系数，最坏情况降到 1.67 倍。代价是正常英文请求多冻结约 33%–50% 的额度，结算时退回。冻多了能退，冻少了要补扣，这个取舍是故意的。

## 2. 并行验收：几条接入线，同一类问题

另外几条线的验收，碰到的问题可以归成一类：上游或网关「没报错」，不代表做对了。

- **文本大模型**。上游兼容 Anthropic Messages 格式的端点，对任何不认识的模型名都返回 200，实际由别的型号回答。探测判通不能只看状态码，要核响应里的 `model` 字段是不是请求的那个。另外，`previous_response_id` 这类依赖服务端会话状态的参数，对无状态上游要显式回 400，不能静默丢掉。
- **长上下文分档**。两个页面各自格式化同一个阈值，一个写「<」一个写「≤」，后端计费是严格大于。改成两处共用一个格式化函数，比较符号跟计费走。见 [计费规则里的坑](/blog/billing-regression/billing-rule-pitfalls/)。
- **视频生成模型的新版本**。后端约 15 处判断写死了旧型号名，收口成一个判定函数加一张按型号的规格表。为了证明测试真的守得住，故意改坏 9 处关键逻辑，每次测试都变红。
- **端到端缺环境**。真实 key 的验证分三层，前端那层卡住了：共享开发后端没部署这个分支，本地也登录不了。最后本地起了 MySQL、Redis、网关、worker、前端全套，用网关自己的会话密钥签一枚 token 注入浏览器，不改代码。见 [异步任务的本地全栈验收](/blog/model-onboarding/async-task-local-full-stack/)。
- **结果是上游直链**。全栈跑通后，我要求按规范查有没有把上游地址给用户，实测给用户的结果视频是上游的直链。最初的归因是「本地没配转存」，这个归因被推翻之后才查到，SDK 里根本没有转存这一步。
- **坏 key 不禁用渠道**。用假 key 连续请求，渠道一直不被自动禁用。任务类 provider 的失败不经过中继层的错误上报，修了四轮。最后在 stream 派发下发现，401 走的是「换渠道」事件，根本不经过终态出口。见 [错误分类器和渠道禁用](/blog/model-onboarding/error-classifier-channel-disable/)。
- **子串规则误归类**。新模型名里的一段子串，命中了另一类模型的判断规则。只给新模型加精确匹配，存量规则不动，再用单测锁住存量模型的返回值。

## 3. 卡住的地方

- **计划外的一笔扣费**。为了让请求打到测试桩，只改了一张表里的上游地址，但 worker 读的是另一张表，请求打到了真上游。之后会花钱的请求前，先单独发一个不花钱的请求，确认流量到了桩，而且核对和提交不写在同一条命令里。见 [付费测试怎么设计](/blog/billing-regression/paid-test-design/)。
- **带着红测试推送了约 3 小时**。rebase 零冲突，测试是按目录挑着跑的，漏了一个目录。rebase 干净不等于完事，挪完基线要跑全量测试。
- **本地跑 Lighthouse 带上了正式的第三方插件**。本地生产构建会把正式的客服插件一起带上，Lighthouse 的 URL 拦截管不到跨进程的 iframe。跑了几轮，正式的客服后台收到约 20 条匿名访客记录。
- **多任务共用一个 SDK 目录**。另一个并行会话在同一个目录里切了分支，这边的 worker 构建失败。之后按任务隔离 worktree，依赖也放进任务自己的目录。见 [多任务并行的 worktree 用法](/blog/git-collab/worktree-multi-task/)。
- **价格不归我定**。调研里写进了一个自定的售价口径，这不是我能定的事。改成按最保守的默认落地，待定项写进决策人一定会看的决策日志。见 [归别人定的事](/blog/methods/others-decision-default-log/)。

## 4. 学到的

- 在被污染的配置下测出的缺陷，修之前先在规范配置下重跑。有一个「硬杀 worker 后约 17 分钟才退回预扣」的问题，在规范配置下重跑两次，都在约 140 秒内完成，最后没改代码。
- 任务结果只存在创建它的进程内存里时，多实例下的查询必须路由回创建它的实例。生产要走 stream 派发，本地单进程跑通说明不了什么。
- 多仓库的合并有顺序：SDK 先合，worker 和网关再钉版本、重新 vendor。
- 一页 Lighthouse 比对照页低 3 分，原因是两个小事叠在一起：HTML 多了 404 字节，正好跨过多一轮 RTT 的阈值；页面又静态引入了一个跨页共享的估价器。改成按需加载后，分数从 82 到 89。见 [首屏包体和 Lighthouse](/blog/frontend/first-load-bundle-lighthouse/)。
- 筛选从交集改并集，计数口径、跨组规则、命中提示都要跟着改；sticky 钉住的一行在矮窗口里会压住下面的列表，最后取消了钉住。见 [筛选改版](/blog/frontend/facet-filter-redesign/) 和 [sticky 的几种失效](/blog/frontend/sticky-layout-failures/)。

验收新上游时，我现在会先过一遍这张判断表：

| 看到的 | 不能推出 | 要再看 |
|---|---|---|
| 参数返回 200 | 参数生效了 | 输出有没有随参数变 |
| 模型名返回 200 | 是这个模型回答的 | 响应里的 `model` 字段 |
| 假 key 返回 401 | 渠道会被禁用 | 渠道状态和错误上报出口 |
| 测试全绿 | 测试守得住 | 故意改坏关键逻辑，看会不会红 |
| 本地单进程跑通 | 生产能跑通 | 多实例下结果落在哪个进程 |

## 收尾

1. **上限在每一步展开之前判** —— 先展开再检查，展开本身就是攻击面。
2. **严格的模式不走通用合并** —— 合并入口会悄悄覆盖已经校验过的字段。
3. **预扣宁多勿少** —— 多冻的结算时退回，少冻的要补扣，还可能补不上。
4. **花钱前先确认流量去了哪** —— 改了配置不等于请求真的到了测试桩。

这周最大的感受是：「没报错」是最贵的一种结果。上游 200、测试全绿、rebase 零冲突，背后都可能藏着没覆盖到的地方。下周节后回来，带着这张判断表接新的模型。
